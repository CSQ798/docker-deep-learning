## 必须讲透的内容

1. **把容器放回工程流程里**：手工执行 `docker build` 的成功不是工程成功；可重复、可审计、可回滚、可协作才是。要讲清从"开发者的命令"到"流水线的产物"这条演化路径。
2. **十二要素应用逐条自查**（要给出十二条与 Docker 的对应关系表，并逐条解释"为什么它对容器世界如此重要"）：
   - 一份基准代码、多份部署；
   - 显式声明依赖；
   - 配置存于环境；
   - 把后端服务当作可替换资源；
   - 严格分离构建与运行阶段；
   - 以无状态进程运行应用；
   - 通过端口绑定提供服务；
   - 通过进程模型进行并发扩展；
   - 可快速启动与优雅终止；
   - 尽量保持开发、预发、生产环境一致；
   - 把日志当作事件流；
   - 管理任务作为一次性进程运行。
   要挑出其中 4—5 条做深入解读，特别是"构建与运行分离""配置存于环境""日志作为事件流""管理任务作为一次性进程"（最后一条要用 `docker compose run` 演示一次性任务如何清理数据，这是极其实用的知识）。
3. **构建一次，处处运行**：为什么不在生产环境重新构建；同一镜像 + 不同配置的策略；镜像作为不可变交付物的价值。
4. **镜像标签与版本策略**（要给出一套可落地的规范）：
   - `latest` 的问题；
   - 语义化版本、Git 提交短哈希、时间戳、分支名各自的用途；
   - 推荐的"多标签指向同一 digest"策略（同时打 `1.4.2`、`1.4`、`sha-abc1234`）；
   - 如何用 `docker image inspect --format "{{index .RepoDigests 0}}"` 拿到 digest 做记录。
5. **多环境配置**：开发 / 测试 / 生产三套配置的组织方式；配置进环境变量、密钥进密钥系统；"同一镜像、不同注入"的实践；要给出一个 `.env`、`.env.example`、`compose.override.yaml` 的目录结构示例。
6. **CI/CD 与 GitHub Actions**（要给出一份可用的工作流 YAML，并逐段解释）：
   - 一个典型流水线的阶段：安装依赖 → 跑测试 → 构建镜像 → 扫描漏洞 → 推送镜像 → 部署；
   - GitHub Actions 的基本概念：workflow / job / step / runner / secret；
   - 用 `docker/build-push-action` 构建并推送的思路（要讲清所需权限与 `GITHUB_TOKEN`、镜像仓库登录）；
   - **GitHub Actions 提供的构建缓存**（这一点比"写得快"重要得多）；
   - 要诚实说明：这份 YAML 需要读者把镜像仓库信息替换成自己的才能真正跑通。
7. **日志与可观测性**：
   - 日志三大支柱（日志 Logs、指标 Metrics、链路追踪 Traces）与容器带来的新常态（实例随时消失、名字随机、数量动态）；
   - "应用只往标准输出打印"的纪律如何让集中采集成为可能；
   - 结构化日志（JSON）为什么比自由文本好；
   - 健康检查的三种状态与它在编排中的意义；
   - 一个实用的判断：**出问题时你最想知道哪三个问题？** 把这三个问题的答案变成你的监控项。
8. **发布与回滚**：蓝绿、滚动、灰度三种发布策略的直觉解释与代价；容器让回滚变简单的原因是"回滚就是换回上一个镜像"；要给出一次可回滚发布的完整动作序列。
9. **团队协作的固定动作**（本章的"素养清单"）：Dockerfile 要评审、`.dockerignore` 必写、镜像标签不得用 latest、密钥不进仓库、README 写清如何一条命令起环境。

## 必做实验（≥4）
1. 用 `docker compose run --rm <服务> <命令>` 执行一次性管理任务（例如跑数据库迁移），并解释它与 `exec` 的区别。
2. 给同一个镜像打三个标签（语义版本、次版本、短哈希），用 `docker images` 与 `inspect` 观察它们指向同一 digest。
3. 用 `docker compose config` 对比两套环境变量注入下的最终配置差异。
4. 写一份 `.github/workflows/build.yml` 并逐段解释（不必真正跑通，但必须语法正确、逻辑清晰）。
5. 用 `docker logs --since`、`--tail`、`-f` 演练一次"从日志定位问题"的过程。
6. 演练一次"回滚"：构建 v1、构建 v2、把容器切回 v1 的完整命令序列。

## 思考题方向（≥8）
- "构建一次，处处运行"与"每个环境单独构建"各自的代价是什么？
- 如果 `latest` 这么危险，为什么官方镜像还默认提供它？
- 蓝绿与滚动发布，哪个更容易回滚？哪个更贵？
- 你的镜像里有 3 个 CVE 高危漏洞，但修复需要重写一个依赖，你会怎么决策？向谁汇报？
- 日志"写进文件"和"打到标准输出"在排障时的体验差别是什么？
- 如果所有配置都进环境变量，那么一个服务的"完整说明"在哪里？它足够吗？
- 你为什么需要"一条命令起环境"？它和"新人第一天能不能跑起来"有什么关系？
