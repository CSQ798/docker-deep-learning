## 必须讲透的内容

1. **先建立威胁模型**（本章的方法论开篇，必须写透）：
   - 谁在攻击你：外部攻击者、恶意镜像作者、被攻陷的依赖包、容器内被利用的应用漏洞、内部人员的误操作；
   - 资产是什么：数据、凭据、算力、宿主机、内网其他服务；
   - "容器不是安全边界"这句话的正确理解：它**是**一层边界，但强度低于虚拟机，且**配置决定强度**；
   - 安全是成本与收益的权衡：要求读者养成"这条措施在防什么、它的代价是什么"的提问习惯。
2. **容器逃逸的真实路径**（每条都要讲清机理与防御手段，不许只给名词）：
   - 挂载 `docker.sock`（等于把宿主机 root 权限交给容器）；
   - `--privileged`（几乎放弃全部隔离）；
   - 多余的 Capabilities；
   - 挂载了宿主机的敏感目录（`/`、`/etc`、`/var/run`）；
   - 内核漏洞；
   - 以 root 运行 + 内核缺陷的组合。
   要给出一个可演示的、**无害的**实验来让读者体会"挂载 docker.sock 有多危险"：例如在容器内用 curl 通过套接字列出宿主机上的容器（要写得克制，说明这只是演示权限而非教攻击）。
3. **用户与权限**：
   - 镜像里默认是 root 意味着什么；`USER` 指令与 `docker run --user`；
   - 创建非特权用户的 Dockerfile 写法（Node/Python 各给一个真实例子）；
   - 文件权限与卷的组合问题（容器内 uid 与宿主机 uid 不匹配导致的"文件被 root 拥有"）；
   - rootless 模式、用户命名空间映射（讲清思路与收益）。
4. **Capabilities**：把 root 拆成几十项特权；默认丢弃了哪些；`--cap-drop=ALL --cap-add=...` 的最小权限写法；什么场景真的需要加能力（如 ping 需要 `NET_RAW`）。
5. **内核级防护**：seccomp（系统调用过滤）、AppArmor/SELinux（强制访问控制）、只读根文件系统（`--read-only` + `--tmpfs`）的组合拳。要讲清"纵深防御"的思维方式。
6. **镜像供应链安全**：
   - 基础镜像选择与漏洞数量的关系；
   - `docker scout cves`（或 `docker scout quickview`）的使用与输出解读，要说明输出里 severity 的含义；
   - SBOM 与 provenance：它们回答"我的镜像里到底有什么、是谁构建的"；
   - digest 固定与签名（内容寻址为什么能防篡改）；
   - 依赖过期：一个镜像放半年不动，它的漏洞会不会变多？（会，因为漏洞数据库在更新）——这个反直觉点必须写。
7. **密钥治理**：把所有错误做法与正确做法列成对照表：
   - ❌ 写进 Dockerfile 的 `ENV`、`ARG`、`RUN` 命令里（会留在镜像层与构建历史中）；
   - ❌ 提交进 Git 的 `.env`；
   - ❌ 在命令行里明文传（会进 shell 历史与 `docker inspect`）；
   - ✅ 构建期用 BuildKit 的 `--mount=type=secret`；
   - ✅ 运行期用环境变量注入（来自密钥管理系统）或只读文件挂载；
   - ✅ Compose 的 `secrets`、编排系统的 Secret、外部 KMS/Vault。
   - 要给出一个**可验证的演示**：用 `docker history` 证明写进 RUN 的密钥能被看到。
8. **运行时的安全默认值**（给一份可执行的"安全默认清单"）：非 root、只读根文件系统、`--cap-drop=ALL`、限制内存与进程数、不在容器里存密钥、不挂 docker.sock、固定镜像 digest、定期扫描。要明确告诉读者：**不必一次全上，但要知道每一项在防什么**。
9. **安全与工程效率的张力**：安全措施会带来不便（没有 shell 无法调试、只读文件系统导致应用报错）。要讨论如何在不牺牲安全的前提下保持可维护性（多阶段构建 + 独立的 debug 阶段、临时容器排障 `docker debug` 之类的思路）。

## 必做实验（≥4，命令真实可跑，且必须是安全的演示）
1. 用 `docker run --rm alpine id` 显示容器内默认是 root。
2. 用 `docker run --rm --user 1000:1000 alpine id` 观察身份变化。
3. 用 `docker history` 证明 `ENV SECRET=xxx` 或 `RUN echo $SECRET` 留下的痕迹。
4. 运行 `docker scout quickview alpine` 或 `docker scout cves alpine`（若读者的 Docker Desktop 版本不支持，要给出替代：在 Docker Hub 页面查看镜像的漏洞标签，或说明这个命令需要登录）。**必须写出"如果命令不可用该怎么办"的替代路径**，不要制造挫败感。
5. 对比 `alpine` 与 `python:3.12` 的漏洞数量（如果 scout 可用），或对比两者体积与软件包数量作为替代证据。
6. 用 `--cap-drop=ALL` 跑一个容器，观察哪些操作会失败。

## 思考题方向（≥8）
- 如果你只有一天时间加固一个容器，你会优先做哪三件事？依据是什么？
- "容器里是 root 但和宿主机 root 不一样"这句话对在哪里，又危险在哪里？
- 为什么"为了排查问题临时 --privileged"是个陷阱？有没有既能排查又不放弃隔离的办法？
- 一个镜像放半年不动，它的漏洞数量为什么可能变多？这说明了什么？
- 安全措施让开发变慢，你如何在团队里主张安全？用"恐惧"还是用"成本"说服人？
- 如果供应链上游被投毒（你依赖的基础镜像里有恶意代码），你有哪些检测与缓解手段？
- "最小权限"听起来无懈可击，但它的极端形式会让系统无法使用。边界在哪里？
