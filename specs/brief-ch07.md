## 必须讲透的内容

1. **容器网络的必要性**：为什么每个容器需要一个自己的网络视图；如果没有隔离会发生什么（端口冲突、IP 冲突、互相嗅探）。
2. **底层机制（讲清"没有魔法"）**：
   - 网络命名空间：每个容器一套独立的网卡、路由表、端口空间；
   - veth pair：一对虚拟网线，一头在容器里，一头在宿主机网桥上；
   - 网桥（docker0 与自定义网桥）：宿主机的虚拟交换机；
   - iptables / NAT：出网地址转换与入站端口转发的规则载体；
   - 要给出"数据包从浏览器到你容器的完整路径"的逐步讲解（宿主机网卡 → iptables 规则 → 网桥 → veth → 容器网卡 → 应用）。这是本章的高潮段落。
   - 可让读者在容器内验证：`docker run --rm alpine ip addr`、`ip route`（Alpine 需 `apk add iproute2`，要写成一条命令 `docker run --rm alpine sh -c "apk add --no-cache iproute2 >/dev/null && ip addr"`）。
3. **五种网络驱动的定位与取舍**（对比表）：`bridge`（默认，单机）、`host`（共享宿主机网络栈，性能最好但端口冲突风险）、`none`（无网络，用于纯计算）、`overlay`（跨主机，编排系统用）、`macvlan`（让容器像局域网里的物理设备）。要讲清每种"什么时候你会真的需要它"。
4. **默认 bridge 与自定义 bridge 的关键差别**（必须讲透，这是初学者困惑的最大来源）：
   - 默认 bridge **不提供容器名解析**，只能靠 IP 或已废弃的 `--link`；
   - 自定义 bridge **提供内置 DNS**，容器之间可以用**容器名 / 网络别名**互相访问；
   - 因此多容器项目的正确姿势是：`docker network create` 建一个自定义网络，所有容器接上去。
   - 要给出完整的、可跑的双容器实验（例如 `web` + `redis`，web 通过 `redis:6379` 连接）。
5. **`docker network` 命令族**：`create`（含 `--subnet`、`--driver`）、`ls`、`inspect`（看 Containers 字段）、`connect` / `disconnect`（把一个运行中的容器接入另一网络，含"一个容器可接入多个网络"这一重要能力）、`rm`。要解释"容器有多个 IP"这件事如何被用于网络隔离设计。
6. **端口映射的真实原理**：`-p 8080:80` 做了什么；为什么必须发布端口外部才能访问；`-p` 的几种写法（`-p 8080:80`、`-p 127.0.0.1:8080:80`、`-p 8080:80/udp`、`-P` 随机端口）；**为什么"容器内 127.0.0.1"与"宿主机 127.0.0.1"是两个世界**（这是初学者最经典的误解：在容器里连 `localhost:5432` 连不到宿主机的数据库）；端口冲突的排查方法。
7. **内置 DNS 与排障方法**：容器内 `/etc/resolv.conf` 里的 127.0.0.11；用 `nslookup`（或 `getent hosts`）验证解析；**网络排障的固定顺序**：先看容器是否在同一网络 → 再验证名字解析 → 再测端口连通 → 再看应用是否监听在 0.0.0.0 而不是 127.0.0.1 → 最后看防火墙。要讲清"应用绑定地址"这个极高频的真实故障原因。
8. **跨主机网络与 overlay（点到为止，第 12 章展开）**：为什么跨主机通信需要控制平面；VXLAN 的直觉解释（把二层包封装在四层里）。
9. **反向代理与负载均衡的初次登场**：用一个 nginx 容器做反向代理，把请求分发给两个后端容器；讲清"正向代理代表客户端、反向代理代表服务端"的区别；`upstream` 概念。这是第 10、12 章的前菜。

## 必做实验（≥5，命令真实可跑）
1. `docker network ls` 看三种默认网络，`docker network inspect bridge` 看网桥信息。
2. 起两个容器接入默认 bridge，尝试用容器名互相 ping（失败），再用自定义网络重做（成功）。**这是全章最重要的实验**，要写得像一次侦探过程。
3. `docker run -d --name web -p 8080:80 nginx` → 浏览器访问 `http://localhost:8080` → 然后 `docker run -it --rm alpine sh`，在容器里 `wget -qO- http://web` 失败，解释为什么（不同网络 / 无 DNS）。
4. 演示 `127.0.0.1` 陷阱：容器里 `wget -qO- http://127.0.0.1` 失败，改用容器名或 `host.docker.internal`（Docker Desktop 提供）成功。要明确说明 `host.docker.internal` 的用途与局限。
5. 做一个 nginx 反向代理实验：用自定义网络起两个 `nginx`（或 `httpd`）容器，再用一个 nginx 容器作代理，验证轮询分发。
6. `docker network connect` 把一个正在运行的容器接入第二个网络，观察 `inspect` 里出现两个 IP。

## 思考题方向（≥8）
- 为什么默认网桥要故意不支持容器名解析？这种"不便利"有没有安全上的理由？
- 如果每个容器都有自己的网络命名空间，那么"一个容器有多个 IP"这件事为什么是可能的？它有什么用？
- `-p 127.0.0.1:8080:80` 与 `-p 8080:80` 在安全性上差什么？什么场景必须用前者？
- 容器里的应用为什么必须监听 0.0.0.0？如果它监听 127.0.0.1，外部能不能访问？为什么？
- 端口映射的性能代价是什么？什么场景下 `host` 网络值得这个权衡？
- 如果两个容器在同一台机器上，却要通过"网络"通信，这种"绕远路"值得吗？有没有更快的替代？
- Kubernetes 后来发明了 Pod，让多个容器共享网络命名空间。它在解决什么问题？
