剖开 Docker：一台机器里的七个部件

当黑箱变成透明的机械钟，你才真正开始掌握它。

本 章 学 习 目 标
  • 能说清 Docker 为什么采用客户端—服务器架构，以及它给你的两个实际好处与一个实际代价。
  • 能按层级说出 docker CLI、dockerd、containerd、runc 各管哪一段，并解释"为什么这事要拆给四层去做"。
  • 能解释镜像、容器、存储驱动三者的关系：谁是内容、谁是实例、谁是实现者。
  • 能解释为什么 Windows 上必须有 Linux 虚拟机，以及 WSL2 在调用链里站在哪个位置。
  • 能指出 Docker 明确不负责的四件事，并判断一个需求该不该由 Docker 满足。
  • 能画出从敲下 docker run 到看见输出之间的完整路径，并指出每一步可能的失败点。
学 完 之 后 ， 你 应 该 能 够
  • 能画出 Docker 的完整调用链，并标出每一层大致耗时几何。
  • 能用 docker version 与 docker context ls 判断命令行到底连到了哪里。
  • 能独立诊断"连不上 Docker"这类故障，并把它拆成三种彼此不同的原因。
  • 能解释"同一个镜像跑两个容器互不影响"这个现象，并指出它的代价。
  • 能判断一个问题属于 Docker 的职责，还是属于编排、CI/CD、监控的职责。
  • 能在 WSL2 里找到 Docker 的真实数据目录，并解释它为什么不在 C 盘。
  • 能读懂 docker events 的输出，把它当成一台机器的心跳来使用。

第 01 章我们把"为什么"讲完了：你在自己的笔记本上、在别人的服务器上、在机房的某台机器上跑同一套代码，行为却不一样，这种痛从分时系统时代就存在，容器不是凭空出现的答案。我们还做了一件更重要的事——把一条 docker run hello-world 拆开看了一眼，发现那条命令背后已经藏着全书要讲的几乎每一个环节，只是被藏起来了。现在到了把它挖出来的时刻：你敲下的那七个字母，究竟被谁收到、被谁转交、最后被谁执行？为什么一台机器里需要七个部件才能完成这件事？我们从"谁在真正干活"开始。

你敲下的那条命令，其实什么都没干

先做一个也许会让你失望的断言：你输入的那个 docker 命令，本身不会创建任何容器。它不下载镜像，不启动进程，不碰内核。它做的是三件事——读懂你写的一串参数，把它们翻译成一份 HTTP 请求，把信寄出去，等回信，然后把回信排版得好看一点打印给你。

真正干活的是另一个程序，一个在你开机之后就默默待在后台、既不占你的终端也不跟你说话的程序。它在监听一个套接字，等有人寄信过来。这个架构有个正式名字：客户端—服务器架构（Client–Server，简称 C/S 架构）。客户端表达意图，服务器实现意图，两者通过约定的接口通信。你打开浏览器访问网站是同一套模式；你在宿舍用 SSH 连学校服务器，也是同一套模式。Docker 只是把它搬到了你自己电脑内部。

这个设计的第一层好处是：客户端不需要知道自己连的是谁。你的 docker 命令手里拿着一份连接配置，配置里写着目标地址、协议、证书。这份配置在 Docker 里叫 Docker Context（Docker 上下文，即一组"我该连到哪台待命程序"的连接信息）。它默认指向你本机的待命者，但你可以把它改成指向另一台机器上的同一个程序。改完之后，你在宿舍笔记本上敲的 docker ps，列出的会是实验室服务器上的容器——而你一行代码都没改。第二层好处是：命令行接口可以有很多个，待命者只有一个。今天有 docker 命令行，明天可能有图形界面，后天可能有你自己写的脚本调用 HTTP 接口。它们之间不需要互相认识，因为它们都在跟同一个待命者说话。

代价也很实在。既然命令要寄信，收信人就必须活着。收信人不在，你的命令只能报错，而报错信息常常让初学者以为"Docker 坏了"——绝大多数情况下它没坏，只是那个待命的程序没在跑，或者你没连对地址。第 01 章我们说过"容器共享内核"，现在可以再加一句：命令行与引擎之间也共享一条通道，通道断了，一切都会失灵，而通道本身极其容易修复。

比 喻

把 docker 命令行想成你手机上点外卖的那个 App，把待命的后台程序想成餐厅后厨。App 没有锅、没有灶、没有食材，它做的是把你的订单规范化（"一份番茄炒蛋，不要葱"），通过网络送到后厨，然后展示后厨回传的状态。订单能写成标准格式，是因为 App 和后厨事先约好了一套菜单与状态码。有一件小事值得注意：如果订单里要炒的菜后厨现成有半成品，上菜就快；没有，才需要现去菜市场买——这个"现成有没有"，后面会变成一个非常重要的概念。

那么后厨是谁？它的正式名字是 Docker Engine（Docker 引擎，真正干活的那套软件）。引擎内部不是一块铁板，它被拆成好几个各管一段的部件，而这些部件的数量与分工，就是这一章要讲透的东西。在往下走之前，先留一个问题：如果"创建一个被隔离的进程"只是一次系统调用那么简单，为什么 Docker 要把它拆成四层、由四个不同的程序接力完成？答案不会马上出现，它藏在这一章的中段。

前 瞻

第 04 章会把这套"客户端发意图、引擎实现意图"的模式用到排障上：一旦命令返回一个奇怪的状态，你要判断的就不再是"这条命令该怎么改"，而是"引擎此刻认为世界是什么样子"。先把这条通道记住，第 04 章会给它配上一整套检查动作。

七个部件：各自守着哪一段

我们把一台装了 Docker Desktop 的 Windows 笔记本剖开，会看到七个值得单独命名的部件。先说它们的名字与职责，再讲它们之间的层级关系，最后回答那个悬着的问题——为什么这事要拆给四层去做。

docker CLI：只负责说话

docker CLI（Command-Line Interface，命令行界面）就是你在终端里敲的那个 docker。它做的事只有四件：解析参数、读取上下文配置、把请求变成 HTTP 调用、把响应打印成人能读的格式。它没有任何特权，也不常驻，执行完就退出。它有一个常被忽略的能力：它知道自己在跟谁说话。docker context ls 会列出所有连接目标，当前的带一个星号，通常是 default 与 desktop-linux 两项；docker context inspect 则能让你看到某一项背后的端点类型与地址。理解这一点，是你从"会敲命令"走向"知道命令敲到了哪里"的分水岭。

判断"通道是否通"的最低成本动作是 docker version。它会打印两段：Client 描述你手上的命令行，Server 描述那台机器上的引擎。只有当两段都出现时，你的命令行才算真的连上了引擎。 只出现 Client 一节并跟着连接失败，问题就在通道或引擎，不在你的命令。在 Docker Desktop 上的排查顺序是：先看主窗口是否显示引擎正在运行，再用 docker version 确认两段都在，最后用 docker info 核对引擎报告的字段。走完这三步，绝大多数"连不上 Docker"都会现出原型。

docker version
docker context ls
docker context inspect desktop-linux

第一条分两段打印客户端与引擎的信息，请刻意分别读，尤其注意 API 版本那一项——两端可以不同，但需要落在兼容范围内。第二条列出所有连接目标，带星号的即当前目标。第三条输出结构化描述，能看到端点类型与地址；如果它报"找不到上下文"，把名字换成 ls 里实际显示的那个。

dockerd：那个待命的后台程序

有一个细节能证明你的 Docker Desktop 装对了：打开全新的 PowerShell 窗口，敲 docker 就有反应，可 docker.exe 并不在 Windows 的常规程序目录里。答案是安装时 Docker Desktop 把客户端注入了你的用户环境，并在两种模式之间搭了一条桥。这解释了两件小事：卸载它之后 docker 命令会立刻消失；而在 WSL 内部执行 which docker，你可能找到另一个客户端——它与 Windows 侧那个是两份程序，只是配置指向同一个引擎。

守护进程（Daemon，在后台长期运行、不占终端、随时待命的进程）是操作系统的通用概念，Docker 的守护进程叫 dockerd。它是 Docker 世界里权限最高、寿命最长的角色，负责管理镜像、容器、网络、数据卷、构建、日志，监听一个套接字等命令进来：Linux 上通常是 /var/run/docker.sock。那个套接字的权限等同于这台机器的最高权限——谁能跟它说话，谁就能让守护进程以最高权限做任何事。所以"把 docker.sock 挂进容器"等于把整台机器的钥匙交出去，第 09 章会专门算这笔账。

containerd：管生活，不管规矩

containerd（容器运行时管理器）是一个工业级容器运行时，2017 年由 Docker 公司捐给 CNCF 基金会。它接过的活儿很实在：把镜像从仓库拉下来并解开、把层装配成容器看到的根文件系统、创建与启停容器、管理快照、把任务交给下一层。它是引擎的施工队队长：图纸和审批在别人手里，砖瓦水电归它调度。它有个特点值得留意：它并不直接调用内核那套隔离接口，而是把"最后一公里"外包给一个更小的程序，这样就能同时支持多种底层运行时（有的基于内核隔离，有的基于轻量虚拟机）而不必自己改写一遍。这是软件设计里经典的一招：把稳定的编排逻辑与易变的执行细节分开。

runc：真的动手的那个人

runc（OCI 运行时实现）的职责单一到近乎朴素：读一份配置文件，照着配置调用内核接口，把进程关进该关的笼子里，把该挂的目录挂好，然后启动目标程序。它的运作方式是一次性的：活儿干完就退出，把现场交给容器里的 1 号进程。理论上你可以不用 Docker 而直接手写一份配置去调用它——这件事有很强的教学价值，因为它会让你彻底相信"容器没有魔法"。runc 遵循的是 OCI 运行时规范，由开放容器倡议（Open Container Initiative，OCI）制定。OCI 是本章最重要的名字之一，因为它解释了一个现象：为什么 Kubernetes 可以不用 Docker 却仍然跑着容器。标准的存在让容器从某家公司的产品变成整个行业的接口。

镜像仓库：镜像世界的物流中心

镜像仓库（Registry，存放与分发镜像的服务器）不在你的机器上，它在网络那头。docker pull nginx 默认去 Docker Hub（Docker 官方的公共镜像仓库）取，那是目前世界上最大的镜像集散地。仓库体系有三个层级，初学者最容易混淆：Registry 是仓库服务本身；Repository 是某个镜像名下所有版本的集合（nginx 就是一个 Repository）；镜像标签（Tag，版本别名）指向集合里的某个具体版本（nginx:1.27 就是一个 Tag）。这个区分决定了你命令里的名字长什么样：推送到私有仓库时，名字会变成 registry.example.com/team/app:1.4.2，冒号前那一长串塞了仓库地址、命名空间与仓库名，最后才是标签。看懂了这个结构，你就不会再把"镜像名"当成一个不可拆分的字符串。

Docker Desktop：把这一切塞进 Windows 的包装盒

Docker Desktop（Docker 桌面版）是官方为 Windows 和 macOS 提供的桌面应用，把 Docker Engine、Docker CLI、Compose、构建引擎、一个单节点的 Kubernetes、图形界面打包成一个安装包。在 Linux 上这些东西可以一个个装上，在 Windows 上不行——原因在第四节展开。它常被初学者当成"Docker 本身"，这个误解会带来真实的排障困难：容器跑不起来时，是图形界面没启动？是里面的引擎没起来？还是引擎起来了但上下文指错了？这三件事的修法完全不同。

WSL2：藏在键盘底下的那台 Linux 机器

WSL2（Windows Subsystem for Linux 2，适用于 Windows 的 Linux 子系统第二代）是微软提供的、在 Windows 上运行真实 Linux 内核的技术，底层是轻量虚拟化。Docker Desktop 默认把 Engine 放在一个 WSL2 发行版里运行，让 Windows 侧的 docker 命令通过一条通道连进去。你在 PowerShell 里敲 docker ps，请求先离开 Windows，进入那台看不见的 Linux 机器，才交给真正的 dockerd。

七个部件到这里齐了。但它们不是七个并列的兄弟，而是一条有明确上下关系的链条。下面的表格把它们放在一起对照，你要重点看两列——"它住在哪"和"它有没有特权"。

四层接力：为什么要把简单的事情拆成四份

现在回答那个悬着的问题：把"创建一个被隔离的进程"拆给四个程序去做，是不是过度设计？一次创建容器，说到底不就是几次系统调用吗？先看事实：这四层各自只做一小段，任何一层都不试图包揽全部。再看得失：每多一层就多一次进程间通信、多一份出错可能；但同时也多了一道可以独立替换、独立升级、独立测试的边界。

这个取舍在 2016 年前后变成了现实问题。当时 Docker 把 containerd 拆出来，很多人不理解：为什么要从自己身体里割下一块？答案后来变得清楚——Kubernetes 想直接使用容器运行时，却不想依赖整个 Docker；再后来 OCI 运行时规范确定，runc 也可以被换成别的实现。于是出现了这样的可能：同一台机器上，命令行来自一家，守护进程来自一家，运行时来自另一家，它们靠标准接口对接。分层不是为了好看，是为了让每一层都能被替换，从而让整个系统不必被任何一家公司绑死。

为了让这件事更具体，我们看一眼机器上真实存在的进程。

docker run -d --name proc-demo alpine sleep 300
docker exec proc-demo ps -o pid,ppid,args
docker events --since 1m

在容器里执行 ps，你会看到一个极短的进程表：PID 1 就是 sleep 300 本身。这就是"容器里的 1 号进程"的含义——它不是 init 系统，而是你的应用。第三条命令打印最近一分钟的事件流（container create、container start、exec_create 等）与时间戳，它是观察部件接力最直接的窗口。

把四层的接力关系画成一张表，并给出一个非常实用的东西：每一层失败时你看到的错误长什么样。排障的本质就是把错误信息定位到某一层。

方 法

遇到任何工具报错时，先做一件比搜索更快的事：判断这条错误是"哪一层说出来的"。方法很简单——看错误里的名词。提到 flag、command，是客户端在抱怨你的语法；提到 daemon、socket、connect，是客户端够不着引擎；提到 manifest、layer、pull、blob，是仓库或镜像装配环节；提到 runtime、namespace、cgroup、exec，是最后一公里。把错误定位到层，再去搜这一层的关键词，答案会精确得多。这个习惯不只对 Docker 有用：任何分层系统（网络协议栈、编译器、浏览器）都可以这样切。

方 法

docker info 是一份"我的引擎现在什么样"的体检报告，但初学者常被它上百行输出淹没。只看五个字段就够了：OSType 决定你能运行哪些镜像；Storage Driver 决定层怎么被叠起来，出文件类怪问题先看它；Cgroup Version 是资源上限的实现机制，第 04 章限制内存时会回到这一行；Docker Root Dir 是镜像与容器实际所在的位置，C 盘告急时它是第一现场；Total Memory 是那台机器（在 Windows 上就是 WSL2）能用的内存，常小于你笔记本标称的内存，因为虚拟化会留出一部分。

docker info --format "{{.OSType}} | {{.StorageDriver}} | {{.CgroupVersion}} | {{.DockerRootDir}} | {{.MemTotal}}"

你会得到一行被竖线分隔的值。把它抄进笔记并标注每一项的含义——这是属于你机器的指纹。若 MemTotal 换算成 GB 后明显小于买电脑时那个数字，不要怀疑 Docker 算错了，那是虚拟化边界上的正常损耗。

回 望

第 01 章我们确认过一条判断：容器不是虚拟机，它共享宿主机的内核。现在这张表把它具体化了——前四个部件全都在共享同一个内核的前提下工作，它们做的事情是"向这个内核提出隔离请求"，而不是各自造一个内核出来。你在第 01 章用 uname -r 看到的那个版本号，正是这四个部件共同的施工依据。

前 瞻

第 09 章会回到 dockerd 那条高权限通道，算清"把套接字挂进容器"到底有多危险；第 12 章会展示 Kubernetes 如何直接把 containerd 当成执行者，那时你会发现这条四层链条只是换了一个发号施令的人，中间三层几乎原封不动。

docker run 的几百毫秒：逐步拆解

现在走一遍完整流程。目标是让你合上页面后，能在纸上把这条路径默画出来。我们先用 docker run --rm hello-world 走六个阶段，假设本地没有这个镜像——这个假设很重要，因为"第一次"和"第二次"的经历完全不同；随后用 docker run -d --name web -p 8080:80 nginx 把每个部件都叫醒一遍。

阶段一：从你的按键到一封信

你在 PowerShell 里敲下回车，Windows 找到 PATH 里那个 docker.exe 并启动它。CLI 解析参数：run 是子命令，--rm 是一个选项，hello-world 是要用的镜像；随后读取当前上下文（桌面版默认通常是 desktop-linux），把你这一串意图序列化成一份 HTTP 请求。请求体大致是"用 hello-world 这个镜像创建容器，创建完立刻启动，退出后自动删除"。这一步之后命令行已经不能反悔：它把请求发出去，然后阻塞在那里等回信。这也解释了为什么按 Ctrl-C 有时"杀不掉"容器——你杀掉的是客户端，不是服务端已经收到的订单。

阶段二：请求穿过那台看不见的 Linux 机器

在 Windows 上，这封信要先进入 WSL2。请求到达真正的 dockerd，守护进程先看本地有没有 hello-world 这个镜像。答案是没有，于是它决定去仓库取——这是它作为决策者的职责，具体的取件动作它交给 containerd。

阶段三：把镜像从网络那头搬到本地

这一步最花时间，也最少被初学者理解。你写下的是 hello-world，但网络那头收到的不是一个名字，而是一串问题：这个名字属于哪个仓库服务？它的标签指向哪份清单？清单里有没有适配我这个平台（操作系统加处理器架构）的版本？每一层的哈希是什么？于是取件分成几步，每一步都可能失败，失败信息各不相同：解析镜像名，确定去哪个仓库服务；请求标签对应的清单，标签不存在就报 manifest unknown；清单里没有你这个平台的版本，就报 no matching manifest for linux/amd64；逐个下载层，网络中断会出现 layer download 相关错误；最后校验每一层的内容哈希，对不上就拒绝使用——这是内容寻址带来的安全性，第 03 章细讲。

这一段的耗时完全由网络决定，可能几百毫秒，可能几十秒。Docker Hub 对匿名与登录用户都有拉取速率限制，这也是很多团队搭私有仓库的现实动机之一。这里顺手埋一个代价问题：如果引擎每次都要向网络确认"本地这个镜像是不是最新的"，它就必须联网；而十个容器共用一批已经下载好的层，意味着这一步在绝大多数时候可以完全跳过——镜像一旦落到本地，创建容器就不再需要网络。 这条判断对"内网离线部署"极其重要，第 10 章会把它展开成一套完整做法。

阶段四：装配一个"根目录"

层下载完，containerd 把它们解开、按顺序叠好，再在上面加一层空的可写层，合成一个容器能看到的根目录。这一步在 Linux 上通常由联合文件系统完成，Docker 默认的存储驱动 overlay2 就建立在它之上。这里有个隐含的惊喜：如果这台机器上已经有别的镜像用过同一批底层，这些层不会被重复下载，也不会重复占用磁盘——这就是第 01 章那个实验里"两个容器却只有一个 ubuntu 镜像"的原因。装配完成后，containerd 生成一份描述：根在哪、要隔离哪些东西、限制多少资源、启动哪个程序、带哪些环境变量，然后把它交给 runc，自己退到幕后继续管理生命周期。

阶段五：runc 调用内核，把进程关进去

runc 做的事情可以粗暴地概括为"按照配置，向内核提出一连串请求"：创建一个新进程，让它拥有自己的进程号视图（于是它以为自己是 1 号）、自己的网络视图（于是它有自己的一套网卡与端口，第 07 章展开）、自己的挂载视图（于是它看到的根是这个容器专属的根）与自己的主机名；按照配置设定内存与 CPU 上限；丢掉一批危险的特权。这一切在内核里都是毫秒级操作，因为没有任何东西被创建成"一台机器"，只是给一个进程换了几个视角。runc 完成设置、启动目标程序之后自己退出；从此刻起，容器里的 1 号进程就是那个程序本身，它写标准输出的每一行都会被捕获，成为你稍后用 docker logs 看到的内容。

阶段六：结果怎么回到你的屏幕上

hello-world 打印完那段话就退出了，退出码 0。这个状态沿着来路回传：containerd 记录容器结束与退出码，dockerd 更新账本，把容器最终状态记成 Exited (0)；因为你带了 --rm，它顺手把容器与可写层删掉。回信沿着相反方向走完整条链路，回到那个一直在等的 CLI 手里，被排版成几行好读的文字。把六个阶段放进一张表，并给出一个关键判断：哪些阶段会被缓存，哪些不会。这张表也是你日后优化启动速度时的对照清单。

动手实验一：让同一条命令从慢变快

这个实验的目的不是跑通，而是让你亲眼看到缓存的形状。先删除本地可能存在的 hello-world 镜像，然后运行两次，再解释时间差去了哪里。追问：如果我把镜像删掉再跑一次，为什么它可能比第一次快？提示，想一想"下载"与"在本地装配"是两件不同的事。

docker rmi hello-world
docker run --rm hello-world
docker run --rm hello-world

第一条命令删除本地镜像（如果之前没拉过它，会提示 No such image，这不算错）。第二条会重新下载并运行，你能看到 Pull complete 之类的进度提示。第三条几乎瞬间返回，那一串下载提示完全消失——请留意，它打印出的那封信内容与第二条一模一样：快的部分不是程序的运行，而是镜像的获取。

动手实验二：用 nginx 走完"命令 → 组件 → 结果"

这个实验把本章所有部件串成一条可以复述的故事线。按顺序执行四条命令，并说出每一步分别由哪个部件完成。注意端口写法：冒号左边是宿主机的端口，右边是容器内的端口，方向不能反，第 07 章讲它的实现原理。

docker run -d --name web -p 8080:80 nginx
docker ps
docker inspect web
docker logs web

第一条返回一长串容器 ID：CLI 把意图寄给了引擎，引擎向仓库取了镜像并创建、启动了容器。第二条列出运行中的容器，端口一列会显示 0.0.0.0:8080->80/tcp，它读的是引擎的账本，全程不碰容器。第三条把容器的完整描述打印成 JSON，重点看 State 里的状态与退出码、NetworkSettings 里的地址、Mounts 里的挂载点——这些就是引擎记的账。第四条读的是容器主进程写到标准输出的内容。容器名 web 在这里第一次体现价值：后续命令都用它指代容器，不必去记那串随机 ID。

在浏览器里打开 http://localhost:8080，你会看到 nginx 欢迎页，这一跳背后是宿主机的转发规则在起作用。接着做两次追问。第一问：把 -p 8080:80 里两个数字对调成 -p 80:8080 会怎样？想一想谁在监听哪个端口，就会明白为什么反了会打不开。第二问：如果启动时报 Bind for 0.0.0.0:8080 failed: port is already allocated，说明宿主机上已经有别的程序占用了 8080，最常见的情况是你之前运行过一个没删掉的容器。这时有两个选择：清理旧容器，或者换一个宿主机端口。

docker run -d --name web2 -p 8081:80 nginx
docker ps --format "table {{.Names}}\t{{.Ports}}\t{{.Status}}"

第一条换用 8081 端口再起一个同样的容器，这次不会冲突。第二条用自定义格式列出容器名、端口与状态，输出比默认格式清爽得多——这项技能在你同时跑五个容器时会变成刚需。做完之后记得清理现场：docker rm -f web web2。

易 错 点

初学者最容易在这件事上形成错误直觉：把"第一次慢"归因于"容器启动慢"，于是得出结论"容器也不快啊"。实际慢的是镜像下载，属一次性成本；容器自身的启动开销是另一回事。区分这两笔账决定了你的优化方向——如果慢在网络，该做的是镜像加速或换更小的基础镜像；如果慢在启动，该做的是减少应用自身的初始化工作。用错方向，你会花大量时间优化一个根本不是瓶颈的环节。

镜像、容器、存储驱动：谁是谁

第 01 章留了一个问题没有正面回答：如果两个容器真的互相隔离，为什么 docker images 里那个 ubuntu 只有一份？现在可以回答了，而且答案会把三个最容易混淆的概念彻底分开。

先说镜像。镜像（Image）是一个只读的、分层的、自包含的打包模板：里面有文件系统内容，也有启动时要执行的命令、环境变量、暴露的端口这类元数据。关键在于它不是"一个大文件"，而是"一组层加上一份配置"。层（Layer）是镜像的组成单位，每个构建指令通常产生一层，层内部记录的是"相对于上一层，文件多了什么、变了什么、删了什么"。层不可变：一旦生成，它的内容就被算成一个哈希值，从此这个名字就代表这些字节。容器（Container）则是镜像的一次运行实例，结构上等于"镜像的全部只读层"加"一层属于它自己的可写层"，再加运行时状态（进程号、网络地址、挂载点、退出码）。所有"我在容器里改了文件"的行为，落点都在那一层可写层里，永远不会碰底下的只读层——这就是两个容器互不干扰的全部机理，而它的代价也在这句话里：每个容器都必须为自己改动的每个字节付出一次复制，所以可写层是昂贵的临时空间，不是廉价的数据仓库。

最后说存储驱动。存储驱动（Storage Driver）是实现者，是真正把这套"只读层加可写层叠成一个根目录"的规则落到磁盘上的那个组件。Linux 上 Docker 默认用 overlay2，它建立在联合文件系统（UnionFS，把多个目录叠加成一个统一视图的能力）之上。你不必一开始就钻进去，但要知道它的存在，因为容器里所有奇怪的文件行为都从这里出来：读一个没改过的文件，它来自只读层，几乎不花额外代价；改一个没改过的文件，存储驱动先用写时复制（Copy-on-Write，先共享、要改才复制）把它整份复制到可写层，再在你复制出来的那份上修改；删掉一个来自只读层的文件，磁盘上不会少任何东西，只是被放了一个"白障"标记，让它在合并视图里消失。这三条规则解释了三个你早晚会撞上的现象：删了大文件镜像体积却没变小、改一个大文件会突然卡一下、把数据库数据目录放在可写层里会越跑越慢——它们不是三个独立的怪问题，而是同一个机制的三张脸。

回 望

第 01 章那个"两个容器、一个镜像"的实验，当时只能给出一个模糊说法："它们共享了底下的东西。"现在这个说法可以升级成精确的三段式：共享的是镜像的全部只读层，各自独有的是自己那一层可写层，负责把两者叠起来的是存储驱动。你在这个机制里看到的每一次"省"，代价都是一次"复制"。

下面的表格把三者摊开对比，这是本章你最该记住的一张表。

有一个命令专门用来观察"可写层与只读层的分界"，值得你养成习惯。docker diff 会列出容器相对镜像发生了哪些文件变化：A 表示新增，C 表示内容改动，D 表示删除。

docker run -d --name diff-demo alpine sleep 600
docker exec diff-demo sh -c "echo hello > /mark.txt"
docker diff diff-demo

你会看到一行以 A 开头的输出，指向 /mark.txt——这就是可写层里新增的文件。接着用 docker rm -f diff-demo 删掉这个容器，重新起一个同名容器进去看，文件不存在了。请解释：文件去哪了？它有没有可能还在磁盘上？第二个问题第 06 章展开，你现在就可以猜一次。

还有一个容易被跳过的细节：可写层与镜像之间的边界，不是"安全的边界"。可写层里的文件对你的容器来说是私有的，但它在磁盘上仍然躺在宿主机的文件系统里，用最高权限是能看到的。容器给你的是视图隔离，不是数据保险箱。这个区别在安全语境下极其重要，第 09 章会算清这笔账。

思 考
  1. 如果可写层这么贵，为什么 Docker 不干脆让容器直接修改镜像的只读层？改成就地修改之后，哪三件事会立刻变得不可能？提示：从"多个容器共享同一个镜像"这个前提出发。
  2. 假设你有一个 2 GB 的模型文件放在镜像里，容器启动时需要在它基础上追加几 KB 元数据。按照写时复制的规则，这次操作会付出多大代价？如果你每天启动这个容器一百次，你该怎么改设计？提示：回想"数据要放卷里"这条纪律，它真正的原因是性能还是持久化？
  3. 白障机制让"删除"变成了"加一个标记文件"。这带来一个好处和一个坏处，你能各说出一个吗？提示：好处与"不破坏底层"有关，坏处与"你以为删了其实没删"有关。

Windows 上为什么必须有一台 Linux 虚拟机

现在回答那个被推迟的问题：为什么 Docker Desktop 在 Windows 上要偷偷开一台 Linux 机器？答案要从第 01 章的结论倒推。容器之所以轻、之所以快，是因为它不虚拟硬件，而是借宿主机的内核。那么问题就变成一句很朴素的话：内核必须提供那些隔离能力。命名空间（namespace，让进程对全局资源的视野变成独立一份的机制：进程号、网络、挂载点、主机名、用户等）在内核里提供；cgroups（控制组，给一组进程设定 CPU、内存、磁盘 IO 上限并统计实际用量的机制）在内核里提供；联合文件系统同样依赖 Linux 的挂载与文件系统能力。这三样东西，Windows 内核不提供。

于是只有两条路。一条是让 Windows 原生实现一套等价机制，这就是 Windows 容器：它确实存在，也有自己的镜像格式（基于 Windows 基础镜像，动辄几个 GB），靠"进程隔离"或"Hyper-V 隔离"运行。另一条是承认现实——既然你需要 Linux 内核，那就在 Windows 上跑一个真实的 Linux 内核。Docker Desktop 默认选第二条路。

WSL2 就是在做这件事。它不是模拟器，也不是翻译层，而是一台跑在轻量虚拟化之上的真实 Linux 内核；你可以在 PowerShell 里进入它，执行 uname -r 看到和普通 Linux 一样的版本号样式（通常带 WSL2 字样）。Docker Desktop 会在其中安装一个专用发行版，引擎就跑在里面。所以你这台笔记本的真实拓扑是这样的：Windows 是外面的世界，WSL2 是里面那台机器，dockerd 住在里面，容器也住在里面。

wsl --list --verbose
wsl uname -r
wsl ls /var/run/docker.sock

第一条列出你所有的 WSL 发行版与它们的版本号、状态，你会看到 Docker Desktop 创建的那个发行版（名字里通常带 docker）。第二条打印出真实的 Linux 内核版本并带 WSL2 标识——你由此确认"容器脚下踩的是一颗真正的 Linux 内核"。第三条打印出那个套接字文件，它就是引擎待命的地方。

这个拓扑能解释很多你迟早会遇到的怪事。第一件是 C 盘空间：镜像和容器都住在 WSL2 的虚拟磁盘里，那个磁盘在 Windows 上表现成一个文件，通常叫 ext4.vhdx。你 pull 了一堆镜像忘了删，C 盘就会悄悄变小，而"我的 D 盘明明很大"帮不上忙。第二件是跨系统文件性能：代码放在 C 盘、用绑定挂载挂进容器，每一次读写都要穿过 Windows 与 Linux 两层文件系统，速度会明显下降。第三件是路径与内存：容器里的 /app 是那台 Linux 机器上的路径，和你 D 盘上的目录没有关系，除非你明确挂载；而 Docker Desktop 能用多少内存是按那台虚拟机给的，可以在设置里限制——好处是防止一次跑飞的构建把笔记本拖到卡死。

所以"把代码放哪儿"在 Windows 上有一个明确答案：放进 WSL 的 Linux 文件系统里（例如你的 Linux 用户主目录下），用 VS Code 的 WSL 模式打开它。这不是洁癖，这是性能。

docker info --format "{{.OSType}} | {{.Driver}} | {{.DockerRootDir}}"
docker info --format "{{.Name}} | {{.ServerVersion}}"

第一条打印引擎的操作系统类型（应该是 linux）、它使用的存储驱动（通常是 overlay2）与数据目录（在 WSL 里表现为 /var/lib/docker）。第二条打印那台 machine 的名字（桌面版上通常叫 docker-desktop）与引擎版本号。两条合起来回答了"我的 Docker 到底住在哪、用的是什么实现"。

这里值得停下来问一个尺度更大的问题：既然 Windows 上跑 Linux 容器需要一台轻量虚拟机，那么"容器比虚拟机轻"这个结论在 Windows 上还成立吗？答案有点微妙。成立的层面在容器之间——同一台 WSL2 里跑十个容器，只共享一台轻量虚拟机，容器之间的开销依然是进程级的；不成立的层面在"从零开始跑第一个容器"——那一次你必须先有一台 Linux 机器，这笔开机成本由 Docker Desktop 与 WSL2 共同承担，通常在你开机后一次性付清。容器的轻是相对同一台宿主机而言的，一旦宿主机本身需要靠虚拟化换来内核，这笔账就要算在宿主机头上。

易 错 点

把"这台 WSL2 虚拟机"和"容器"混为一谈，会引出两个具体错误动作。第一个是看到容器里没有 systemd、进程表里只有一两个进程，就以为环境坏了，于是想方设法在容器里装 init 系统——实际你要装的是能正确处理信号的小工具，而不是一整套服务管理器（第 04 章会讲停容器为什么慢）。第二个是以为删掉所有容器和镜像就能立刻释放 C 盘空间——WSL2 的虚拟磁盘不会自动缩回，得走专门的压缩流程。知道"有这回事"和"知道该敲哪条命令"，中间隔着的正是这一章讲的那条调用链。

我还想把 Docker Desktop 在 Windows 上的两种后端放在一起对比，因为它直接决定你机器上多出来的是什么。较早的 Hyper-V 后端会单独开一台轻量 Linux 虚拟机；较新的 WSL2 后端复用 WSL 的 Linux 内核。两者都是虚拟化，区别在于这台虚拟机的内核从哪来、你还能不能顺手用它做别的事。

第 01 章我们从 dotCloud 与 2013 年那场演示讲到 OCI 标准，当时说"容器从一家公司的产品变成了整个行业的接口"。这一节补上了另一半：接口的代价。当你坚持用 Windows 又想要 Linux 容器时，必须接受一台虚拟机作为中间人；这不是 Docker 设计得不好，而是"共享内核"这个前提在 Windows 上无法直接满足。技术方案的边界，往往就写在它最核心的那条假设里。

Docker 不负责什么

把一台机器拆开之后，最后一件必须做的事是：把它的职责范围也画一条线。初学者最常见的困惑不是"某条命令怎么用"，而是期待 Docker 解决一件它从来没打算解决的问题，然后在反复尝试中耗尽耐心。

第一件不在职责内的事是编排。编排要回答的问题包括：这个服务该放在哪台机器上、某台机器挂了怎么把容器挪走、怎么把流量分给三个副本、怎么滚动升级不中断服务、怎么在流量上来时自动扩到十个副本。这些问题的前提是"有多台机器"，而 Docker 在单机上的能力（包括 Compose）本身不解决跨机器调度。你可以在单机上把三个副本跑起来，但谁来决定把请求分给哪一个，那是编排层或反向代理的事。第 12 章会带着这一章的调用链去看 Kubernetes 是怎么接手的。

第二件是持续集成与持续交付（Continuous Integration / Continuous Delivery，CI/CD）。Docker 提供的是交付物——一个可以被搬运、被复现的镜像。至于"代码一推送就自动构建、跑测试、推送到仓库、部署到测试环境"这条流水线，是另一个系统的工作，Docker 只是流水线上最重要的那个环节。反过来说，镜像做得干净、标签管得清楚，你的流水线才有可能简单；这两件事的关系是"镜像质量决定流水线复杂度"，而不是"有了流水线就不必管镜像"。

第三件是备份。容器与镜像可以删了重建，所以它们不需要备份；真正需要备份的是数据卷里的东西、数据库里的数据、你辛苦积累的训练产物。Docker 提供了卷这个放数据的地方，但没有提供备份策略、没有提供异地副本、没有提供恢复演练。把数据放进卷里只是第一步，"卷坏了怎么办"是你要自己回答的问题。第 06 章讲数据时会把这件事讲到底。

第四件是监控与告警。docker stats 能让你看几秒钟的实时占用，docker events 能让你看到事件流，但"凌晨三点内存涨到 90% 时给谁发消息""这个接口的响应时间是否劣化""过去一周的错误率趋势如何"，这些属于可观测性系统的工作。Docker 在这里的贡献是重新定义了日志的流向：容器里的应用只管往标准输出打印，由外部系统收集，这就是 docker logs 背后的哲学，也是第 10 章可观测性那一节的起点。

为了把边界说得更锋利，我们用一张表把"你以为是 Docker 的事"和"真正负责的层级"对上。

看到最后两行的对比，你应该能读出这一章真正想教给你的态度：知道一个工具负责什么，和知道它不负责什么，是同一件事的两面。一个工具越强大，越容易被人当成万能答案；而工程师的专业性，恰恰体现在能准确说出"这个问题的答案不在这个工具里"。这条判断力在后面会反复被用到，尤其是在你遇到"我明明用了容器，为什么环境还是会不一致"这类问题时——第 10 章的十二要素应用会逐条告诉你，哪些环境差异应该被注入，哪些才应该被固化。

一个工具真正的形状，是由它拒绝做的事决定的。

动手实验三：把你自己的机器画出来

这个实验没有标准答案，目的是把这一章从"读懂了"变成"能画出来"。实验目的：让你手上这台机器的拓扑从想象变成事实。你要找出四件事——命令行连到了哪里、引擎住在哪个操作系统里、它用什么方式管理文件系统、它的数据放在哪个目录。

docker context ls
docker version
docker info --format "{{.OperatingSystem}} | {{.OSType}} | {{.Driver}}"
docker system df

第一条告诉你当前上下文以及所有可选目标，注意带星号的那一行。第二条把客户端与服务端分开打印，你要学会分别读这两块——只有当两块都出现时，才说明命令行真的连上了引擎。第三条回答"引擎住在哪个系统上、用什么存储驱动"。第四条给出镜像、容器、卷、构建缓存各占多少空间，并告诉你其中多少是可回收的。

预期现象：你会看到 OSType 是 linux，即使你正坐在 Windows 前面；存储驱动是 overlay2；数据目录在 Linux 的路径下。解释为什么：这四行输出合起来证明了一件事——你的容器从来没有在 Windows 上跑过。追问一个变体：如果你在 PowerShell 里执行 wsl --list --verbose 再执行一次 docker version，两份输出之间能不能看出对应关系？如果能，你就已经能独立回答"Docker Desktop 出问题时该看哪里"了。

自测：检验你是否真的学懂了

检 查 题
  1. 你敲下 docker version，屏幕上只出现 Client 一节，后面跟着一句连接失败。把这句报错定位到四层链条里的某一层，并说出你的第一步动作。
    参考答案

    这是"客户端够不着守护进程"，属于 dockerd 那一层的连通性问题，不是安装问题也不是镜像问题。判断依据是报错里出现了 connect 或 daemon 这类词，而不是 flag、manifest、runtime。第一步不是重装 Docker，而是确认引擎是否在运行：图形界面里的引擎状态、wsl --list --verbose 里那个 Docker 发行版是否在跑。若引擎活着，第二步才检查上下文是否指对了目标。评分要点：能说清"报错里的名词决定它属于哪一层"，且第一动作不是重装。

  2. 请按从外到内的顺序，写出在 Windows + Docker Desktop（WSL2 后端）上，一条 docker ps 请求经过的所有环节。
    参考答案

    PowerShell 里的 docker.exe（CLI）解析参数并读取上下文 → 通过通道把请求交给 WSL2 里的 dockerd → dockerd 从账本里取出容器列表 → 结果沿原路返回给 CLI → CLI 排版打印。关键点是这道题里没有任何"容器被创建"的动作：docker ps 只读账本，全程不经过 containerd 与 runc。评分要点：顺序正确，并能指出这一步不涉及 containerd 和 runc。

  3. 下面这条命令会输出什么？为什么第三个字段通常不是 Windows 风格的路径？ 
    docker info --format "{{.OSType}} | {{.Driver}} | {{.DockerRootDir}}"
    参考答案

    会输出类似 linux | overlay2 | /var/lib/docker 的一行。第三个字段不是 Windows 路径，因为引擎本身运行在 WSL2 的 Linux 环境里，它报告的是"自己所在机器"上的路径。在 Windows 上看到这个路径，是"命令在 Windows、引擎在 Linux"最直接的证据。评分要点：能解释这不是路径显示错误。

  4. 一个同学说他"把 Docker 里的文件删了，但 C 盘空间没变多"。请给出至少两种彼此不同的解释。
    参考答案

    第一种：他删的是容器里的文件，那只是在可写层加了一个白障标记，底下的只读层一个字节都没少。第二种：他确实删掉了容器和镜像，但 WSL2 的虚拟磁盘文件不会自动缩回，需要通过压缩流程才能真正把空间还给 Windows。可能还有第三种：残留的卷或构建缓存仍占着空间，要用 docker system df 才看得见。评分要点：能区分"层内删除"与"虚拟机磁盘回收"这两个完全不同的机制。

  5. 为什么 Docker 要把"创建容器"拆成 containerd 和 runc 两层？如果合并成一层，会失去什么？
    参考答案

    拆开是为了把稳定的编排逻辑（拉镜像、装配根文件系统、管理生命周期）与易变的执行细节（具体怎么调用内核实现隔离）分开，让执行细节可以被替换——这直接促成了 OCI 运行时规范，也让 Kubernetes 可以绕过 Docker 直接使用 containerd。合并成一层会失去可替换性：换一种隔离技术就得重写整个运行时，同时也失去一层可独立升级、独立测试的边界。评分要点：答出"可替换性／标准接口"这个核心理由，并举出 Kubernetes 或 OCI 作为证据。

  6. 判断题并说明理由：容器启动快，是因为它启动了一个精简版的 Linux。
    参考答案

    错。容器根本没有启动任何操作系统，它只是给一个进程换了几个视角：进程号视图、网络视图、挂载视图、主机名，再加上资源上限。容器里那个根目录是若干只读层加一层可写层叠加出来的结果，不是一份被启动起来的系统。物理原因是不复制内核、不模拟硬件，所以开销接近普通进程。评分要点：指出"没有启动操作系统"，并提到命名空间与联合文件系统。

  7. 你要给别人演示"容器共享镜像的只读层"，手上只有一台机器。请设计一个能在一分钟内完成、且结论可见的演示。
    参考答案

    可行方案：先后运行两个基于同一个基础镜像的容器，在其中一个里新增一个文件，然后在两个容器里分别查看该文件是否存在；用 docker diff 给出更精确的证据——只有改过的那个容器会显示 A 记录。再补一个反向证据：docker images 里那个基础镜像只有一份，且 docker system df 显示的镜像总占用远小于"两份镜像相加"。评分要点：有对照组、有可见证据、能解释证据对应哪个机制。

  8. 为什么"把 docker.sock 挂进容器"被说成危险动作？请从架构角度解释，而不是用"权限很大"这种笼统说法。
    参考答案

    因为那条套接字是客户端与守护进程之间的唯一通道，谁能向它发请求，谁就能让守护进程（一个以最高权限运行的常驻进程）替自己做事。挂进容器之后，容器里的程序就获得了"向引擎下单"的能力：它可以要求启动一个把宿主机根目录挂进去的新容器，从而事实上越过自己在原容器里受到的隔离。危险的不是"权限大"这个形容词，而是它拿到了对决策者发号施令的通道。评分要点：能说出"通道等同于代替守护进程做决定"。

  9. 命令预测：下面两条命令的输出会有什么不同？为什么？ 
    docker run --rm alpine echo hi
docker run --rm alpine echo hi && docker run --rm alpine echo hi
    参考答案

    两条命令的第二行都会打印两个 hi，内容完全一样，唯一差别是跑几次。真正值得注意的不是输出差异，而是两次执行之间的耗时差异：第一次可能需要下载 alpine 的层，第二次几乎瞬间完成，因为层已经在本地的镜像存储里，containerd 不需要再去仓库取。评分要点：能指出"没有输出差异，差别在时长与本地缓存是否命中"，并说明缓存命中省掉的是下载与解包，而不是容器启动。

  10. 故障诊断：同学在 Windows 上运行 docker run --rm hello-world，得到报错 no matching manifest for windows/amd64 in the manifest list entries。请解释发生了什么，并给出修复方向。
    参考答案

    这是镜像选择环节失败，属于 containerd 那一层的错误。原因是引擎当前被配置成运行 Windows 容器，而 hello-world 主要面向 Linux 平台（或者反过来）。修复方向是让两边对齐：把引擎切回 Linux 容器模式（Docker Desktop 提供了切换入口），或者改用与引擎类型匹配的镜像。通用价值在于：镜像与引擎的"平台类型"必须一致。评分要点：把错误定位到镜像／平台匹配环节。

  11. 方案取舍：你要在一个容器里跑一个会持续写日志文件的应用，日志每天增长 1 GB。请给出至少两种方案，并说明各自的代价。
    参考答案

    方案一：把日志目录挂到数据卷或绑定挂载上，让它落在可写层之外。代价是你要自己管理磁盘上限与轮转，卷不会自动清理。方案二：改造应用，让它把日志写到标准输出，由外部系统收集与轮转，这是容器世界的常规做法。代价是需要引入收集链路，本地调试时要习惯 docker logs。方案三：两者结合，本地开发用文件加轮转，生产用标准输出加收集。评分要点：至少两种方案、代价明确，并能指出"写在可写层里"是三者共同要避免的错误。

  12. 动手任务：用 docker events 与 docker ps 观察一次完整的容器生命周期。要求你写出执行顺序与你看到的事件序列。
    参考答案

    典型顺序是：先在一个终端执行 docker events（它会持续等待，不返回），再在另一个终端执行 docker run -d --name t alpine sleep 60，随后 docker stop t，最后 docker rm t。事件流里大致会依次出现 container create、container start、container die、container destroy 这几类事件，每条都带时间戳。要看懂的是每一个事件对应哪个部件的动作：create 与 start 是决策与执行，die 记录退出，destroy 是清理与记账。评分要点：命令顺序合理、事件名称基本准确、能把这些事件映射回部件分工。

  13. 开放题：有人说"我在 Windows 上用 Docker，就等于在虚拟机上跑容器，所以容器相对虚拟机的所有好处都没了"。请评价这句话。
    参考答案

    一半对一半错。对的部分：从零开始跑第一个容器需要一台 Linux 机器，这笔开机与内存成本确实由 WSL2 承担，"容器毫无虚拟化开销"在 Windows 上不成立。错的部分：这笔成本是一次性的、被所有容器共享的；在那台 Linux 机器内部，容器之间依然只付出进程级开销——启动依旧是百毫秒量级，十个容器不会变成十台虚拟机，镜像层依然按内容共享。评分要点：能同时说出"哪部分代价真实存在"和"哪部分结论依然成立"。

  14. 概念辨析：请分别用一句话说明镜像、容器、存储驱动三者的关系，并指出哪一句话在排障时最有用。
    参考答案

    镜像是一份可搬运的只读内容加元数据；容器是这份内容的一次运行实例，多了一层只属于自己的可写层；存储驱动是把只读层与可写层叠成一个根目录的那个实现。排障时最有用的是第三句：当出现"改了文件却找不到""删了文件空间没变""大文件写入突然变慢"这类现象时，答案都在存储驱动这一层。评分要点：三句话界限清楚、不互相串味，并给出一个具体排障场景来支持判断。

  1. 合上页面，用自己的话向一个没学过 Docker 的同学解释"为什么我敲的 docker 命令自己什么都不干"。他会追问"那谁在干"，你能答上来吗？提示：把"表达意图"和"实现意图"这两个词用上，再补一句这个分工带来的好处。
  2. 不看笔记，把 docker CLI、dockerd、containerd、runc 这四层从外到内默写一遍，并在每一层旁边写一个它失败时会出现的错误关键词。提示：如果某一层你想不出错误关键词，说明你还没真正见过它出错。
  3. 用一句话说清镜像、容器、存储驱动三者的关系，要求这句话里同时出现"只读""可写""实现"三个词。提示：能压成一句话，说明三者在你脑子里已经不是三个孤立名词。
  4. 为什么同一个镜像在两个容器里同时运行，改文件互不影响，而磁盘上却只有一个镜像？把机理讲一遍，再补一句"代价是什么"。提示：代价那段比机理那段更能说明你是否真的懂了。
  5. 如果让你只用一条命令证明"我的容器跑在 Linux 上"，你会敲哪一条？为什么它比看图形界面更有说服力？提示：想想哪一条输出是引擎自己说的，而不是界面替你总结的。
  6. docker run 的耗时里，哪一段被缓存了、哪一段永远不会被缓存？把这个区分讲给一个总抱怨"Docker 很慢"的同学听。提示：网络与磁盘是两笔账。
  7. 说出两件 Docker 明确不负责的事，并为每一件给出一句话的理由，说明为什么它不该由 Docker 负责。提示：从"这需要什么信息、Docker 恰好没有这些信息"这个角度想。
  8. 你在 WSL2 里看到 /var/lib/docker 这个路径，它在 Windows 上对应到哪里？为什么这个对应关系会让你某天突然少掉几十 GB 的 C 盘空间？提示：一个虚拟磁盘文件，和它只增不减的性格。
  9. 如果明天 Docker 公司消失了，你机器上这条调用链还能跑吗？请从本章讲过的标准与部件出发回答。提示：想想哪些部件已经不属于这家公司了。
  10. 这一章里哪一句话让你最不舒服、最想反驳？把它写下来，然后想一下：你反驳它的依据，是事实，还是你从别处听来的说法？提示：忍不住想反驳的地方，通常正是你下一篇笔记该写的地方。

本章总结

  • Docker 采用客户端—服务器架构：命令行只负责表达意图，真正干活的是后台那个待命的守护进程。好处是客户端可以指向任意一台机器，代价是通道断了命令就失灵。
  • 七个部件不是并列的兄弟，而是一条有上下的链：docker CLI 说话，dockerd 决策与记账，containerd 装配与管生命周期，runc 调用内核完成隔离，镜像仓库在网络上供货，Docker Desktop 把它打包进 Windows，WSL2 提供那颗必须存在的 Linux 内核。
  • 把简单的事情拆成四层，换来的是每一层都可以被替换。containerd 独立、runc 遵循 OCI 运行时规范，直接后果是 Kubernetes 可以不用 Docker 却仍然在跑容器。
  • 一条 docker run 的完整路径是：解析 → 寄信 → 穿过 WSL2 → 查本地镜像 → 从仓库取层并校验 → 装配根文件系统 → 调用内核关进程 → 回传退出码。每一步都可能失败，而错误信息里的名词会告诉你它在哪一层。
  • docker run 的快不均匀：第一次运行主要慢在网络下载，镜像已在本地时才轮到百毫秒级的启动开销。把这两笔账混在一起，你的优化方向必然错。
  • 镜像、容器、存储驱动的关系是三段式：镜像是只读内容与元数据，容器是镜像加一层独享的可写层，存储驱动是把它们叠成一个根目录的实现者。
  • 写时复制是这一切的物理基础，也是那三个经典怪现象的同一个源头：容器里删文件不释放空间、改大文件突然卡顿、频繁写大文件越跑越慢。
  • Windows 上必须有 Linux 虚拟机的根本原因，是容器依赖的都是 Linux 内核能力（命名空间、cgroups、联合文件系统），Windows 内核不提供。Docker Desktop 的默认答案是 WSL2。
  • WSL2 让容器的轻在容器之间依然成立，但在"从零跑第一个容器"这件事上，虚拟化的成本真实存在，只是被所有容器分摊了。
  • Docker 不负责编排、不负责 CI/CD、不负责备份、不负责监控告警。这一章最重要的一个判断是：一个工具的专业边界和它的能力同样重要——能准确说出"这个问题的答案不在这个工具里"，是工程师与工具使用者的分界线。
  • 排障的正确姿势是先把错误定位到层，再搜索这一层的关键词；这个习惯适用于所有分层系统，不只是 Docker。

你把一只木箱拆成了木板、钉子与榫头，第一次看清了它是怎么被拼起来的。从此再听到"Docker 出问题了"，你心里不会只剩一团黑，而是一条可以从头查到尾的路径——哪一段断了，就去修哪一段。接下来，我们要认真看一看这只箱子里装的货物本身：那些被称为"层"的东西，如何被算出哈希、如何被共享、如何在你改一行代码之后决定重建几步。第 03 章，我们从"镜像不是一个大文件"讲起。

拓 展 阅 读
  • Docker 是什么官方文档 https://docs.docker.com/get-started/docker-overview/ 官方对架构的权威表述，比任何二手文章都准确。重点读讲 Docker Engine 与客户端—服务器那几段，带着一个问题读：官方把哪几件事归给了 daemon，哪几件归给了 CLI？这和本章的划分是否一致？
  • containerd 官网官方站点 https://containerd.io/ 读完你会对"运行时管理器"这个身份有实感：它管理什么、不管理什么、被谁调用。带着本章的问题去读——为什么 Kubernetes 愿意直接用它？看完它的功能清单，试着为"分层是为了可替换"这条判断再补一个证据。
  • 开放容器倡议（OCI）标准组织 https://opencontainers.org/ OCI 是本章最重要的名字。先只读首页对两个规范（镜像规范、运行时规范）的一句话介绍，弄明白"标准管的是格式与接口，不管实现"。不要一开始就钻进规范正文，那是第 03 章之后的事。
  • Docker Desktop 文档官方文档 https://docs.docker.com/desktop/ 你机器上那个包装盒的说明书。重点看 Windows 相关的安装要求、后端选择与资源设置几节，读的时候带着本章那两个具体问题：内存上限在哪里调、虚拟磁盘怎么回收空间。
  • WSL 官方文档（中文）官方文档 https://learn.microsoft.com/zh-cn/windows/wsl/ 直接讲清你机器上那台"看不见的 Linux"。重点看安装、发行版管理与文件系统那几节，读的时候带着两个问题：我的代码放在哪一侧？为什么跨侧访问会慢？
  • 命令行参考官方文档 https://docs.docker.com/reference/cli/docker/ 把它当成字典而不是教材。本章出现的每一条命令都能在这里查到完整参数，建议现在就去查 docker events 与 docker info，看看它们的输出里还有哪些字段是你没注意过的。
值 得 品 读 的 书
  • 《深入浅出 Docker》 Nigel Poulton 著 补上"整体图像"这件最难自学的事。它的图多、字少、讲法克制，正好可以把本章的调用链在纸上画第二遍。适合现在就读，带着一个问题读：作者画的那张组件图，和我自己画的差在哪里？

  • 《The Linux Command Line》 William Shotts 著 补上容器脚下的那块地。不建议整本读完，而是当成工具书：每当你在 WSL 或容器里遇到一条看不懂的命令，回来查它的出处。长期看，命令行基本功决定了你能在容器里走多深。
