第 10 章流 水 线 之 上 · ENGINEERING

工程化：从"跑起来"到"交付出去"

把镜像变成流水线上的产品，而不是手工打磨的工艺品。

本 章 学 习 目 标
  • 能说清"我这台机器上跑通了"与"这件事被工程化"之间的四道门槛，并说明每道门槛把风险交给了谁。
  • 能逐条对照十二要素应用审视自己的项目，判断哪些条目已在容器里自动成立、哪些必须靠你亲手做出来。
  • 能解释"构建一次，处处运行"为什么不是口号，而是把"环境"这个变量从运行时彻底移走的一次手术。
  • 能设计一套镜像标签与版本策略，并说清每个标签的读者是谁、覆盖它会造成什么后果。
  • 能读懂一份 GitHub Actions 工作流的全部分段，并解释构建缓存为什么是流水线里最贵的一件事。
  • 能描述可观测性三支柱各自回答什么问题，并把它翻译成"我的服务该打印什么、暴露什么"。
  • 能区分蓝绿、滚动、灰度的代价与回滚难度，并在给定场景下做出取舍。
学 完 之 后 ， 你 应 该 能 够
  • 能为一个真实项目写出镜像标签规范，并用 inspect 拿到 digest 做发布记录。
  • 能用一个 .env、一个 .env.example 和一套 override 文件，把开发、测试、生产三套配置组织清楚。
  • 能写出一份语法正确、逻辑完整、带构建缓存的 GitHub Actions 工作流，并逐段讲出每一段的目的。
  • 能为容器设计健康检查与结构化日志，让排障从"登录机器翻文件"变成"按时间与请求号查询"。
  • 能完成一次可回滚的发布：打标签、推送、部署、验证、必要时切回上一个版本。
  • 能判断一个项目的工程化处在哪个阶段，并列出下一步最值得补的那三件事。

第 09 章我们把门锁好了：镜像扫描、最小权限、密钥不进仓库、供应链上的每一环都有人负责。那一章结束时你手里已经有一座像样的房子，但它还只是"你自己的房子"。真正的难题才刚刚开始：三个月后你自己还装得起来吗？同学第一次拿到这个仓库，要花几小时还是三条命令？半年前那个"还能用"的版本，你还找得回来吗？前面九章回答的是"容器怎么运行"，这一章回答一个新问题——一年之后，这套东西还跑得起来吗？答案不在任何一条 docker 命令里，而在你对流程的设计里。

手工执行的边界：为什么"跑起来"是工程成功的反面

先演一遍脑子里的小实验。你在项目目录里第一次敲下这条命令：

docker build -t myapp:demo .

构建成功，最后一行打印出镜像名和那串 sha256 开头的 ID，docker run 起来，浏览器里页面正常打开。这一刻是前九章的高潮，也是大多数初学者以为的终点。

现在把同样的命令再执行三遍，每次换一个条件。第二次，你删掉了源码里半个函数，构建依然成功——构建过程只关心文件长什么样，不关心代码能不能跑。第三次，包管理器从源上拉到的某个小版本恰好发布了新版，构建也成功，只是镜像里躺着一个和你昨天不一样的东西。第四次，同学在他笔记本上执行，卡在某个系统库上，回你一句"你这东西在我这儿构建不过"。

四次都"跑起来了"的尝试，给出了四个不一样的世界。这就是手工执行的第一个边界：它保证了这一刻的成功，却不承诺任何一次重复。而软件工程绝大部分痛苦，恰恰来自"重复"——重复部署、重复排障、重复交接、重复回滚。

四个门槛：可重复、可审计、可回滚、可协作

把"跑通"变成"工程"，中间隔着四道递进的门槛。

第一层，可重复。同样的输入，在任何一台装了 Docker 的机器上得到行为一致的产物。第 05 章那份 Dockerfile 已经解决了大半：基础镜像锁住了操作系统家族，指令锁住了安装步骤，.dockerignore 锁住了参与构建的文件范围。剩下那半在第 03 章就埋了伏笔——只要你写 apt-get install curl 却不写版本号，你的"可重复"就依赖着某个远端仓库今天的心情。

第二层，可审计。出了事能回答"这个正在跑的容器是哪份代码、哪次提交、哪一步构建出来的"。手工执行时代这个问题几乎无解，你只能凭记忆。一旦镜像标签对应到 Git 提交、构建由机器自动完成并留下日志，"凭记忆"就变成了"凭记录"——责任归属从人转移到了流程。

第三层，可回滚。回滚（rollback，把线上服务换回上一个已知可用的版本）必须是五分钟内能完成、不重新构建、不重新编译、不临时写代码的动作。第 09 章讲不可变基础设施时提到"用新镜像替换旧镜像"，价值就在这里：旧版本并没有被销毁，它只是暂时退场。

第四层，可协作。一条命令能起环境，一份文档能说清流程，新人第一天的成本是可预测的。这一层听起来最软，实际上最贵，因为它决定了团队的知识能不能沉淀成资产，而不是散落在每个人的聊天记录里。

比 喻

手工执行像一位老师傅在作坊里打椅子：他能打出极好的椅子，但每一把都略有不同，手艺也无法完整传给徒弟。工程化像一条流水线：单件产品未必有老师傅的巅峰水平，但它能稳定产出规格一致的产品，任何一个人请假都不会让产线停摆。

比喻要还回来：流水线真正的代价是前期投入与灵活性下降。你首先要为流水线本身做很多工作，其次一旦它定死，做一把完全另类的椅子会变得别扭。工程化不是无条件的正确，它是规模和时间的函数：一个人做玩具项目，手工执行完全够用；一旦有第二个人、第二个月、第二个环境，收益就迅速压过成本。你要学会判断自己站在哪一侧。

方 法

判断一个团队的工程化水平，有个省事的问法："你们上一个版本是怎么发布出去的？要回到上上个版本，需要几步、多久？"如果回答里出现"我得找某某人""我得先把服务器上改回去""大概一两个小时吧"，那么无论镜像写得多漂亮，工程化都还没开始。检验工程化的标准不是工具，而是最坏情况下的动作成本。这套方法可以迁移：想评估任何系统的健壮性，不要看它在顺利时多快，要看它在出问题时的恢复时间。

回 望

第 05 章优化构建缓存时，视角是"让你的开发体验从每次两分钟降到每次三秒"。本章把这些知识换一个坐标系重讲一遍：在流水线里，缓存不再是你个人的舒适度问题，而是整个团队的钱和等待时间。第 05 章讲过的层顺序艺术，会变成 CI 上"缓存命中率"这个可以被测量、被优化、也会被一次错误改动悄悄毁掉的指标。

前 瞻

第 12 章会讲编排系统。先埋一个伏笔：本章你会亲手写出"发布与回滚"的动作序列，每一步都是你手动敲的命令、你要记的步骤数。到了第 12 章，这套序列会被交给编排系统的一个字段——你只声明"滚动更新到新镜像，最多容忍一个实例不可用"，剩下由机器执行。现在手动做一遍，是为了将来能看懂机器替你做的那一遍到底做了什么。

思 考
  1. 如果一个人写的小工具永远不会被别人使用、也永远不会上线，还有必要把它容器化、给它写 CI 吗？请给出判断标准，而不是"要"或"不要"。 提示：想想工程化投入的成本由谁承担、收益由谁获得，以及"将来会不会有第二个人"的概率有多大。
  2. 四个门槛里哪一个最难补齐？如果你只有一周时间，你会先补哪一个？ 提示：可以从"哪一层缺失会让其他三层失效"这个角度想。

十二要素应用：一份为容器时代写好的自查清单

看第四列：十二条里只有少数几条是 Docker 替你自动办到的，剩下的都要你亲自动手。这个发现比清单本身更重要：容器不是工程化的自动售货机，它只是让正确的做法变得便宜。下面挑四条展开，它们分别在讲时间、变量、输出与动作，也是初学者最容易读懂字面却做错的地方。

深入一：构建与运行分离，是整套体系的地基

这条只有一句话：严格分离构建阶段和运行阶段。构建阶段的产物是一个不可变的交付物，运行阶段只做一件事——使用它，不允许编译、安装、改文件、联网下载。为什么它是地基？因为它把不确定性压缩到了一处。如果生产环境还能编译代码，"这次上线的是什么"就取决于那台机器上恰好装着哪个版本的编译器；如果运行阶段还能联网下载依赖，"今天能跑"和"明天能跑"就是两件事。而构建的不确定性有天然的好处：构建可以失败，构建失败没有后果，构建是在一台随时可以扔掉的机器上发生的。

Docker 让这件事变得物理化，而不只是纪律化。第 03 章讲过层与写时复制，现在可以接上：只读层就是这个交付物，可写层就是运行时留下的临时噪音。还有一个容易忽略的细节：构建期与运行期的变量是两套东西。ARG 只在 docker build 期间存在，它的值可能留在构建历史里、能被 docker history 看到，所以用 ARG 传密钥很危险；ENV 设置的才是运行期环境变量，会被容器里的进程继承。构建期与运行期不仅阶段不同，它们的信息可见性也不同。

深入二：配置存于环境——好处、边界与那个说不出口的代价

这一条说的是：把会随部署环境变化的东西（数据库地址、日志级别、第三方服务端点、功能开关）放进环境变量，不要写死在代码里，也不要写进镜像。好处很直观：同一份镜像可以在你笔记本上连本地数据库，在测试环境连测试库，在生产环境连生产库——三处用的是同一个摘要，"测试过的就是上线的"第一次可以字面成立。而且环境变量在容器启动那一刻注入，它不改变镜像，所以不破坏第 09 章那条纪律——镜像里不该有任何秘密。

配置载体何时生效留在镜像里吗改一次要重建吗适合放什么
写死在代码里构建期是要，且要改代码几乎什么都不适合
ENV 指令写进 Dockerfile运行期，但值固化在镜像里是要不随环境变化的默认值
ARG 构建期参数仅构建期值可能留在构建历史要构建变体开关，不放秘密

配置从代码里被移走了，却没有被搬到任何一个能被完整阅读的地方。工程化的大量工作，本质上都是在为"被移走的东西"补一个落点。

这一条最容易被滥用的一面就在这里。如果所有配置都进了环境变量，那"这个服务完整的样子"在哪里？打开仓库，你看到的是一串 ${DATABASE_URL}；打开服务器，你看到的是注入进去的值，却不知道还有哪些变量是必需的。工程上的答案很朴素：让必需变量的清单本身也进仓库——一份 .env.example，列出每个变量名、含义、示例值、是否必填。它不含任何真实秘密，却让"这个服务的完整说明"重新有了落点。

易 错 点

把 .env 提交进 Git 是最常见、也最容易被忽略的一条。它的危险在于"看起来没问题"：文件就在项目根目录，写起来方便，Compose 自动就会读。可一旦推送到远端，口令就永久留在了 Git 历史里——删掉文件并不能删掉历史。第 09 章讲过密钥不进仓库，这里补上具体动作：把 .env 写进 .gitignore，把 .env.example 提交上去，并在代码评审时专门看一眼这两个文件的状态。自查方法：在仓库根目录运行 git check-ignore -v .env，如果它没有输出任何规则，说明你并没有忽略它。

深入三：日志作为事件流，和深入四：管理任务作为一次性进程

日志这一条将在第七节彻底展开，这里只讲核心纪律：应用只管把日志写到标准输出和标准错误，绝不自己打开文件、切割文件、压缩文件。传统做法里应用要负责落盘、轮转、保留策略，结果是日志分散、格式各异、没人知道该看哪一个。容器把这件事一刀切开：应用产生事件，运行平台负责收集、传输、存储与检索。它的前提是你必须接受一个反直觉的事实——容器的文件系统是临时的。你把日志写进 /var/log/app.log，容器一删日志就没了；容器还在，你也得先进去才能 cat。写文件是给一个随时会死的东西写日记，写到标准输出才是把事情交给活着的人。

第四条，管理任务作为一次性进程，是十二条里最实用也最少被提起的一条：数据库迁移、缓存预热、批量清理、数据导出这类"跑完就该退出"的任务，应该作为独立进程运行，而不是塞进常驻服务的启动脚本。为什么？因为常驻服务可能同时启动多个副本，三个副本会同时执行迁移，谁先谁后全看运气；更糟的是迁移一旦失败，容器会陷入"启动—失败—重启"的循环，而它本来只是一个一次性动作。

实验一：用一次性容器跑管理任务

实验目的：体会"跑完即销毁"的管理任务与常驻服务的区别，并搞清 docker compose run 与 docker compose exec 的分工。把下面的内容保存成 compose.yaml：

services:
  db:
    image: postgres:16-alpine
    environment:
      POSTGRES_PASSWORD: example
    volumes:
      - pgdata:/var/lib/postgresql/data
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U postgres"]
      interval: 5s
      timeout: 3s
      retries: 10
  migrate:
    image: postgres:16-alpine
    environment:
      PGPASSWORD: example
    depends_on:
      db:
        condition: service_healthy
    entrypoint: ["psql", "-h", "db", "-U", "postgres", "-c"]
    command: ["CREATE TABLE IF NOT EXISTS visits (id serial primary key, at timestamptz default now());"]
volumes:
  pgdata:

migrate 的 entrypoint 把 psql 固定成"必须执行的程序"，command 才是这一次要执行的 SQL——这正是 ENTRYPOINT 与 CMD 的经典分工。depends_on 用了 condition: service_healthy，意味着 migrate 会等到数据库真的能接受连接才启动，而不只是等到容器被创建；第 08 章讲过默认的 depends_on 只保证"启动了"，这里用的才是"就绪了"。

docker compose up -d db
docker compose run --rm migrate

你会看到 migrate 执行那条 SQL、打印出 CREATE TABLE，然后立刻退出，并因为 --rm 被自动删除。再运行一次，它仍会打印 CREATE TABLE 但表不会重复创建，因为 SQL 里写了 IF NOT EXISTS——这就是"迁移脚本必须可重复执行"的朴素含义。此时 docker compose ps 只会列出 db，migrate 没有留下任何痕迹。

请解释为什么这一次不该用 docker compose exec：exec 的前提是"目标容器正在运行"，而管理任务在定义上就不是长期存在的东西；更重要的是，exec 会复用那个常驻容器的环境，让"我要跑一个任务"和"我要进这个服务顺手敲点什么"混在一起。第 04 章讲过 exec 的纪律是"用于排障，不用于改配置"，这里补上后半句：要改的东西，应该写成一次性任务，让它成为可以被评审、被重放的一行命令。追问一个变体：如果迁移必须跑在和应用完全相同的镜像里，compose.yaml 该怎么改？提示：把 migrate 的 image 换成应用镜像，用 entrypoint 覆盖启动命令——这样迁移用的代码和线上跑的代码来自同一个镜像，不可能出现"迁移脚本版本和应用对不上"的事故。

回 望

第 08 章你学过 Compose 的 run、exec 与 override 文件，当时它们的身份是"开发时的便利工具"。本章把它们提升成了流程的一部分：run 是执行一次性任务的正式通道，override 文件是多环境配置的组织手段。同一个命令，在不同规模的项目里有完全不同的分量。

构建一次，处处运行：把"环境"这个变量移走

"构建一次，处处运行"（build once, run anywhere）被印在无数幻灯片上，但它真正的技术含义常被含糊过去。它不是在说"镜像可以在任何地方运行"，而是在说一句更硬的话：从测试环境到生产环境，被搬运的那个东西必须是一个字节都不差的同一份镜像。不是同一个 Dockerfile 重新构建出来的两份，是同一份。

为什么"重新构建"不行？因为构建不是纯函数。同一个 Dockerfile 在两次执行之间，至少有四样东西可能已经变了：基础镜像的标签可能被重新推送过内容，包管理器源里的依赖可能发布了新版本，构建缓存可能命中了不同的旧层，网络下载回来的东西可能根本不是同一份文件。第 05 章结尾那个前瞻里埋的雷，现在炸了——你写在 Dockerfile 里每一行"依赖网络、依赖时间"的指令，在"重新构建"这个前提下都会变成一枚不确定性的种子。

不可变交付物的价值，在于它把讨论变成了事实

当镜像成为唯一的交付物，团队里很多争论会自动消失。"你测的是这个版本吗"不再需要凭记忆回答，因为你可以把两边的摘要打印出来直接比；出事之后"线上跑的是什么"也不再有歧义空间。第 09 章讲供应链安全时提到的 SBOM（软件物料清单）之所以有意义，前提也是这个：只有交付物不可变，关于它的清单才有意义。下面这条命令值得从今天开始养成习惯，每次发布都留下一行摘要：

docker image inspect myapp:1.4.2 --format "{{index .RepoDigests 0}}"

你会得到形如 myapp@sha256:一长串十六进制 的输出。它和 myapp:1.4.2 的区别是根本性的：标签是一个可以被覆盖的指针，"1.4.2 指向谁"取决于仓库里最后一次推送；摘要是内容自己算出来的指纹，无法被冒充，也无法被悄悄换掉。发布记录里写标签是给人看的，写摘要是给未来的自己留证据。假如输出为空，通常说明这个镜像只存在于本地、还没被推送到任何仓库，本地镜像没有仓库摘要可谈。

把这条纪律延伸到拉取环节：生产环境甚至可以直接按摘要拉取，docker pull myapp@sha256:...，这样就彻底断开了"标签被重新指向"的风险。代价是这一行没有人能一眼读懂，所以它更适合写在部署清单里，旁边备注人类可读的版本号。

同一镜像、不同配置，具体长什么样

把"构建一次"落到实处，需要一套三层的组织方式：镜像提供代码与运行时，配置由环境注入，环境之间的差异被压缩到尽可能小的几个变量上。假设你已经构建并推送了 myapp:1.4.2，现在要在测试环境验证它：

docker pull registry.example.cn/team/myapp:1.4.2
docker run -d --name myapp-test -p 8081:8000 -e APP_ENV=staging -e LOG_LEVEL=debug -e DATABASE_URL=postgres://app@db-test:5432/app registry.example.cn/team/myapp:1.4.2

这条命令里有三类信息：镜像引用（不可变的那一半）、端口映射（部署位置的差异）、三个环境变量（环境差异的那一半）。验证通过之后，生产环境要执行的命令和它几乎一样，只有 -e 的值和端口不同。如果两者的差异需要你改 Dockerfile，那说明你把环境差异错误地烤进了交付物。

还有一个容易被忽略的细节：发布时顺手把源码版本注入镜像，好让排障时一眼确认"线上跑的是哪次提交"。常见做法是在构建时把 Git 提交号作为构建参数传进去，应用启动时打印出来。请你自己想一想：如果把提交号写进 Dockerfile 里的 ENV，会发生什么？答案是每次提交都会让这一层之后的缓存全部失效——因为 ENV 的值变了。所以正确的位置通常是构建参数，或者干脆由运行时的环境变量注入。缓存与可追溯性在这里是有张力的，这个张力你要自己权衡，而不是背一个结论。

易 错 点

"我们生产是单独构建的"这句话往往伴随两个听起来很合理的理由：构建参数不同，或安全上不想让生产镜像经过测试环境。第一个理由通常不成立——构建参数不同意味着你交付了两个不同的东西，"测试过的就是上线的"立刻失效，正确做法是把差异移到运行期的环境变量。第二个理由值得认真对待，但它真正的解法是限制谁能拉取镜像、谁能推进发布，而不是在生产环境重新构建一份。每当你想"再构建一次"，先问一句：我到底是想改变产物，还是想改变它的配置？

思 考
  1. "构建一次，处处运行"与"每个环境单独构建"各自的代价是什么？请说出两种代价，并指出它们分别由谁承担。 提示：把代价分成"机器的时间""人的时间""事故的风险"三类，看看分别落在哪一侧。
  2. 如果同一个镜像要在两种 CPU 架构的服务器上运行，你还能坚持"构建一次"吗？如果能，这次构建和普通构建有什么不同？ 提示：想想镜像里的二进制文件是怎么来的，以及构建时是谁在执行编译器。
展开：多平台构建与"构建一次"的边界

"处处"的边界是运行环境的操作系统与 CPU 架构。容器共享宿主机内核，所以 Linux 容器只能跑在 Linux 内核上（Windows 上的 Docker Desktop 正是靠 WSL2 或虚拟机提供这个内核）。CPU 架构的差异更直接：为 x86_64 编译的二进制在 ARM 机器上无法执行。

解法不是"每个平台分别构建一次"，而是用 BuildKit 的多平台构建能力一次产出多个平台的镜像，并让它们共用一个清单标签；拉取时 Docker 会按当前架构自动挑选。但要留意一个常被误解的细节：构建 ARM 镜像时构建机上需要有能执行 ARM 代码的模拟层（通常是 QEMU），所以"一次构建出所有平台"往往慢得多，也可能在某些依赖上因模拟而失败。真正的取舍是：只在确实需要发布的平台上构建。

展开：为什么"可复现"至今仍很难做到百分之百

理论上，内容寻址加不可变镜像已经足够复现任何一次交付。实践中有几个缺口：基础镜像标签的内容可能被重新推送（所以严谨的做法是 FROM 里写摘要）；容器里如果有文件记录了构建时间戳，两次构建的产物哈希必然不同；某些语言的构建工具会把路径信息写进二进制，导致同一份源码在不同目录下构建出不同产物。

你真正需要的是判断力：知道哪些地方天然不确定，从而在关键处（基础镜像、依赖版本）主动锁死，在无关处（构建缓存、时间戳）接受波动。工程上通用的表达方式是——不是追求完美，而是让不确定性被看见、被记录、被限定在可控范围内。

镜像标签与版本策略：一套能落地的规范

如果说镜像是一份交付物，标签就是它的通讯录——决定谁能找到它、以什么名字称呼它、以及这个名字在什么情况下会指向别的东西。镜像标签（Tag）是一个可变指针，指向某个具体的镜像内容摘要。可变既带来方便，也带来灾祸。第 03 章辨析过标签与摘要的区别，本节把它变成一套可以写进团队规范的策略。

latest 到底错在哪里

先澄清一个误解：latest 不是"最新的版本"，它甚至不保证是最近的，它只是"当你不写标签时默认使用的那个标签"。真正的问题是它的语义在时间上不可预测：昨天和今天拉取 myapp:latest 得到的东西可能完全不同，而你的命令里看不出任何差别。它一举摧毁了前面几节建立的全部收益——不可重复、不可审计、不可回滚，因为"回滚到 latest"这句话本身没有意义。

那为什么官方镜像还默认提供它？因为 docker pull nginx 这种"我不想关心版本，给我一个能用的"的用法确实存在，latest 让这条命令可以省掉标签。它服务的是探索与体验场景，不是交付场景。由此得到一个折中判断：latest 可以存在，但它不许出现在任何部署命令里。

思 考
  1. 如果 latest 这么危险，为什么官方镜像还默认提供它？如果让你设计一套公共镜像仓库的默认行为，你会怎么改，代价是什么？ 提示：从"两种完全不同的使用者"这个角度想——一个在探索，一个在交付。

每种标签都有自己的读者

一条实用的经验：不要问"哪个标签最好"，而要问"这个标签是给谁看的"。同一个镜像可以同时挂多个标签，它们服务于不同的读者与自动化流程。

标签形式示例主要读者特点与风险
语义化版本（三段式）1.4.2人、发布记录、审计不可变，语义清晰；需要纪律性地遵守"改了才递增"
次版本浮动1.4想自动获得补丁更新的使用者内容会变，但它承诺兼容；需要有人真的在维护它
主版本浮动1想获得小版本更新的使用者变化范围更大，用于对外承诺"接口不变"
Git 提交短哈希sha-a1b2c3d机器、排障、追溯唯一且不会重名；对人不可读，无法判断新旧
时间戳20250114-0930人、快速判断先后可读性好；与代码版本没有直接对应
分支名main、feature-login开发与预发环境天然的浮动标签，被覆盖是常态；绝不用于生产
环境名staging、production部署脚本最危险的一类：把"环境"放进了镜像名，等于承认不同环境用不同镜像

看最后两行。环境名标签的危险不在于技术，而在于它在习惯上鼓励了一件错事：让生产使用一个独立的镜像，于是"同一份交付物"这条底线悄悄没了。latest 的危险则在于它伪装成"我不用选"，实际上是"我把选择权交给了时间"。

推荐做法：多标签指向同一份内容

可以照抄的策略是：一次构建，打上多个语义不同的标签，推送全部标签，让它们指向同一个摘要。具体到 1.4.2 这个版本，你要打三个：

docker build -t myapp:1.4.2 -t myapp:1.4 -t myapp:sha-a1b2c3d .
docker push myapp:1.4.2
docker push myapp:1.4
docker push myapp:sha-a1b2c3d

三条 -t 写在同一次构建里是关键——如果分三次构建再分别打标签，你就得到了三个内容可能不同的镜像，多标签策略的意义就没了。短哈希换成你当前提交的实际值，用 git rev-parse --short HEAD 可以得到。推送要逐个来，因为 docker push 一次只处理一个标签。

这样安排之后，三个标签各有用途：1.4.2 是审计与发布记录里的准确名字；1.4 让使用者在不改小版本的前提下自动拿到补丁；sha-a1b2c3d 把镜像和代码提交绑在一起，让排障能从镜像倒推到源码。它们指向同一个摘要，所以"用户拉 1.4 得到的东西"与"审计上写的 1.4.2"在内容上完全一致。配套的另一件事是浮动标签要有人负责：推出 1.4.3 时把 1.4 重新指向新摘要，靠人记早晚会忘，靠流水线做它就变成一行代码。

实验二：亲手验证三个标签指向同一个摘要

实验目的：亲眼看到"标签是多对一的指针"，并学会用 inspect 读出它们的真实身份。

docker pull alpine:3.20
docker tag alpine:3.20 myapp:1.4.2
docker tag alpine:3.20 myapp:1.4
docker tag alpine:3.20 myapp:sha-a1b2c3d
docker images myapp --format "{{.Repository}}:{{.Tag}} {{.ID}} {{.Size}}"

你会看到三行输出，Repository 与 Tag 不同，但最后的镜像 ID 完全相同——这三个名字指的是同一份内容，磁盘上也只存了一份。docker tag 并不复制任何数据，它只是给同一个镜像增加了一个名字。你以为你在"打标签"，其实你在"建立引用"。

docker image inspect myapp:1.4.2 --format "{{index .RepoDigests 0}}"
docker image inspect myapp:1.4 --format "{{index .RepoDigests 0}}"
docker image inspect myapp:sha-a1b2c3d --format "{{index .RepoDigests 0}}"

这三条对只在本地存在的镜像可能都输出空行，因为 RepoDigests 记录的是"这个镜像从哪个仓库以什么摘要被拉取或推送过"，而你这几个标签还没离开过本机。想让实验完整，先推到你有权限的仓库（Docker Hub 免费账号即可），再运行这几条，你会看到三个标签输出完全相同的摘要。这个"先推送才有摘要"的细节本身就是一课：摘要属于仓库里的内容，不属于你本地的名字。

请解释为什么把 myapp:1.4 推送之后，myapp:1.4.2 的 RepoDigests 里也会出现同一个摘要？追问一个变体：如果同学在他机器上把 myapp:1.4 重新推送成了别的内容，你的发布记录里那条摘要还有效吗？想清楚这两问，你就理解了为什么"发布记录写摘要"比"写标签"更可靠。

方 法

版本策略这类问题的通用思考方式是：先确定"谁是读者"，再确定"允不允许变化"。每个名字（标签、文件名、接口版本号）都在回答同一个问题——它承诺的内容会不会变。会变的东西给人用，不会变的东西给机器和审计用；两者混用就会出事。这个框架你已经在别处见过：数据库加字段时要保证旧代码仍能读，因为旧代码是新数据的另一个读者；函数返回值不轻易加字段，因为调用方是你无法控制的读者。把"读者与稳定性"这个二维表格内化成直觉，你以后设计任何命名规范都会快得多。

前 瞻

第 11 章会讲 AI 场景与模型部署。到那时你会发现标签策略换了一身衣服又出现了一次：模型文件同样需要"哪个实验、哪份数据、哪组超参数"的追溯，同样不能用"最新那个"来指代。数据版本、实验追踪、模型注册这三件事，和本章的镜像标签是同一道题。

多环境配置：把差异集中到一处

上一节讲的是"别让不同环境拿到不同镜像"，这一节讲它的另一半：既然镜像相同，环境之间的差异只可能存在于配置里。问题于是变成"怎么把差异组织得既能一眼看清，又不容易泄漏秘密"。先确定三套环境各自要什么：开发环境要改代码立即生效、日志详细、能用调试工具；测试环境要尽量接近生产的拓扑、数据可以随便清空、能反复重建；生产环境要稳定、安全、可观测、变更可追溯。这三套环境的差别，理想情况下应该只剩下少数几个变量的值，而不是两套 Compose 文件、两套 Dockerfile、两套部署脚本。

一份可以直接照抄的目录结构

下面这个结构把"不变的部分"和"随环境变化的部分"物理分开了：

myproject/
  Dockerfile
  .dockerignore
  compose.yaml
  compose.override.yaml
  .env.example
  .env
  .gitignore
  src/

compose.yaml 是各环境共享的骨架；compose.override.yaml 只在开发时被自动叠加（运行 docker compose up 时 Compose 会自动读取它）；.env 存放本地实际值并被 .gitignore 排除；.env.example 只写键名与示例值并被提交进仓库。通常还会有针对性的覆盖文件，例如 compose.prod.yaml，用 -f 显式指定来叠加。

# .env.example —— 复制成 .env 之后再填真实的值；本文件不含任何秘密
APP_ENV=development
LOG_LEVEL=info
APP_PORT=8000
DATABASE_URL=postgres://app:CHANGE_ME@db:5432/app

.env.example 的作用是充当"必需变量的清单"，同时它也是一份文档：新人拿到仓库，复制成 .env，把 CHANGE_ME 替换掉，就能起环境。里面的值必须是明显无效的占位符，绝不能是真实的测试环境口令——否则它迟早会被当成"反正是测试环境"而被复制到各处。

services:
  app:
    build: .
    environment:
      LOG_LEVEL: debug
    volumes:
      - ./src:/app/src
    ports:
      - "${APP_PORT:-8000}:8000"

开发用的覆盖文件集中"只有开发才需要"的东西。build: . 只在开发出现，意思是"从本地源码构建"；生产的部署清单里会换成 image: 加具体标签，绝不构建。volumes 把本地源码挂进容器，这是第 06 章讲的绑定挂载最正当的用途。端口用了 ${APP_PORT:-8000}，意思是"环境里有 APP_PORT 就用它，没有就用 8000"，它让同一个文件在别人机器上也能跑。

实验三：用 compose config 看穿最终配置

实验目的：回答第二节留下的问题——配置被搬进环境变量之后，"这个服务的完整说明"到哪里去找。让它自己算出来给你看。docker compose config 会把所有文件、环境变量、默认值合并之后，打印成一份展开完毕的最终配置；它不启动任何容器，纯粹是一个渲染器。

docker compose --env-file .env config

输出里所有 ${...} 都已被替换成具体的值，环境变量落到各服务的 environment 下，端口、卷、依赖关系都是最终形态。这份输出就是你缺失的那份"运行时刻的真实说明书"——它比手写文档准确，因为它是从唯一的事实来源算出来的。

docker compose --env-file .env.example config > config.dev.txt
docker compose --env-file .env.prod config > config.prod.txt
docker diff config.dev.txt config.prod.txt

两次输出的差异应当只出现在你预期的那几个变量上。如果差异里冒出了"某个服务多了一个挂载""生产环境居然还带着 build 指令""端口映射不一样"，那就说明你所谓的"同一份交付物"是假的——配置已经把环境差异偷偷扩大成了部署差异。每次改配置先渲染一遍、看一眼差异，这个习惯值得养成。Windows 上没有 diff 也可以用 PowerShell 的 Compare-Object 对比两个文件。

请解释为什么"差异只有三个环境变量"这件事值得这么用力地追求？追问一个变体：如果测试环境必须用一个和开发不同的第三方服务地址，而这个地址在代码里被读取了两次（一次发请求，一次生成回调链接），你怎么保证两次读到的一定一致？

易 错 点

把 .env 当成"配置文件"来用，会让它越来越像代码：各种开关、路径、甚至 JSON 片段都塞进去，最后没人知道哪些变量还有人在读。治它的一条纪律是：任何一个环境变量都必须能在仓库里的某处被找到用途——要么被 Compose 文件引用，要么被应用代码读取。定期把 .env 里的键与代码里读取的键做一次对照，多余的删掉。同时记住 .env 的三个限制：它是纯文本、不提供权限控制、在容器里不可见（除非显式注入），所以真实秘密的正确归宿是密钥管理系统，而不是一个文件。

回 望

第 08 章讲 Compose 时，override 文件是"让一份文件服务多种场景"的技巧。本节补上了它的工程位置：它是"同一镜像 + 不同注入"在单机环境下的载体。第 08 章还提到过 Compose 与生产环境的边界，现在这个边界更清楚了——它替不了的是多机调度、滚动更新与自动扩缩容，那是第 12 章的内容。

思 考
  1. 如果所有配置都进了环境变量，一个服务的"完整说明"到底在哪里？它足够吗？如果不够，你打算怎么补？ 提示：想想新人入职第一天，他需要知道哪些信息才能安全地启动这个服务。
  2. 有人提议"把测试环境的 .env 直接拿来当生产的起点，改几个值就行"。请列出至少两个反对理由，并给出替代方案。 提示：从"谁有权看到什么"和"哪一份文件会被谁复制"两个角度想。

CI/CD：让机器执行你写下的动作序列

到这一节为止，你已经有了一份可复现的 Dockerfile、一套标签规范、一套多环境配置。但它们目前仍然是"知识"，需要人记得去执行。持续集成与持续交付（CI/CD）要做的事只有一句话：把这些动作从人的记忆里搬到仓库里。三个缩写值得分清：持续集成（Continuous Integration，CI）说的是开发者频繁把代码合并到主干，每次合并都由机器自动构建、自动跑测试；持续交付（Continuous Delivery，CD）说的是每次通过测试的提交都产生一个随时可发布的版本，发布与否由人决定；持续部署（Continuous Deployment）则再进一步，通过测试就自动上线。三者的技术差异只在"最后一公里有没有人工闸门"。

一条典型流水线的阶段是：安装依赖 → 跑测试 → 构建镜像 → 扫描漏洞 → 推送镜像 → 部署。注意顺序里的两个意图：测试在构建之前，因为构建比测试贵，早点拦住坏代码可以少浪费机器时间；扫描在推送之前，因为镜像一旦进了仓库就可能被别人拉走。第 09 章讲的漏洞扫描与密钥管理，正是在这个位置嵌进流程的。

GitHub Actions 的五个基本概念

这套手册用 GitHub Actions（GitHub 的自动化流水线服务）作例子，理由很实际：它内置于代码托管平台，不必自己搭 CI 服务器，对个人与教学项目几乎零成本。它的概念只有五个，理清关系再读 YAML 就不会迷路。

概念它是什么一个类比你要注意什么
workflow（工作流）仓库 .github/workflows/ 下的一个 YAML 文件一整套作业规程一个仓库可以有多个工作流，各自独立触发
job（作业）工作流里的一段任务，默认并行，也可声明依赖规程里的一道工序不同 job 默认在不同机器上跑，文件不共享
step（步骤）作业里顺序执行的单个动作，可以是命令，也可以是别人写好的 action工序里的一个操作同一个 job 里的 step 共享文件系统与工作目录
runner（运行器）真正执行作业的那台机器干活的机床托管 runner 每次都是全新环境，跑完即销毁
secret（密钥）加密存储、只在运行时注入的敏感值保险柜里的钥匙平台会对它打码，但仍要避免主动打印

这里有一条纪律值得单独说：托管 runner 每次都是全新的。你不能依赖上一台机器留下的任何东西——不能依赖装过的依赖、上一轮的产物、那份"上次构建留下的缓存"。这既是安全性的来源，也是效率问题的根源：没有额外机制，每次流水线都要从零重建镜像。

一份完整的工作流，逐段解释

下面这份文件保存为 .github/workflows/build.yml，职责很清楚：代码被推到主干或打上版本标签时，跑一遍测试，构建镜像，推送到平台自带的镜像仓库，并把构建缓存存起来给下次复用。它在语法上是完整的，但镜像路径必须由你替换成自己的用户名与仓库名，测试命令也要换成你项目的真实命令。请不要把它当成"复制粘贴就能跑"的成品。

name: build-and-push

on:
  push:
    branches: [main]
    tags: ["v*"]
  pull_request:
    branches: [main]

permissions:
  contents: read
  packages: write

jobs:
  build:
    runs-on: ubuntu-latest
    steps:
      - name: 取出源码
        uses: actions/checkout@v4
      - name: 准备构建引擎
        uses: docker/setup-buildx-action@v3
      - name: 登录镜像仓库
        if: github.event_name != 'pull_request'
        uses: docker/login-action@v3
        with:
          registry: ghcr.io
          username: ${{ github.actor }}
          password: ${{ secrets.GITHUB_TOKEN }}
      - name: 跑测试
        run: |
          node --version
          npm ci
          npm test
      - name: 构建并推送镜像
        uses: docker/build-push-action@v6
        with:
          context: .
          push: ${{ github.event_name != 'pull_request' }}
          tags: |
            ghcr.io/example-owner/example-repo:sha-${{ github.sha }}
            ghcr.io/example-owner/example-repo:latest
          cache-from: type=gha
          cache-to: type=gha,mode=max

这份 YAML 里的 action 名称与主要参数是写作时的常见写法，但第三方 action 的主版本号与大版本行为会随时间演进。请以 GitHub Marketplace 上该 action 的当前文档、以及 Docker 官方文档的构建章节为准核对版本号与参数含义——把 action 的版本号当成"依赖版本"来对待，是流水线上一条基本纪律。更严谨的团队会把 action 固定到提交摘要，而不是浮动的大版本标签。

触发段（on）声明"什么时候跑"：推送到 main、推送到以 v 开头的标签、以及对 main 发起的拉取请求。对拉取请求也跑一次，是为了在代码合入前给出反馈；标签触发则对应"我要发一个正式版本了"。权限段（permissions）是安全上很关键的一小段：平台会为每次运行生成临时令牌 GITHUB_TOKEN，默认权限可能比你需要的宽，所以这里显式收窄成两条——contents: read 允许读代码，packages: write 允许推送镜像包。第 09 章的最小权限原则，在这里有了具体形态：给流水线的令牌，只给这次任务真正需要的那两项权限。

取出源码把仓库拉到 runner 上，后面所有步骤都以它为起点，请别省掉它——runner 是全新环境。准备构建引擎（setup-buildx）把 BuildKit 配置好，第 05 章讲过它带来并行构建与缓存挂载，在 CI 里显式设置是为了让构建步骤拿到一致的、可配缓存的引擎。登录镜像仓库拿凭据换推送权限：registry 写 ghcr.io；username 用 github.actor，也就是触发这次运行的账号；password 用 secrets.GITHUB_TOKEN，那是平台自动生成并注入的临时令牌，你不需要自己创建任何密钥。这正是"用平台自带令牌"比"自己造一个长期有效的口令塞进 secret"更安全的地方——它天然是临时的、按次有效的。请注意那个 if 条件：拉取请求来自不可信的提交时不应该登录仓库。

跑测试用最朴素的 run 步骤直接在 runner 上执行 shell 命令，这一段必须由你替换：用 Python 就是先装依赖再跑 pytest，用 Go 可能是 go test ./...。它有一个容易被忽视的价值：它让"构建失败"与"代码有问题"成为两件可以被区分的事。构建并推送是整个文件的核心：context: . 表示构建上下文是仓库根目录；push 用了一个条件表达式，意思是"只有在不是拉取请求时才推送"，让拉取请求只验证"能不能构建成功"；tags 里现在写了两条，一条带提交号，一条是 latest。按照第 04 节的规范，这里的 latest 是一个需要被替换掉的坏例子，正确做法是换成你自己的语义化版本号，或只推提交号标签、把浮动标签交给发布流程。我故意把它留在正文里，因为"看懂一份工作流里哪一行不合规范"本身就是本章要训练的能力。

构建缓存：CI 里最贵的一件事

回忆第 05 章的核心结论：构建缓存让"改一行代码"只重建一层。但那条结论有个前提——缓存要在两次构建之间活下来。在你笔记本上这个前提天然成立，因为缓存就在本地磁盘上。在 CI 里它不成立，因为 runner 每次都是新的，上一次的缓存随机器一起被销毁了。如果你什么都不做，流水线每次都要把依赖从头装一遍。一个前端项目装依赖花两分钟，一个 Python 项目装深度学习框架花十几分钟，一个 Go 项目编译花五分钟——这些成本会乘以你每天提交的次数、团队人数、以及未来几年。它是流水线里最容易被忽略、又最容易被度量的浪费。

type=gha 就是解决这个问题的：它让 BuildKit 把缓存导出到平台管理的缓存存储里，并在下一次运行时导入回来。cache-to 末尾的 mode=max 表示"把中间层的缓存也一并导出"，而不是只导出最终镜像用到的层——这让多阶段构建里的编译阶段也能命中缓存，代价是缓存体积更大。这是一个典型的工程取舍：缓存更全，但传输与存储成本更高。请养成一个习惯：在流水线输出里找那句关于缓存命中与导出的提示，把它当成需要盯着看的指标。缓存失效的常见原因是 Dockerfile 前面某层的输入变了，例如你把源码在依赖安装之前就 COPY 了进去，或者某个构建参数变了。在 CI 里，层顺序写错不再是"我多等三分钟"，而是"整个团队每天多等几百分钟"。

展开：CI 里缓存失效的一个隐蔽陷阱

有一种写法会让缓存永远失效，而且很难从输出里看出来：把随每次提交变化的值（提交号、构建时间）作为构建参数传进 Dockerfile，并且在依赖安装之前的某一层使用它。因为你每次提交都会改变这个参数，从那一层开始的所有缓存都会失效，包括后面昂贵的依赖安装层。

判断方式很简单：打开 CI 的构建输出，看依赖安装那一步是不是显示 CACHED。如果不是，就用二分法找——把可疑的那一行往下挪，或者把它改成运行时注入的环境变量。先定位"哪一层的输入变了"，再决定这个输入该不该出现在这一层。

方 法

面对一份陌生的 CI 配置，不要从第一行往下读。先找三样东西：触发条件（它什么时候跑）、权限声明（它拿到了什么令牌）、最后一步做了什么（它把什么放到了哪里）。这三样决定了这次运行的风险面，剩下的是细节。这与读 Dockerfile 时"先判断四段骨架"是同一套方法论：先抓结构，再看实现。读任何基础设施配置都可以这样问：它是被什么触发的？它能碰到什么？它失败时会留下什么？

易 错 点

把密钥直接写在 YAML 里，或用 echo 打印出来"方便调试"，是流水线上最常见的泄漏路径。平台会对密钥的值做日志打码，但打码不是万能的：值如果被拼接、编码、分段输出，就可能绕过打码；而写在普通环境变量里的口令根本不会被当作密钥处理。另一条容易忽略的：拉取请求触发的运行可能来自你不认识的人，所以任何需要在拉取请求里执行的脚本都要假设它是不可信的——这也是示例里那个 if 条件存在的意义。自查方法：打开最近几次运行的日志，搜索你的口令前缀、连接串关键字，看有没有明文出现。

日志与可观测性：在容器会消失的世界里看清系统

容器给排障带来一个残酷的新常态。你以前学的办法是"登录出问题的那台机器，看日志文件"，在容器世界里这办法会同时撞上三个障碍：实例随时会消失（容器被杀掉重建，现场就没了）、名字是随机的（一串自动生成的字母数字，你甚至不知道该登哪台）、数量是动态的（高峰期有二十个副本，你不可能逐个去看）。应对它的武器叫可观测性（Observability），指的是"通过系统对外的输出推断其内部状态"的能力。它有三个支柱，各回答一个不同的问题，把它们混为一谈是设计监控时最常犯的错误。

支柱它回答什么典型形态成本主要在哪里容器时代的特殊难点
日志（Logs）发生了什么？细节是什么？一行行带时间戳的事件文本或 JSON存储与检索成本随流量线性增长实例会消失，必须靠外部采集
指标（Metrics）整体状况如何？有没有异常？可聚合的数值序列，如每秒请求数、内存占用标签维度组合数膨胀带来的基数问题实例名随机，标签要谨慎设计
链路追踪（Traces）这一个请求经过了谁？慢在哪一段？跨服务的一串有父子关系的跨度采样与存储，全量采集很贵请求跨越多个短命容器，需要传播标识

三者可以互补而不可互相替代：指标告诉你"有异常"，日志告诉你"异常是什么"，链路告诉你"异常发生在哪一段"。没有指标的团队会在用户投诉后才发现问题，只有指标的团队会在发现问题后无从下手，只有日志的团队会在查询时被数据量压垮。

从"应用只写标准输出"到能查的日志

第二节那条纪律现在展开：应用只往标准输出和标准错误写，其余交给平台。它靠的是 Docker 的日志驱动——把容器主进程写到标准输出与标准错误的内容接住，交给配置好的后端。默认是以 JSON 形式落到宿主机文件里，所以 docker logs 才能读出来；在编排环境里通常会被配置成直接转发到集中式日志系统。这里有个务实的取舍：默认的日志驱动不会自动限制文件大小，一个话多的容器可以把宿主机磁盘写满。所以生产环境里，日志驱动的配置和日志内容的设计同等重要——要么给日志设置大小与文件数上限，要么把日志送到专门的系统里去。第 02 章提过守护进程配置文件，那里就是设置的地方。

docker run -d --name web nginx:alpine
docker logs web
docker logs --tail 20 web
docker logs --timestamps web
docker logs --since 10m web
docker logs -f web

依次是：看全部、只看最后二十行、带上时间戳、只看最近十分钟、持续跟随。排障时最有用的组合是后三个。先用 --since 把时间窗口缩小到故障发生的那一段（这一步能省掉九成的无效阅读），再 --timestamps 确认事件之间的先后，最后 -f 盯着看它以什么节奏继续出问题。如果你只是 docker logs web 从头翻，在流量大的服务上会在几万行里迷失。值得你亲手演练的顺序是：先制造一个错误（比如把某个必填环境变量故意写错），再按"先看容器还在不在 → 看退出码 → 看时间窗口内的日志"走一遍。第 04 章讲过退出码的读法，把它和日志连起来就是一套完整动作：退出码告诉你"它是怎么死的"，日志告诉你"它临死前在做什么"。

结构化日志：为什么一行 JSON 胜过一句人话

自由文本日志是写给人看的，读者是人的眼睛；结构化日志是写给机器解析的，读者是检索系统。区别在排障时会变得极其具体。假设你要回答"过去一小时内，某个接口状态码为 500 的请求有多少条？平均耗时多少？"用自由文本，你可能要写一条脆弱的正则，还要祈祷字段顺序没变；用结构化日志，答案是两个字段的过滤加一次聚合。人可读与机器可解析并不是不可兼得的，一份 JSON 日志照样可以被格式化成人能读的样子，但反过来不成立。一个务实的建议是至少保证三件事：统一的时间戳、一个级别字段、一个能串起同一次请求的标识。前两个让你能筛选，第三个让你能把一次请求在多个服务、多个短命容器里留下的痕迹串起来；而传递它的代价，正好是链路追踪要解决的问题。

健康检查：三种状态，以及它不该做什么

健康检查（HEALTHCHECK）是告诉容器运行时"如何判断我是否还健康"的机制，状态有三种：starting 表示还在启动中（这个阶段失败不算失败）、healthy 表示通过检查、unhealthy 表示检查连续失败。两个关键细节：第一，unhealthy 不会让容器自动重启。它只是把事实记录下来，供你、供 Compose、供编排系统决策。很多人第一次用健康检查时最困惑的正是这里——他们以为配了它容器坏了就会自己重启。要它自己重启，你需要的是重启策略或编排系统针对健康状态的策略。第二，健康检查判断的是"这个进程还活着并且在正常工作吗"，不是"整个系统是好的吗"。如果你的应用依赖的数据库挂了，应用本身可能仍然健康（它还在监听端口、还能返回错误页面），把它标成不健康并不会修复数据库，只会让编排系统去重启一个没坏的东西。由此得到一条设计准则：健康检查应该检查"这个实例自己能不能提供服务"，而不是"它依赖的东西是否都好"。重启能解决的是进程内部状态损坏、连接池卡死这类问题；解决不了的是配置错误和依赖宕机。

展开：出问题时你最想知道哪三个问题

把所有可观测性需求压缩成三个问题，然后让每个问题都有一个能被查询的答案。

  1. 坏了没有？这是"症状"层的问题，需要一个反映用户体验的指标：成功率、延迟的分位数（比如第 95 百分位）、队列积压长度。它应该能在用户大规模投诉前就报警。
  2. 影响了谁、影响了多少？这是"范围"层的问题，需要能按维度切分的指标：哪些接口、哪些租户、哪些版本、哪些地区。它决定了你是立刻回滚还是可以慢慢查。第 04 节那套标签规范在这里会救你一命——如果指标里带了镜像版本这个维度，你能在三秒内回答"是不是这次发布引起的"。
  3. 从什么时候开始的？这是"时间"层的问题，需要指标的时间序列与变更记录对齐。它把"最近有没有改过什么"变成一次可查证的比对，而不是一场会议。

请把这三个问题抄下来，贴在你设计监控时能看见的地方。它们也解释了为什么"部署记录"属于可观测性的一部分——不知道自己什么时候变了什么，第三个问题就永远答不上来。

思 考
  1. 把日志写进文件，和打到标准输出，在排障时的体验差别到底在哪里？请举出一个"写文件反而更方便"的具体场景，并说明为什么它不能推翻这个纪律。 提示：想想在没有集中日志系统的环境里，一个还活着的容器能提供什么。
  2. 如果你的服务每秒产生一万条日志，你会全部保留、采样保留，还是只保留错误？请给出判断依据，并说出你的选择会让哪一类问题变得难以排查。 提示：想想"日志是证据"和"日志是成本"之间的紧张关系。

发布与回滚：把最危险的十分钟变成例行公事

发布是整套流水线里唯一直接面对用户的动作，也是风险最集中的十分钟。三种主流策略解决的是同一个问题——如何在不中断服务的前提下把新版本交给用户，区别在于它们付出的代价和能容忍的故障类型不同。

策略直觉解释资源代价回滚难度适合什么
蓝绿发布准备一整套新环境（绿），验证通过后把流量一次切过去；旧的整套留着（蓝）最高，需要两倍的实例与相应的数据库兼容性最低，切回流量即可，秒级对回滚速度要求极高、资源不紧张的关键服务
滚动发布一批一批地替换实例，替换完一批健康后再换下一批最低，几乎是原地替换需要再滚一轮回去，耗时且期间新旧版本共存实例多、能容忍短暂新旧混跑的普通服务
灰度发布先让一小部分流量（比如百分之五）走新版本，观察指标再逐步放量中等，需要流量切分能力中等，把那一小部分流量切回去，影响面已被限制变更风险高、希望用真实流量验证的服务

三种策略其实是三个不同位置的取舍点。蓝绿买的是"回滚快"，代价是钱；滚动买的是"省资源"，代价是回滚慢和过程复杂；灰度买的是"风险可控"，代价是需要流量切分能力和更长的观察时间。没有一个选项是无脑正确的，选哪个取决于你最怕什么。灰度还有一个常被忽略的条件：新版本必须能与旧版本同时处理数据。如果新版本改了数据库结构而旧版本还在读那张表，灰度期间的"新旧混跑"就会变成灾难。这引出一条通用规则：发布策略的可行性，最终由数据兼容性决定，而不是由部署工具决定。

思 考
  1. 蓝绿与滚动，哪一个更容易回滚？哪一个更贵？如果只能选一个用在你的课程设计上，你选哪个，为什么？ 提示：先把"回滚需要几步"和"多花多少钱"分别写下来，再比较。
  2. 为什么"回滚"在容器时代变得简单了？请指出这个"简单"成立的前提条件，并举出一个它并不简单的场景。 提示：想想数据库里那些已经被新版本改过的数据。

一次可回滚发布的完整动作序列

下面这套动作是第四节标签规范与本节发布策略的结合，目标是"任何一个步骤出错，都能在五分钟内退回到一个已知可用的状态"。请在本地用一个最小的服务把整条序列走一遍，包括最后那次故意回滚。

docker build -t myapp:1.0.0 -t myapp:sha-aaa1111 .
docker run -d --name myapp-v1 -p 8080:8000 myapp:1.0.0
docker build -t myapp:1.1.0 -t myapp:sha-bbb2222 .
docker run -d --name myapp-v2 -p 8081:8000 myapp:1.1.0
docker logs --since 2m myapp-v2

前四步搭出了一个"蓝绿"的最小形态：v1 在 8080 上服务，v2 在 8081 上待命，两者可以同时访问、互不干扰。第五步是验证动作——没有验证的切换不叫发布，叫冒险。验证要看三件事：服务能不能连上、日志里有没有报错、关键接口的返回是否符合预期。在本地你可以用浏览器打开两个端口对比，真实环境里这一步应该尽量自动化。

docker stop myapp-v1
docker rm myapp-v1
docker run -d --name myapp-v1 -p 8080:8000 myapp:1.1.0

验证通过之后，"切流量"在单机环境里通常表现为把反向代理的指向改掉，或者把宿主机端口让给新版本；无法做零切换时，退而求其次的动作就是这里写的：停掉旧容器，用同样的名字和端口起新的。注意"复用同一个容器名和端口"的技巧——对使用者来说地址没有变，只有背后的镜像换了。这个动作会有几秒不可用窗口，所以它不是蓝绿，而是"停走式更新"：优点是简单到不可能做错，缺点是那几秒真实存在。

docker stop myapp-v1
docker rm myapp-v1
docker run -d --name myapp-v1 -p 8080:8000 myapp:1.0.0
docker image inspect myapp:1.0.0 --format "{{.Id}}"

假设指标显示新版本有问题，回滚的全部内容就是"用旧镜像再起一次"。旧镜像还在本地（不在就从仓库按标签或按摘要拉回来），旧配置还在环境变量里，旧代码还在 Git 历史里。这就是不可变交付物给你买来的东西：你不需要撤销任何操作，你只需要重新启动一个你已经有的东西。最后那条 inspect 是让你把回滚后的镜像 ID 记进记录里——一次没有记录的回滚，等于给下一次发布埋了一个新谜题。

请解释为什么这次回滚如此轻松，前提条件是什么？追问一个变体：如果 1.1.0 已经执行过一次数据库结构变更，回滚到 1.0.0 之后它会怎样？想透这个问题，你就理解了为什么很多团队把"数据库变更与代码发布解耦"列为硬规定——通常做法是让变更保持向后兼容，先让两边都能读，等新版本稳定之后再清理旧结构。

为什么"发布记录"是一项技术设施

回滚要快，前提是你能在三秒内回答"上一个好版本是哪个"。这句话听起来像文档问题，实际上是技术问题：它要求发布动作产生一条机器可读的记录，最小可行的记录至少包含四个字段——时间、镜像摘要、配置的版本、执行人或触发这次发布的提交。这条记录的价值在故障时会被放大：有它，你可以在事故会议上说"十点零七分我们把摘要为某个值的镜像切上了生产，十点十二分指标开始异常"，然后所有人一起讨论技术问题；没它，会议会先花二十分钟争论"到底改没改"。

易 错 点

三个发布环节上的典型错误。第一个是只回滚代码不回滚配置：新版本带来了一组新的环境变量，回滚时只换了镜像，旧代码读到了它不认识的变量而行为异常。第二个是回滚之后没有重新验证：以为切回去就完事了，实际上旧版本也可能因为数据变化而失效。第三个是把回滚当成最后手段而不是常规操作：如果一次回滚要被追问"你怎么搞的"，团队就会倾向于硬撑着往前修，而往前修往往比回滚风险更大。健康的团队文化里，回滚是一次普通的操作，不是一次认错。

前 瞻

第 12 章你会看到编排系统如何把本节这一串手工命令压缩成一份声明：你写"期望三个副本、逐批替换、最多一个不可用、镜像换成某个版本"，系统负责执行、等待健康检查、在失败时停下。当编排系统告诉你"滚动更新卡住了"，你能立刻想到它在等的是健康检查。自动化不会替你理解问题，它只是替你把已经理解的事情重复做一万遍。

团队协作的固定动作：把素养变成清单

最后一节讲的东西最不技术，却最容易决定你在团队里的口碑。前面八节讲"系统应该怎么设计"，这一节讲"人应该养成什么习惯"。之所以要把习惯写成清单，是因为素养在没人提醒时会悄悄退化，而清单让正确的事情不依赖记忆与自觉。

一页纸的工程素养清单

一、Dockerfile 要评审。它不是"配置"，它和代码一样决定系统行为：基础镜像决定攻击面，USER 决定权限，CMD 决定停机是否优雅。评审时最该看四件事：基础镜像是否锁了版本、依赖安装是否在源码复制之前、是否以非 root 用户运行、有没有把秘密写进 ENV。

二、.dockerignore 必写。它同时解决三件事：构建速度（少发送几百 MB）、镜像体积（不把 node_modules 和日志带进去）、安全（不把 .env 与 .git 带进去）。第 05 章讲过构建上下文是整包发送的，所以它不是优化项，而是必需品。

三、镜像标签不得用 latest。完整版本是：部署清单里不得出现 latest，所有发布必须能回答"具体是哪个版本"。第四节那套多标签策略就是它的落地方式。团队里通常把它做成自动检查——流水线发现部署配置里出现 latest 就直接判定失败，而不是靠人眼在评审时发现。

四、密钥不进仓库。第 09 章与本章都反复强调。补一条可执行的检查：提交前运行一次 git status，确认 .env 不在待提交列表里；更进一步是配一个提交前的钩子自动拒绝可疑文件名。自动化的检查胜过善意的提醒，因为善意在赶时间的周五晚上会失效。

五、README 写清如何一条命令起环境。合格的版本包含三件事：前置条件（需要装什么、什么版本）、复制 .env.example 到 .env 并填哪些值、以及那条唯一的启动命令。如果起环境需要六步且每步都有"注意别忘了"，那不是新人笨，是文档不合格。

六、任何一次变更都能被回滚。这要求发布时记录镜像摘要与配置版本，也要求数据库变更保持向后兼容。它是本章所有纪律里唯一一条"平时看不出价值、出事时决定生死"的。

七、日志里不许出现秘密。调试时打印完整连接串、把整个请求体记下来、把令牌写进日志字段，这三件事都极其常见，也极其危险——日志往往存在权限更宽松的地方、副本更多、保留时间更长。判断标准很简单：假设这段日志会被贴在公开的 issue 里，你还敢不敢写？

八、基础镜像与依赖的升级要有节奏。不升级意味着漏洞越积越多，随时升级意味着某次构建会突然失败。可行的做法是定期（比如每月）主动升级一次并跑完整测试，而不是等漏洞报告来了才被动处理。

比 喻

这份清单像飞机起飞前的那张检查单。飞行员的技术远比清单复杂，但他们依然逐项打勾，因为人的记性在压力下不可靠，而清单不会累、不会慌、也不会因为"今天赶时间"而跳过一项。

回到技术本体：清单的价值完全取决于它是否被无例外地执行。一个可以随手跳过的检查单等于没有检查单，一个只在事故之后才被想起来的规范等于没有规范。所以真正要设计的不是清单本身，而是它的执行方式——哪些条目由流水线自动检查、哪些需要评审时明确提问、哪些需要定期复盘。把清单变成机制，是这一整章反复出现的同一个动作。

新人第一天：一个非常诚实的检验标准

如果只能保留一个指标来衡量团队的工程化水平，我建议用这个：一个从没接触过这个项目的人，从拿到仓库地址到能跑起完整环境并验证它工作，需要多长时间？这个指标好用，是因为它同时压力测试了本章几乎全部内容：需要 README 里清楚的步骤，需要一条命令能起环境，需要依赖能被装好，需要知道要填哪些变量，需要在出问题时能看到线索。这条路上任何一处含糊，都会在第一天暴露。反过来，如果你正在维护别人写的项目，把这件事当成一次演练：找一个同学照着 README 从头做一遍，你只在旁边记录他卡在哪里，不要出声提示。你会得到一份比任何代码评审都诚实的改进清单。每一个"他就卡在这里"的时刻，都是你的项目在向你索要一个机制。

第四到第六个实验，交给你自己

实验四：写一份自己的 CI 工作流。把第 06 节那份 YAML 复制到你自己的仓库，把镜像路径改成你自己的，把测试步骤改成项目的真实测试命令。不必真的推送到远端，但要做到两件事：逐行解释每一段在做什么，以及指出哪一行是你认为最可能出错的一行。愿意更进一步的话，提交上去跑一次，打开运行日志看构建缓存那一步打印了什么。

实验五：从日志定位一个问题。设计一个不会被报错直接指出的故障——例如把某个超时参数改得极小，让它在压力下偶尔失败，然后只用日志去定位它。记录你实际执行过的每一条命令，以及每次缩小范围的理由。做完之后你对"日志该记什么"会有完全不同的直觉，因为你自己就是那个查询者。

实验六：完整演练一次回滚。按第 08 节的序列做一遍，再给自己加两条约束：回滚全过程必须在五分钟内完成；回滚之后必须能说出你回滚到了哪个摘要。做完回答一个问题：如果生产是四台机器上的八个副本，这套动作会发生什么变化？这个问题的答案就是下一章之后的内容。

回 望

第 09 章讲安全时留下的最后一个印象是"纪律比工具重要"。本节把这句话推进了一步：纪律要长期活下去，就必须变成机制——变成流水线里的一条检查、评审清单里的一个问题、README 里的一行命令。第 09 章的密钥管理、非 root 运行、漏洞扫描这三件事，在本章的流水线里各自找到了固定位置：密钥走运行时注入，非 root 由 Dockerfile 评审把关，扫描卡在推送之前。

    docker build -t web:2.0.0 -t web:2 -t web:sha-abc1234 .
    参考答案

    三个标签，指向同一个镜像内容（同一个镜像 ID，也就是同一份内容摘要）。关键在于三条 -t 属于同一次构建，所以只有一个产物，三个名字都是它的引用。如果分三次构建再分别打标签，则可能得到三个内容不同的镜像。这一点在排查"为什么两个标签的大小不一样"这类怪事时很有用。

  3. docker image inspect 某标签时 RepoDigests 输出为空。请说出至少两种可能的原因。
    参考答案

    原因一：这个镜像其实没有推送成功，或推送到了另一个仓库名，本地记录里不含它。原因二：你查询的标签对应的是本地构建、从未与任何仓库交互过的镜像，没有仓库摘要可谈。原因三：本地存在同名但不同来源的镜像，RepoDigests 只记录与仓库有关联的那些。要点：区分"本地名字"与"仓库摘要"两个层次。

  4. 为什么 docker compose run --rm migrate 比把迁移写进服务启动命令更合适？请从"副本数量"和"失败后果"两个角度回答。
    参考答案

    副本角度：常驻服务可能有多个副本同时启动，启动脚本里的迁移会被并发执行多次，可能互相破坏；一次性任务只有一个实例，跑完即退出。失败后果角度：启动脚本里的迁移失败会让容器陷入重启循环，问题被放大成"服务起不来"；一次性任务失败就是一条命令返回非零，可以停下来看日志、修好再跑。补充：一次性任务能写进流水线、被评审、被重放。

  5. 判断对错并说明理由："既然 unhealthy 不会让容器重启，那 HEALTHCHECK 在生产环境里没什么用。"
    参考答案

    错。unhealthy 本身不触发重启，但它是被你、被 Compose、被编排系统读取的事实：可以阻止有问题的实例接收流量（编排系统把它从服务端点摘掉），可以让依赖它的服务等待就绪，也可以作为告警来源。真正没用的是"配了健康检查却没有任何人或系统读它"。评分要点：能说出 unhealthy 的消费者是谁。

  6. 你的流水线每次在装依赖上花掉十几分钟。请写出三种改法，按改动成本从低到高排序，并说明每种改法的代价。
    参考答案

    一、启用构建缓存导入导出（cache-from 与 cache-to），成本最低，代价是缓存存储与传输开销。二、检查 Dockerfile 层顺序，确认依赖清单早于源码被复制，成本很低而收益最大。三、精简依赖（去掉只在开发时用的包、把编译工具链放进多阶段构建的早期阶段），成本中等，需改动项目本身。可选四：把依赖预装进内部基础镜像，成本与维护责任都最高。

  7. 请预测这条命令的输出与随后 docker compose ps 的结果，并解释原因。 
    docker compose up -d db
docker compose run --rm migrate
docker compose ps
    参考答案

    第一条只启动数据库并放到后台；第二条先等数据库通过健康检查，再执行迁移、打印结果后退出，并因 --rm 立即删除容器；第三条只列出 db——migrate 是一次性任务，不属于"当前正在运行的服务"这个集合。如果输出里出现了 migrate，最常见的原因是漏写了 --rm，或误用了 up 而不是 run。

  8. 一个服务过去一小时里错误率从百分之零点一涨到百分之三。你手上有日志、指标和链路追踪。请写出排查顺序，并说明每一步在找什么。
    参考答案

    先看指标的时间序列，确定异常开始的确切时刻以及它是否与某次发布、配置变更或依赖故障对齐（回答"从什么时候开始"）。再按维度切分指标（接口、租户、可用区、镜像版本），确定影响范围（回答"影响了谁、影响多少"）。然后在日志里按那个时间窗口与维度过滤，找到具体错误信息与堆栈（回答"是什么"）。若错误跨越多个服务，用链路追踪定位是哪一段变慢或失败。评分要点：先缩小范围再深入细节。

  9. 请指出下面这段部署配置的问题，并给出修改方案。 
    steps:
  - name: 部署
    run: docker run -d --name app -p 80:8000 myapp:latest
    参考答案

    主要问题是用了 latest：不可审计、不可回滚，也无法回答"线上跑的是哪一版"。改成具体的语义化版本或提交号标签，并在发布记录里同时写入镜像摘要。可补充的次要问题：没有重启策略；固定容器名会让重复部署因名字冲突而失败（需要先删旧容器或改用不同名字）；部署前缺少验证与失败时的回滚路径。

  10. 有人说："我们的 .env 里没有秘密，只有开关和地址，提交进 Git 也没关系。"请给出你的回应，并说出他可能没想到的一个后果。
    参考答案

    今天没有秘密不代表明天没有：文件一旦提交，历史便永久保留在仓库副本里，将来任何人往里加口令都会被连带暴露，而且删文件删不掉历史。他可能没想到的后果：内网地址与账号结构本身属于信息泄漏；这份文件常成为"从测试复制到生产"的模板，一次手滑就把测试口令带进生产；团队里后来的人会认为这个文件可以提交，规范被稀释。正确做法是 .env 进 .gitignore，另立 .env.example。

  11. 请解释为什么"把 Git 提交号写进 Dockerfile 的 ENV"会伤害构建缓存，并给出两种替代方案。
    参考答案

    ENV 的值是那一层输入的一部分：每次提交号变化，这一层及其之后的所有层都被判定需要重建，写在它后面的依赖安装、源码复制都会重跑。替代一：用构建参数（ARG）在构建时注入，并放在尽可能靠后的位置。替代二：完全不在构建期注入，改由运行时环境变量或启动脚本从外部读入并在启动日志里打印。评分要点：能说出"层输入变化导致后续全部重建"的机制。

  12. 你要给一个每天只更新一次、但一旦出错会影响很多用户的服务选发布策略。三者怎么选？说明判断依据，以及你放弃了什么。
    参考答案

    没有唯一答案，评分看推理。若"出错影响大"是首要约束，倾向灰度：先用少量真实流量验证，影响面被限制，回滚只需把那部分流量切回去，放弃的是"上线即全量"的确定性与更短的窗口。若"回滚必须几乎瞬时"是首要约束，倾向蓝绿：整套新环境就绪后切换，回滚就是切回来，放弃的是资源效率与成本。滚动通常被排除在首选之外，因为新旧混跑期间问题直接影响全部用户，且回滚要再滚一轮。

  13. 请设计一个检查动作，用来验证"你的项目真的做到了一条命令起环境"，并说明它为什么比读 README 更可靠。
    参考答案

    把仓库克隆到一个全新目录（或让不了解项目的同学来做），执行前删除本地遗留的 .env、卷与镜像，然后严格按 README 执行，全程不做 README 没写的动作，记录卡住的每一处。它更可靠，是因为读文档时你会自动脑补省略的步骤——"这里当然要先装个包""这个变量当然要填"——而真正执行的人不会脑补。评分要点：强调"全新环境""不做文档外的动作""记录卡点"。产物是一份按痛感排序的改进清单。

本章总结

  • 手工执行的边界不在于做得对不对，而在于它只保证这一次：它不可重复、不可审计、不可回滚、不可协作，而这四件事正是软件长期存活的条件。
  • 工程化有四道递进的门槛：可重复由 Dockerfile 负责，可审计靠标签与构建记录，可回滚靠不可变交付物，可协作靠一条命令起环境与清晰的文档。
  • 十二要素应用是一份比 Docker 更早出现、却为容器量身定做的自查清单；十二条里只有少数几条由 Docker 自动满足，其余都要你亲手做出来。
  • 构建与运行分离是整套体系的地基：构建集中所有不确定性，运行阶段只使用一个不可变的产物，不允许编译、安装、改文件、联网下载。
  • 配置存于环境是"同一镜像、不同注入"的实现方式，代价是服务的完整说明被拆散了，需要用 .env.example 与 docker compose config 把它重新拼回来。
  • 管理任务应该作为一次性进程运行：docker compose run --rm 让迁移这类动作可重复、可评审、可重放，塞进启动脚本则会在多副本时变成灾难。
  • 构建一次，处处运行，指的是同一个摘要被搬运到每个环境；生产环境重新构建会让"测试过的就是上线的"这句话失效。
  • 标签是可变指针，latest 服务探索而不服务交付；可落地的策略是一次构建打上语义化版本、次版本浮动与提交号三个标签，让它们指向同一个摘要。
  • CI/CD 的本质是把动作从人的记忆搬进仓库；工作流里最贵的是构建缓存，因为托管 runner 每次都是全新的，缓存不会自己活下来。
  • 可观测性三支柱各回答一个问题：指标告诉你有没有坏、日志告诉你坏在哪、链路告诉你慢在哪一段；出问题时你最想知道的三个问题是"坏了没有""影响了谁""从什么时候开始"。
  • 健康检查只记录事实，不会自动重启；unhealthy 的价值在于它被谁读取，而不是它本身能做什么。
  • 蓝绿买回滚速度，滚动买资源效率，灰度买风险可控；无论选哪一种，回滚能不能成功最终由数据兼容性决定。
  • 这一章最重要的一个判断是：工程化的检验标准不是工具，而是最坏情况下的动作成本——出问题时你能不能在三秒内说清线上跑的是哪个版本，以及能不能在五分钟内退回到上一个已知可用的版本。

读到这里，你手里多了一件前面九章都没给过你的东西：一种把"我会做"翻译成"别人也能重复做"的能力。容器让你把应用装进木箱，工程化让你在木箱上刻下编号、写下清单、留下返航的航线。海面看起来平静了，而真正的远航才刚开始——下一章你会遇到一群脾气大得多的乘客：模型、数据、显卡。你已经准备好的这套流水线思想，会是驯服它们最重要的工具。
