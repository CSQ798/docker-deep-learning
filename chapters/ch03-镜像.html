镜像：代码如何凝结成一块可搬运的化石

层是 Docker 世界里最美的抽象

本 章 学 习 目 标
  • 能说清镜像是"若干只读层 + 一份配置 + 一份清单"的组合，而不是装在硬盘上的一个大文件。
  • 能解释内容寻址带来的三个真实好处：跨镜像去重、可校验完整性、可被精确到字节地指定。
  • 能解释层为什么不可变、为什么"删掉文件的层"不会让镜像变小，以及白障在文件系统里做了什么。
  • 能讲出写时复制的懒惰策略，并指出它最贵的那个场景。
  • 能完整拆解一个镜像名字的每一段，说清默认值从哪里来、标签与摘要各自的可信度边界在哪。
  • 理解 latest 为什么危险，以及"去掉标签"为什么会带来另一种失控。
  • 能从磁盘占用角度解释"镜像大小"与"实际占用"为什么不是一回事。
学 完 之 后 ， 你 应 该 能 够
  • 读懂 docker image inspect 的 JSON，指出 Architecture、Config.Cmd、RootFS.Layers、GraphDriver 各在说什么。
  • 读懂 docker image history，把每一层对应回某条构建指令，判断哪些层可以合并掉。
  • 判断两个镜像是否共享底层，并用一条命令给出可验证的证据。
  • 解释 docker pull 输出里 Pull complete、Already exists、Verified Checksum、Digest 各自的含义。
  • 诊断镜像磁盘异常：是悬空镜像、中间层、构建缓存，还是数据卷。
  • 为真实小项目设计可复用、可追溯的镜像命名规范，并写成别人能照做的规则。
  • 从一个空目录出发，独立完成写 Dockerfile、构建、打标签、运行验证、推送的全流程。

第 02 章我们把 Docker 拆成七个部件，还跟着一条 docker run 走完它在几百毫秒里经过的每一站。那一趟旅程里有个环节我故意讲得很快：containerd 从镜像仓库把"层"拉下来、解包、叠成根文件系统。当时我说"层留到下一章"。现在就是下一章。镜像这个词让人困惑，是因为它同时指了三样东西：一堆只读层的组合、一份描述怎么启动的配置、一份由内容算出来的清单。这三样东西遵守同一条原则——内容决定身份。这条原则一旦被你想通，一大堆看似无关的现象会突然连成一条线。为什么两个容器共享一个镜像却互不污染，为什么你删掉一个大文件镜像反而没变小，为什么改一行代码会让后面所有层全部重建，为什么生产环境宁可用一串看不懂的 sha256 也不用 latest——它们都是同一条原则的回声。

镜 像 是 化 石

镜像的四个反直觉现象，与它真正的结构

我不想先给你定义。定义是别人嚼过的东西，你记住它、但不会相信它。我们先把手指放到键盘上，让 Docker 用输出反驳你的直觉。确认 Docker Desktop 已启动、左下角显示绿色，然后打开 PowerShell。

docker pull alpine
docker images

表头是 REPOSITORY、TAG、IMAGE ID、CREATED、SIZE；如果它整张是空的，那不是出错，是"你还没有任何本地镜像"。拉取之后表里出现了 alpine、latest、一个 12 位十六进制的 IMAGE ID、时间，以及八兆上下的 SIZE。Windows 上 Docker Desktop 显示的数字可能与 Linux 略有差异（存储驱动与文件系统块分配的处理不同），我们后面专门讲这个差异。先记住量级：八兆左右——一个能跑 shell、有包管理器、有基础命令集的 Linux 环境，大小相当于两张手机照片。

docker tag alpine kaoyan-alpine:test
docker images

第二条命令没有输出，第三条之后你会看到两行：alpine:latest 与 kaoyan-alpine:test，而它们的 IMAGE ID 完全相同。你没有复制任何数据，却多出了一个"镜像"。这两行到底是什么关系？

docker image inspect alpine --format "{{.RootFS.Layers}}"

你会看到一串用方括号括起来的 sha256:... 摘要，中间用空格隔开。模板整体要用双引号包住，PowerShell 才会把它当成一个参数传给 docker。如果花括号让它犯难，也可以去掉 --format 直接看完整 JSON，自己找 RootFS 这一段。

四个现象摆在一起，它们各自都在反驳一个想当然。

你看到的现象它反驳的直觉它暗示的真相
alpine 只有八兆左右"操作系统环境至少几百兆起步"镜像里不含内核，只有一个精简的用户态文件系统
两个名字的 IMAGE ID 相同"打标签会复制一份镜像"标签只是指向已有内容的指针，不占额外空间
RootFS.Layers 是一串摘要，不是路径"镜像对应硬盘上的某个大文件"镜像由多个层组成，每层有自己的内容指纹
docker image history 里有 0B 的行"有变化就一定有体积"0B 有两种成因：只改了配置，或这一层没有携带文件内容

有一个问题你此刻还回答不出来，请先存在脑子里，读到后面我们回来收账：如果每一层都有内容指纹，那么"用同一份 Dockerfile 构建两次，会得到同一个镜像吗"？把内容寻址想透之后，你会知道答案比"是"或"不是"都更微妙。

它其实是三样东西：层、配置、清单

你先在脑子里扔掉一个画面：镜像是硬盘某个角落里一个叫 nginx.img 的大文件，拷贝它就能搬走一整个环境。这个画面非常符合直觉，也非常错误。我们把它导出成普通文件，再拆开看。

docker save alpine -o alpine.tar
tar -tf alpine.tar

docker save 把镜像导出成普通 tar 归档，任何解压工具都能打开（Windows 10 以后自带 tar，可以直接用）。你会看到三类东西：若干以 .tar 结尾的层归档；一个 index.json 之类的清单；以及一串没有扩展名、名字本身就是 sha256 摘要的文件，那是配置与清单本体。一个"镜像文件"里装的是这些小文件，不是一整块文件系统。这个区别听着琐碎，却是理解后面一切的钥匙。

层是一份文件系统变更集。构建时每执行一条会改动文件系统的指令，引擎就把"这一条相对于上一条，新增了什么、改了什么、删了什么"打包成一个 tar 归档。层记录的是差分而不是快照，不会把整个根目录再存一遍。这带来两个后果：一是体积上的优雅——在一个八兆的 alpine 之上装一兆的小工具，第二层只有一兆量级；二是层无法独立存在，它里面只有 /usr/bin/mytool，而它依赖的库在下面几层里。所以层的列表是有序的，你动了下面某一层，上面所有层都会失配。

配置是一份 JSON：给哪种架构与操作系统用、默认执行什么命令、预设了哪些环境变量、声明了哪些端口、以什么用户运行，以及最关键的一项——它引用了哪几个层的摘要、按什么顺序。配置是镜像的"人格"。同一堆层，配置不同就是两个不同的镜像；反过来，两个镜像可以共享全部层，却因为差了一个环境变量而各自拥有不同的摘要。

docker image inspect alpine --format "{{.Architecture}} {{.Os}}"

输出类似 amd64 linux。这两个字段决定这个镜像能不能在你的机器上跑，也解释了"为什么 M 系列芯片的 Mac 上拉某些镜像会拉到另一个版本"。模板里的字段名大小写敏感，写成 architecture 会得到空值——不是命令坏了，是你问了一个不存在的字段。

清单的角色是索引：把"这个镜像是谁"与"它的部件分别是哪些"连起来。你会在两处遇到它。一处是 docker pull 最后那行 Digest；另一处是当你请求一个多架构镜像时，Docker 先取回一个清单列表，里面写着"如果你是 amd64 就取这一份、如果你是 arm64 就取那一份"，再去取真正需要的那一份。这也解释了一个常见疑问：为什么 pull 输出的 Digest 和 inspect 出来的某个层摘要不一样？因为它们本就是两个层级的东西——清单摘要是整份文件的指纹，层摘要是其中一块的指纹。

比 喻

你可以把镜像想成一只被拆开运输的集装箱：层是一块块标准化的箱体，配置是贴在箱门上的作业单（装着什么、到港后怎么启动、给谁用），清单是那张运单（这一票共几个箱体、编号依次是多少）。港口不需要认识你，只需按编号核对箱体有没有被掉包；整只集装箱可以被重新拼装，而每一块箱体也可能同时属于另外几只集装箱。

比喻到这里收回技术上：这只集装箱并没有一个"总重量"，因为箱体是共享的。运单上的重量是箱体之和，码头上实际堆放的箱体可能远少于这个数——这不是记账错误，而是共享的必然结果。

回 望

第 02 章我们跟着一条 docker run 走过：docker CLI 把请求发给 dockerd，dockerd 让 containerd 去准备镜像，containerd 发现本地没有就去找镜像仓库，把各层下载、解包，用存储驱动叠成根文件系统，再把配置交给 runc 去真正启动进程。当时那句"镜像拉取时下载的是层"现在可以拆得更精确：containerd 下载的不是一个文件，而是一组各自带摘要的层，加上一份写明这些层按什么顺序叠、叠完之后用什么命令启动的配置。

易 错 点

最常见的两个误解，都是把镜像等同于"硬盘上的一个文件"。第一个是以为 docker tag 会复制镜像，于是为了"备份"拼命打标签，最后发现磁盘一个字节没省。第二个是以为删掉镜像就等于删掉所有数据，于是不敢删——其实 docker rmi 删的是"这个名字对内容的引用"，只有引用归零、且没有别的镜像依赖那些层时，层才会被回收。判断一个操作动了什么，永远先问：它删的是引用，还是内容？

内容寻址：名字由内容算出来，而不是由人写上去

现在进入本章的地基。如果你只带走这一章的一个观念，请带走它：在镜像世界里，身份不是被授予的，而是被计算出来的。一个层的名字是它全部内容的哈希值，一个镜像的身份最终也落在内容上。没有人有权给它起名，也没有人能冒充它。

哈希函数是一台单向榨汁机：你喂给它任意长度的字节，它吐出固定长度的一串字符（SHA-256 是 64 个十六进制字符）。同一输入永远得到同一输出；输入改一个 bit，输出就面目全非；想从输出倒推输入，在计算上不可行。它在工程上特别有用的三件事是：校验完整性、去重、命名。镜像系统把这三件事全都用上了。

内容寻址的性质它带来的能力它能解释的现象
相同内容必然得到相同摘要跨镜像、跨项目、跨机器去重十个基于 alpine 的镜像只占一份 alpine 层
内容变一个字节，摘要完全不同可验证完整性，传输损坏会被发现拉取时出现校验和错误，Docker 重试而不是将就
摘要无法被伪造或反向构造可精确定位到一份确切内容用 digest 拉取时，拿到的不可能是别的东西
摘要是内容的后验事实，不是先验约定无需中心机构分配编号任何人都能在私有仓库造镜像，摘要规则全球一致

把这几条串起来，得到一个很强的结论：标签是可变的指针，摘要是不可变的内容身份。你今天打上 app:1.0 的东西，明天可能被另一次构建覆盖成完全不同的内容，标签本身不会报警；但如果你记下的是 sha256:某串字符，那么任何地方、任何时间，它对应的都是同一份字节。前者是人类方便的别名，后者是机器可信的坐标。

再往前一步，会遇到一个乍看违反直觉的推论：既然每层都由内容算出摘要，那么同一个层天然可以被任意多个镜像引用，而每个镜像自己的摘要由配置内容决定——配置里记录了层的摘要列表。这意味着两个镜像可以共享全部相同的层却拥有不同的镜像摘要；反过来，两个镜像摘要相同，则它们的每个字节都相同。

现在回答前面存下的那个问题。用同一份 Dockerfile 构建两次，会得到同一个镜像吗？如果两次构建中所有输入完全相同——同样的基础镜像摘要、同样的文件内容、同样的指令、同样的构建参数、同样的目标架构——那么层摘要会一致，最终镜像摘要也一致，答案是"会"。只要有任何一样东西变了，答案就变成"不会"。哪些东西会变？文件内容当然算，还包括：基础镜像在你上次构建之后被上游更新了（你用 latest 的时候）；你复制进去的源码里有一个被自动生成的时间戳文件；构建时执行了一条访问网络、把当前时间写进产物的命令。最阴险的是那些看不见的输入——它们不写在 Dockerfile 里，却实实在在地改变着层的字节。

这就是可复现性的真正难点：可复现不是"我把命令记下来了"，而是"我能指出全部输入，并让它们一个都不变"。

思 考
  1. 如果层的身份完全由内容决定，那么"我的镜像里包含了一份被删掉的密钥"这件事，严重性到底在哪里？docker image history 能看到它吗？docker image inspect 能看到吗？如果都看不到，别人怎么才能发现？提示：想想"删掉"这个动作在层里是怎么被记录的，再想想层本身是不是一份完整的文件包。
  2. 假设你负责一个每天构建上百次镜像的团队。"同一份 Dockerfile 构建两次得到同一个镜像"这个性质，对团队来说是锦上添花，还是业务刚需？如果它不成立，最先出问题的环节是哪一个？提示：可以从"出了问题该回滚到哪一份"这个角度想。
  3. 内容寻址让相同内容自动去重。它会不会带来隐私问题？如果两家竞争公司在同一个仓库里推镜像，会发生什么，这算不算信息泄漏？
  4. 哈希函数总有一天可能被攻破（历史上 MD5、SHA-1 都倒下了）。如果镜像系统使用的哈希被证明可以构造碰撞，这个体系哪一部分会先崩塌——去重、校验，还是"用 digest 定位"本身？
方 法

面对一个抽象的机制，不要一开始就去读规范。先去找"一个能被你亲手观察到的现象"，然后倒推机制。这一节走的就是这条路：先看到 IMAGE ID 相同、看到 RootFS.Layers 是一串摘要，再去问"为什么同一份内容会有同一个名字"。这个顺序比先背定义有效得多，因为机制只有在解释现象时才被真正记住。以后再遇到类似概念（Git 的提交哈希、Kubernetes 的资源版本号），都可以用同一个套路：找一个可观察的输出 → 提出假设 → 设计一个能反驳假设的实验 → 回文档确认。

写时复制与 OverlayFS：容器里的文件系统是怎么长出来的

层是只读的。只读的东西怎么变成能跑、能写、能删文件的容器？答案是给这摞只读层顶上盖一层薄薄的可写层，再让操作系统用一个"看起来只有一份"的目录把它们合成起来。这个合成工作由联合文件系统（UnionFS，把多个目录叠加成统一视图的文件系统能力）负责，Linux 上最常用的实现叫 OverlayFS，Docker 默认的存储驱动 overlay2 就基于它。

叠加的规则很朴素。OverlayFS 把若干目录按优先级排成一列：下面的都叫下层，最上面可写的那层叫上层，合成之后暴露给你的那个目录叫合并视图。读取时自上而下找，上面找到了就不看下面；写入时永远写进上层。容器启动的那一刻，Docker 为它准备一个空的上层目录，镜像的所有层作为下层挂进去。

关键在写入。假设容器要修改 /etc/hosts，而它来自镜像的倒数第二层（只读）。系统不能直接改，因为那一层可能同时被另外九个容器共享着——改了就等于改了别人。于是采用写时复制（Copy-on-Write，CoW）：先把这个文件完整复制一份到可写层，再在副本上修改，原来那一份纹丝不动。

读文件自上而下找、写文件复制到上层再改、删文件用标记遮蔽下层——这三句话就是本节的骨架。前两句好懂，第三句是下一节的主角。现在先讲代价。写时复制是一种懒惰策略：先共享，要改才复制。它把成本从"总是付出"推迟到"真的需要时才付出"，极其划算。但代价分几个层次。

第一层是单次写放大：要修改一个 500 MB 文件里的一行，第一次写会触发完整的 500 MB 拷贝，你只改了 1 KB，却付出了 500 MB 的 IO 与空间；改完之后第二次、第三次写就便宜了。第二层是空间不可回收：可写层里的东西不会因容器停止而消失，你在容器里下载了 2 GB 数据集忘了删，它就在那里。第三层最容易被忽略，也最重要：可写层的性能特征与普通目录完全不同。数据库这种"随机读写频繁、文件体积大、还要求 fsync 语义"的程序放在可写层上跑，每一次大文件改写都可能付出一次全量拷贝。

这三点合起来，构成了第 06 章"数据必须外置"的技术根据。很多人以为把数据放卷里只是为了怕丢，那只说对了一半，另一半是性能。可写层用来放"临时变化"，不是用来放"长期状态"。

docker run --rm alpine sh -c "echo hello > /tmp/probe.txt && ls -l /tmp/probe.txt"

你会看到 /tmp/probe.txt 被创建，大小 6 字节。它写在只属于这一次运行的临时可写层里，--rm 让容器退出后一切被清理，不会污染本地。sh -c 后面那一整串要用双引号包住，用单引号在 PowerShell 里会被当成普通字符。

docker run --rm alpine sh -c "echo hello > /tmp/probe.txt && rm /tmp/probe.txt && echo done"

输出 done，文件被创建又被删除，容器里干干净净。这个实验看起来无聊，但它正是理解白障的引子：请你想一想，"删除"这个动作，在只有只读层和一层可写层的前提下，究竟留下了什么痕迹？

回 望

第 01 章我们做过一个实验：启动两个容器，往第一个里写文件，第二个里看不到。当时归因于"隔离"。现在能给出更精确的答案：两个容器共享同一份只读镜像层，但各有自己的可写层，所以写在容器一里的文件根本不在容器二的可写层，而镜像层从未被改动。那个"为什么 docker images 里只有一个 ubuntu 镜像"的追问也有了答案——被共享的部分是只读的，只读的东西不需要多份。写时复制让"共享"与"互不干扰"这两件本来矛盾的事同时成立。

  1. 如果写时复制让"读"几乎免费、"第一次写"很贵，那么设计一个容器化应用时，你会怎么安排哪些文件只读、哪些会被频繁写？如果一个应用天生要频繁改写一个巨大的数据文件，你还会容器化它吗？提示：从"谁来承担这次拷贝"这个角度想——是运行时的用户，还是构建时的一次性成本。
  2. 写时复制的"懒惰"是不是可以无限推广的美德？现实里有没有一类场景，懒惰反而导致总成本更高？试着举一个不属于计算机领域的例子。

白障：为什么你删掉的文件还在镜像里

把上一节末尾那个问题正面回答。假设你有一个 100 MB 的镜像，某一层里塞了一个 80 MB 的日志文件，你在后面某一层把它删掉。这个镜像现在多大？直觉会说 20 MB 左右。真实答案：还是 100 MB 出头，甚至更大。删除不但没有减小镜像，反而多了一个层的开销。

原因在于"删除"在联合文件系统里的实现方式。下层只读、不能改，所以"删掉下层里的一个文件"不可能真的去下层把它抹掉。系统的办法是：在可写层里放一个特殊标记，声明"这个名字被遮蔽了"。这个标记叫白障（Whiteout）。在 OverlayFS 里它是一个特殊文件，路径表现为原文件名加前缀，比如 /etc/hosts 被遮蔽时会出现一个 /etc/.wh.hosts；删整目录时还有更省事的机制，叫不透明目录，用一个带标记的空目录声明"这个目录下面以我为准"。两种机制目的一样：用最小的代价遮盖下面。

于是你得到一个荒谬但完全合理的局面：磁盘上确实有两份东西——底层的 80 MB 还在，遮蔽标记只是一张纸条。叠加出来的视图里你看不到那个文件，一切"看起来对了"，但那份 80 MB 一个字节都没少。

这也补全了 0B 那个疑问的另一半。docker image history 里 0B 的行有两种截然不同的成因：一种是指令只改了配置（ENV、CMD、EXPOSE），根本不涉及文件；另一种是指令只写了元数据或遮蔽标记，携带的文件内容为零。"0B"不等于"什么都没发生"，只等于"这一层没有携带新的文件内容"。

这个机制还有一个更刺人的版本：如果你的构建过程里曾经把一个密钥文件 COPY 进镜像，然后在后面某层删掉——密钥仍然完整地留在底下那颗层里，任何拿到镜像的人都可以逐层解开归档把它找出来。正确的问题不是"我怎么删掉它"，而是"我怎么让它从来没有进来过"。注意方向：它是向前防守，不是向后清理。

易 错 点

初学者在这里最常踩的坑是"用删除来瘦身"：先下载一个大压缩包、解压、用，然后 rm 掉压缩包，以为镜像会变小，结果比不解压还大。正确做法有三种。如果那些文件是构建的中间产物，就把"下载、解压、使用、清理"写在同一条 RUN 指令里，让它们只在同一层里出现又消失。如果它们是编译工具链，用多阶段构建，让它们干脆不出现在最终镜像的层里。如果它们是运行时必需的，那就没有"删掉"这个选项，只能接受体积，或者换更小的基础镜像。自查动作：每次构建完跑一次 docker image history，哪一层的体积超出预期，那一层就是你优化体积的第一目标。

现在你有工具去调查"两张 python 镜像大小差好几倍"这个现象了。

docker image history python:3.12-slim
docker image history python:3.12

把两张表并排看：先找两边都有、体积相同的层（共享的底座），再找从哪一层开始体积出现分岔，然后读那一层的 CREATED BY 写了什么。完整版通常含编译工具链与开发头文件，因为官方镜像的设计目标是"拿来就能编译 C 扩展"；-slim 剥掉了这些。不同版本的差异不一样，你需要自己从 history 里找线索。

展开：如果底层是共享的，为什么我在一个镜像里"改了东西"，另一个镜像不受影响？

因为镜像的层是只读的，而"改"需要可写层。容器运行时 Docker 为每个容器单独准备可写层，构建时为每一层单独生成新的只读层，两种情况下被共享的层从头到尾都是只读的。这也意味着一个重要的安全属性：即使运行中的容器里发现了被篡改的文件，那个篡改也一定在可写层上，把容器删掉重开，一切就回到镜像定义的状态。这就是"不可变基础设施"在文件系统层面的具体样子。

展开：白障、不透明目录，以及"删掉一个目录"会发生什么

删单个文件用白障标记；删一整个目录时逐个子文件打白障太啰嗦（上万文件的目录就要上万张纸条），所以联合文件系统还有"不透明目录"：在可写层创建一个与原目录同名的空目录并设置不透明标记。日常使用中你不需要手动创建这些标记，但当你要在宿主机层面排查"为什么这个文件删了还在"时，知道该找这些点号开头的特殊文件，能省下你半小时。

前 瞻

第 09 章会从安全角度把这件事讲成一条纪律：镜像里不该有任何秘密。到那时我们会把这一节的机制拿来当证据——你无法"删掉"一个曾经进过层的东西，所以只能在它进来之前拦住它。BuildKit 提供的构建期密钥挂载（把密钥临时挂进构建过程、不写入任何层）以及软件物料清单，都是围绕这个机制设计的防线。现在你只要带走一个判断：把秘密安全地放进镜像这件事，做不到。

镜像的名字：一段语法，三段权力

你已经知道镜像的"内容身份"是摘要。但人不能靠 sha256 交流，所以这个世界还需要一套人类可读的命名规则。这套规则看起来琐碎，其实是整个镜像生态的秩序来源：它决定了你的镜像能推到哪、别人怎么找到它、以及你写错一个字会撞上什么错误。

[registry[:port]/][namespace/]repository[:tag][@digest]

方括号里的部分都可以省略。省略之后 Docker 会替你补上默认值——而"默认值是什么"恰恰最需要讲清楚，因为大量困惑都来自"我以为我写的是 A，其实系统理解成了 B"。

第一段是 registry，镜像仓库服务，由主机名加可选端口组成。不写时，Docker 默认去 Docker Hub，也就是 docker.io。这里有个非常容易踩的细节：只有当名字里出现点号或冒号时，Docker 才会把第一段当成 registry 主机名。所以 nginx 被理解成"Docker Hub 上的 nginx"，而 ghcr.io/owner/app 里的 ghcr.io 被正确识别成主机名。副作用是，如果你自建的内网仓库主机名就叫 registry，写 registry/myapp 会被理解成 Docker Hub 上的一个仓库，然后你收到"不存在"或"没有权限"，并且找不到原因。

第二段是命名空间，用斜杠与仓库名隔开。Docker Hub 上的官方镜像使用 library 这个命名空间，所以 nginx 的完整身份其实是 docker.io/library/nginx:latest。命名空间是权限与信任的边界：library 里的镜像由 Docker 与上游社区共同维护，背书的含义与你随便一个账号推上去的同名镜像完全不同。第三段是 repository，指某一个镜像的全部版本集合。第四段是标签，第五段是摘要。

书写规则：仓库名必须小写，用点、连字符、下划线分段；标签最长 128 个字符，允许字母数字与下划线、点、连字符，不能有斜杠。写错时 Docker 会报格式错误，信息通常还算清楚。

docker tag alpine:latest myrepo/alpine:v1
docker images

多了一行 myrepo/alpine:v1，IMAGE ID 与 alpine:latest 完全一致。这条命令没有复制任何数据，也没有联网，它只是在本地那张"内容到名字"的映射表里加了一条记录。所以 docker tag 永远瞬间完成，无论镜像多大——它做的是起名，不是搬家。请把这句话刻在脑子里：打标签不复制内容，删标签不删除内容。

另一个方向的操作是删除，用 docker rmi。这里有个微妙之处：如果你给一个镜像打了多个标签，rmi 某个标签时，Docker 先检查"删掉这条引用之后还有没有别的名字指着这份内容"。有的话，它只删这条引用，内容原地不动；没有的话，它才去真正回收那些层，而回收时还要再检查有没有别的镜像在用同一层。所以你偶尔会看到输出是 Untagged 而不是 Deleted，那不是失败，那是"引用被摘掉了"。

方 法

遇到"这条命令到底做了什么"这类问题时，最省时间的办法不是猜，而是设计一个能暴露差别的最小实验。刚才那个 docker tag 实验只用了两条命令，就把"最贵的操作"和"最便宜的操作"分开了：一个可能动几 GB 数据，一个只写一行记录。以后遇到任何镜像操作，你都可以问自己三个问题：它联网吗？它可能复制数据吗？它删的是引用还是内容？把答案写下来，你对整个系统的掌控感会立刻不同。面对陌生系统，不要背命令清单，而要找出它内部什么东西便宜、什么东西昂贵。

回 望

第 02 章讲客户端与守护进程时，我们说 docker 命令本身不干活，它只是把参数组装成一个请求发给 dockerd。现在你看到了这条架构的另一面：正因为命名解析发生在守护进程那一侧，镜像名字的语法规则、默认值填充、标签与摘要的关系，全部由服务端统一执行。你换一个客户端、换一种语言调用接口，规则完全一样。这也是镜像命名能成为跨工具、跨平台通用语言的原因。

标签、摘要与仓库：从你的笔记本到别人的机器

标签的问题不在于它不好用，恰恰在于它太好用——灵活到可以被随意改写，而没有任何机制会因此报警。同一条 docker tag，既可以给你刚构建出来的新镜像命名，也可以把某个正在被生产环境使用的名字，指向一份完全不同的内容。

标签是一个可变的指针，它可以指向不同的内容而不改变自己的名字。这句话的三个后果，每一个都在真实项目里造成过事故。

后果一：两次 docker pull 可能给你不同的东西。今天你拉 app:1.0，明天再拉，如果中间有人重建并覆盖了这个标签，你拿到的就是另一份内容，而你的配置一个字都没改。它不报错，只是"行为变了"。后果二：同一个标签在不同机器上可以对应不同内容——你的本机因为某次本地构建把它指向了本地版本，服务器上指向仓库版本，"在我机器上能跑"换了一身衣服又回来了。后果三：回滚变得不可信，你想"回到 1.0"，但如果 1.0 期间被别人覆盖过，你回到的根本不是当初那一版。你以为在做时间旅行，实际上在开盲盒。

那为什么还要发明标签？因为人类需要它。摘要是一串 64 个字符的十六进制，没有任何语义，也不可能被记住。没人能靠肉眼看出 sha256:9f3a... 和 sha256:c41d... 哪个是上周的版本、哪个修了那个 bug。标签是人类贴在机器坐标系上的便利贴。标签服务于人的阅读与沟通，摘要服务于机器的精确与可信。成熟团队同时用这两样：对外沟通用标签，部署时用摘要锁定。

docker pull nginx:1.27-alpine

注意最后一行的 Digest。即使你指定了标签，Docker 也会把解析出来的摘要显示给你——它在提醒："你用的是标签，但这是它此刻对应的确切内容。"把这一行存进部署配置，就是一个可靠的锁定动作。

docker pull nginx@sha256:你的Digest里的那串字符

这条命令用摘要而不是标签来拉取。如果那份内容在仓库里存在，你会拿到完全正确的一份；如果不存在，命令会失败，而不是"给你一个差不多的"。后一种行为才是关键——摘要不会将就。请把上一条输出里的 Digest 原样粘过来，不要照抄示例字符串。

那么 latest 到底错在哪里？它的真实身份是"当你没写标签时 Docker 替你补上的默认值"。于是有两种情况。第一，标签为 latest 的镜像未必是最新的：如果你的 CI 每次都推 latest，它确实是最近一次推送的内容；但如果某个镜像三年没更新，它的 latest 就是三年前的东西。第二，本地已有 latest 时，docker pull 不一定会去远端重新取。

docker pull alpine:latest

注意 Status 那一行。当本地内容已是最新时，它会说 Image is up to date。这个行为本身是对的（省流量），但它意味着你没法靠"我刚 pull 过"来证明"我拿到的一定是最新内容"。

生产环境的标签纪律可以归纳成三条能直接照做的规则。第一，永远不用 latest 做部署，把它留给"我随便跑一下试试"的本地实验。第二，用能表达含义的版本号，比如 1.4.2、2025.03.11、或 Git 提交号的前几位，让人一眼看出新旧。第三，关键部署用摘要锁定；如果因为可读性必须用标签，至少让标签本身不可变——只发布新标签，永不覆盖旧标签。

第三条里有个用词值得停下来想：标签的"不可变"不是技术上的不可变，它只是一种团队纪律。技术允许你覆盖任何标签，是你自己决定不去覆盖。这意味着它是一份需要被人遵守的规矩，而规矩会被人遗忘、被人绕过。凡是依赖"人一定记得"的机制，都迟早会失效。这正是第 10 章要把标签规则写进流水线的原因：让机器执行纪律，而不是指望某个人记得。怎么让镜像从你的笔记本走到别人的机器上？承担这件事的是镜像仓库（Registry，存放与分发镜像的服务器）。

怎么让镜像从你的笔记本走到别人的机器上？承担这件事的是镜像仓库（Registry，存放与分发镜像的服务器）。它的三个层级名字很像，混用会让你说话表意不准，排查问题时也会找错地方。

Docker Hub 是默认的那一个，也是全球最大的镜像集散地。它上面有两类镜像值得你知道：官方镜像位于 library 命名空间下，由 Docker 与上游软件社区共同维护；认证镜像由商业厂商发布并维护。它有两个现实限制，你迟早会撞上。第一是速率限制：匿名用户与登录用户的拉取配额不同，超过之后会收到明确的拒绝。第二是网络可达性：国内网络下从它拉取可能很慢甚至失败。前者最直接的应对是登录账号；后者的常见做法是配置镜像加速器，但这里有个安全判断必须说明白——加速器能看到你请求了什么镜像，所以私有镜像绝不能走不可信的加速通道。这也是企业愿意自建私有仓库的重要动机之一。

docker login

它会交互式地问用户名和密码，凭据通常存在本地凭据文件或系统凭据管理器里，而不是明文写在配置文件中。如果在公共电脑上操作，登录前先想清楚这一点。退出用 docker logout。

docker tag kaoyan-alpine:test 你的用户名/kaoyan-alpine:test
docker push 你的用户名/kaoyan-alpine:test

第一步把本地镜像改成仓库能接受的形式——注意是加名字，不是复制。第二步把内容推上去。如果跳过第一步直接 push，Docker 会因为"这个名字不属于任何你拥有权限的仓库路径"而拒绝。这个报错的措辞常让人以为是自己没登录，其实是名字格式不对。请把"你的用户名/"当成通行证：它既是寻址路径，也是权限范围。

展开：OCI 标准与"镜像仓库不只是一家公司的服务"

镜像格式不是 Docker 公司私有的东西。开放容器倡议（OCI）维护着镜像规范与运行时规范，把"一个镜像应该长什么样"写成了公开、可实现的接口。正因为格式是标准的，你才可以用 Docker 构建、用 containerd 运行、用 Kubernetes 调度、用别的工具扫描漏洞，而不会被困在某一家公司的工具链里。它还有一个务实后果：许多仓库、构建工具、扫描工具彼此兼容，你可以按需替换其中任何一个环节。以后你读到"某某平台支持 OCI 镜像"，应该知道那句话的分量——它说的是"你的镜像可以直接拿过去用"。

用了半年 Docker 之后，你几乎一定会遇到这个场景：磁盘红了，打开一看，Docker Desktop 的虚拟磁盘占了几十 GB，而你印象里"我只有几个小镜像"。先看全貌，再拆细节。

docker system df

一张表分四类统计：Images、Containers、Local Volumes、Build Cache。每行有两列值得对比：SIZE 是总量，RECLAIMABLE 是可回收量。构建缓存那一行经常大得惊人——那是构建过程产生的中间层，因为可能被复用而没有立刻删掉。在 Windows 上，这套统计是在 Docker Desktop 的虚拟机内部进行的，反映的是虚拟机磁盘里的占用，与你在资源管理器里看到的那个大文件不是一对一的。

docker images -f "dangling=true"

如果你重新构建过同名同标签的镜像，这里会列出若干行，REPOSITORY 与 TAG 都显示为 <none>。这就是悬空镜像：内容还在，但已没有任何标签指着它。成因通常是某次你把 app:1.0 重新构建，新内容拿走了这个名字，旧内容被摘掉了标签。这里必须分清两种"没有标签"的镜像：悬空镜像无人引用，是纯粹的空间浪费；中间层也没有标签，但它是另一个镜像的某一层，被别的镜像踩在脚下，默认视图里看不到，加 -a 才显示。

docker images -a

加上 -a 之后行数会多很多，其中不少 REPOSITORY 显示为 <none>。不要随手删它们：如果某个正在使用的镜像依赖某一层，Docker 会阻止你删，或者告诉你删了会影响谁。

docker image prune

不加参数时只删除悬空镜像——无人引用、纯属浪费的那一批。它会先列出要删的东西让你确认，输入 y 才执行。这是最温和的一条，日常用它就够了。

docker image prune -a

加 -a 之后范围扩大到"所有没有被任何容器使用的镜像"。这是本质差别：你只是本地放着备用的那些镜像也会被删，下次要用得重新下载。它在 CI 机器上有用处，但绝不能变成你的习惯动作。

docker system prune -a --volumes

最后这条最危险，因为它连数据卷一起删。卷里可能放着你的数据库文件——那是删掉就真的没有的东西，镜像还可以重新下载，数据不行。请把它当成"格式化硬盘"级别的操作：执行之前先想清楚，这台机器上有没有任何数据是你无法重建的。

为什么镜像不多，磁盘却涨得比想象快？因为占用空间的东西不止镜像：构建缓存会积累，容器停止之后可写层还在，匿名数据卷会随着容器反复创建而悄悄堆积，还有你根本没注意过的悬空镜像。清理的正确顺序是"先看清，再动手"：先用 docker system df 看哪一类最大，再进那一类用 ls 加过滤器找具体对象，最后才决定删什么。

最后回到那个最反直觉的点：为什么把 docker images 里所有 SIZE 加起来，数字会明显超过实际磁盘占用？因为 SIZE 显示的是"这个镜像的各层之和"，共享的层被每个镜像重复计入了。十个基于 alpine 的镜像，每一个都会把那份八兆左右的底层算进自己的 SIZE，而磁盘上它只存在一份。Windows 的差异也在这里：镜像内容存放在虚拟机的文件系统里，块分配方式与稀疏文件的处理都会影响"实际占用"，所以 SIZE 是可靠的相对比较，但不是精确的磁盘账单。

易 错 点

两个高频误判。第一个是把 <none> 直接等同于垃圾：其实有两种 <none>，一种是真正的悬空镜像，可以清；另一种是被别的镜像依赖的中间层，删它会连带影响别的镜像——好在默认视图里看不到后一种。第二个误判是看到"镜像只有几百兆"就以为磁盘不会涨：真正让磁盘爆掉的常常是构建缓存和无名的匿名卷，它们不出现在 docker images 里，只在 docker system df 里现形。磁盘出问题时，第一条命令永远是 docker system df，而不是随手 prune。

回 望

第 02 章讲 Docker Desktop 时提过一句：Windows 上没有 Linux 内核，所以它替你开了一台 Linux 虚拟机，再把命令行接进去。现在这句话有了具体的重量：你所有的镜像、层、可写层、数据卷，都存放在那台看不见的虚拟机里。这就是为什么"文件在哪"这个问题在 Windows 上格外难回答，也是为什么你在资源管理器里删不掉某一层、却能在 docker 命令里删掉它。第 06 章讲数据卷时，我们会把"数据到底存在宿主机哪里"彻底摊开。

前 瞻

这一章我们把层讲清楚了，但没有讲"怎么让层为自己服务"。第 05 章会从另一头切进来：Dockerfile 的每一条指令分别会产生什么样的层、指令的先后顺序如何决定构建缓存能不能命中、多阶段构建怎样让编译工具链干脆不进入最终镜像。到那时你会用回本章的两个结论——层记录差分、层按内容寻址——去解释为什么"把变化最频繁的步骤放在最后"这样一条看似经验的规矩，其实是被机制逼出来的必然。

前 瞻

第 10 章我们会把这一节的规则变成流水线里的具体动作：每次推送代码自动构建镜像，同时打上两个标签——一个是语义化版本（给人看），一个是 Git 提交号（给机器追溯），然后让部署脚本按提交号或摘要去拉。到那时你会发现，"标签 vs 摘要"不只是一个概念辨析，它直接决定你半夜被叫起来时能不能在五分钟内定位到线上跑的是哪一份代码。第 09 章还会补上另一块：摘要与漏洞扫描如何配合——扫描结果绑定在摘要上，才能在镜像内容不变的前提下判断这个漏洞我到底有没有。

思 考
  1. 如果所有团队都严格遵守"永不覆盖标签"的纪律，标签可变这件事还会造成问题吗？反过来说，如果标签真的成了不可变的，它与摘要的区别还剩多少？提示：想想"谁有权改"和"改了之后谁能看出来"这两个问题。
  2. 你是三人小团队的负责人，项目部署在一台自己的服务器上。你会要求团队用摘要部署吗？如果用，你会怎么解释"为什么配置里要贴一串看不懂的字符"，才能让他们不觉得这是形式主义？
  3. 有一种做法是"用日期当标签"，比如 2025-03-11。它比 latest 好在哪里，又留下了什么新问题？如果一天要发布三次呢？提示：从"同名不同内容"这个角度想。

完整旅程：从一个空目录走到一个可发布的镜像

理论讲到这里，该上路了。我们从桌面上一个空文件夹开始，一步一步走到"这个镜像已经推到仓库里，别人可以拉下来运行"。请照着做，哪怕你觉得自己已经懂了——这条路上有几个细节，只有亲手敲过才会记住。

mkdir fossil-demo
cd fossil-demo
notepad app.py

mkdir 建目录，cd 进去，notepad 是 Windows 自带的记事本，它会问你"找不到 app.py，要不要新建"，选是。保存时把"文件类型"改成"所有文件"，文件名确确实实写成 app.py。这一步会卡住不少初学者，而且报错往往出现在很后面（构建成功但运行时报找不到文件），所以在这里多花十秒。

import platform
import sys

print("python:", platform.python_version())
print("machine:", platform.machine())
print("system:", platform.system())
print("arguments:", sys.argv[1:])

这一段是 Python 源码，不是 shell 命令。它把 Python 版本、机器架构、操作系统、以及你传给容器的参数打印出来。把 system 打印成 Linux 这件事本身就是个小震撼——你在 Windows 上构建的镜像，运行起来是一台 Linux。

notepad Dockerfile

同样的方式新建，文件名就是 Dockerfile，没有扩展名。同样注意保存成"所有文件"，否则可能变成 Dockerfile.txt，而 docker build 会找不到它。

FROM python:3.12-slim

WORKDIR /app

ENV DEMO_MODE=learning

COPY app.py /app/app.py

CMD ["python", "/app/app.py"]

五行，四个概念。FROM 选定底座，用 -slim 而不是完整版，是你为体积做的第一次主动取舍。WORKDIR 设定之后各指令的工作目录。ENV 写进镜像配置，运行时容器里会带着这个环境变量。COPY 把你的代码真正带进镜像。CMD 定义容器默认执行的命令，JSON 数组这种写法叫 exec 形式，可以避免被 shell 再解释一遍。

docker build -t fossil-demo:1.0 .

你会看到分步骤的输出，每一步有编号，最后一行是 Successfully tagged。命令最后那个点表示"构建上下文是当前目录"，也就是把当前目录的文件交给构建引擎。它意味着目录里有什么就被发送什么——如果这里有几百兆数据或不该外传的文件，它们会一起被打包送过去。这就是必须写 .dockerignore 的原因，第 05 章会专门讲。

docker image history fossil-demo:1.0

这就是你刚才那五行指令的逐条账本。注意不是每行都占体积：FROM 那行会显示基础镜像的体积，COPY 那行会显示你脚本的大小，而 ENV、WORKDIR、CMD 那几行的 SIZE 是 0B——它们只改配置，不产生新的文件系统层。这正是我们从开头追到现在的那个 0B 疑问的完整答案。

docker run --rm fossil-demo:1.0

四行输出：python 3.12 的某个具体小版本、machine 显示 x86_64、system 显示 Linux、arguments 是空列表。请停在这里想一件事：你在这台 Windows 机器上，用一个亲手写下的文件，造出了一个会打印 Linux 的东西，全程没有配置过任何环境。这就是容器这个词真正的分量。

docker run --rm fossil-demo:1.0 甲 乙 丙

这次 arguments 会变成 ['甲', '乙', '丙']（中文显示异常就换成 abc def）。它展示了镜像是"可执行文件"这件事：你可以在镜像名后面直接追加参数，它们会被交给 CMD 里定义的那个程序。这正是 ENTRYPOINT 与 CMD 分工的现实意义，第 05 章会把这两个指令讲透。注意 CMD 可以被整体替换——如果你在 docker run 后面写了另一个程序名，CMD 就完全失效。

docker tag fossil-demo:1.0 你的DockerHub用户名/fossil-demo:1.0
docker push 你的DockerHub用户名/fossil-demo:1.0

第一条只加了一个名字，本地什么都没复制。第二条会真正上传，逐层推送，已经在仓库里的层会显示已存在而被跳过——这正是层共享在分发环节的体现：只要某些层的哈希与图库里已有的一致，就不会重复上传。推送完成后打开 Docker Hub 你的仓库页面，你会看到这个镜像以及它的 1.0 标签。

.git
__pycache__
*.pyc
.env
node_modules

这是 .dockerignore 的内容示例，不是命令。五条规则分别排除版本控制目录、Python 缓存、编译产物、环境变量文件、前端依赖目录。它的必要性有三个理由：速度（不必把无用文件传一遍）、体积（避免把无用文件 COPY 进镜像）、安全（避免把密钥、.env、.git 带进镜像）。原则只有一条：凡是构建不需要、或不该被别人看到的东西，都应该在这里被拦下。写好之后重新构建一次，注意"发送上下文"那个数字的变化。

docker run --rm -e DEMO_MODE=debug fossil-demo:1.0

最后一个实验：-e 在运行时给容器传环境变量。它和 Dockerfile 里的 ENV 是两回事——ENV 是镜像里写死的默认值，-e 是运行时从外面覆盖它。同一份镜像，换一个环境变量就换一种行为，这就是十二要素应用里"配置存于环境"的意思，也是"构建一次、到处运行"这句口号真正的含义。

方 法

每学完一个工具，做一次"从零重来"的练习，是性价比最高的巩固方式。现在请把终端关掉，从 mkdir 开始再走一遍，中间不许看上面的内容，只在卡住时回来查。第二遍会快得多，而且你会发现真正的卡点不再是命令，而是几个判断：该用哪个基础镜像、什么该放进 .dockerignore、标签该怎么起。这些判断才是能力，命令只是它的表达形式。

镜像不是一个更大的文件，而是一叠可以被反复拆开、重新拼装的账本。你写的每一行构建指令，都在某一页上留下一条不可涂改的记录。

思 考
  1. 你刚刚把镜像推到了公开的 Docker Hub。请诚实评估：这个镜像里有没有任何你不想公开的东西？你是怎么确认的——是你记得没有，还是你真的查过？提示：可以从"我能不能逐层解开这个镜像看看里面有什么"这个动作想起，也可以想想 docker history 能告诉你什么、不能告诉你什么。
  2. 如果明天 Docker Hub 宣布对免费账号的公开仓库数量设限，你的项目会受什么影响？你会把镜像挪到哪里？迁移成本主要在哪里——是重新构建，还是别的什么？
  3. 你希望别人如何信任你发布的这个镜像？如果换成"这是一家银行发布的基础镜像"，你希望他们额外提供哪些信息，才能让你敢在自己的系统里用？

自测：检验你是否真的学懂了

检 查 题
  1. 用一句话说清"镜像"由哪几部分组成，每一部分负责什么。
    参考答案

    三部分：一组只读层（记录相对上一层的文件系统变化）、一份配置（JSON，记录架构、操作系统、默认命令、环境变量、以及引用了哪些层）、一份清单（把名字与内容摘要、以及多架构的分支关系连起来）。要点是不要把三者混成一个，尤其要提到配置也参与决定镜像摘要。

  2. 你运行 docker images，看到两个不同仓库名、不同标签的镜像，IMAGE ID 完全相同。解释这是怎么发生的，并说明这两个镜像占多少磁盘空间。
    参考答案

    它们其实是同一份内容被起了两个名字。docker tag 只增加一条"名字到内容"的映射记录，不复制数据，所以磁盘上只有一份内容。判断思路：IMAGE ID 相同即内容相同，接着问"我到底有几份内容"。如果两者共享全部层但不是同一个镜像对象，IMAGE ID 会不同，那种情况要另判。

  3. 一条 docker pull 的输出里出现了 Already exists、Pull complete、Verified Checksum、Digest 四样东西，分别说明它们的含义。
    参考答案

    Already exists 表示这一层本地已有（层摘要相同），跳过下载；Pull complete 表示某一层下载并解包完成；Verified Checksum 表示内容通过哈希校验，没有损坏或被掉包；Digest 是整份镜像清单的摘要，也就是这一份内容的精确坐标。评分要点：能说清"按摘要去重"与"校验"分别对应哪一行。

  4. 如果下面这条命令单独作为一层执行，镜像会变小吗？为什么？
    RUN rm -rf /var/lib/apt/lists/*
    参考答案

    不会变小，反而多了一层的开销。前面的层是只读的，删除只能通过白障标记遮蔽下层文件，被删的数据仍完整保存在底层。如果它和下载、安装写在同一条 RUN 里，那些文件只是在构建过程中临时存在、最后没有进入层，才能真正省下体积。要点：删除改变的是文件视图，不是层的内容。

  5. 命令预测：你有一个名为 app:1.0 的镜像，先执行 docker tag app:1.0 app:2.0，再执行 docker rmi app:1.0。app:2.0 还能用吗？磁盘空间被释放了吗？
    参考答案

    app:2.0 仍然可用，磁盘空间没有释放（最多释放掉那一行记录），因为内容仍被 app:2.0 引用着。这题考的是"引用与内容"的区分：rmi 先摘引用，只有引用计数归零且没有任何镜像依赖这些层时，层才会被回收。

  6. 你写了 docker pull ghcr.io/team/app:dev。请指出 registry、命名空间、仓库、标签分别是什么，并说明如果把 ghcr.io 换成一个不含点号的名字会发生什么。
    参考答案

    registry 是 ghcr.io，命名空间是 team，仓库是 app，标签是 dev。如果第一段不含点号也不含端口，它就不会被当成主机名，而会被理解成 Docker Hub 上的一个仓库路径，于是命令要么报不存在、要么拉到一个完全无关的同名仓库。评分要点：能指出"点号或端口决定第一段是不是主机名"这条规则。

  7. 为什么"用 latest 部署生产"是坏主意？请给出至少两个不同层面的理由。
    参考答案

    层面一：latest 不代表最新，它只是没写标签时的默认值，谁是它由仓库里最后一次推送到这个标签的内容决定。层面二：即使远端已更新，本地已有 latest 时 pull 也可能报告已是最新而不重新下载，你会误判版本。层面三：回滚不可信，你无法确定某个时刻的 latest 对应哪份内容。评分要点：能区分"标签的语义"与"拉取行为"两个层面。

  8. 现象解释：一个 100 MB 的镜像，某一层删掉了一个 80 MB 的目录，之后 docker images 显示这个镜像变成 120 MB 左右。请解释这个数字。
    参考答案

    80 MB 的数据仍在底层，没有任何字节被释放；新增的那一层里包含遮蔽标记（白障或不透明目录），本身虽然极小，但层的元数据与目录项仍占一点空间，加上原有体积，于是总体略大于原来的 100 MB。"变大"这个现象恰恰是理解白障最有力的证据。

  9. 故障诊断：你在容器里往一个目录写文件，速度很慢，而且随着文件变大越来越慢。给出至少两个可能原因，并说明用什么命令验证。
    参考答案

    原因一：写入发生在可写层，第一次修改大文件触发完整拷贝（写放大）。原因二：该目录被匿名卷覆盖或根本没挂卷，数据反复经过联合文件系统的复制路径。验证手段：用 docker inspect 看挂载点确认目录是否落在卷上，用 docker system df 看可写层与卷的占用，用 docker stats 观察块设备读写。要点：能说出"第一次写最贵"这个机制并给出验证动作。

  10. 方案取舍：你要给一个 40 人的团队定镜像标签规范。写出你的规则，并说明每条规则为解决什么风险而存在。
    参考答案

    参考规则：只发布新标签、永不覆盖旧标签（防内容静默变化）；版本号与 Git 提交号双标签（人可读 + 机器可追溯）；生产部署按摘要锁定（防仓库侧被改动）；禁止 latest 用于任何部署（防歧义）。评分要点：每条规则都要挂在一个具体风险上，而不是笼统说"更规范"。提到"用流水线强制执行"可以加分。

  11. 动手任务：拉取 python:3.12-slim 与 python:3.12，用 docker image history 找出体积差在哪一类层上，并写出推理过程。
    参考答案

    思路：先对比两张表里共有且体积相同的层（共享的底座），找出从哪一层开始出现差异，再读那一层的 CREATED BY 内容。差异通常出现在工具链与开发头文件相关的层上，因为完整版镜像的设计目标是开箱即可编译 C 扩展。评分要点：不在于结论精确到哪一层，而在于你是否用了"先找交集、再找分岔点"的方法，并且用 history 而不是靠猜。

  12. 请解释：为什么 docker images 里所有 SIZE 相加往往大于磁盘实际占用？这对你选择基础镜像有什么启发？
    参考答案

    因为 SIZE 显示的是"这个镜像的各层之和"，共享层被每个镜像重复计入，而磁盘上只存一份。启发有两点：一是选择相同或相近的底座可以让不同项目大量共享层，节省磁盘与下载时间；二是评估"我到底占了多少"要看 docker system df，而不是把 images 的 SIZE 相加。

  13. 概念辨析：如果层的身份完全由内容决定，那么"层不可变"是否意味着镜像不能被修改？如果不能修改，我们平时"更新镜像"到底在做什么？
    参考答案

    不可变指的是层的内容不会被就地改写。所谓更新镜像，实际上是产生新的层、新的配置、新的摘要，然后用新标签指向它，或者覆盖一个旧标签。旧内容可能因为无人引用而被回收，也可能仍留在磁盘上。要点：区分"修改内容"与"用新内容替换引用"。

  14. 动手任务：导出一个小镜像，用 tar 列出内容，指出哪几个文件属于层、哪几个属于配置与清单。
    参考答案

    先 docker save 导出，再用 tar 列出文件名。以 .tar 结尾的是层归档；index.json 一类的文件是清单；其余以 sha256 摘要为名的文件是配置与清单本体。评分要点：能说出"三类文件各自对应本章讲的哪一样东西"，并意识到镜像导出后是可被任意工具检查的普通文件集合。

本章总结

  • 镜像不是一个大文件，而是三样东西的组合：一组只读层、一份描述怎么启动的配置、一份把名字与内容连起来的清单。
  • 层记录的是相对于上一层的变化（新增、修改、删除），不是完整快照。因为只记变化，相同变化必然得到相同的层，跨镜像共享才成为可能。
  • 内容寻址是本章的地基：身份由内容算出，不由人授予。它同时带来去重、校验、精确定位三种能力。
  • 标签是可变的指针，摘要是不可变的内容身份。标签服务于人的阅读，摘要服务于机器的可信，成熟做法是两者并用。
  • latest 的真实含义是"没写标签时的默认值"，不是"最新版本"。本地已有 latest 时拉取甚至可能不重新下载，这会让你误判版本。
  • 写时复制让"共享"与"互不干扰"同时成立：读时共享只读层，写时把文件复制到可写层再改。代价是第一次修改大文件要付出完整拷贝。
  • 删除下层文件靠白障标记，它只遮蔽视图，不回收数据。所以删除不能让镜像变小，反而多一层开销。
  • 可写层适合放临时变化，不适合放长期状态。这是"数据外置"的技术根据，也是性能判断，不只是怕丢数据。
  • 镜像名字的每一段都有默认值，而默认值往往正是困惑的来源：不写 registry 就去 Docker Hub，不写标签就是 latest。
  • docker images 的 SIZE 是各层体积之和，共享层被重复计入，所以加总大于磁盘实际占用。要看真实占用请用 docker system df。
  • <none> 有悬空镜像与中间层两种，危险性不同；清理命令的差别全在参数上，prune -a 与 --volumes 是完全不同量级的动作。
  • 这一章最重要的一个判断：只要一样东西曾经进入过某一层，它就永远在那份镜像里。你能做的不是事后删除，而是事前不让它进来。

现在回头看，你手上其实多了一件东西。你第一次拥有了一个可以被精确指认的交付物——它有内容摘要，有逐层账本，有可复用的底座，还有一条别人能重走一遍的构建路径。代码从这一刻起不再只是你文件夹里的文本，而是一个可以被搬运、被验证、被追溯的实体。至于这份实体在运行时怎样开始、怎样结束、怎样优雅地退出，是下一章的事。你会发现，那里面有相当一部分问题的根源，仍然落回我们这一章讲过的层与可写层。
