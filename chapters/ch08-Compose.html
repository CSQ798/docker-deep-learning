第 08 章声 明 式 的 世 界 · COMPOSE

Compose：把一整座机房写进一个 YAML 文件

从"我敲了一堆命令"到"我描述了我想要的世界"。

本 章 学 习 目 标
  • 能说清命令式与声明式这两种思维的差别，并解释为什么"环境"这种东西天然适合被描述而不是被执行。
  • 能解释 Compose 为什么存在：它把哪些命令、哪些参数、哪些隐含依赖收进了一份文件，代价又是什么。
  • 能读懂一份 compose.yaml 的层级结构，知道每个字段大致落在哪一层、解决哪一类问题。
  • 能解释 Compose 自动创建的网络与服务名解析之间的关系，以及为什么内部连接不需要发布端口。
  • 能说清 depends_on 的能力边界，并用"容器启动"与"服务就绪"这两个不同的概念解释它为什么经常失效。
  • 能判断一份配置里哪些值属于"环境差异"，哪些值属于"密钥"，并据此决定它们该写在哪里。
  • 能说清 Compose 做什么、不做什么，并给出至少三条"该考虑转向 Kubernetes"的具体判断依据。
学 完 之 后 ， 你 应 该 能 够
  • 能写出一个包含 web、数据库、缓存三层、带健康检查、带命名卷的多服务 compose.yaml，并一次启动成功。
  • 能用 docker compose config 打印最终生效的配置，并据此判断多文件合并、变量插值、默认值的真实结果。
  • 能设计并排查服务启动依赖问题，判断该用健康检查、应用重试，还是两者都要。
  • 能设计一套环境变量与密钥的分层方案，并写出对应的 .gitignore 规则与 .env.example 模板。
  • 能用 profiles 让一份文件同时服务日常开发、联调与排障三种场景。
  • 能用基础文件加覆盖文件的方式区分开发与生产，并用 config 命令验证合并结果而不是靠猜。
  • 能判断一个项目是"单机 Compose 足够"，还是"必须上编排系统"，并说清理由。

上一章结束时，你已经能在自己的笔记本上手工搭出一座小小的网络城市了：用一条命令建自定义网络，用几条 docker run 把 nginx、Redis、Postgres 接进去，再用服务名让它们互相喊话。你甚至亲手验证过"默认网桥不支持容器名解析、自定义网络支持"这个关键差别。然后你合上电脑，第二天重新打开项目，翻出昨天记下的那六条命令：第一条里有端口和卷，第二条里有三个环境变量，第三条的名字你写错了一个字母，第四条你忘了它需要先连上网络。你花了二十分钟把环境恢复到昨天的样子，并且并不确定这次和上次是不是同一套东西。这一章要解决的就是这二十分钟。我们要把"我曾经敲过那一串命令"换成"我描述了我想要的那套东西"，并让机器负责把现实拉向这个描述。这件事的名字叫 Docker Compose（Compose，多容器应用编排工具）。它的分量远比"少敲几条命令"要重——它是一次思维方式的换轨。

两种思维：执行步骤，还是描述状态

先说一件可能让你意外的事：Compose 里最值得学的东西不是 YAML 语法，而是它背后那种叫声明式的思维方式。YAML 只是这种思维目前最流行的一件外衣，换成 TOML、JSON 甚至一套图形界面，思想都不会变。所以这一节我们先把两种思维方式摆清楚，再去谈文件长什么样。

你前面七章学到的一切，几乎都是命令式的。命令式（imperative）的意思是：你告诉机器"做什么动作、按什么顺序做"。docker network create、docker run -d --name db、docker run -d --name web，这是一份动作清单。动作清单有三个天然属性。第一，顺序即逻辑：先建网络再起容器，顺序反了就是报错，因为逻辑本身依赖先后。第二，状态藏在你的脑子里：这串命令执行完之后世界是什么样，需要你在心里模拟一遍才知道；机器不会替你记。第三，不可重复执行：你再跑一次，第一个动作就会失败，因为那个网络已经存在了。于是你被迫要么先手动清理，要么给每条命令都加上"如果不存在才执行"的判断——这就是命令式世界里的日常家务。

声明式（declarative）的意思是：你描述"最终应该是什么样"，然后由一个执行者负责对比现实与描述的差距，并采取动作把差距抹平。你不说"先建网络再起容器"，你只说"这里应该有一个名叫 db 的服务、它连在项目网络上"。剩下的事——网络存不存在、容器是不是已经在跑、镜像要不要先拉——全部由执行者去算。这个执行者有一个专门的词，叫调和循环（reconciliation loop）：读期望、看现实、算差距、动手、再看一遍，直到两者一致。

比 喻

命令式像给厨师念菜谱：先热锅，再倒油，油温七成下葱姜，炒香后放肉。每一步都得说，火候还得靠他判断。声明式像在餐厅点单：我要一份红烧肉，不要香菜，米饭两碗。你不关心他先切肉还是先烧水，也不关心他用哪口锅。这个比喻里最要紧的一点是：厨师如果发现肉已经炖好了，他不会再炖一遍——在你没说话的层面上，系统自己完成了幂等这件事。

回到技术本体。点单的比喻有一个不够用的地方：餐厅只服务一顿饭，而你的项目环境要反复重建、要交给同学、要在另一台机器上复现。这才是声明式真正值钱的场景。想想"环境"这种东西的属性：它需要被反复创建（每天上班、每次换电脑、每台 CI 机器）；它需要被评审（"你把数据库端口暴露到公网了？"这个问题应该在代码评审里被发现，而不是在事故复盘里）；它需要被版本化（三个月前那套能跑的环境，长什么样）；它需要被复制（同学照着你的文件就能跑起来）。这四条要求，命令式的"动作清单"一条都满足不了——清单可以被复制，但清单里没有世界的样子。

我用一张表把这两种思维彻底摊开。请注意最后一行：这一行是本章后面所有麻烦的根源。

维度命令式声明式
你交付的是什么一串动作和它们的顺序一份"世界应该是什么样"的描述
谁负责顺序你。写错了就报错执行者。它自己算依赖与先后
重复执行会怎样大概率报错（对象已存在）收敛到同一个结果，通常无副作用

表里最后两行值得再展开一层。很多人第一次接触声明式工具时的爽点是"我不用管顺序了"，但真实情况是：顺序没有消失，它只是从"你写的一行行代码"搬到了"系统内部的依赖图上"。你写进 compose.yaml 的每一个隐藏依赖——比如 web 需要 db 的密码变量、需要 db 的卷已经初始化完——系统并不会自动知道，除非你显式声明。于是声明式配置的典型失败模式不再是"命令报错，我看得见"，而是"命令全都成功了，但服务是坏的"。这是一种更贵、更隐蔽的失败。你现在应该能理解我为什么说声明式不是银弹：它用"配置的可读性"换走了"执行的可见性"，而你必须用纪律把可见性挣回来——本章后面反复出现的 docker compose config 就是这个纪律的核心动作。

这里插一个悬念，先不回答：如果声明式系统在每次启动时都要"对比现实与期望"，那它凭什么知道一个容器是"符合期望的"？容器存在就算符合吗？镜像还是那个镜像吗？里面的数据库真的能接受连接了吗？这个问题的答案，会在第四节变成你半夜排障时唯一的线索。

回 望

第 04 章我们讲过重启策略（--restart）里的 unless-stopped：它表达的不是"启动一次"，而是"保持运行"。当时我提了一句，说这是"声明式期望状态的雏形"。现在这句话要兑现了——Compose 里的 restart 字段就是同一个概念被写进了文件。第 05 章我们讲 Dockerfile 时说它是基础设施即代码（Infrastructure as Code，IaC）在日常开发中最常见的落地；compose.yaml 是它的同族兄弟，只不过一个描述"镜像怎么长出来"，一个描述"一群容器怎么一起活"。

思 考
  1. 声明式把"怎么做"藏进了执行者内部。这对你来说失去的是什么？在什么情况下你反而必须知道"怎么做"？提示：想想性能调优、想想"为什么它启动要 40 秒"、想想那些"配置写对了但就是慢"的场景。
  2. 如果一份声明式配置可以反复执行且结果相同（幂等），那它是否意味着"环境永远不会漂移"？现实中有哪些漂移是配置文件管不到的？
  3. 命令式世界里，"回滚"是执行反向动作；声明式世界里，"回滚"是换回旧的描述。这两种回滚各自会在什么情况下不彻底？

为什么是 Compose：把咒语抄写成清单

有了上一节的底子，现在可以老老实实做一次对比实验了。我请你真的动手做，不要只是读。我们要搭一个最小的三层应用：一个 Postgres 数据库、一个 Redis 缓存、一个用 nginx 假装的 web 服务（它需要几个环境变量才能"假装"知道自己该连哪里）。先用手工命令，再用 Compose。

实验目的：亲眼看见"命令式在几个服务之后就崩溃"这件事，并算清它崩溃的具体成本。预期现象分两半——前半段你会觉得还行，后半段你会开始烦躁。

docker network create appnet

docker volume create pgdata

docker run -d --name db --network appnet --restart unless-stopped -e POSTGRES_USER=app -e POSTGRES_PASSWORD=devsecret -e POSTGRES_DB=appdb -v pgdata:/var/lib/postgresql/data postgres:16

docker run -d --name cache --network appnet --restart unless-stopped redis:7-alpine

docker run -d --name web --network appnet --restart unless-stopped -p 8080:80 -e DB_HOST=db -e DB_PORT=5432 -e DB_NAME=appdb -e REDIS_HOST=cache nginx:1.27-alpine

这是四条 docker run 加两条前置命令，一共六条。现在把它们抄进一张纸，然后把纸撕掉，只凭记忆重敲一遍——你会发现自己在两个地方犹豫：卷名到底是 pgdata 还是 pg_data，环境变量的名字到底是 DB_HOST 还是 DATABASE_HOST。这两处犹豫，就是你未来的两次事故。跑完可以用 docker ps 确认三个容器都在跑。

现在把同一件事写成 compose.yaml。请新建一个空目录（比如 D:\lab\ch08），把下面这份文件存成 compose.yaml，然后在同一目录里执行启动命令。

name: ch08lab

services:
  db:
    image: postgres:16
    restart: unless-stopped
    environment:
      POSTGRES_USER: app
      POSTGRES_PASSWORD: devsecret
      POSTGRES_DB: appdb
    volumes:
      - pgdata:/var/lib/postgresql/data

  cache:
    image: redis:7-alpine
    restart: unless-stopped

  web:
    image: nginx:1.27-alpine
    restart: unless-stopped
    ports:
      - "8080:80"
    environment:
      DB_HOST: db
      DB_PORT: "5432"
      DB_NAME: appdb
      REDIS_HOST: cache

volumes:
  pgdata:

注意三件事。第一，顶层的 name 指定了项目名，它会影响后面所有自动生成的资源名（网络叫 ch08lab_default，卷叫 ch08lab_pgdata）——这是第 06 章讲过的命名规则在 Compose 里的体现。第二，db 和 cache 都没有端口映射，因为它们只需要被同一项目里的服务看见，不需要被你的浏览器看见。第三，environment 里我特意用键值对写法而不是列表写法，具体原因第三节讲。

docker compose up -d

你会看到 Compose 依次输出：创建网络 ch08lab_default、创建卷 ch08lab_pgdata、创建三个容器。整个过程不需要你说"先建网络"——它从服务之间的引用里自己算出了这件事。启动完成后 docker compose ps 会给你一张表，包含容器名（形如 ch08lab-web-1）、镜像、状态和端口。注意容器名里带了一个数字 1：因为一个服务可以有一个以上的副本，名字必须留出空间。

现在做那个最关键的对比。请你像老师检查作业一样，逐条回答下面这些问题。第一，这六条命令里有哪些参数被抄错了会导致什么后果，你当时能立刻发现吗？第二，如果同学问你"这个项目用了哪几个组件、它们怎么连的"，你是让他看你的六条命令，还是让他读这三十行 YAML？第三，如果三个月后要改数据库密码，你要在几个地方改？第四，如果要把这套环境搬到实验室的另一台电脑上，你要复制的是命令历史还是这个目录？第五，如果你不确定一份配置合并后到底长什么样，你有什么办法确认？

前四问的答案都会指向同一个方向：命令的问题不在于长，而在于它没有"世界的样子"。一份 YAML 里，服务的数量、名字、连接关系、端口、卷全部是可见的；一条命令里，只有"这个容器"。这就是 Compose 存在的第一层理由：它给的是一份可以被读、被评审、被 diff 的东西。而第五问的答案，是本章最重要的方法论，我留到第六节专门讲。

方 法

把"手工命令"翻译成声明式配置时，有一个非常好用的动作：先写注释，再写字段。你可以在 compose.yaml 顶部用 # 写下这个应用的意图（"三层：web 对外，db 与 cache 只对内；数据必须落盘；开发期不需要认证"），然后一个服务一个服务地填。写完之后读一遍注释和字段，问自己"这段话能不能从下面的字段里推出来"。推不出来的部分，往往是配置的缺口。这个动作的深层意义是：配置文件的第一读者是人，第二读者才是机器。

易 错 点

初学者最常见的 Compose 事故，是在项目目录里已经有旧容器的情况下反复改配置。改了 ports、改了 volumes、改了 image 之后直接 docker compose up -d，然后发现"我的改动没生效"。原因是：Compose 认为这些容器已经存在，只做增量收敛，很多字段（特别是 ports 和 volumes）不会在旧容器上被修改。正确的动作是 docker compose up -d --force-recreate，或者干脆 docker compose down 之后重来。自查方法：把 docker compose config 的输出和你以为的配置对一遍，再看 docker inspect 里容器的实际配置，两者不一致就是这个问题。

回 望

第 04 章我们把 docker run 的参数比作一套心智拼图：-d、-p、-v、-e、--network、--restart。现在你可以把那张拼图直接贴到 YAML 上：-e 变成 environment，-v 变成 volumes，-p 变成 ports，--network 变成 networks，--restart 变成 restart，--name 变成服务名加项目名前缀。第 07 章你自己敲过的 docker network create appnet，现在被 Compose 自动完成了——它默认就给项目建一个专属网络。你并没有失去控制权，只是把这个决定交给了默认值，而默认值是可覆盖的。

compose.yaml 的骨架：从顶层到服务

这一节我们正式拆解文件结构。目标不是让你背字段表——背不完，也不该背——而是让你建立一张地图：遇到一个需求时，知道该去文件的哪一层找答案。YAML 本身是一种用缩进表示层级的文本格式，它的语法陷阱我在后面会单列一个折叠块。

骨架·上：一个项目由哪几类东西组成

compose.yaml 的顶层有几个键，它们的地位是并列的：services、networks、volumes、configs、secrets，外加可选的 name。services 是唯一必填的，其他都是"你在下面引用了，就在这里声明"的登记处。这种"引用必须先登记"的设计在配置语言里很常见，它的好处是配置不会悄悄地创建你不认识的东西。

顶层键它在说什么不写会怎样
name项目名，决定自动生成的资源名前缀取当前目录名，改名目录会造出一套新资源
services这个应用由哪些逻辑单元组成没有可启动的东西，Compose 直接报错
networks需要几条自建网络、用什么驱动Compose 自动建一条名为"项目名_default"的 bridge 网络，所有服务都接在上面
volumes需要几个具名数据卷服务里引用到的具名卷会报错；匿名卷仍可用但难以管理
configs要挂进容器的非敏感配置文件你只能靠卷或绑定挂载带配置文件进去
secrets要挂进容器的敏感内容你只能靠环境变量传密钥，而这有明确的代价

这里有一个很多人第一次会困惑的点：服务（service）不是容器。服务是"应该有几个副本、用哪个镜像、暴露哪个端口、依赖谁"这样一份期望；容器是这份期望在某一台机器上被实现出来的具体产物。第 02 章我们说服务与容器的关系像"岗位"与"某位在岗员工"：岗位描述的是职责，员工是此时此刻承担职责的那个人。员工离职了岗位还在；你把容器删了，服务定义仍然躺在文件里，再 up 一次就又有一位新员工上岗。理解这个区别，你才能理解为什么 docker compose scale web=3 是有意义的（同一个岗位三个人），而 docker rename 是没意义的（你改不了岗位定义）。

骨架·下：服务级最常用的那十几个字段

服务下面的字段很多，但真正每天都会用到的就是十几个。我按"你遇到什么问题就找哪个字段"的顺序排列，而不是按字母顺序——这样它更像一张索引，而不是一本字典。

字段解决什么问题要点
image用哪个现成镜像不写标签等于 latest，生产上等于赌博
build镜像要自己构建可写字符串（上下文）或对象（context、dockerfile、args、target）
command / entrypoint覆盖镜像里的默认启动命令command 对应 Dockerfile 的 CMD，entrypoint 对应 ENTRYPOINT
ports把端口发布到宿主机只在需要外部访问时写；写法是"宿主机:容器"
expose声明容器监听的端口（仅文档性质）它不发布端口，很多老教程把它和 ports 搞混
environment往容器里注入环境变量支持列表与键值对两种写法，键值对更可读
env_file从一个文件批量注入环境变量适合放不需插值的成批变量
volumes挂载数据卷或宿主机目录短语法简洁，长语法能表达 read_only 等更多意图
networks接入哪些网络、用什么别名不写就接入默认项目网络

restart退出后是否自动拉起unless-stopped 是最常用的选择
deploy.resources.limits限制 CPU 与内存对应第 04 章讲过的 cgroups 资源限制
profiles按场景决定是否启动让一份文件服务多种用途
user / working_dir以哪个用户、在哪个目录里跑非 root 运行是安全基本功，第 09 章展开
labels给容器打元数据标签用于分类、监控筛选、CI 标记

我想特别讲讲 build 和 volumes 这两个字段的写法差异，因为它们能很好地说明"短语法与长语法"这件事的一般规律。看下面两段。

services:
  api:
    build: ./api

  api2:
    build:
      context: ./api
      dockerfile: Dockerfile.dev
      args:
        NODE_ENV: development
      target: builder

  store:
    volumes:
      - pgdata:/var/lib/postgresql/data
      - ./nginx.conf:/etc/nginx/conf.d/default.conf:ro

  store2:
    volumes:
      - type: volume
        source: pgdata
        target: /var/lib/postgresql/data
      - type: bind
        source: ./nginx.conf
        target: /etc/nginx/conf.d/default.conf
        read_only: true

api 与 api2 是同一个东西的两种写法：短语法只能表达"上下文在哪"，长语法能表达用哪个 Dockerfile、传什么构建参数、停在哪个构建阶段（第 05 章的多阶段构建在这里被 Compose 引用）。store 与 store2 同理：短语法里那个结尾的 :ro 就是长语法的 read_only，但长语法还能表达绑定挂载的传播行为、卷的子路径等更细的选项。规律是：短语法为常见情况服务，长语法为精确意图服务。两者都能跑，选哪个取决于你想让配置多"自解释"。

易 错 点

两个关于卷的高频坑。第一，- pgdata:/var/lib/postgresql/data 里的 pgdata 看起来和本地目录没什么区别，但它指的是"具名卷"，而且必须在顶层 volumes 里登记；如果你写成 - ./pgdata:/var/lib/postgresql/data，它就变成了绑定挂载，把宿主机当前目录下的 pgdata 目录挂进去——第 06 章讲过这两者在行为、权限、跨平台表现上的区别。第二，在 Windows 上用绑定挂载时，相对路径 ./data 能正常工作，但一旦写成绝对路径就要注意盘符形式的差异；如果你不确定最终挂载了什么，docker compose config 会把解析结果打出来给你看，别猜。

展开：YAML 的四个语法陷阱，以及为什么配置语言总在"人性化"和"无歧义"之间摇摆

第一个陷阱是缩进。YAML 用空格缩进表示层级，不允许用 Tab 字符。你在编辑器里看着一样对齐的两行，如果一行用了 Tab，解析器会直接报错，而且报错信息常常指向别处。建议在编辑器里把 Tab 自动转成两个空格。

第二个陷阱是布尔值的歧义。YAML 有一批"看起来像字符串其实不是"的写法：no、yes、on、off、true、false。如果你写了 PASSWORD: no，读到的可能不是你想要的字符串。所以凡是环境变量的值，一律加引号：写成 POSTGRES_PASSWORD: "123456" 而不是裸写。我上面示例里的 DB_PORT 故意写成 "5432"，就是这个原因——不引号的话它容易被当成整数，而环境变量只能是字符串。

第三个陷阱是冒号。冒号后面必须有一个空格，KEY:value 和 KEY: value 不是一回事。这也意味着当值本身包含冒号（比如 "127.0.0.1:5432" 或者 cron 表达式）时，加引号更安全。

第四个陷阱是"看起来像列表项的字符串"。以短横线加空格的写法在 YAML 里是列表标记，如果某个值恰好以 "- " 开头，就必须加引号。

关于 version 字段，我要专门说一句，因为你在网上会看到大量写着 version: "3.8" 的示例。Compose 文件规范的这个版本字段在新版本的 Compose 里已经不再需要，官方现在的建议是不写它。你照抄老教程时看到它，不必惊慌，但也不必跟着写。至于示例里的其他字段，请养成一个习惯：看到不认识的字段，先去 docker compose config 里验证它是否被接受，再决定用不用。拼错的字段名会让你付出很长时间的排查代价，而 config 会立刻告诉你答案。

前 瞻

你在这一节学的每一个概念，都有一份几乎同名的对应物在 Kubernetes 里等着你：services 对应 Service 与 Deployment，volumes 对应 PersistentVolumeClaim，healthcheck 对应探针（probe），environment 对应 ConfigMap 与 Secret，name 对应命名空间（Namespace）。第 12 章我们会把这张对照表完整铺开。现在先埋一句：K8s 难学，往往不是因为它的概念新，而是因为学它的人不知道自己已经在 Compose 里见过同构的东西。

自动网络与服务名：DNS 替你搬走的那块砖

第 07 章最让你有收获的实验，大概是在容器里用服务名访问另一个容器：在默认网桥上失败，在自定义网络上成功。现在回头看那个实验，Compose 悄悄替你做了三件事。

第一件：建网络。上一节 docker compose up -d 输出里那一行"创建网络"，就是 Compose 为项目建的 bridge 网络。默认情况下所有服务都接入它，所以服务之间天生互通，你不需要写任何 networks 字段。第二件：注册名字。每个服务被创建时会把名字注册进 Docker 内置的 DNS；具体来说，服务名本身可用作别名，容器名（形如"项目名-服务名-序号"）也可用。第三件：隔离。项目网络是项目专属的，你的 ch08lab 项目里的 web 解析不到隔壁项目的 db——两个项目即使服务重名也不会串线。

这三件事加起来，直接回答了一个从第 07 章一路追过来的问题：为什么容器之间要连 db:5432 而不是 localhost:5432？因为 localhost 在容器的网络命名空间里指的是"这个容器自己"。你的 web 容器里没有跑 Postgres，当然连不上。这不是 Docker 故意为难你，这是网络命名空间的必然结果——每个容器一套独立的网卡、路由表和端口空间，localhost 是其中最私密的那一个地址。而 db 能被解析，是因为 Docker 在 127.0.0.11 上跑了一个内置 DNS 服务器，专门为自定义网络里的容器服务。

易 错 点

"内部连接不需要发布端口"这件事，我说十遍都不过分。很多同学写完 compose.yaml 之后，习惯性地给数据库也加上 ports: - "5432:5432"，理由是"不然连不上"。结果有两个：一是宿主机 5432 被占用，如果你同时跑两个项目就会冲突；二是你把数据库暴露给了宿主机可达的所有网络，而它可能只有一个开发用的弱密码。正确做法是：只有需要从宿主机或外部访问的服务才写 ports。你在宿主机上用数据库客户端调试时确实需要它，那就把它留在覆盖文件里（第五节讲），而不是焊死在基础文件里。

顺便解释一个你迟早会撞上的现象。有些服务需要一个"人能访问的管理界面"，比如数据库的网页客户端。它属于"我偶尔要看一眼"的东西，不属于应用本体。如果把它写进基础文件，每个人每天 up 都会多起一个容器；如果不写，你调试时又得单独敲一条 docker run。这个两难，第七节的 profiles 就是专门为它准备的答案。先记住这个场景，我们到时回来兑现。

思 考
  1. Compose 用服务名做 DNS 是"方便"，但它也意味着任何接入同一网络的服务都能解析到任何其他服务。这种"默认全互通"是安全的设计吗？如果你想让 web 连不上 db 的管理端口，你会怎么做？
  2. 如果服务名解析依赖一个内置 DNS 服务器，那这个服务器自己挂了会怎样？你的应用该怎么设计才能不把全部身家押在"启动时解析一次"上？
  3. 第 07 章讲过 host.docker.internal 可以让容器访问宿主机。那么在 Compose 场景下，什么情况下你反而需要它？它和"用服务名"在架构含义上有什么本质区别？

依赖与配置：让一群服务真正跑起来

前面几节讲的是"文件怎么写"。这一节讲的是"为什么写对了还是跑不起来"，以及"哪些值不该出现在这份文件里"。这两件事看着不相关，其实同源：它们都涉及"服务之外的东西"——一个是别的时间点上的服务，一个是别的地方存的值。

depends_on 的陷阱与三层解法

现在揭晓我在第一节埋的那个悬念。声明式系统每次启动都要对比现实与期望，那么它凭什么认为一个容器"符合期望"？最朴素的答案是：容器在跑就算。而这个朴素答案，正是初学者在 Compose 里踩得最惨的一个坑。

我们先复现这个坑。请把下面的内容写成一份新的 compose.yaml（或者在之前的文件上加），然后启动，然后立刻看 web 的日志。

services:
  db:
    image: postgres:16
    environment:
      POSTGRES_USER: app
      POSTGRES_PASSWORD: devsecret
      POSTGRES_DB: appdb

  web:
    image: python:3.12-alpine
    depends_on:
      - db
    command: python -c "import socket,time; socket.create_connection(('db',5432),timeout=2); print('connected')"

这条 command 做的事非常纯粹：尝试在 2 秒内连上 db 的 5432 端口，成功就打印 connected，失败就抛异常退出。启动之后用 docker compose ps 看状态，你很可能会看到 web 已经退出（Exit 1），而 db 显示 Up。如果你第一次跑就成功了，别高兴，把 docker compose down 之后连续跑三次——这个坑的特点是偶发，取决于你的机器那一刻有多快。

思 考
  1. 为什么 depends_on 明确写了依赖，web 还是会连不上？请用"进程已启动"和"端口已就绪"这两个词解释这件事，而不是说"Compose 有 bug"。

揭晓答案。depends_on 默认保证的是启动顺序，不是就绪状态。它做的事是：先把 db 的容器创建并启动，再创建并启动 web 的容器。请体会这两句话的差距——"db 容器启动了"意味着一个 postgres 进程被创建了；但 PostgreSQL 从被创建到能接受 TCP 连接之间，还要经历初始化数据目录、建立共享内存、启动后台进程、打开监听套接字这一串步骤。对一个全新的数据目录，这个间隔在你笔记本上大约是几百毫秒到几秒；如果数据目录里已经有一堆数据要做崩溃恢复，它会更长。而 depends_on 不等这段时间，它只等"容器进入 running 状态"这个事件，然后立刻去启动 web。于是 web 冲上去连接，撞上一个还没开门的数据库，退出码 1。

这个坑的真正教训不在 Compose 里，而在"启动顺序"这个念头本身。当你写下 depends_on 时，你脑子里想的是"我要保证一件事做完再做下一件"，这是一个命令式的念头。但 Compose 给你的只是一个顺序提示，它无法把"做完"这个概念读出来——因为"做完"需要一个判断标准，而标准必须由你提供。这就引出了三层解法。我把它们列成一张表，请注意最后一列：越往下走，方案越健壮，而复杂度也在转移。

层次做法它保证什么它不保证什么什么时候够用
零：什么都不做不写依赖，让应用自己崩什么都不保证一切。但你被迫直面失败几乎不用。除非你能接受手工重启
一：depends_on（短写法）只列服务名容器创建与启动的先后服务是否可接受连接依赖方启动极快，或本身能重试
二：depends_on + condition + healthcheck给被依赖方定义健康检查，依赖方等它 healthy被依赖方通过了你的健康判定后才启动依赖方依赖方在运行中途挂掉；健康判定的准确性编排单机环境、演示、本地开发
三：应用自身重试与容错代码里做带退避的连接重试，失败不致命无论依赖何时就绪、何时重启，最终都能连上需要你写代码，且要有上限与日志生产环境的基本要求

现在看第二层具体怎么写。关键动作是给 db 加一个 healthcheck，然后把 depends_on 从列表写法换成对象写法。

services:
  db:
    image: postgres:16
    environment:
      POSTGRES_USER: app
      POSTGRES_PASSWORD: devsecret
      POSTGRES_DB: appdb
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U app -d appdb"]
      interval: 5s
      timeout: 3s
      retries: 10
      start_period: 10s

  web:
    image: python:3.12-alpine
    depends_on:
      db:
        condition: service_healthy
    command: python -c "import socket; socket.create_connection(('db',5432),timeout=2); print('connected')"
    restart: on-failure

这里每个字段都有明确含义。test 是"用什么命令判断健康"，pg_isready 是 Postgres 官方镜像里就带的探测工具，它连上数据库回答"能否接受连接"。interval 是检查间隔，timeout 是单次超时，retries 是连续失败多少次才判为 unhealthy，start_period 是"启动宽限期"——在这段时间内失败不算失败，给数据库留出初始化的时间。换成 condition: service_healthy 之后，web 的容器会一直等到 db 变 healthy 才被创建。再跑三遍，你会看到 web 稳定地打印 connected。这正是第 05 章讲过的 HEALTHCHECK 概念，在 Compose 里的写法。

但第二层不是终点，有三个理由。第一，健康检查是"抽样"而非"保证"：它每 5 秒问一次，数据库完全可能在你依赖它的那一刻刚好在做 checkpoint 而短暂卡住。第二，它只管启动那一刻：web 跑了六个小时，数据库被重启，这时 depends_on 早就退场了，谁负责重连？第三，它把可靠性绑在了编排工具上：一旦你离开 Compose，这套等待逻辑就得重写一遍。

第三层——应用自己的重试——才是唯一能跟着代码走的方案。思路很简单：连接失败不是"异常"，而是"常态之一"；把"连上数据库"写成一个会重试、会退避、会有上限、会打日志的过程。退避（backoff）指间隔逐渐加长，比如 1 秒、2 秒、4 秒、8 秒，上限 30 秒。为什么要退避？如果依赖方正被一千个客户端同时猛敲，固定间隔的密集重试会变成压垮它的最后一根稻草——分布式系统里非常经典的一种自伤。上限则是为了避免你的服务永远卡在"正在重试"，让运维分不清它是死了还是在等。

这里有一句我想让你抄在笔记本上的话。

依赖不是"等它准备好"，而是"它随时可能不在"。

这句话的分量，你要到第 10 章读十二要素应用（The Twelve-Factor App）时会再体会一次：那份方法论里有一条叫"后端服务视为资源"，说的就是数据库、缓存、消息队列这些外部依赖应该被当成可以随时替换、随时掉线的附加资源，而不是你程序里那个理所当然存在的东西。第 12 章讲 Kubernetes 时你还会再遇到它：K8s 会不断重启、迁移、杀死你的容器，任何假设"我的邻居永远在"的设计都会当场碎掉。

回 望

第 05 章讲 HEALTHCHECK 指令时我留过一句：unhealthy 不会让容器自动重启，它只是把事实记录下来，供你、供 Compose、供编排系统决策。那个"供 Compose 决策"当时还是张空头支票，现在你要亲手兑现它——Compose 里 healthcheck 字段写的是同一种健康判定，而 depends_on 的 condition 正是它的消费者。同一个概念在 Dockerfile 里声明、在 Compose 里被消费，这种"一个机制横跨两个层次"的配合，是这套工具链的常态。

展开：健康检查该检查什么？一个从"能连上"到"能干活"的梯度

很多人写健康检查时只写"进程还在吗"，这几乎没有信息量。往深走，健康检查有三个层次，它们对应三个不同的用途，混用会出大问题。

第一层叫存活（liveness）：这个进程还活着吗？判据往往极简，比如一个 HTTP 接口返回 200。它的用途是"如果它死了，请重启它"。

第二层叫就绪（readiness）：这个实例现在能接受请求吗？判据通常包含依赖状态，比如"数据库连接池可用、缓存能 ping 通"。它的用途是"如果不能，请先不要把流量给它"。

第三层叫深度检查（deep check）：它真的能完成一次业务动作吗？比如真的执行一次只读查询或写一条心跳记录。代价是它会消耗资源，而且会把依赖的抖动传导成自己的不健康。

Compose 的 healthcheck 只有一个概念，不区分存活与就绪，所以你要自己决定把它当哪一种用。如果你把它当就绪用（推荐给"被依赖方"），判据应该包含依赖；如果你把它当存活用（适合"服务本体"），判据就应该尽量简单，否则一个外部依赖的抖动会让你的容器被判成不健康，触发不必要的重启，而重启并不能修好别人的数据库。把别人的病当成自己的病来治，是健康检查最常见的误用。

易 错 点

三个关于 depends_on 与 healthcheck 的事故模式。第一，depends_on 的短写法（只写服务名列表）和对象写法（带 condition）看起来差别很小，但行为差别巨大，请务必用 docker compose config 确认你写的那份最终是什么样子。第二，别把 condition: service_started 误当成"就绪"，它和默认行为基本等价。第三，也是最隐蔽的一个：健康检查失败不会让容器自动重启，它只是把事实记录下来（这在第 05 章讲过）。所以如果你指望"unhealthy 会自动拉起"，你会等来一个永远不健康但永远在跑的容器。要让它重启，你得自己配 restart 策略或让应用自己退出。

方 法

面对"服务之间谁先谁后"这类问题，有一个通用的思考动作：把"顺序"改写成"条件"。命令式思维问"我先做 A 再做 B"，声明式思维问"B 需要 A 满足什么条件"。前者只能得到一个时间上的先后，后者得到一个可以被检查和重试的判据。这个改写动作不只适用于 Compose：你在写脚本、写 CI 流水线、写部署手册时都可以用它。凡是你能写出条件的依赖，就能自动等待；凡是只能写成顺序的依赖，就只能靠祈祷。

配置与密钥：三个放变量的地方，和一条纪律

上一节我们讨论的是"服务之间的时间关系"，这一节讨论"值和环境的关系"。Compose 里放变量的地方有三个，初学时最容易混成一团。先把它们分开定义清楚，再讲它们怎么相互作用。

第一个地方是 .env 文件。它在项目目录里，Compose 启动时会自动读它，作用范围是 Compose 自己——也就是"用来渲染 compose.yaml 的那些变量"，它最主要的用途是支持 compose.yaml 里的 ${变量名} 插值。第二个地方是服务下的 env_file 字段，它指定一个或多个文件，把里面的键值对注入到容器进程的环境里。第三个地方是服务下的 environment 字段，也是注入到容器进程的环境，但值直接写在 compose.yaml 里。

.envCompose 自己，用于插值与默认值项目级的可变开关：端口号、镜像标签、项目名不能，如果里面含密钥
env_file 指向的文件容器进程的环境成批的、不需要插值的运行时配置不能，如果里面含密钥
environment容器进程的环境明确、少量、希望一眼看见的变量能，只要不含密钥
secrets以文件形式挂进容器密码、令牌、证书原文不能，但可以进"来源声明"

插值的写法有两种，都值得记：${VAR} 表示"用这个变量，如果没定义就报错或留空"，${VAR:-default} 表示"用这个变量，没定义就用 default"。第二种在实际项目里价值极高，因为它让配置文件可以有一个安全的默认行为：没有 .env 也能跑起来，只是用开发默认值。

services:
  web:
    image: nginx:${NGINX_TAG:-1.27-alpine}
    ports:
      - "${WEB_PORT:-8080}:80"
    environment:
      DB_HOST: db
      DB_PORT: "5432"
      LOG_LEVEL: ${LOG_LEVEL:-info}
    env_file:
      - .env.app

这份配置在三种情况下都能跑：有 .env 且定义了 NGINX_TAG，就用你指定的标签；没有 .env，就用 1.27-alpine、8080、info 这三个默认值。.env.app 里放的是"不需要被 Compose 读、只需要被应用读"的变量，比如应用自己的功能开关。注意 environment 里的值优先写死或用 ${...} 显式引用——把两种机制混着用而不加区分，是困惑的主要来源。

方 法

关于"谁是最终生效的值"这个问题，正确的态度不是背规则，而是打印出来看。在项目目录里运行 docker compose config，它会输出一份把插值、默认值、多文件合并全部应用完毕的最终配置。这是本章最重要的方法：不要猜配置，打印它。配置文件的复杂度来自"多个来源叠加"，任何人在心里模拟三层叠加都会出错，而机器不会。把这条纪律扩展到 Docker 之外也一样管用：只要一个系统由多层配置叠加而成（nginx 的 include、Git 的 config、Kubernetes 的 patch），就一定有办法把"最终生效值"打印出来。找到那个办法，是你从初学者变成老手的分水岭。

关于 env_file 与 environment 谁覆盖谁，我要非常克制地说话：不同版本的 Compose 在这件事上的行为有过调整，env_file 里的变量是否参与 compose.yaml 的插值也随版本变化。所以我不给你一个可能过期的结论，我教你自己验证：同一个变量在两处给不同的值，跑一次 docker compose config，再进容器用 printenv 看一眼真实环境，二十秒就有答案——而且这个答案是你机器上、你这个版本上的真答案。

docker compose config

docker compose exec web printenv DB_HOST

docker compose exec web printenv POSTGRES_PASSWORD

第一条命令打印最终合并结果，你能在里面看到插值后的端口、镜像标签、以及所有环境变量。第二条命令进到运行中的 web 容器里读一个变量。第三条命令如果你在写真实项目时这样用，请立刻停下——把密钥打到终端上会进入你的命令历史、终端回滚缓冲、也许还有录屏。

现在讲纪律。密钥（secret，指密码、令牌、私钥、证书这类一旦泄漏就得换掉的东西）的纪律只有一条，但它有三个具体动作。第一条纪律：密钥永远不进版本库。对应的具体动作是写 .gitignore。

# .gitignore 里至少要有这几行
.env
.env.*
!.env.example
*.pem
*.key
secrets/

前三行的逻辑是：忽略所有 .env 及其变体，但 !.env.example 是一个"反向规则"，把模板文件重新纳入版本控制。这是最实用的一招——你提交一份只含变量名和假值的模板，别人复制成 .env 填真值。后三行是防止你把证书和私钥顺手扔进仓库。

# .env.example —— 可以进 Git 的那一份
POSTGRES_USER=app
POSTGRES_PASSWORD=change_me
POSTGRES_DB=appdb
WEB_PORT=8080
LOG_LEVEL=info

模板的价值在于它同时是文档：新人拿到仓库，读 .env.example 就知道要配哪些变量，不必问你。把它当成 API 文档来维护——变量增删了，模板跟着改。

第二条纪律：密钥不要写进镜像。第 05 章讲 ARG 和 ENV 时我说过：ARG 的值会留在构建历史里，可以用 docker history 看到；ENV 写入的值会永久留在镜像里，任何拿到镜像的人都能 docker inspect 出来。Compose 的 secrets 字段是这条纪律的落地工具之一：它让密钥以文件形式出现在容器里（通常是 /run/secrets 下的一个文件），而不是出现在环境变量和镜像层里。

展开：为什么"环境变量传密钥"也是一种妥协，而不只是最佳实践

你可能听过"十二要素应用推荐把配置存环境变量"，于是以为环境变量传密钥是标准答案。它在"配置与环境解耦"这个目标上确实是最好的选择，但在"密钥保密"这个目标上它是打折的。

原因有三个。第一，环境变量会被继承：任何由你的进程启动的子进程都能看到它，你调用的第三方库也能读到它。第二，环境变量容易泄漏到"非预期的地方"：崩溃转储（crash dump）、诊断接口、某些框架的调试页面、以及 docker inspect 的输出——后两者尤其危险，因为 inspect 的输出经常被贴到 issue 和群里求助。第三，环境变量很难轮换：改一个环境变量意味着要重建容器，而挂载的文件可以在不重启的情况下被替换（虽然应用得支持重新读取）。

所以更完整的分层是：非敏感的配置用环境变量，敏感的值用文件挂载（secrets），而真正的生产环境里，密钥应该由一个专门的密钥管理系统下发，而不是由你的 compose.yaml 提供。这条路的终点在第 09 章会讲得更清楚：密钥管理、最小权限、非 root 运行，是同一个安全思路的三个侧面。今天你要带走的具体结论很简单：如果你的 compose.yaml 里出现了 PASSWORD: "真实密码"，那这份文件就已经不能进 Git 了，而它本来是可以进的。

第三条纪律：在密钥上不要追求"方便"。任何让你"少输一次密码"的机制，都在某个地方替你保存了它：写进文件的密码、记住密码的客户端、导出到环境变量的脚本。你省下的时间，是把风险转嫁给了"所有能读到那个地方的人"。Compose 在这里的取舍很有意思——它本可以像某些工具那样自动注入环境变量，却选择了"把密钥当文件挂"这种更笨、更透明的方式。笨，是因为它要求你的应用会读文件；透明，是因为你随时能看到密钥在哪、谁能读到。

思 考
  1. .env 这么方便，为什么又说它危险？请从"文件会被复制到哪些地方"这个角度列举至少三种泄漏路径。
  2. 如果一份 compose.yaml 完全不含密钥，也不含任何环境相关的值（端口、日志级别都外部化了），它进 Git 还有什么风险吗？
  3. 你的同学把 .env 提交进了公开仓库，五分钟后删掉了。这五分钟造成了什么？他该做什么？
  4. 密钥轮换（定期更换密码）的代价是什么？如果一个系统的密钥轮换需要停机四小时，它实际上会不会被轮换？这对你的架构设计意味着什么？
前 瞻

这一节里出现了三个会在第 10 章长大的种子。第一，compose.yaml 里那些 ${...} 在 CI 里会由流水线的环境变量提供，你的配置一行都不用改——这就是十二要素里"配置存于环境"的收益。第二，secrets 与 .env 的分层，会决定你在流水线里怎么安全地注入生产密钥。第三，你在本地这套"基础文件 + 覆盖文件"的做法（下一节），在 CI 与生产部署里会以几乎相同的形式再现。第 09 章则会从另一头补上：以非 root 用户运行、给容器最小权限、扫描镜像漏洞——那些是"就算密钥没泄漏，也别把整台机器交出去"的功课。

profiles 与多文件：一份文件，多种场景

前面我们一直假设"一份 compose.yaml 描述一套环境"。现实里没有这么简单：你至少需要两套。开发时你想要绑定挂载源码、调试端口、一个能看数据库的管理界面；演示或部署时你想要固定的镜像标签、没有调试端口、只有必要的服务。这一节讲两种处理差异的工具，它们的适用范围不同，很容易被混用，所以先把边界划清。

profiles：同一个文件里的开关

profiles 解决的是"服务级别的有无"。它的规则非常简洁：打了 profiles 标签的服务，只有在对应 profile 被激活时才会启动；没有打标签的服务，永远会启动。激活方式是在命令上加 --profile，或者设置 COMPOSE_PROFILES 环境变量。

services:
  web:
    image: nginx:1.27-alpine
    ports:
      - "8080:80"

  db:
    image: postgres:16
    environment:
      POSTGRES_PASSWORD: devsecret

  adminer:
    image: adminer:4
    profiles: ["debug"]
    ports:
      - "8081:8080"

  seed:
    image: python:3.12-alpine
    profiles: ["tools"]
    depends_on:
      - db
    command: python -c "print('假装在灌测试数据')"

默认情况下，docker compose up -d 只会启动 web 和 db——adminer 与 seed 被跳过。加上 docker compose --profile debug up -d，adminer 才会起来，你可以在浏览器访问 http://localhost:8081 看数据库里的表。想一次激活多个：docker compose --profile debug --profile tools up -d。如果你在浏览器里打不开 8081，先确认自己有没有加上那半个命令——这是最常见的自伤。如果这条命令提示拉不到镜像，先确认 adminer 这个镜像名与标签在你的网络环境下可用，再继续这一节。

docker compose --profile debug up -d

docker compose --profile debug ps

docker compose --profile debug up -d --build

第二条命令值得记住：ps 默认只显示"没有 profile 的服务"加上当前激活的，所以带上同样的 --profile 你才能看到完整的在跑的服务列表。第三条加了 --build，因为调试场景常见"我改了代码想立刻看到效果"。

易 错 点

profiles 有两个必须知道的边界。第一，如果某个被激活的服务依赖一个"没被激活的 profile 服务"，Compose 会报错而不是悄悄帮你启动它——这是好事，因为它不替你猜。反过来，如果你把 db 打了 profile 标签而 web 没有，那默认启动就会失败，因为 web 等不到 db。原则是：被别的服务依赖的基础服务，不要打 profile 标签。第二，profile 名字不是权限机制。任何能改文件的人都能激活任何 profile，它不是"给管理员用的隐藏服务"，它只是为了减少日常噪音。

多文件覆盖：让差异显式地分离

profiles 只能加服务，不能改同一个服务的字段。当差异出现在"同一个服务的不同配置"上时，你需要多文件叠加。Compose 的规则是：如果你在当前目录里放了 compose.yaml 和 compose.override.yaml，那么后者会被自动叠加到前者上，你不需要任何额外参数。想用别的文件名或叠加更多层，就用 -f 显式指定，顺序即叠加顺序。

# compose.override.yaml —— 开发环境专属，不进生产
services:
  web:
    volumes:
      - ./src:/usr/share/nginx/html:ro
    ports:
      - "8080:80"
      - "9229:9229"
    environment:
      LOG_LEVEL: debug

这份文件的意图非常清楚：开发时把本地 src 目录挂进去（改代码立刻生效，不用重建镜像）、多开一个调试端口、把日志级别调高。它之所以叫 override，就是因为它只想"补充和覆盖"基础文件，而不是替代它。注意它与基础文件写得一样简——你只写差异，重复写在两处会让以后改配置的人不知所措。

现在讲本章最重要的方法论，也是我在第二节末尾留的那个问题的答案。多文件叠加的合并规则细节很多：有些字段是替换（比如 image 这种标量），有些是追加或替换（比如 ports、volumes、environment 这些序列），还有各种特殊情况需要 !reset（把这个值清空，回到未设置状态）和 !override（用我这份整体替换，不要追加）这类标签来处理。这些规则随版本演进，细节也容易记错。

所以我不会在这里给你一份"合并规则圣经"。我要给你的是一个动作：把你写的所有文件都交给 docker compose config，让它打印最终结果。这是本章唯一一个我要求你无条件执行的纪律。理由有三条。第一，正确性：你不会因为记错规则而写出一个有微妙错误的配置。第二，可评审性：把你的基础文件和打印结果一起贴进代码评审，别人能看懂"这个环境最终长什么样"，而只贴两份叠加文件是很难读的。第三，可教学性：当你和别人争论"到底哪个值生效"时，你有一个权威答案，不需要靠记忆和资历。

docker compose config

docker compose -f compose.yaml -f compose.prod.yaml config

docker compose -f compose.yaml -f compose.prod.yaml config --services

docker compose -f compose.yaml -f compose.prod.yaml config --format json

第一条会自动叠加 compose.override.yaml（如果存在）。第二条用显式文件列表替代自动叠加，用来做生产环境的预演——我最推荐这个用法：部署前先看一眼最终配置。第三条只列出最终会有哪些服务名，快速确认有没有把不该出现的服务带进来。第四条输出 JSON，方便交给别的脚本处理或做 diff。

关于"一份 compose.yaml 同时服务开发和生产，是好设计还是坏设计"这个问题，我的看法有点反直觉：共享"结构"，分离"差异"，是好设计；试图共享一切，才是坏设计。结构指的是有哪些服务、谁依赖谁、用哪个数据库——这些在开发和生产里应当一致。差异指的是绑定挂载、调试端口、日志级别、副本数、资源上限——这些本来就应该不同，硬把它们统一起来，只会让你在开发时忍受生产的笨重，在生产时带上开发的隐患。判断一份配置有没有走歪，可以问自己：如果把生产文件删掉只留基础文件，它还能安全地跑在本地吗？能，说明基础文件是干净的。

方 法

这一节的方法可以推广成一条通用原则：当你的配置需要"变体"时，先问差异属于哪一类。是"某些组件的有无"？用开关（profiles、条件包含）。是"同一个组件的不同值"？用叠加（覆盖文件、patch）。是"完全不同的两套东西"？那就别硬凑在一份文件里，分开写。把两类差异混在一个机制里，是配置复杂度失控的起点。你会在这套手册的第 10 章和第 12 章反复看到这条原则的不同化身。

命令流与边界：从 up 到该不该上 Kubernetes

前面七节都在讲"文件怎么写"。这一节换到操作台，把日常会用的命令串成一条完整的流程，然后讨论一件很现实的事：Compose 管到哪儿为止。

命令它做什么你会在什么时候用它
up -d构建（如需）、创建网络与卷、创建并启动容器每天开始工作时
up -d --build同上，但强制重新构建镜像改了 Dockerfile 或依赖之后
ps列出本项目容器与状态怀疑"它到底起没起来"时
logs -f 服务名跟踪某个服务的日志排障的第一动作
exec 服务名 命令在运行中的容器里执行命令排障、进数据库客户端
run --rm 服务名 命令为一次性任务新起一个容器跑迁移、跑脚本、跑测试
config打印最终生效的配置改完配置、部署前、有疑问时
build只构建镜像不启动想在启动前确认构建结果
stop / start停／启已有容器，不删除临时让出资源，稍后继续
restart重启容器改了配置需要重新读取时
pull拉取镜像想提前把镜像准备好
top看项目里各容器的进程怀疑有僵尸进程或异常子进程
down停容器、删容器与网络收工时（保留卷）
down -v同上，并删除声明的卷想彻底重置环境时（危险）

表格里有两行要展开，因为它们各自的"危险点"完全不同。先说 down 与 down -v 的区别，这值得一个完整的实验——用第二节那份三服务的文件就可以，它正好有个带具名卷的 db。实验目的是亲眼确认"容器没了"和"数据没了"是两件独立的事：先 docker compose up -d，往数据库里写一条数据，再 docker compose down，然后 docker compose up -d，看那条数据在不在；再把 down 换成 docker compose down -v 重做一遍。

docker compose up -d

docker compose exec db psql -U app -d appdb -c "CREATE TABLE IF NOT EXISTS t(id int); INSERT INTO t VALUES (1);"

docker compose down

docker compose up -d

docker compose exec db psql -U app -d appdb -c "SELECT count(*) FROM t;"

第一遍的结果应该是 count 为 1——数据还在，因为 down 只删容器和网络，具名卷保留了下来（这是第 06 章"数据卷生命周期独立于容器"的直接体现）。现在再执行 docker compose down -v 然后 up，再查一次，你会看到表不存在或查询报错——卷被删了，数据真没了。请把 down -v 当成"格式化硬盘"同等级别的操作，它和你手敲 docker volume rm 是一回事。

再看 run 与 exec 的区别，这个区别在跑数据库迁移时特别重要。exec 是在一个已经在跑的容器里另开一个进程；run 是新起一个容器来执行一次性任务。为什么这件事重要？因为你做数据库迁移时，需要的是"用新版本的代码去改数据库结构"，这个动作必须发生在新镜像上。如果你用 exec 进那个还在跑旧代码的容器里跑迁移脚本，你跑的是旧脚本——于是数据库结构没改到，而你以为改到了。用 run 就没这个问题：它按你指定的服务定义新起一个容器，用的是这份配置当前的镜像。

docker compose run --rm web python manage.py migrate

docker compose run --rm --no-deps web python -c "print('只跑这一个容器，不拉起依赖')"

docker compose exec db psql -U app -d appdb -c "\dt"

第一条是最典型的迁移姿势：--rm 让容器跑完即删，不留垃圾。第二条演示 --no-deps：有时候你只想要一个干净的一次性容器，不想让它把依赖也拉起来。第三条进数据库列出所有表，注意这个反斜杠命令是 psql 自己的语法，不是 shell。这些命令里的服务名必须与 compose.yaml 里的写法完全一致——写错了会得到"no such service"，这也是 config --services 能帮上忙的地方。示例里的 python manage.py migrate 是占位写法，换成你自己的迁移命令即可。

还有几个命令值得一提。docker compose logs -f web 是排障第一动作，因为它把该服务所有副本的日志汇总输出，还能用 --tail 限制行数；docker compose top 让你看见容器里的进程树，遇到"僵尸进程"这类问题时它是唯一的入口（第 05 章讲 PID 1 时提到过）。至于水平扩缩，docker compose up -d --scale web=3 可以让 web 服务起三个副本，但你会立刻撞上两个限制：一是如果你给 web 写了固定的容器名或固定端口映射，多条副本会冲突；二是 Compose 只有一个内置的 DNS 轮询，没有真正的负载均衡与健康摘除。所以"在单机上横向扩展"这件事，Compose 能做，但只能做到玩具级别。这算不算一个信号，提示你该考虑别的工具了？

展开：deploy 段落在单机上到底管不管用？

你在网上会看到大量这样的写法：把资源限制和副本数写在服务的 deploy 段落下面，比如 deploy.replicas 与 deploy.resources.limits。这套写法来自 Docker Swarm 的 stack 部署格式，Compose 沿用了同一份文件规范。

问题在于，不同字段在"docker compose 单机模式"下的行为并不一致，而且随版本变化。比较稳妥的说法是：资源限制这类字段在较新的 Compose 版本里会应用到单机容器上；而 replicas 这种"调度意图"不会被 docker compose up 当回事，它属于 Swarm 的地盘——单机上的正路是 docker compose up --scale。

我不想给你一份"哪个字段生效"的清单，因为那是会过期的东西。我更希望你养成一个动作：写完 deploy 段落之后，用 docker compose config 看它有没有被接受，再用 docker stats 或 docker inspect 看限制有没有真的落到容器上。如果内存上限毫无变化，你的结论就已经得到了，不需要相信任何人（包括我）。顺带一个事实：Docker Desktop 里整个引擎跑在一台虚拟机里，你能给容器的资源总量受这台虚拟机配置的制约。

能力边界：什么时候该转向 Kubernetes

现在讲这一节真正的重点。Compose 的定位可以用一句话概括：它是单机上的多容器编排。注意"单机"这两个字，它不是谦虚，它是边界。在这个边界之内，Compose 非常好用；越过它，Compose 会以失败而不是以报错的方式告诉你"我不行了"。

把这张表翻译成一句判断依据：当你的需求从"把环境搭起来"变成"让环境在机器出问题时自己撑住"时，Compose 就到头了。具体一点，我列出四条我认为足够硬的信号，满足其中任意一条，你就该认真考虑编排系统了。

第一条，你需要不止一台机器。这不只是资源不够的问题，更常见的理由是可用性：你需要一台机器坏掉时服务还在。而 Compose 的配置文件里没有任何地方能表达"这台机器上的东西应该有一份在另一台机器上"。

第二条，你需要不停机地发布新版本。Compose 的发布方式是替换容器，本机上最平滑也只能做到"一个个换"，而这需要你自己写脚本编排顺序、自己处理新旧共存时的流量切换——当你发现自己的发布脚本越来越长时，你其实是在手写一个简陋的编排器。

第三条，你需要"期望副本数"这个概念的持续保障。restart 策略能处理"容器退出了"，但处理不了"节点没了""我需要从 3 个副本变成 5 个并一直保持 5 个"。区别在于：restart 是容器级的自发行为，副本数是集群级的收敛目标。

第四条，你有多个人、多个项目需要隔离与权限。Compose 的项目名隔离只是"名字上的隔离"，任何人都能改文件、看到所有容器的日志。当团队与项目数量增长到需要"谁能做什么"的粒度时，你需要的是命名空间加角色权限模型。

这四条合起来是一句更朴素的判断：不要把 Compose 用成"小 Kubernetes"，也不要把 Kubernetes 用成"高级 Compose"。你的个人项目、课程设计、实验室演示环境、家里那台 NAS 上的自托管服务，Compose 是正确答案，而且是长期正确答案；那个需要 7×24 小时对外服务、有十台机器和五个团队的订单系统，Compose 不是正确答案，勉强用下去只会把复杂度转移到一堆你自己写的脚本里。

前 瞻

第 12 章我们会把这张对照表逐行展开，讲清 Pod 为什么是最小调度单元、Service 的虚拟 IP 是怎么实现的、控制器循环和你今天在 depends_on 里见到的那种"期望与现实的对比"是不是同一件事。你会发现 K8s 的所有核心概念都能在你今天写过的 compose.yaml 里找到影子：services 是它的 Deployment 与 Service 的合体雏形，healthcheck 是它的探针，volumes 是它的 PersistentVolumeClaim，env_file 是它 ConfigMap 的最简陋版本。先学 Compose 再学 K8s 的人，学的是"同一个思想的放大版"；没学过 Compose 直接学 K8s 的人，学的是"一堆需要死记硬背的名词"。这句话是这套手册排章顺序的最重要理由之一。

最后，我要为 Compose 说一句公道话，免得读完这一节你觉得它是个"过渡产品"。它的价值不因边界而减少。它把"环境"这件事从人的记忆里搬进了版本库，让"我这能跑"这个说法第一次变得可验证——同学拿到你的仓库，一条命令就能得到和你一样的世界。这个成就本身就足够大。至于更大的世界，那是下一段旅程的事。

自测：检验你是否真的学懂了

检 查 题
  1. 请用自己的话分别定义命令式与声明式，并指出"复杂度转移"在两者之间是怎么发生的。
    参考答案

    命令式给动作序列，顺序即逻辑，出错要反向回滚；声明式给期望状态，执行者负责收敛。关键在最后半句：声明式没有消灭复杂度，它把复杂度从"执行顺序与失败回滚"搬到了"依赖声明与状态收敛"。所以写声明式时，"有哪些隐含依赖"必须由你显式说出；说不出来，系统只会安静地给你一个坏结果。评分要点：能说出幂等、条件化、失败模式由报错变成静默错误这三层中的两层。

  2. 你运行 docker compose up -d，没有报错，但 web 日志显示连不上 db。请给出排查顺序，并说明每一步在验证什么假设。
    参考答案

    建议顺序：ps 看 web 是否已退出（假设：它起来就崩了）；logs db 看数据库是否初始化完（假设：它还没就绪）；config 看最终生效的环境变量（假设：DB_HOST 的值不是你以为的那个）；exec web nslookup db 验证解析；exec web 里试探 5432 端口（假设：网络通但没人监听）。要点是每一步排除一类可能，而不是随便试。

  3. 预测输出：一份只写了 web 与 db、没有任何 profiles 字段的 compose.yaml，执行 docker compose --profile debug up -d 会怎样？
    参考答案

    照常启动 web 和 db，不报错。profile 只是筛选条件，没有服务被打标签时它对结果毫无影响。要记住的是机制：没打标签的服务永远在启动集合里，profiles 不是"排除条件"。

  4. 这条命令会输出什么？换到写着 depends_on: - db（列表写法）的配置上，输出会变吗？docker compose config | Select-String "condition"
    参考答案

    对象写法里带 condition: service_healthy 时会匹配到那一行；列表写法通常什么都匹配不到。这一题的用意不是让你背合并规则，而是演示那个动作：用 config 打印配置的真实形状，再用文本工具查你关心的字段。换到 Linux 或 macOS 的 shell 里，把 Select-String 换成 grep 就行。

  5. 为什么 Compose 里的数据库通常不写 ports？什么时候需要写？写在哪个文件里更合适？
    参考答案

    不写有两层原因：内部服务靠服务名在同一项目网络里直连，不经过宿主机；而发布到宿主机意味着任何本机能访问的进程都能尝试连接，开发环境密码通常很弱。需要用宿主机客户端工具调试时才写，而且更适合放进 override 文件或调试用的 profile 服务里，让基础文件保持不暴露数据库。

  6. 某同学把 .env 提交到了公开仓库，发现后立刻删除并 force push。这样做有效吗？他之后必须做哪三件事？
    参考答案

    基本无效。公开仓库会被密钥扫描服务持续监视，密钥常在几分钟内就被抓走；force push 也不删除远端历史对象，按提交哈希仍可能读到旧内容。三件事：把文件里出现过的密钥全部轮换（这是唯一有效补救，删历史只是卫生问题）；确认 .gitignore 生效并补上 .env.example；检查这些密钥的权限范围与使用日志。评分要点：必须包含"轮换密钥"。

  7. 项目里有 nginx、Python API、Postgres、Redis，外加一个只在排障时用的数据库网页客户端。请设计文件结构：谁进基础文件、谁用 profiles、哪些差异进覆盖文件。
    参考答案

    基础文件放 web、api、db、cache 四个服务加 volumes 声明，只有 web 发布端口。网页客户端用 profiles: ["debug"]。开发的覆盖文件放源码绑定挂载、调试端口、LOG_LEVEL、db 的调试端口发布——这些是"同一个服务的不同值"，profiles 管不了。生产文件放固定镜像标签、资源上限、去掉调试端口。评分要点：能区分"有无"用 profile、"不同值"用覆盖。

  8. 解释 docker compose run --rm api ... 与 docker compose exec api ... 的区别，并说明数据库迁移为什么用前者。
    参考答案

    exec 在已在运行的容器里另开进程，用的是该容器创建时的镜像；run 按服务定义新起一个容器，用配置里当前的镜像。迁移要用 run，因为你要跑的是新版迁移脚本；用 exec 的典型事故是跑的是旧脚本，结构没改到，新代码上线后报字段不存在。

  9. 给出至少三条"该从 Compose 转向 Kubernetes"的判断依据，并指出 Compose 在哪一条上彻底无力。
    参考答案

    四条依据：需要跨多机调度与容错；需要不停机滚动发布与回滚；需要持续维持"N 个副本"的收敛目标；需要多团队多项目的权限隔离模型。彻底无力的是第一条：CLI 只与本地 dockerd 通信，文件里没有任何语法能表达"另一台机器上也放一份"，跨主机高可用必须在它之外另建机制。评分要点：能指出这是结构性缺失，不是配置没写对。

  10. 现象诊断：同学说"我改了端口映射、重启了容器，浏览器还是访问不到新端口"。请列出至少三种可能原因。
    参考答案

    一，容器没被重建，ports 不会在旧容器上被修改，需要 --force-recreate 或先 down；二，容器内应用监听在 127.0.0.1 而不是 0.0.0.0，端口发布了也无人应答（第 07 章讲过）；三，宿主机端口被占用，或两个项目抢同一个端口；四，改的不是生效的那份文件（当前目录不对，或 -f 指向别处）；五，浏览器缓存或代理。评分要点：至少三条，且包含"容器未重建"。

    参考答案

    可以用现成 nginx 镜像证明连通性：docker compose exec web nslookup db 与 ... nslookup cache 都应解析出地址；再用 docker compose config 证明最终配置里只有 web 有 ports、只有 db 的卷是具名卷。两份证据合起来说明"声明的关系"与"实际的行为"一致——评分看的是有没有可验证的证据，而不是"看起来跑起来了"。

  12. 方案取舍：课程设计要现场演示，你选"手敲 docker run"还是"docker compose up"？分别说出两者的优势与风险。
    参考答案

    手敲的优势是过程可见、便于临场讲解；风险是记错参数、环境差异导致翻车、时间不可控。compose up 的优势是可重复、失败率低，还能顺势展示一份可评审的配置；风险是"一键完成"显得像黑箱，老师可能追问内部发生了什么。务实做法：平时用 Compose，演示时准备好 config 输出当"展开的图纸"。评分要点：两边都给出优势与风险，并给出可执行的折中。

本章总结

  • 命令式交出的是动作序列，声明式交出的是期望状态；后者没有消灭复杂度，只是把它从"执行顺序"搬到了"依赖关系与状态收敛"。
  • Compose 存在的第一层理由是让环境变成一份可读、可评审、可 diff、可版本化的文件，而不是一串躺在 shell 历史里的命令。
  • 服务不是容器。服务是"应该有几个副本、用什么镜像、依赖谁"的期望，容器是这份期望在某台机器上的实现产物。
  • compose.yaml 的顶层是登记处（services、networks、volumes、configs、secrets），服务级字段按"解决什么问题"来找，不必背字典。
  • 短语法服务常见情况，长语法服务精确意图；两者都能跑，选择标准是配置的自解释程度。
  • Compose 自动为项目建一条网络，服务名与容器名都会被注册进内置 DNS，所以内部连接写 db:5432 而不是 localhost:5432，也不需要发布端口。
  • depends_on 默认只保证容器已启动，不保证服务已就绪。这是"启动顺序"与"就绪条件"两个概念的混淆，不是工具缺陷。
  • 依赖处理的四层是：不管、depends_on、健康检查加 condition、应用自身重试。越靠下越健壮，而生产的底线是最后一层。
  • 健康检查要分清存活与就绪两种用途；把别人的病当成自己的病来治，是它最常见的误用。
  • 放变量的三个地方各司其职：.env 给 Compose 插值用，env_file 与 environment 注入容器环境，secrets 以文件形式交付敏感内容。
  • 密钥纪律只有一条但必须彻底：不进版本库、不进镜像、不追求方便。配套动作是 .gitignore 加 .env.example 模板。
  • profiles 管"服务的有无"，覆盖文件管"同服务的不同值"；两类差异混用一个机制，是配置失控的起点。
  • 本章最重要的一个判断：不要猜配置，打印它。多文件叠加、变量插值、默认值的最终结果一律用 docker compose config 验证，这条纪律比记住任何合并规则都值钱。
  • down 删容器与网络但保留卷，down -v 连卷一起删；后者应当被当成"格式化硬盘"级别的操作对待。
  • run 新起容器执行一次性任务，exec 在已有容器里另开进程；数据库迁移必须用 run，因为它要用新镜像。
  • Compose 是单机编排。它不解决跨主机调度、自愈重调度、滚动发布与集群级权限；当需求从"把环境搭起来"变成"让环境自己撑住"，就该考虑编排系统了。

你在这七章里做的事情，其实一直是在把"我知道怎么让它跑起来"变成"任何人都能让它跑起来"。从第一条 docker run，到写出一份 Dockerfile，到给数据找一条活路，到让容器学会互相说话，再到现在把这一切收进一个文件——你交付的东西越来越不像"操作记录"，越来越像"意图"。这中间有一种安静的成就感：你不再是一个记得住命令的人，你成了一个能描述世界的人。下一章我们换一个方向，去讲一件事所有工程师迟早都必须面对、而且越早面对越好的东西：安全。你会发现自己刚刚写下的那些便利——默认全互通的项目网络、写在文件里的密码、以 root 身份运行的服务——都需要被重新审视一遍。

  • Compose 文档总入口官方文档 https://docs.docker.com/compose/ 本章所有内容的正本。先读它的介绍与快速上手，把 up、down、ps、logs、exec、run 与官方描述对一遍；再带一个具体问题去查，比如"profiles 到底该怎么用"。看到一条命令就敲一遍，别只读。
  • Compose 文件参考规范 https://docs.docker.com/compose/compose-file/ 字段语义的权威出处，也是"不要猜、去验证"里那个"验证"的最终依据。读法是查字典式：别从头读到尾（会淹死），用到哪个字段就跳进哪一小节，特别注意官方对"这个字段何时被忽略""短语法与长语法的区别"的说明。即便如此，最终仍以你机器上 config 的输出为准。
  • Compose 官方示例合集实践案例 https://github.com/docker/awesome-compose 真实可跑的多服务项目模板：不同语言的后端配数据库、配反向代理、配消息队列。价值不在"抄一份来用"，而在对照阅读：挑三个你熟悉的语言栈，看它们的 compose.yaml 怎么组织服务、怎么区分开发与生产，然后问自己"我会不会这么写，为什么"。
  • 十二要素应用（中文）方法论 https://12factor.net/zh_cn/ 这份方法论几乎是为容器的世界量身写的，本章至少有三条与它直接对应：配置存于环境（environment 与 .env）、后端服务视为资源（"依赖随时可能不在"）、管理任务作为一次性进程（compose run）。这周先只读这三条，每条读完回自己的项目问一句"我做到了吗，代价是什么"。剩下九条留到第 10 章系统读。
  • Docker 入门教程官方文档 https://docs.docker.com/get-started/ 它的后半部分有一套从"单容器应用"演进到"多容器 Compose 应用"的完整实操。最有价值的部分不是知识点，而是它安排的顺序：它为什么先让你手工敲命令，再让你写 Compose？想明白这个次序，你就理解了本章第一节那两种思维为什么必须按这个顺序出现。
值 得 品 读 的 书
  • 《Docker 开发指南》 Adrian Mouat 著 这本书偏工程实践，讲的正是"如何把 Docker 用于真实开发流程"，也就是本章到第 10 章之间的那段路。别从第一章顺读，直接找多容器与开发流程相关的章节，带着一个问题读："一个团队日常的开发环境该怎么组织，我现在的做法缺了什么？"
  • 《深入浅出 Docker》 Nigel Poulton 著 如果你在本章任何一处觉得概念的位置不稳——比如"服务与容器的关系""声明式到底是什么意思"——回头翻它对应的章节。它薄、图多、讲得清，适合用来重建整体图像而不是补充细节。把它当成本套手册的并行简版，卡住时用它找回方向。
  • 《凤凰项目》 Gene Kim 等 一本用小说形式讲 IT 交付为何如此痛苦的书，和 Compose 没有一句技术交集，但它能回答本章埋在字缝里的问题：为什么"环境必须能被复现"值得用一整套工具去做？读到书里那些因为环境不一致、手工操作、没有版本记录而引发的连锁事故时，你会对 compose.yaml 的意义有一次情感层面的确认。适合通勤或睡前读。
