网络：看不见的城市，容器之间如何说话

所有虚拟网络的尽头，都是虚拟设备与转发规则。

本 章 学 习 目 标
  • 理解网络隔离为什么必须存在：在一个共享的网络栈里，端口、IP 与流量视野会怎样立刻撞车。
  • 建立一张可以推理的网络地图：网络命名空间、veth pair、网桥、iptables 这四层各自负责什么，如何咬合。
  • 能解释数据包从浏览器出发到进入容器的每一步，并指出哪一步出错会表现为哪种故障。
  • 分清五种网络驱动的定位与代价，能判断一个新项目该选哪一种、为什么。
  • 说清默认 bridge 与自定义 bridge 的差别不只是"方便"，而是名字解析、隔离范围与可维护性的整体不同。
  • 理解端口映射的真实机制，以及 127.0.0.1 在容器内外为什么是两个世界。
  • 掌握网络排障的固定顺序，能在十分钟内把"连不上"收敛到一个具体环节。

  • 能读懂 docker network inspect 的输出，指出网关地址、子网与已接入的容器。
  • 能判断一条 -p 参数到底把端口发布到了哪个宿主机地址上，并说出它的安全含义。

  • 能用一个 nginx 容器搭出最小可用的反向代理与轮询负载均衡。
  • 能向同学讲清 VXLAN 的直觉，并说出跨主机网络为什么必须依赖一套控制平面。

上一章我们建好了港口：数据卷让重要的东西活过容器的死亡，你的数据库终于敢放进容器里了。可是当你真的把数据库、缓存、后端和前端四个容器同时跑起来，新的沉默出现了——它们彼此看不见。后端的日志里写着"连接 redis 失败"，前端的日志里写着"上游不可达"，而你盯着四个都是 Up 状态的容器，不知道问题在哪儿。本章要解决的就是这件事：这些木箱之间如何说话。它们是四个进程，跑在同一台机器上，共用同一个内核，却需要一整套虚拟的网络世界才能互相找到；而正是这套"看不见的东西"，决定了你的应用能不能被外面访问、你的服务名会不会在某次重启后失效、你的数据库端口会不会暴露给整栋宿舍楼。学完这一章，你会得到一张能自己推理的网络地图，而不是一串需要背诵的命令。

为什么每个容器都要有自己的网络世界

先把话说清楚：如果不给容器做网络隔离，会发生什么？这不是一个假想的危险，而是你几乎必然会在某个下午撞上的三件事。

第一件是端口冲突。你做了一个小项目：一个 API 服务、一个管理后台、一个监控面板。如果它们共享宿主机的网络环境，那就是三个进程在抢同一个命名空间里的端口表——你的 API 监听 3000，后台也想监听 3000，第二个启动的直接报"地址已被占用"并退出。你想改端口，但改端口要改配置、改前端请求地址、改部署脚本，而且你根本没有理由让它们不冲突：它们是三个独立的应用，凭什么要互相知道对方占用了哪个端口？

第二件是 IP 与主机名冲突。共享网络栈意味着共享主机名、共享路由表、共享 DNS 配置。你手上有一个镜像要给两个不同项目复用，两个项目都要求自己叫 app.local，都要把上游指向 db:5432，但它们的 db 是两台不同的数据库。共享的网络视野里，这个冲突没有任何优雅的解法。

第三件更隐蔽，也更严重：互相嗅探。同一台机器上的进程如果在同一个网络栈里，往往能看到彼此的流量；一个存在漏洞的服务被攻破之后，它可以顺手探测、甚至劫持同宿主机上另一个服务的通信。这在"一台机器只跑一个应用"的年代是可以忍受的，在"一台机器跑二十个租户容器"的今天完全不能接受。

那给每个容器一份独立的网络环境，代价是什么？答案会让你安心：几乎没有代价。因为这份"独立的网络环境"并不是一台虚拟交换机加一张真实网卡，而是内核里的一张表。Linux 内核提供了网络命名空间，它隔离的东西非常具体：网络设备、IPv4 与 IPv6 协议栈、路由表、防火墙规则、端口号（套接字），以及 /proc/net 与 /sys/class/net 这两份目录视图。也就是说，每个网络命名空间里都有一份独立的"我有哪些网卡、我的路由怎么走、我的端口被谁占了"的记录。

比 喻

给每个容器一个网络命名空间，像是给同一栋宿舍楼里的每个房间装一部独立的内线电话：每个房间自己的号码表、自己的通话记录、自己的占线状态，互不干扰。而你要让两个房间通话，就得拉一根线、配一个总机。这就是后面要讲的那三样东西——虚拟网线、虚拟交换机、转发规则。

先做一件最基础的事：亲眼看看容器里的网络视图到底长什么样。下面的命令会在一个临时容器里装上网卡查看工具，然后打印它的网卡清单。注意整条命令写成一行，因为容器里的包管理器（Alpine 用的是 apk）默认没有 ip 命令。

docker run --rm alpine sh -c "apk add --no-cache iproute2 >/dev/null && ip addr"

你会看到两份东西。一份是 lo，回环接口，地址固定是 127.0.0.1/8，它的作用是"只跟我自己说话"。另一份是 eth0，一个以太网接口，地址形如 172.17.0.2/16。请注意三件事：这个地址你从来没有配置过；这个容器也没有任何物理网卡；而 172.17 这个网段在你的宿舍网络里根本不存在。这个地址是被"发"给它的——谁发的，就是接下来两节要回答的问题。

同一个容器里还有一份路由表，它告诉你"要出这个容器，该把包交给谁"：

docker run --rm alpine sh -c "apk add --no-cache iproute2 >/dev/null && ip route"

输出通常是两行：一行说 172.17.0.0/16 这个网段直接可达，走 eth0；另一行说其它所有地址（default）都交给 172.17.0.1。而 172.17.0.1 正是宿主机上那个虚拟交换机的地址。记住这个数字，它是本章后面所有路径分析的起点：容器眼里的"世界之门"，就是宿主机上的 docker0 网桥。

你还可以看到容器自己的主机名，以及它眼里的 DNS 配置。这两样东西在不同网络里的表现差异，恰好是后面几节的主线，先留个印象：

docker run --rm alpine sh -c "hostname; cat /etc/resolv.conf"

hostname 会打印一串十二位的容器 ID，这就是你不在 run 时用 --name 指定名字的后果：名字是随机分配的。cat /etc/resolv.conf 会打印出容器的域名解析配置，你会看到一个很不寻常的地址 127.0.0.11。它不是任何真实的公共 DNS 服务器，而是 Docker 在每个容器的网络命名空间里放的一个"内线总机"。为什么需要它，第六节会给你完整答案。

回 望

第 02 章我们拆开过 Docker 的内部结构，说 dockerd 是那个真正干活的守护进程，负责管理镜像、容器、网络与存储；当时"网络"只是列举里的一个词。现在你看到它的产物了：那个 172.17.0.2 的地址、那个 172.17.0.1 的网关、那份写着自己主机名的 /etc/hosts，全部是 dockerd 在你敲下 docker run 的几百毫秒里，替你向内核申请并配置出来的。第 02 章讲的是"谁在干活"，这一章讲的是"它干了什么"。

这张表里最值得你停下来想一想的是最后一行。网络隔离给的不只是"不冲突"，还有"不被看见"。这也是后面讨论默认网桥为什么故意"不便利"时的关键线索。

这里留下本章第一个悬念，你现在不必回答，但请把它放在脑子里：如果每个容器都被隔离在自己的网络世界里，那"两个容器之间说话"这件事，凭什么能发生？它们之间那条线路是真实的吗？是谁插上的？

思 考
  1. 如果隔离做得再彻底一点——每个容器一个独立的内核、完全看不到彼此——开发体验会变成什么样？这种"彻底的隔离"在什么时候反而是缺点？提示：可以从"调试一个跨容器的问题需要多少步骤"这个角度想。
  2. 端口冲突看起来只是个麻烦，但如果把它当成一种"信息"，它泄漏了什么？换句话说，一个攻击者能不能靠扫描端口冲突来推断宿主机上跑了什么？

没有魔法：四样东西撑起全部容器网络

现在来兑现那句话：所有虚拟网络的尽头，都是虚拟设备与转发规则。这一节我们要把四样东西逐一看清——网络命名空间、veth pair、网桥、iptables。看完之后你会发现，容器网络里没有任何一环是"凭空发生"的。

第一样：网络命名空间（一份独立的网络配置表）

网络命名空间（Network Namespace）不是一个"程序"，也不是一个"设备"，它是一份配置集合：这个空间里有哪些网络设备、IPv4/IPv6 协议栈怎么配、路由表怎么走、防火墙规则是什么、哪些端口被占了。用一句人话说，它回答"你能看见哪些网卡、你的包往哪儿走"。

方 法

面对任何"隔离"机制，问三个问题就能把它拆开：隔离的是什么（资源种类）、颗粒度是什么（谁来承担这份独立配置）、成本付在哪里（内存、CPU，还是可调试性）。网络命名空间隔离的是网络配置，颗粒度是每个容器一份，成本几乎只有内核里的一张小表——代价则是你在宿主机上"看不见"了，排障必须靠一套约定好的工具链。

第二样：veth pair（一根虚拟网线的两端）

veth（Virtual Ethernet Pair，虚拟以太网卡对）永远是成对出现的，像一个管道的两端：你从 A 端塞进一个数据包，它会从 B 端出来。它不能单独存在，也不存在"只有一头的 veth"。这个特性不是限制，而是它的全部用途——它是"跨命名空间通信"的唯一桥梁。

Docker 启动一个容器时做的事是这样的：先建立一个新的网络命名空间，然后创建一对 veth，把其中一头放进容器里改名为 eth0，配上地址（比如 172.17.0.2/16）和一条默认路由；另一头留在宿主机的网络命名空间里，接到一个虚拟交换机上。所以你在容器里看到的 eth0，从来不是"模拟网卡"，它就是一根虚拟网线插在容器上的那一端。你可以从容器内部看到两个描述它身份的原始文件：

docker run --rm alpine sh -c "cat /sys/class/net/eth0/iflink; cat /sys/class/net/eth0/address"

第一行输出一个数字，它指向 veth 另一端在宿主机网络命名空间里的接口编号；第二行是 eth0 的 MAC 地址，因为你没有指定它，所以它由内核随机生成。这两个普通文件摆在 /sys 里，本身就说明容器里的"网卡"是由一串编号和地址描述出来的内核对象，不是什么特殊装置。

另一端长什么样？这需要绕过容器的网络命名空间，直接看宿主机的网络视图，办法是用 --network host 启动容器（在 Windows 上看到的是引擎所在那台 Linux 虚拟机的视图，下一段的折叠块会解释）。

docker run --rm --network host alpine sh -c "apk add --no-cache iproute2 >/dev/null && ip -br link"

你会看到 eth0 之类的"真网卡"、一个名叫 docker0 的网桥接口，以及若干 veth 开头、带随机后缀的接口——后者就是容器里那些 eth0 的另一端。ip -br link 是简写输出，一行一个设备，不会像 ip addr 那样长到占满屏幕。顺带说明：--network host 让这个临时容器直接借用宿主机的网络，所以它连 --publish 都不需要，这就是 host 网络驱动的本质。

到这里，第二个悬念可以揭晓一半了：两个容器之间确实有一条"线"，但它不是网线，而是一对 veth；线的一头在容器里，另一头不在对方容器里，而是去了一个共同的地方。

第三样：网桥（宿主机上的虚拟交换机）

这个"共同的地方"就是网桥。Docker 启动时会在宿主机上创建一个名为 docker0 的虚拟网桥，它是一个软件交换机：凡是通过 veth 接到它上面的接口，都属于同一个二层网络，可以直接互相通信，不需要经过任何外部设备。默认 bridge 网络的子网通常从 172.17.0.0/16 开始，docker0 在其中占一个地址（通常是 172.17.0.1），作为所有容器的网关。

名字也解释清楚了：你创建的每一个自定义网络，Docker 都给你建一座独立的虚拟交换机，互不相通。默认 bridge 上的容器与自定义网络上的容器之所以"看得见网卡却互相连不上"，原因就在这里——它们接在不同的交换机上，而交换机之间没有连线。

那出网怎么办？容器的地址是 172.17.0.2 这样的私有地址，公网无法回包。于是宿主机在放包出去时把源地址悄悄换成自己的地址（这个动作叫源地址转换，Source NAT，简称 SNAT），回来时再换回去。对公网上的服务器来说，它只看得见宿主机的地址，完全不知道后面还有一层容器。

易 错 点

最常见的误判是把"能上网"当成"能被访问"。容器能访问外网靠的是出站方向的地址转换；外面要访问容器，靠的完全是另一套机制（入站的端口转发，也就是 -p）。这两件事没有任何关系，可以一个通一个不通。当你发现"容器里能 curl 通百度，但手机连不上我的网页"时，请不要怀疑网络坏了——你只是还没给入站方向开一扇门。

第四样：iptables（转发规则的载体）

iptables 是 Linux 内核里负责检查、修改、转发数据包的框架（内核部分叫 netfilter，命令行的名字叫 iptables）。Docker 用它做三件大事：出站的地址伪装（SNAT）、入站的端口转发（目标地址转换，Destination NAT，简称 DNAT）、以及不同网络之间的隔离。把它想成宿主机上的交通规则：包不认人，只认规则，规则怎么写，包就怎么走。

这套规则藏在两张表里：地址转换的规则在 nat 表，过滤与拦截的规则在 filter 表。想看它们，用下面这条命令——它借一个 host 网络的容器去看宿主机的规则；如果你本机装了 WSL2 发行版，也可以在 WSL 里直接执行里面的那半条命令：

docker run --rm --network host alpine sh -c "apk add --no-cache iptables >/dev/null && iptables -t nat -L -n | head -40"

你会看到 DOCKER、DOCKER-ISOLATION-STAGE-1、DOCKER-ISOLATION-STAGE-2 三个自定义链。DOCKER 链里那些形如 DNAT tcp dpt:8080 to:172.17.0.2:80 的规则就是端口映射的真身，读作"凡是打到本机 8080 端口的 TCP 包，把目的地址改成 172.17.0.2 的 80 端口"。结尾的 head -40 只是为了别刷满终端；dpt 是 destination port（目的端口）的缩写，认识这一条缩写你就读得懂大部分规则行。

隔离规则更值得看一眼，它回答了一个你迟早会问的问题：既然都在宿主机上，为什么 A 容器连不上 B 容器？

docker run --rm --network host alpine sh -c "apk add --no-cache iptables >/dev/null && iptables -L DOCKER-ISOLATION-STAGE-1 -n"

你会看到一条 DROP 规则，形如"从 docker0 进来的包，如果目标是某个自定义网桥的子网，直接丢弃"。这就是"不同 bridge 网络默认不能互通"的实现方式：不是网卡不可达，而是宿主机主动把跨网络的包丢掉了。理解了这一点，你以后再看 docker network connect 就会觉得很自然——它做的事就是让一个容器同时出现在两座交换机上，绕过这条隔离规则。

展开：为什么在 Windows 上要绕一圈"容器里的容器"才能看宿主机

Windows 没有 Linux 内核，不能原生运行 Linux 容器。Docker Desktop 的做法是在 WSL2 或 Hyper-V 里跑一台真正的 Linux 虚拟机，把 dockerd 放在里面，再把命令行接进去（第 02 章讲过这个结构）。所以有两个完全不同的"宿主机"概念：你的 Windows 电脑，以及真正跑 dockerd 的那台 Linux 虚拟机。容器网络建在后者之上：docker0 网桥、veth、iptables 规则全在那台虚拟机的内核里；用 --network host 启动的容器看到的也是那台虚拟机的视图，而不是 Windows 的视图。两个视图由 Docker Desktop 的一层转发缝合起来，这层缝合也是"端口映射能用、但有时行为与预期略有差别"的原因。想直接进那台 Linux 虚拟机，可以在 PowerShell 里执行 wsl，在那里你能用 ip、iptables、ss 这些原生命令。

高潮：一个数据包从浏览器到你容器的完整路径

场景很具体：你在 PowerShell 里执行了 docker run -d --name web -p 8080:80 nginx，然后在浏览器里打开 http://localhost:8080。屏幕上出现了 nginx 的欢迎页。这中间到底发生了什么？

第 0 步，准备。dockerd 收下这条命令，做了四件事：创建容器自己的网络命名空间；创建一对 veth，一头放进容器改名为 eth0，配地址 172.17.0.2/16，另一头接到 docker0 网桥；在宿主机 nat 表里插入一条 DNAT 规则，把本机 8080 端口的包改写到 172.17.0.2:80；同时插入一条 filter 表规则，允许这个目标地址与端口的入站包通过。到这里，门和路都建好了，只是还没有包出发。

第 1 步，你的浏览器。浏览器把 http://localhost:8080 解析成本机地址 127.0.0.1，向 127.0.0.1:8080 发起一条 TCP 连接。这一步没有任何 Docker 参与：它只是一个普通的本地连接请求，源地址与目的地址都是本机。

第 2 步，出站规则检查与本机路由。数据包在内核里走的是 OUTPUT 链，随后交给路由决策。目的地是 127.0.0.1，也就是本机，于是包不会离开这台机器，它在回环接口上"绕了一圈"之后进入了 nat 表的 PREROUTING 之后的那一段处理链。这里就是 Docker 插入规则的地方：DOCKER 链发现有一条针对 8080 的 DNAT 规则，于是把包的目的地址从 127.0.0.1:8080 改写成 172.17.0.2:80。

第 3 步，转发决策。既然目的地址已经不再是本机，内核就打开 IP 转发功能（这正是 net.ipv4.ip_forward 对容器至关重要的原因），把包从"发给本机"切换到"替别人转发"。

第 4 步，filter 表把关。转发的包要过 FORWARD 链，Docker 在这里插了规则：目标是 172.17.0.2 的 80 端口，属于已发布端口，允许通过。没有这条规则，包会在这里被丢掉——这就是"没写 -p 就一定访问不到"的物理原因。

第 5 步，进网桥。包被送到 docker0 这个虚拟交换机，交换机查它自己的转发表（由 veth 的 MAC 地址学习而来），发现 172.17.0.2 对应某一个 veth 接口，也就是容器那根网线的宿主机端。

第 6 步，过 veth。包从 veth 的宿主机端进去，从容器端出来，出现在容器的网络命名空间里。这是纯粹的"内核内搬运"，不经过任何物理网卡，也不出机器。

第 7 步，容器内核处理。目的地址 172.17.0.2 正是容器 eth0 自己的地址，包被交给监听 80 端口的那个进程——nginx。

第 8 步，应用接收。这里有一道很多人栽过的关：nginx 必须监听在 0.0.0.0:80 上（意思是"所有网卡地址上的 80 端口"）。如果它监听 127.0.0.1:80，包虽然已经正确到达容器的 eth0，却找不到接收者，内核只能回一个连接被拒绝。nginx 官方镜像默认监听 0.0.0.0，所以它是好的；但你自己写的 Python、Node、Go 服务很可能默认只听 127.0.0.1，这就是本章反复要讲的那个高频故障。

第 9 步，回程。nginx 把响应发回源地址——注意源地址已被改写成 172.17.0.1（网桥的地址）。回程包过 veth、过网桥到达宿主机，nat 表的 POSTROUTING 链把它改回 127.0.0.1，于是浏览器看到的响应来自它以为的那个地址。连接成立，页面出现。

九个步骤里，有六个是内核在几百微秒内完成的。你之所以需要知道它们，不是因为要背诵，而是因为每一个环节都对应一类可以观察、可以定位的故障：-p 写错就是第 2 步没有规则；防火墙挡了就是第 4 步被丢；不同网络连不上是第 5 步根本没接到同一座交换机；应用绑定错了是第 8 步无人接收。这句话请记住：

容器网络里没有魔法，只有虚拟设备与转发规则；排障之所以能"有章法"，是因为数据包的路径是有顺序的。

思 考
  1. 在上面这条路径里，哪一步是可以被省掉的？如果 Docker 不做 DNAT，而是直接把容器的地址改成宿主机的地址，会带来什么新问题？提示：想想"两个容器都想用 80 端口"这件事。

五种网络驱动：一张表看清它们各自的用途

上面讲的 docker0 只是其中一种做法。Docker 允许你换"驱动"（driver），也就是换一套连接方式的实现。选驱动很像给电脑选上网方式：走网口、连 Wi-Fi，或者干脆不联网。能做什么、代价是什么，全都不同。常用的有五种。

五种驱动各自的定位

bridge 是最常用的默认值：Docker 建一座虚拟交换机，容器接上去拿到内网 IP，彼此可通，出网靠地址伪装，入站要显式发布端口。99% 的单机场景从它开始就够了。它的行为你已经很熟：容器有 IP、需要 -p、外面看不见它。

host 让容器直接借用宿主机的网络栈——不新建网络命名空间，容器的 80 端口就是宿主机的 80 端口。好处是路径最短：没有 veth、网桥和 DNAT，性能损耗几乎为零。代价是失去隔离：端口直接冲突，容器里的应用能看见宿主机上其它进程的网络行为，也无法再"把 80 映射到 8080"，因为根本不存在两个地址。需要它的场合很具体：极低延迟或极高吞吐的服务、要监听大量端口的服务，以及排查宿主机网络问题的调试容器。

none 更极端：除回环接口外什么都没有，容器只有 lo。它看起来没用，实际用途明确——纯计算任务（批量数据处理、编译、加解密）不该有任何联网能力，以免被利用来外传数据。给只该算数的容器装网卡是扩大攻击面。

overlay 解决"容器不在同一台机器上"的问题：它把多台宿主机上的容器组织进一个虚拟网络，让它们看起来像在同一个局域网里。这是编排系统的地盘，单机用笔记本几乎不会碰；一旦用上多台服务器，它就是必需品。

macvlan 走另一条路：容器直接拿到局域网里的真实 IP，在路由器看来它就是一台独立物理设备，适合必须像物理机一样接入现有网络的应用。代价是占用局域网 IP，且依赖宿主机网卡支持混杂模式——很多无线网卡与云环境并不支持。

驱动独立网络栈独立 IP怎么发布端口真正需要它的场景
bridge有有（内网地址）必须用 -p 显式发布单机绝大多数服务与开发环境
host没有，共享宿主机就是宿主机地址不需要也无法发布对性能敏感、或要监听海量端口
none有，但为空只有 lo无法发布纯计算任务、要求绝对无网络
overlay有有（虚拟网段）由编排层管理跨多台主机的同一应用
macvlan有有（真实局域网地址）不需要，直接暴露必须像物理设备融入现有网络

默认 bridge 与自定义 bridge：名字解析的分水岭

现在回答最实用的那个问题：默认 bridge 和你自己 docker network create 出来的网络差在哪里？第一层差别是名字解析，第二层是隔离范围，第三层是灵活性。最要命的是第一层，所以先做实验，跟着一步步走，不要跳。

案发现场：两个 alpine 容器都接在默认 bridge 上，它们能靠名字互相搭话吗？先起 web，跑 sh 并挂着（之后在它内部下命令）；再起 api，同样挂着。两个命令各放一个终端里更清楚。

docker run -dit --name web alpine sh

你会看到输出一串容器 ID，然后命令立刻返回（-d 是后台运行，-i 保持标准输入打开，-t 分配伪终端）。这里没有指定 --network，所以它接在默认 bridge 上。接着起第二个，写法完全一样，只是名字不同。

docker run -dit --name api alpine sh

同样立刻返回。现在用 docker ps 能看到两个都在跑。接下来这一步，是把问题变成证据的关键：我们要从 web 的"内部视角"去连 api。

docker exec -it web ping -c 1 api

你会看到一行错误，形如 ping: bad address 'api'。注意错误的措辞：bad address，不是"连接超时"，也不是"网络不可达"。这一点极其重要——它说明 ping 连一个 IP 都没能算出来。包根本没有被发出去，因为它不知道该往哪儿发。这就是第 6 节要讲的"名字解析失败"，它与"网络不通"是两类完全不同的故障，排障时第一步就要分清。

猜想：如果问题出在名字上，绕过名字就该能通。api 的 IP 是多少？直接问 Docker。

docker inspect -f '{{range .NetworkSettings.Networks}}{{.IPAddress}}{{end}}' api

你会得到一个 172.17.0.x 形式的地址（具体数字取决于当前有几个容器接着默认网桥）。--format 里那段 {{...}} 是 Go 模板语法，意思是"把网络配置里每一个网络的 IPAddress 字段依次打印出来"。注意它是 range——后面你会看到，一个容器可以属于多个网络，所以这个字段其实是一个集合。现在把 IP 填进去，再试一次：

docker exec -it web ping -c 1 172.17.0.3

把 172.17.0.3 换成你刚刚 inspect 出来的真实地址再执行。这一次你会看到 ping 通了的输出——1 packets transmitted, 1 received，延迟通常在 0.1 毫秒上下，因为这两个包根本没离开这台机器，全在 docker0 上就完成了交换。结论已经很清楚了：路是通的，名字是不通的。同一个默认网桥上的容器能互相通信，但只能靠 IP 地址。

为什么？默认 bridge 的 DNS 服务是关着的，容器里那份 /etc/resolv.conf 直接指向宿主机或外部解析器，根本不认识"api"。更糟的是默认网桥上 Docker 的名字解析只认 --name 显式指定的名字，不认随机名，你连"猜名字"这条路都没有。

同一个故事用自定义网络重讲一遍：先建一座自己的交换机，再让两个容器都接上去。

docker network create mynet

你会看到输出一串网络 ID。默认驱动就是 bridge，所以这条命令等于"给我建一座新的虚拟交换机"。可以用 docker network ls 看到它出现在列表里，名字是 mynet，驱动是 bridge，作用域是 local。现在把两个容器接上去——注意，容器已经在跑了，但要把它们从默认网桥挪到 mynet，最干净的做法是删掉重建，而不是事后硬接（事后硬接的命令我们下一节会讲，它有自己的用途）。

docker rm -f web api
docker run -dit --name web --network mynet alpine sh
docker run -dit --name api --network mynet alpine sh

三条命令依次执行：前两条命令先强制删掉旧容器（-f 会直接杀掉正在运行的容器，只用于这种一次性的实验容器），然后重新创建时加上了 --network mynet。现在重复那个关键测试，看看名字有没有活过来。

docker exec -it web ping -c 1 api

这一次的输出了：PING api (172.19.0.3): 56 data bytes，然后是正常的回包统计。注意括号里的那个 IP——ping 自己告诉你，它已经把名字 api 解析成了 172.19.0.3。这个解析是谁做的？容器里那份 /etc/resolv.conf 指向 127.0.0.11，Docker 在那个网络里放的内置 DNS 服务器应答了这次查询。这也是"自定义网络自动提供名字解析"的全部机制。你可以顺手验证一下解析这一环本身：

docker exec -it web nslookup api

你会看到几行输出，其中 Server 一行指向 127.0.0.11，Name 一行是 api，Address 一行是它的地址。这比 ping 更能证明"名字解析"这件事真的发生了，因为 ping 只能告诉你"通了"，nslookup 能告诉你"是谁回答的"。如果 nslookup 里显示的服务器是你宿舍的路由器地址而不是 127.0.0.11，那就说明这个容器并不在任何一个自定义网络上，DNS 服务没有被启用。

实验结束，三个结论：默认网桥上的容器能通信，但只能靠 IP，且 IP 会在重建后变化；自定义网络上的容器可以用名字互访，名字由内置 DNS 提供；所以"多容器项目要用自定义网络"不是图方便，而是不被随机 IP 绑架。官方对照表在本章末尾的资源里。

对照项默认 bridge（docker0）自定义 bridge（docker network create）
容器名解析不支持，只能靠 IP，或用已废弃的 --link支持，用容器名或网络别名即可
隔离范围所有未指定 --network 的容器都挤在这里只有显式接入的容器才能互相看见
运行中接入其他网络不支持，必须停下来重建docker network connect 可在运行中接入或摘除
配置方式改 daemon.json，改完要重启 Docker建网络时用参数指定，互不影响
环境变量共享只有 --link 时代的老机制没有，改用卷或环境变量显式传递

这张表里有一个容易被忽略的差异，值得单独说：自定义网络的隔离范围是"只有接进来的容器才能互相看见"。默认网桥上挤着你所有没写 --network 的容器——包括你三个月前随手跑起来、早就忘了的那个测试容器。它现在能看到你今天跑起来的数据库。这不是理论的担忧，而是默认配置的常态。

展开：默认网桥为什么不干脆也把 DNS 打开

一个自然的疑问是：既然内置 DNS 这么好用，为什么不给默认 bridge 也配上？历史原因是默认网桥早于内置 DNS 出现，它的名字解析靠的是往每个容器的 /etc/hosts 里写条目（以及 --link 时代的环境变量注入），这种"写死文件"的做法在容器频繁重建时几乎无法维护。技术原因是默认网桥是全局共享的、跨项目的：如果它提供名字服务，那么你在项目 A 里叫 web 的容器，和项目 B 里叫 web 的容器，就必须争同一个名字，而 Docker 无法判断哪一个是"你的 web"。设计上的原因是 Docker 官方已经把默认 bridge 明确定位为遗留细节，不推荐用于生产：它无法按项目划分边界，配置只能整体改，接口能力也被固定住了。所以"给每个项目建一个自定义网络"不只是一个技巧，而是这套设计里被期待的使用方式。想验证这一点，可以去读官方桥接网络文档里"用户自定义桥接与默认桥接的差别"那一节，它列了五条，其中第一条就是名字解析。

思 考
  1. 默认网桥不支持名字解析，客观上让"随手跑起来的容器"之间更难互相发现。这种"不便利"能不能被解释成一种安全设计？还是它只是历史包袱被事后合理化了？两种解释各自的证据是什么？提示：对比一下"默认拒绝"和"默认允许"两种设计哲学，各自会带来什么样的日常摩擦。
  2. 如果两个容器在同一个自定义网络上，它们之间"所有端口都互相开放"，这和你对"网络应该最小暴露"的直觉冲突吗？你能想出什么办法在同一个网络内部再做细粒度限制？提示：Docker 的桥接网络驱动支持一个开关，用来关闭容器间的互通。

第 08 章讲 Compose 时，你会发现 compose.yaml 里根本不需要你手动 docker network create：Compose 会为整个项目自动建一个网络，并把每个服务用服务名注册进去。所以你在 Compose 里写 redis://redis:6379 就能直接工作，而这一章你手工做的那些事——建网络、接容器、验证名字解析——全部由它代劳。先在这里埋一个伏笔：这也意味着，同一个 compose 文件在不同项目目录下跑，网络是彼此隔离的；当你想让两个 Compose 项目互相通信时，需要的正是这一章学到的"把容器接入另一个网络"。

docker network 命令族与一个容器的多个身份

前面你已经零散用过几个网络命令，现在把它们排成一排看清楚。这一族命令只有六个动词，每一个都对应一个真实需求，没有一个是为了凑数而存在的。

建、看、删：create / ls / inspect / rm

create 建网络。最值得掌握的三个参数是 --driver（换驱动）、--subnet（指定子网，格式是 CIDR，Classless Inter-Domain Routing，无类别域间路由，写成 10.10.0.0/24 这样）和 --gateway（指定网关地址）。指定子网不是炫技，而是为了在需要和公司内网或校园网做路由时，让地址段不冲突。

docker network create --driver bridge --subnet 10.10.0.0/24 --gateway 10.10.0.1 net10

你会看到一串网络 ID。这条命令建出一座地址段为 10.10.0.0/24 的虚拟交换机，网关定为 10.10.0.1。之后接上去的容器会拿到 10.10.0.2、10.10.0.3 这样的地址。为什么要自己指定？因为当你把容器网络和公司内网打通时，如果两边的地址段撞车（比如都用默认的 172.17），路由就会彻底混乱。养成"生产环境显式指定子网"的习惯，可以省掉未来一次很痛的迁移。

ls 列网络。默认情况下你会看到三个：bridge、host、none，它们是 Docker 预建的，作用域 scope 都是 local。inspect 是这一族里信息最密的命令，它把一个网络的完整状态摊开给你：子网、网关、驱动、已接入的容器及其 IP。

docker network inspect mynet --format '{{range .IPAM.Config}}{{.Subnet}} via {{.Gateway}}{{end}}'

你会看到一行形如 172.19.0.0/16 via 172.19.0.1 的输出。IPAM 是 IP Address Management（IP 地址管理）的缩写，这一段描述的就是这个网络的地址池与网关。省略 --format 直接 inspect 会给你一大段 JSON，里面有 Containers 字段，列出所有接入的容器名、各自的 IPv4 地址和 MAC 地址——这是排障时判断"这个容器到底在哪些网络上"的首选证据。养成"不先猜、先 inspect"的习惯，你会少走很多弯路。

rm 删网络。删除的前提是没有容器还接着它，否则 Docker 会拒绝并告诉你原因。这个限制是善意的：它防止你在还有容器依赖某个网络时把它拆掉。

docker network rm net10

如果 net10 上还有容器，你会看到形如 "network net10 has active endpoints" 的错误，含义是有容器仍然挂在这个网络上。要么先 docker network disconnect 把容器摘下来，要么直接 docker rm -f 掉那些容器。看到这条报错请不要以为命令写错了——它是保护机制在起作用。

connect / disconnect：给运行中的容器加一条线路

这两个动词是自定义 bridge 相对默认网桥最实用的优势：它允许你在容器运行期间改变它的网络身份，不用重建。它最典型的用法是做"网络边界"的缝合——让一个容器同时属于两个网络，成为两个世界之间唯一的通路。

docker network create frontend
docker network create backend
docker run -d --name web --network frontend nginx
docker run -d --name db --network backend alpine sleep 3600
docker network connect backend web

四条命令：建两个网络，让 web 只在前端网络、db 只在后端网络，最后把已经在运行的 web 也接进后端网络。执行完最后一条之后再 inspect 一次 web，你会看到 Networks 字段下同时列出了 frontend 与 backend 两个网络，各有一个 IP——这就是"一个容器多个 IP"的实现方式：一个 veth 一根线接一座交换机，接两次就有两根线、两个地址。这样的拓扑有一个很实际的好处：db 从来没有出现在前端网络上，所以即便前端被攻破，它也只能顺着 web 这一个受控的出口去找 db，而 db 本身从不暴露给整个前端。

你还可以给接入的网络起别名，让同一个容器在不同网络里叫不同的名字：

docker network connect --alias database backend web

执行后，在 backend 网络里，其它容器既能用 web 也能用 database 找到它。网络别名在真实项目里很有用：同一个容器在后端网络里以 database 的身份被访问，这样就算哪天你换掉了实现它的容器名，后端服务的配置也不用改。--alias 可以重复给多次，也就是一个容器在一个网络里可以有多个名字。别忘了摘除的那一半：docker network disconnect backend web 会让 web 立刻从后端网络消失，正在建立的连接也会被切断，所以它更适合清理，而不是"热切换"。

易 错 点

三个坑，每一个我都见过有人踩。其一：docker network connect 之后以为"重启一下就生效了"，其实它当场就生效，不需要重启容器——反过来说，你如果在容器里写死了某种网络配置，connect 之后的应用行为可能和你预期不同。其二：把 --network 写成两个（docker run --network a --network b），docker run 只接受一个 --network，第二个会被忽略或报错，要接两个网络必须用 connect。其三：在没有 --subnet 的网络上用 --ip 固定地址，会报错说用户指定的地址不在网络范围内，因为 Docker 无法验证。固定地址在需要时可做，但请记住它违背了容器的"随时重建"前提：一旦你依赖某个固定 IP，你就失去了编排系统最想要的自由度。

回 望

第 04 章我们在讲 docker run 的参数时，把 -p 和 --network 列在"常用参数"里一带而过，说"端口映射和网络留到后面讲"。当时你只需要知道它们存在；现在它们终于被解释清楚了——publish 是把宿主机端口接到容器端口上的一条 DNAT 规则，network 是选择这个容器接在哪座虚拟交换机上。回头翻一下第 04 章那张参数表，你会发现每一个参数现在都能被"翻译"成内核里的一件具体事情，这就是判断自己是否真的学懂了一个工具的粗糙但有效的标准。

方 法

查一个陌生命令的最快路径不是搜索引擎，而是命令自己的帮助：docker network --help 会列出全部子命令，docker network connect --help 会列出它的全部参数。这条路径有三个好处：版本一定对得上、不会读到三年前的博客、而且帮助文本里的用词就是官方文档的用词，你能顺着它去搜更深的资料。把"先看 --help，再看 inspect，最后才搜索"当成默认顺序，你的排障会稳得多。

端口映射：从宿主机的一扇门，到容器里的一个人

现在把镜头对准 -p。每个人第一次跑容器都会写它，但它常被误解成"把容器的端口暴露出去"——真实机制比这句话精确得多。

-p 8080:80 里冒号前后是两个世界：左边 8080 是宿主机端口，右边 80 是容器网络命名空间里的端口，冒号就是那道 DNAT 规则。所以"端口映射"有点误导：它不是把端口"搬"过去，而是在包到达宿主机时改写目的地址、返回时改写源地址。真实的监听者只有容器里那个进程，宿主机上没人监听 8080——很多人第一次就踩这个坑，在宿主机上查端口发现没进程，以为服务没起来。

两边还可以不一样：-p 80:80 让左右一致，读起来省心。别把顺序写反——写反了不报错，只会让你访问的端口不对，白白排查半天。

写法有四种，各有用途，见表。

写法实际做了什么何时用代价或风险
-p 8080:80容器 80 → 宿主机所有地址的 8080本地开发、手机同局域网访问整栋宿舍楼网络都可能连到你
-p 127.0.0.1:8080:80只发布到宿主机回环 8080只给自己或本机代理局域网其它机器访问不到
-p 8080:80/udp只发布 UDPDNS、游戏、自建 VPN 等 UDP 服务忘了 /udp 时规则只覆盖 TCP
-P把 EXPOSE 的所有端口随机映射到宿主机高位端口快速起实验容器、端口无所谓端口号随机，脚本里必须先查
-p 8080:80 -p 8443:443可重复，发布多个端口同时需要 HTTP 与 HTTPS每个端口都要单独写

它们不是"四种写法"，而是四个决定：给谁看、只给自己看、什么协议、不在乎号码。默认发布到宿主机所有地址；写成 -p 0.0.0.0:8080:80 就把 IPv6 排除在外。精确说明在官方文档的端口发布与桥接网络两页，需要时去查。

-P 还有一个实用用法：镜像里没有 EXPOSE（声明容器打算对外提供哪个端口）时，-P 什么都映射不出来，所以它能顺带告诉你陌生镜像声明了哪些端口：

docker run -d --name web-random -P nginx
docker port web-random

第二条命令会打印形如 80/tcp -> 0.0.0.0:32768 的映射关系，左边是容器端口和协议，右边是宿主机被分配到的端口。而随机端口是从一个高位区间里挑的，所以每次重建都可能不一样。docker port 这个命令在你忘了 -P 分配了哪个端口时是唯一可靠的答案——不要靠 docker ps 里那串输出里的 PORTS 列去猜，直接问 docker port 更干脆。

那个经典的陷阱：容器里的 127.0.0.1 是谁

这是本章最值得反复强调的一件事。假设 PostgreSQL 直接装在 Windows 上监听 5432，你起一个容器去连 localhost:5432，连不上；换 127.0.0.1:5432，还是连不上。而宿主机上的客户端能连上，于是你开始怀疑 Docker。

问题不在 Docker 也不在数据库，而在"localhost 是谁"取决于你站在哪个网络命名空间。127.0.0.1 不是地址，是"我自己"的写法；在容器里它指容器那张 lo 网卡，数据库却在这台"自己"之外、宿主机上。所以容器连 127.0.0.1:5432，问的是"我自己的 5432 有服务吗"，答案是没有。你可以自己确认：

docker run --rm alpine sh -c "cat /etc/hosts; cat /etc/resolv.conf"

你会在 /etc/hosts 里看到 127.0.0.1 localhost 以及容器自己的主机名（一串容器 ID），在 /etc/resolv.conf 里看到 127.0.0.11。这两份文件告诉你：容器有一套完全独立的"本机"概念，而它并不知道你 Windows 上那个数据库的存在。

那容器怎么访问宿主机上的服务？Windows 和 macOS 上的 Docker Desktop 提供了约定名字 host.docker.internal，它在容器内解析成宿主机（那台 Linux 虚拟机）可达的地址：

docker run --rm alpine sh -c "apk add --no-cache curl >/dev/null && curl -s http://host.docker.internal:8080"

前提是你先在宿主机上用其它方式起了一个监听 8080 的网页服务（比如同在 Docker Desktop 上跑一个 docker run -d -p 8080:80 nginx）。命令会打印出那个网页的 HTML——你的容器通过这个名字找到了宿主机上的服务。如果宿主机上什么都没有，你会看到 curl 的报错，形如 Failed to connect。请注意 127.0.0.1 和 host.docker.internal 的区别不是"哪个更短"，而是"指谁"：前者指容器自己的回环接口，后者指宿主机。

host.docker.internal 有三个局限。第一，它是 Docker Desktop 的便利，原生 Linux 默认没有，要用 --add-host=host.docker.internal:host-gateway 手动加。第二，它的地址依赖 Docker Desktop 内部实现，别记那个具体 IP，也别写进配置默认值。第三，它解决的是"容器找宿主机"，与"外部找容器"无关：同学访问你的网页靠 -p 发布到局域网的端口。

比 喻

把端口映射想成宿舍楼的会客制度。宿主机是一栋楼，容器是楼里的房间，-p 8080:80 相当于在一楼大厅设一个"8080 号接待窗口"，贴告示："从这个窗口来的访客，请带去 302 房间的 80 号工位。" 楼外的人只能通过窗口找人，走不进 302 房间的门。而 127.0.0.1 是"本房间内的镜子"——对着它说话只有你自己听得到；宿主机前台的镜子与容器房间里的镜子是两面。

"应用该监听哪儿"和上面的机制是一体两面。监听 0.0.0.0 表示所有网卡地址都接收，从 veth 进来的包能被接住；监听 127.0.0.1 只接容器回环的连接，从 eth0 来的包被内核拒绝，宿主机上的连接全部失败。很多框架默认 127.0.0.1（假定你在本机开发、不想被同网段扫到），这在容器里恰好是最坏的默认值。下面用一个例子看这个过程，同时验证一个权限事实：

docker run -d --name lo-only --user 1000 -p 8081:80 nginx

这条命令说明了两个知识点。第一，--user 1000 让容器里的主进程以非 root 用户运行，而它仍然能绑定 80 端口——因为 Linux 把"绑定 1024 以下端口"这个特权拆成了独立的 CAP_NET_BIND_SERVICE 能力，Docker 默认并没有把它从容器里拿掉。这个事实打消了很多人的顾虑：用非 root 用户跑 nginx 是可行的，第 09 章讲安全时我们会把它变成常规做法。第二，nginx 官方镜像默认监听 0.0.0.0，所以这个容器即使以非 root 运行也能被从外部访问到，浏览器打开 http://localhost:8081 应该能看到欢迎页。

判断应用监听在哪个地址，最直接的办法是进容器看监听列表：

docker exec -it web bash -c "apt-get update >/dev/null && apt-get install -y iproute2 >/dev/null && ss -lntp"

这条命令先装 netstat/ss 所在的工具包，再打印所有正在监听的 TCP 端口。输出里会有两列关键信息：Local Address 和对应的进程。你会看到形如 0.0.0.0:80 或 127.0.0.1:80 的地址。如果是前者，外部可达；如果是后者，无论 -p 怎么写都不可达。这一条检查值得你放进肌肉记忆，因为它是"端口映射配对了但访问不了"这类问题最快的判定手段。如果你更喜欢轻量一点的写法，nginx 镜像里没有 ss，但可以看它自己的端口配置文件，或者用 docker exec web nginx -T 打印全部生效的配置，在里面搜 listen 指令。

展开：端口映射的性能代价到底有多大

端口映射不是"没有代价的转发"：包进出都要多过几次检查与改写，进入宿主机时过 nat 表的 DNAT 与 filter 表的 FORWARD，出容器时反向转换。都在内核里、以微秒计，对普通 Web 服务不是瓶颈——真正的开销来自网络栈的额外跳数与连接跟踪表（conntrack）的条目维护，只在每秒几十万次新建连接这类极端场景才显现。所以换 host 网络的判断标准不是"我想更快"，而是"是否压到了要省这几微秒的量级"，以及"是否接受端口不能再映射、隔离消失的代价"。绝大多数项目不值得；值得的是高频交易、大规模压测的目标服务本身、海量短连接的自定义协议服务。另有某些协议（需要真实源 IP 或特定二层行为）在 DNAT 后行为会变，改用 host 能绕开。

思 考
  1. -p 127.0.0.1:8080:80 与 -p 8080:80 在安全上的差别，本质上不是"谁能访问"，而是"暴露面有多大"。你能说出三种必须用前者的场景吗？宿舍局域网算哪一种？提示：想想同学、室友、同一层楼的人和学校网络策略能看到什么。
  2. 同一台机器上的两个容器，却要经过网桥、iptables、地址改写才能通信，这种"绕远路"值得吗？更快的替代方案是什么？省下的延迟换来了什么？提示：对比"两个进程直连 127.0.0.1 的不同端口"和"两个容器走容器网络"，算上隔离、可移植性、可替换性。

内置 DNS 与网络排障的固定顺序

127.0.0.11 是 Docker 放进每个容器网络命名空间里的 DNS 服务器。它不是宿主机上的进程，也不是公网地址，而是容器那片虚拟网络里的内线总机。这也解释了为什么在容器里 ping 127.0.0.11 可能失败：回环接口上并没有真的监听服务，只有 DNS 查询这类特定流量会被接住。

容器里的应用想解析某个名字时，先读 /etc/resolv.conf，看到 nameserver 127.0.0.11，于是把查询发给它。这个内线总机先翻自己的名单（这个网络里所有容器的名字与别名），命中就直接回答；否则转发给上游解析器。

docker run --rm --network mynet alpine sh -c "cat /etc/resolv.conf"

你会看到 nameserver 127.0.0.11 一行，可能还有 options ndots:0 之类的配置。作为对比，把同一条命令的 --network mynet 去掉，也就是接到默认网桥上，再看一次：nameserver 会变成宿主机的解析器地址，没有 127.0.0.11。这两次输出的差别，就是"自定义网络支持容器名解析、默认网桥不支持"的最直接证据——不需要任何推理，看文件就能确认。

解析成功与否，用 nslookup 或 getent hosts 直接问最简单。排障时它们的分工不同：nslookup 会告诉你是哪台服务器回答的，适合确认"内置 DNS 到底在不在场"；getent hosts 走系统解析路径，和应用实际用到的解析链一致，适合确认"应用会不会解析成功"。

docker run --rm --network mynet alpine sh -c "nslookup api; getent hosts api"

前提是你在前面那个实验里已经把 api 挂在 mynet 上并让它继续运行。输出里 nslookup 会显示 Server: 127.0.0.11、Name: api、Address: 172.19.0.3；getent 会打印一行"地址 名字"。如果 api 容器已经被你删掉了，两边都会报解析失败，这本身也是一次有用的观察：名字是跟着容器活着的，容器没了，名字也没了。

网络问题的特点是可能性太多，初学者最常走的路径是"连不上 → 一定是网络不通 → 重启容器 → 重装 Docker"，一次都没缩小范围。正确的做法是沿着数据包的路径，按固定顺序逐层排除，每层只问一个问题。下面这个顺序请抄在笔记本上。

顺序要问的问题具体命令这一层失败的典型症状
第 0 步容器还活着吗？主进程还在吗？docker ps -a状态 Exited，轮不到查网络
第 1 步两个容器在同一网络吗？docker inspect 看 Networks名字解析失败，或 ping IP 也不通
第 2 步名字能解析成地址吗？nslookup 或 getent hostsbad address，包没发出去
第 3 步端口连得上吗？wget -qO- 或 nc -zConnection refused 或超时
第 4 步应用在监听吗？听的是哪个地址？ss -lntp / nginx -T / 应用日志只监听 127.0.0.1，外部一律失败
第 5 步宿主机防火墙挡了吗？发布地址对吗？docker port，检查安全软件本机能访问、别的机器不能

顺序的原则是从最可能、最便宜的检查开始。第 1 步排最前，因为它是容器网络里最高频的失败原因；第 2 步紧跟，因为它和"网络不通"是两件不同的事，错误措辞会直接告诉你答案。也不建议一上来就 ping：它用 ICMP，很多环境会禁掉，不通不代表端口不通。

把顺序走一遍：自定义网络里跑着 web 与 redis，web 日志反复刷"无法连接 redis"。

docker ps -a --format "table {{.Names}}\t{{.Status}}\t{{.Networks}}"

第 0 步与第 1 步合并在这一条命令里完成。你会看到一张表：名字、状态、所属网络。如果 redis 的状态是 Exited (1)，那就与网络无关，去看它的日志。如果 redis 显示 Up 但 Networks 列是 bridge 而 web 在 mynet 上，那么答案已经出来了——它们不在同一座交换机上。这条命令值得背下来：它用一条命令同时回答"活着吗"和"在哪个网络"两个问题，比 docker ps 默认输出信息多得多，也比 inspect 快得多。

docker exec -it web nslookup redis

第 2 步。如果这一步返回名字与地址，说明解析没问题，怀疑对象转向端口；如果这一步报错，问题就锁定在"不在同一网络"或"redis 的名字不是 redis"。这里有个很隐蔽的变体：redis 容器如果在 docker run 时没有用 --name，它的随机名字没人知道，即使在同一网络上你也只能靠别名或 IP 访问它。所以给每个需要被访问的容器起名字，是一条纪律，不是习惯。

docker exec -it web sh -c "apk add --no-cache wget >/dev/null && wget -qO- redis:6379"

第 3 步，测端口连通。注意这个探测的预期输出很奇怪：如果 redis 正常工作，wget 很可能报错退出，因为 6379 端口上跑的是 Redis 协议而不是 HTTP，wget 发出的 HTTP 请求会得到一堆不认识的字节。这里的关键不是"成功还是失败"，而是错误信息的种类：如果错误里出现 connection refused 或 connection reset，说明端口是开的、有程序在应答（只是协议不对），链路没问题；如果错误是 bad address，那是解析问题；如果是超时，那才可能是防火墙或路由问题。这也是为什么排障时要读错误信息的措辞，而不是只看"成没成功"。想更干净地测端口，可以换成 nc -z -v redis 6379，Alpine 上通过 apk add --no-cache netcat-openbsd 安装。

docker exec -it redis sh -c "redis-cli config get bind; ss -lntp"

第 4 步，直接问应用自己。redis-cli config get bind 会返回 Redis 实际绑定的地址，如果是 127.0.0.1，那容器网络里的任何访问都不会成功；如果是 * 或 0.0.0.0，绑定就是开放的。ss -lntp 会打印监听列表，能同时确认端口与地址。把"问应用自己"当成第 4 步的核心动作：不要猜应用听了哪儿，让它自己说。

它背后有一条更值得记住的判断：把"不通"拆成"不活着、不在同一网络、名字解析不了、端口没开、绑定地址错、被防火墙拦下"这六个状态，一条命令排除一个。这种拆解能力不是网络知识带来的，而是排障方法论带来的——换到磁盘、内存、权限上，同样的六步式思路依然成立。

网络问题之所以让人挫败，不是因为它复杂，而是因为"连不上"这三个字把六种完全不同的原因压缩成了一句话。

方 法

给自己准备一个"排障脚本本"：把检查顺序写成一份可以照着敲的清单，每遇一次故障就记下"这次是第几步、症状是什么错误措辞"。三个月后你会得到一份极有价值的私人资料："哪种错误信息对应哪种原因"的映射，而它只能这样积累。同时练一件反直觉的事：改配置之前，先记下当前状态（inspect、ps、日志），因为改动之后再想复原"故障现场"就晚了。

易 错 点

最后强调一次那个最高频的真实故障：应用在容器里跑着，日志显示"Listening on 127.0.0.1:8000"，-p 8000:8000 也写了，浏览器却打不开，容器状态一切正常。这不是 Docker 的问题，是应用只听自己说话。解法是把监听地址改成 0.0.0.0（不同框架参数名不一样：host、bind、listen，或环境变量 HOST）。它之所以高频，是因为在非容器环境里永远不会暴露：宿主机上直接跑，127.0.0.1 和浏览器的 localhost 是同一个地方；搬进容器，那面"镜子"才变成两面。

前 瞻

第 10 章讲工程化时，我们会把这一节的排障顺序伸进 CI/CD 流水线：测试在不同阶段失败时，"在哪一层失败"的判断方式和这里一样，只是检查对象从容器变成流水线阶段。第 09 章讲安全时还会处理：既然容器之间默认能互通，"谁能和谁说话"就是网络边界设计，也是第 4 节"一个容器两个网络"的放大版。

跨主机网络与 overlay：当容器不再住在同一栋楼里

到这一节为止，我们讨论的所有东西都建立在一个前提上：所有容器跑在同一台机器上。想象你租了两台云服务器，一台跑网页、一台跑数据库，你希望它们像面对面一样通信。两台时你可以手动配路由、配防火墙；但你有了十台、五十台，而且容器还在不断重建、换 IP 时，手动维护就彻底不可能了。

问题的根源在于：同一台机器上的容器通信能自动化，是因为"公交总站"就在本地——docker0 网桥、veth、iptables 全部由本机的 dockerd 掌握，它知道谁在哪儿。跨主机时，每台机器只知道自己的容器，没有任何一方掌握全局名单。所以跨主机网络的第一个必需条件不是"更快的线路"，而是一套控制平面：一个所有节点都认可的、描述"谁在哪个节点上"的权威记录。这份记录一旦有了，剩下的才是"包怎么过去"。

Docker 的答案叫 overlay 网络（Overlay Network，覆盖网络）：在现有网络之上再铺一层虚拟网络。底层那层（承载流量的真实网络，通常叫 underlay）可能只是几台云服务器之间的内网；上层那层是容器眼里的虚拟网络，容器在其中看到 10.0.x.x 这样的地址，和旁边的容器处在"同一个网段"里，完全不知道自己的包被包了一层、跨过一段真实网络、又在对面被拆开。

展开：VXLAN 到底"封"了什么，为什么要把二层塞进四层

实现这种"套一层"最常用的技术叫 VXLAN（Virtual Extensible LAN，虚拟可扩展局域网）。它的做法是：把容器发出的整个以太网帧（二层数据，含原始源与目的 MAC 地址、原始 IP 头）当成普通数据负载，在外面套一个 UDP（User Datagram Protocol，用户数据报协议）包头和一个新的 IP 头，通过底层网络送到对端；对端剥掉外层，把里面那个原始帧交给自己机器上的容器网络。这就是"把二层包封装在四层里"的字面含义。为什么要这么做？因为二层网络天然不能跨越三层边界——你没法把一个以太网帧直接"路由"过互联网，而封装之后承载它的就是一个普通 UDP 包，可以像任何流量一样被路由、被穿越 NAT。为了知道哪个容器在哪个节点上，overlay 还需要一份分布式的键值记录保存成员与位置。这份记录就是前面说的控制平面，你在单机上完全不需要它，所以 overlay 永远和编排系统一起出现。

overlay 的代价也要说清楚，否则你会误以为它是"更好"的网络。第一，每个包多一层封装，包变大（VXLAN 的封装头有几十字节），接近网络最大传输单元时容易分片或需要调整 MTU——表现为"小请求正常、大文件传输卡住"。第二，它要求宿主机之间在特定端口上互通，严格的企业防火墙里可能要额外申请。第三，控制平面本身是需要运维的组件。第四，调试难度上了一个台阶：容器里看到的是虚拟地址，排查真实链路时得在多个抽象层之间来回切。

对比项单机 bridge（本章主线）overlay（跨主机）
谁掌握全局名单本机 dockerd，天然知道必须有一套控制平面来同步
容器地址的含义本机虚拟网段，仅本机可见全网虚拟网段，所有节点可见
包在路上长什么样不做额外封装原始帧被套进 UDP 里，包变大
失败时的排障难度一条 inspect 多半就有答案要在虚拟层与真实链路之间来回对照
什么时候真的需要单机上的全部场景服务分布在多台主机且要按名字互访

这一节到此为止，先把它压缩成一句判断：你看到的每一个容器地址，都是内核里一份配置表加上一根虚拟网线造出来的；你认为的"网络"，在这里只是一组设备与规则。跨主机之后这套判断依然成立，只是记账的人变多了。

前 瞻

第 12 章会展开这一节的另一半：在 Kubernetes 里，每个 Pod 拿到集群内可达的地址，跨节点的通信由集群网络插件负责，而服务发现则由集群自己的 DNS 提供——你会发现它的每一块都和这一章讲过的机制对应：名字解析对应内置 DNS，地址分配对应 IPAM，隔离对应网络策略。到那时你再回看这一节的 VXLAN 解释，会有一种"原来是同一件事换了个规模"的踏实感。现在先记住这条线索就够了：规模一变，问题就从"怎么连线"变成"谁来记账"。

反向代理与负载均衡：第 10、12 章的前菜

最后一个问题，也是你很快就要用到的：一个镜像只能起一个容器，那我要跑三个实例分摊流量，别人该访问哪个？答案是把"访问入口"从应用本身剥离出来，交给一个专门的中间层。这一节我们用 nginx 容器搭出最小可用的版本，你在第 10 章会看到它在多环境部署中的位置，在第 12 章会看到它在集群里的正式形态。

先分清两个容易混淆的角色。正向代理代表客户端：你配置浏览器走某个代理，代理替你去访问外部网站，网站看到的是代理的地址，不知道你是谁。反向代理代表服务端：用户访问的地址其实是代理的地址，代理决定把这次请求交给后面哪个服务，用户完全不知道后面有几个实例、分别在哪。一句话分辨：正向代理藏起客户端，反向代理藏起服务器。这两个词里的"正"和"反"，指的是代理站在哪一侧。

nginx 做反向代理的核心是配置里的 upstream 块——它定义一组后端服务器，然后 proxy_pass 把请求交给这一组。下面是完整实验，一共五条命令，从建网络到验证轮询。

docker network create lbnet
docker run -d --name web1 --network lbnet nginx
docker run -d --name web2 --network lbnet nginx

三条命令：建一个专用网络 lbnet，起两个来自同一 nginx 镜像的容器 web1 与 web2。注意两者都没有写 -p——按设计它们不该被外部直接访问，外部只能通过代理进来，这就是反向代理的一个额外好处：后端根本不需要发布端口，攻击面立刻小一圈。现在验证它们在同一座交换机上且名字可解析：

docker exec -it web1 nslookup web2

你会看到 127.0.0.11 返回 web2 的地址。这一步是实验的地基：如果它失败，后面的 proxy_pass 一定失败，所以必须在配代理之前先确认它。接下来写代理配置。

@'
events {}
http {
  upstream backend {
    server web1:80;
    server web2:80;
  }
  server {
    listen 80;
    location / {
      proxy_pass http://backend;
    }
  }
}
'@ | Set-Content -Encoding ascii lb.conf

@' 与 '@ 包起来的东西叫 here-string，作用是把多行文本原样写出去，不需要转义引号；结尾的管道把它交给 Set-Content 写成文件 lb.conf，-Encoding ascii 保证换行与编码不会给容器里的 nginx 添麻烦。写完请用 Get-Content lb.conf 检查一遍——配置写错了却直接拿去启动，是新手最常见的时间黑洞。注意 upstream 里用的是容器名 web1、web2 而不是 IP，这正是自定义网络提供名字解析带来的好处。

docker run -d --name lb --network lbnet -p 8080:80 -v "${PWD}/lb.conf:/etc/nginx/nginx.conf:ro" nginx

启动代理容器，把它接在同一个 lbnet 上，发布 8080 给你自己访问，并把刚写的配置以只读方式挂进去（-v 里的 ${PWD} 在 PowerShell 里会展开成当前目录的绝对路径，避免 Windows 路径被误解；:ro 防止容器改坏你的文件）。配置有语法错误时容器会立刻退出，此时 docker logs lb 能看到 nginx 的报错行号。

docker exec -it lb nginx -t

这条命令让 nginx 只检查配置语法、不启动服务，输出形如 syntax is ok 与 test is successful。养成"改完配置先 -t 再重启"的习惯，能省掉大量"容器起不来但不知道哪儿错了"的时间。

1..6 | ForEach-Object { docker exec lb sh -c "wget -qO- http://localhost"; Start-Sleep -Milliseconds 300 }

PowerShell 的循环写法 1..6 | ForEach-Object 会把花括号里的命令执行六次。每次让代理容器内部的 wget 请求 http://localhost，也就是打到 lb 容器自己的 80 端口上，命中 nginx 的代理配置，再由它转给 upstream 里的后端。注意请求的是 localhost 而不是 backend——backend 只是 nginx 配置里的 upstream 名字，是一个只对 nginx 有意义的标签，不是能被 wget 解析的主机名。执行完之后看日志：

docker exec -it lb sh -c "tail -n 8 /var/log/nginx/access.log"

你会看到最近八行访问日志。关键不是行数，而是每行末尾的 upstream_addr 字段——这一版配置里它显示的是 172.x.x.x:80 形式的后端地址，你会看到两个不同地址交替出现（比如 .2 与 .3 轮着来），这就是轮询（round-robin）在起作用：nginx 默认按顺序把请求分给 upstream 里的每一个后端。如果你的输出里只有一个地址反复出现，检查一下是不是 web2 没起来（docker ps 看状态），或者 upstream 块里少写了一行。想让结果更直观，可以把后端换成能显示自己身份的内容——例如给两个容器各自挂一个不同的 index.html，那样浏览器刷新就能看到页面在变；不过要注意浏览器有自己的缓存，验证分发请优先看日志而不是看页面。

这个实验里藏着一个你必须意识到的事实：轮询负载均衡的前提是"有多个后端"，而"有多个后端"的前提是后端无状态。如果 web1 把用户的登录会话存在自己的内存里，那么用户的下一次请求被分到 web2 时就会掉线。这就是第 06 章讲"容器无状态、数据外置"的另一个动机：把会话、上传的文件、缓存统统挪到容器外面，后端实例变得可以任意增删替换，负载均衡才有意义。反过来，如果你暂时不想引入这些组件，nginx 的 ip_hash 之类的策略可以让同一个客户端固定落到同一个后端，但那只是把问题往后推——它牺牲了均匀性，也解决不了实例重启导致的会话丢失。

再补一个在第 10 章会大放异彩的细节：nginx 不仅能转发 HTTP，还能作为七层路由的入口，按域名分、按路径分、终止 TLS、压缩、限流。当你把多个服务放进同一台机器时，用两个 server 块按域名分流，就能让一个 80 端口服务多个站点。这也是"反向代理"从实用技巧上升为架构组件的原因：它是外部世界与内部世界之间唯一的那道门，而门是最适合做策略的地方。

前 瞻

第 10 章讲工程化时，我们会把这里的 nginx 代理换成更完整的形态：多环境配置、TLS 证书从哪来、上线时怎么让流量平滑地从旧版本切到新版本。第 12 章讲集群时，你会发现 Kubernetes 里的 Ingress 与 Service 正是这个角色的标准化版本——你手工写的 upstream 块会变成一份声明式的资源定义，而 nginx 的 hostname 分发会变成集群级别的路由规则。所以这一节的实验不是玩具：它是你理解入口层全部设计的第一块砖。

回 望

第 06 章讲存储时，我们说过一句话：数据与网络都是"容器与外界的接口"。现在这句话可以对照着读了。存储那一侧的回答是"把重要的东西放到容器外面，用卷和挂载接进来"；网络这一侧的回答是"把不该看见的东西关在容器里面，只开该开的那扇门"。两个问题的形状惊人地相似：都是"容器的边界在哪里、边界上放什么"，只是一个管数据流，一个管流量。同时也回想一下第 06 章强调的"容器随时会消失"：这句话在网络上产生的直接后果就是容器 IP 不可依赖，所以我们必须用名字——而名字服务正是这一章的主角。数据和网络这两章合起来，其实是同一套思想的两次应用。

思 考
  1. 在你刚才搭的这套结构里，"谁需要知道谁的存在"？如果现在把 web2 换掉、重新起一个叫 web3 的容器，需要改哪些文件？这个答案告诉你这套设计的耦合程度是怎样的。提示：从 upstream 块、代理容器、外部用户三个角度分别看一遍。
  2. 如果把代理这一层去掉，让用户直接访问两个后端，你需要付出什么代价？为什么现实系统几乎总是选择"多加一层"？这一层带来的新的失败模式是什么？提示：想想代理本身挂了会怎样，以及这时候你有没有备用入口。

检 查 题
  1. 为什么不能让所有容器共享宿主机的网络栈，然后靠"约定好端口不冲突"来解决？请从至少三个角度说明这种约定为什么在工程上站不住。
    参考答案

    其一是约定会腐坏：端口表要人维护，而容器会被频繁创建，人工同步的清单很快失效。其二是你没有权限约定：镜像作者可以决定自己的应用监听 80，你无法要求所有开源镜像避开某个端口。其三是撞车的代价高：症状是服务起不来，排查者看到的是应用报错，很难立刻想到根因在宿主机端口表。还有第四点：即便端口不冲突，共享网络栈也意味着流量彼此可见，隔离带来的安全收益全部消失。评分要点：说出"可维护性"或"隔离"之一并给出场景。

  3. 预测现象：在默认 bridge 上，容器 A 执行 ping 172.17.0.3 成功，执行 ping B 失败并报 bad address。请你完整解释这两个结果为什么不同，并说明这证明了什么。
    参考答案

    第一个命令用的是地址，内核不需要解析，直接按路由表走 eth0、经 docker0 送到对方，所以同一座虚拟交换机上的两个容器能互相 ping 通。第二个命令用的是名字，解析要问 DNS，而默认 bridge 的容器 /etc/resolv.conf 里指向的不是内置 DNS（127.0.0.11），没有一方认识 B 这个名字，于是解析失败。证明的是：链路连通性与名字可用性是两件独立的事，必须分开验证。评分要点：提到"默认网桥不提供名字解析"与"解析失败发生在发包之前"。

    参考答案

    原有地址不变，新增一个来自第二个网络网段的地址，也就是同一容器同时拥有两个 IP，因为两个网络各给它插了一根 veth。验证方式：inspect 两个网络都能在名单里看到它；或 inspect 容器，NetworkSettings.Networks 下有两个网络名，各有独立 IP。它能解决网络分段：让一个容器同时属于前端与后端网络，成为两个安全域之间唯一的通路，而数据库只出现在后端网络里。评分要点：说出"两个 IP 同时存在"和"用它缝合网络边界"。

  5. 预测现象：docker run -d --name web -p 127.0.0.1:8080:80 nginx 之后，你本机浏览器打开 http://localhost:8080 能看到页面，同一宿舍的同学访问 http://你的IP:8080 却打不开。请解释原因，并说出这个写法的适用场景。
    参考答案

    因为 -p 里显式写了 127.0.0.1，DNAT 规则只对本机回环地址上的 8080 生效，来自局域网网卡的包不匹配这条规则，也没有对应的转发规则，于是被丢弃或拒绝；浏览器走的是本机回环，命中规则，所以能打开。适用场景：只希望自己或本机上的另一个组件访问。典型例子有管理后台、调试用的数据库端口、只给本机代理转发的端口。顺带要意识到：默认的 -p 8080:80 会发布到宿主机所有地址上，在宿舍网这种共享网络里等于对同网段所有人开放。评分要点：点出"规则只对回环地址生效"这一机制。

  6. 预测现象：容器里执行 ip addr 看到 eth0 是 172.17.0.2，执行 ping 127.0.0.1 成功，执行 wget http://127.0.0.1 失败（connection refused），而宿主机的浏览器访问 http://localhost:8080 成功。请你解释后面两个现象为什么会同时出现。
    参考答案

    ping 127.0.0.1 成功只说明容器内的回环接口在工作，它不涉及任何服务。wget 失败是因为容器自己的 80 端口上没有进程监听——127.0.0.1 在容器里指容器自己，而 nginx 并不在这个容器里。宿主机浏览器成功，是因为请求发到了宿主机，DNAT 规则把它改写到了真正跑着 nginx 的 172.17.0.2:80。结论：127.0.0.1 的含义随命名空间改变，容器内外是两个世界。

  7. 预测现象：docker run --rm alpine nslookup web 的输出里，Server 一行显示的是你宿舍路由器的地址，而不是 127.0.0.11。这个输出说明了什么？你会怎么修？
    参考答案

    说明这个容器没有接入任何自定义网络，因此 Docker 没有为它启用内置 DNS，它用的是宿主机的解析配置。修复方式是把容器接到自定义网络上（创建时用 --network，或运行中用 docker network connect），并确认该网络里确实有名为 web 的容器——两个条件同时满足，nslookup 才会由 127.0.0.11 应答。还有一个常被忽略的前提：名字解析只登记显式命名（--name）的容器，自动生成的随机名字不会被登记。评分要点：因果关系要说对——DNS 服务器地址是结果，网络选择才是原因。

  8. 预测现象：docker run -d --name db --network backend -p 5432:5432 postgres，然后你从宿主机上的数据库客户端连接 localhost:5432，成功；但你在同一个 backend 网络里的应用容器里去连 localhost:5432，失败。请解释，并给出两种正确的连接写法。
    参考答案

    宿主机客户端连 localhost:5432 成功，因为 -p 把宿主机 5432 的包转发给了容器，宿主机的 localhost 就是宿主机自己。应用容器里的 localhost 则是那个容器自己，上面没有数据库，所以失败。两种正确写法：一是用服务名 db:5432，前提是两者在同一自定义网络上且数据库容器用 --name db 启动；二是用 host.docker.internal:5432，它能解析到宿主机，从而走已发布的端口回到数据库容器——代价是多绕一圈并依赖 Docker Desktop 的实现。第一种是推荐做法。

  9. 故障诊断：你在自定义网络里跑了一个 Node 服务与一个 Redis，Node 日志显示反复重连 redis:6379 失败。请写出你的排查顺序（至少四步），并说明每一步会用什么命令、什么样的输出会让你排除这一层。
    参考答案

    第一步查两个容器是否都活着、是否在同一网络：docker ps -a --format "table {{.Names}}\t{{.Status}}\t{{.Networks}}"，若状态为 Exited，问题与网络无关。第二步查解析：docker exec -it node nslookup redis，能返回地址就转向端口。第三步测端口：nc -z -v redis 6379，重点读错误措辞——refused 说明端口开着但协议不对，bad address 是解析失败，超时可能是被拦截。第四步问应用自己听在哪儿：redis-cli config get bind 与 ss -lntp，若绑定 127.0.0.1，同网络内访问必然失败。再往后才是宿主机防火墙。评分要点：顺序要体现"从最便宜、最可能的一步开始逐步收敛"。

  10. 故障诊断：一个自己写的 Python 服务打包成镜像后 docker run -d -p 8000:8000 myapp，容器状态 Up，docker logs 里显示 "Serving on http://127.0.0.1:8000"，浏览器打不开。请给出你的判断、验证方法和修复方向。
    参考答案

    判断：应用只绑定了容器内的回环接口，从 veth 进来的包不会被它接收，端口映射虽然在宿主机上生效了，到容器里却无人接。验证：进容器执行 ss -lntp，看 Local Address 那一列是 127.0.0.1:8000 还是 0.0.0.0:8000。修复：把监听地址改成 0.0.0.0（不同框架的参数名不同，常见的是 --host、bind、listen 或环境变量），重建镜像。评分要点：要指出这是应用配置问题而非 Docker 问题，并说出"veth 上的包不会被回环监听接住"。

  11. 方案取舍：A 项目对网络延迟极度敏感，每秒要处理几十万次请求；B 项目是一个课程设计，老师和同学都要从浏览器访问。请分别给出网络驱动的选择与理由，并说出你放弃了什么。
    参考答案

    A 项目考虑 host 网络：省掉 veth、网桥、DNAT 与 conntrack 这几层开销，路径最短。放弃的是端口映射的自由（容器直接占用宿主机端口，不能改号）、与宿主机其它服务的隔离、以及"每个容器一套独立网络配置"带来的可替换性。B 项目用自定义 bridge 加 -p 发布端口：它需要外部可访问、需要名字解析，且对延迟毫无敏感度。放弃的是一丁点转发开销，换来隔离、可映射、可按项目划分网络。评分要点：必须给出"放弃了什么"。

  12. 动手任务：创建两个自定义网络 front 与 back，让一个 nginx 容器同时接入这两个网络，再各起一个 alpine 容器分别只接入其中一个。请写出全部命令，并说明用什么命令证明 nginx 有两个 IP，以及在 front 网络里的 alpine 能不能用 nginx 的 IP 访问 back 网络里的那个 alpine。
    参考答案

    命令：docker network create front；docker network create back；docker run -d --name proxy --network front nginx；docker network connect back proxy；docker run -dit --name a --network front alpine sh；docker run -dit --name b --network back alpine sh。证明两个 IP：docker inspect proxy，NetworkSettings.Networks 下 front 与 back 各有 IPAddress。第二个问题：不能。front 里的 a 解析不到 b 这个名字（不在同一网络，内置 DNS 不登记），即使查到 b 在 back 里的 IP 也连不通，因为宿主机有隔离规则专门丢弃跨 bridge 网络的包。proxy 能同时看到两边，是因为它接在两个网络上。评分要点：给出"两个 IP 的证据"与"跨网络默认被阻断"。

  13. 动手任务：用 docker network alias 让同一个容器在两个网络里用两个不同的名字被访问，并用命令验证两个名字都能解析。请写出命令，并说明这个能力在真实项目中的用途。
    参考答案

    核心命令：docker network connect --alias database backend web，然后分别在两个网络里的容器上执行 nslookup 验证——在 backend 网络的容器里 nslookup database 与 nslookup web 都应返回同一地址，而在 frontend 网络里只应解析得到 web。用途：让不同的消费者用符合自己语境的名称访问同一个服务（后端代码里叫 database、运维视角里叫 web），替换实现时不必改动调用方配置，也让"服务的逻辑名"与"容器的物理名"解耦。评分要点：说出"解耦名字与容器"这一层。

  14. 概念辨析：正向代理与反向代理都叫"代理"。请用一句话分别说清它们代表谁，然后各举一个你在日常上网中可能真的遇到过的例子。
    参考答案

    正向代理代表客户端，它替客户端去访问外部；反向代理代表服务端，它替服务端接收请求。日常例子：正向代理常见于学校或公司的统一出口代理，你的浏览器是被代理的那一方；反向代理则是你访问的每个大型网站背后几乎都存在的东西——域名解析到的是代理，代理再决定把请求交给哪台服务器，这一章搭的 nginx 容器就是它。一句话分辨：如果用户知道自己在用代理，那是正向；如果用户以为自己在直接访问服务，那多半是反向。评分要点：必须答出"代表谁"。

本章总结

  • 容器网络要同时满足两件互相拉扯的事：彼此隔离，又能按需通信。隔离靠网络命名空间，通信靠虚拟设备与转发规则。
  • 网络命名空间是一份独立的网络配置表，管网卡、路由、防火墙规则、端口与解析配置。它几乎不花成本，代价是宿主机上"看不见"了。
  • veth pair 是一根虚拟网线的两端，一头在容器里成为 eth0，一头在宿主机的网桥上。它不能单独存在，这正说明它天生就是为了跨越两个命名空间。
  • 网桥就是宿主机上的一台虚拟交换机。每个自定义网络都是一台独立的交换机，接在不同交换机上的容器默认无法互通，靠 iptables 的隔离规则实现。
  • 端口映射不是"把端口搬过去"，而是宿主机上的一条 DNAT 规则加上一条 filter 放行规则，另外还有出站方向的地址伪装负责让容器能上网。
  • 默认 bridge 与自定义 bridge 最关键的差别是容器名解析：默认网桥只认 IP，自定义网络有 127.0.0.11 这个内置 DNS，所以多容器项目必须自建网络。
  • 一个容器可以接入多个网络，于是拥有多个 IP。这个能力不是奇技淫巧，它是"把不该互通的两片网络用唯一一个受控出口缝起来"的标准手法。
  • 容器里的 127.0.0.1 与宿主机的 127.0.0.1 是两个不同的地方。应用必须监听 0.0.0.0 才能被外部经端口映射访问到，这是最高频的真实故障之一。
  • 网络排障有固定顺序：先看活着吗、再看是否同网络、再看名字解析、再看端口连通、再看应用监听地址、最后看防火墙。每一步只问一个问题，逐步砍掉可能性。
  • 跨主机网络的难点不在于线路，而在于没有谁是全知的，因此必须先有一套控制平面来记账；VXLAN 解决的是"怎么把二层帧送过去"，控制平面解决的是"送去哪儿"。
  • 反向代理代表服务端接收请求，它让你可以把多个后端藏在一道门后面做负载均衡；而负载均衡成立的前提是后端无状态，这与第 06 章"数据外置"是同一条原则。
  • 这一章最重要的一个判断：容器网络里没有任何一环是魔法，每一个"连不上"都能对应到数据包路径上一个具体环节；你需要的不是记住更多命令，而是知道包应该走哪条路、在哪一步能看见它。

木箱已经装好，货也固定好了，现在它们终于能互相打招呼。你亲手让两个互不相识的进程在一次请求里握了手，而这次握手穿过了四层虚拟设施、九步转发规则，全部发生在同一台机器内部，耗时不到一毫秒。看不见的东西从来不等于不存在，它只是还没有被你想明白。下一章，我们要把这套手工命令写进一个 YAML 文件——当 Compose 替你自动建网络、自动登记服务名时，你会发现自己能看懂它省略掉的每一个动作。
