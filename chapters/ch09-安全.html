安全：把门锁好，比祈求没人来更可靠

隔离不是理所当然的，它是你亲手配置出来的。

本 章 学 习 目 标
  • 能说清威胁模型是什么：在写下任何一条加固参数之前，先回答"我在防谁、防什么、愿意付多少代价"这三个问题。
  • 能准确解释"容器不是安全边界"这句话的含义——它确实是一层边界，但强度低于虚拟机，而且强度由你的配置决定。
  • 能说清容器逃逸几条主要路径各自成立的机理，并指出每一条路径对应的、代价最小的那项防御。
  • 能解释"容器里的 root 和宿主机的 root 不一样"这句话对在哪里、又危险在哪里。
  • 能说清 Capabilities、seccomp、AppArmor 或 SELinux、只读根文件系统各自拦住了什么、拦不住什么，以及为什么它们必须叠在一起才叫纵深防御。
  • 能解释镜像的漏洞数量为什么是"镜像加时间加漏洞数据库"三者的函数，而不是镜像身上一个固定的属性。
  • 能说清密钥为什么会永久留在镜像里，以及"我把文件删掉了"为什么删不掉它。

第 08 章你把一整座机房写进了一个 YAML 文件：web、db、缓存，一条 docker compose up 就把它们全建起来，服务之间靠名字互相找到，数据躺在命名卷里。那份文件读起来像一份设计图，你大概也体会到了"声明式"带来的踏实。现在请你回头看一眼那份文件里的一行——数据库的密码。它可能写在 environment 里，可能放在同目录的 .env 里，可能被你提交进了 Git。你写过它，你确认过它能跑，但你没有问过一个问题：这个密码现在存在于哪些地方？谁会看到它？第 08 章教你把世界描述出来，这一章要教你的，是给你描述出来的这个世界配上一套边界。因为容器给你的隔离不是天生就牢靠的，它是一堆默认值和一堆你亲手写下的参数共同决定的成果；你每多写一个 --privileged，就有一层默认防护悄悄退场。

先问"我在防谁"：威胁模型这门手艺

先说一件你大概没留意过的日常。上周你为了让室友用手机看看课程设计的效果，把容器的 8080 端口映射了出去。如果你这台笔记本接在家里的路由器后面，这个端口其实还停在内网里，公网上的人看不见它；可如果你在校园网、宿舍楼的共享网络里，或者为了给异地的同学演示而做过端口转发，那么这个端口就是对着世界开着的。接下来的事情非常朴素：自动化扫描器不需要知道你是谁，它只是在全网扫每一台机器的每一个常见端口，再试着敲几条最常见的问题。你可以自己验证——把 nginx 容器跑起来、映射一个端口、过一天再回来看日志，那些 404 请求的路径集中得让人心里发凉：找一个叫 .env 的文件、找 /admin、找 wp-login.php。它们不是冲你来的，它们是冲所有没锁门的房子来的。

这段铺垫只想说明一件事：安全不是从背参数开始的，而是从"我在防谁"开始的。同一台笔记本放在宿舍当学习机，和放在机房里当你们小组要做三个月的服务端，需要的防护强度完全不同。用同一套配置对待这两种场景，你会在一边浪费精力，在另一边漏掉要害。

我把"先想清楚再动手"这套习惯叫作威胁模型（Threat Model，对"谁可能以什么方式伤害什么"的一次结构化思考）。它一点都不神秘，就是三个问题：我在防谁？我在防什么？我愿意为此付多少代价？三个问题里最难的是第三个，因为它逼你承认安全是有价格的，而不是一句正确却无法执行的口号。一个不肯谈代价的安全方案，最后的结局通常是被所有人绕过。

再来看资产这一侧。你要保护的东西大致是四类：数据（数据库内容、模型权重、用户填过的表单）、凭据（云服务密钥、数据库密码、SSH 私钥、以及那个权限等同于宿主机 root 的 docker.sock）、算力（你的显卡被别人拿去挖矿，是这类攻击最常见也最直接的经济动机）、以及宿主机本身与它所在的网络（一次成功的逃逸能让你内网里那些没设密码的服务全部暴露）。把这四类资产和你上面列出的对手排在一起，你会发现威胁模型最后落在纸上的样子极其朴素：一张表，几行字。它的作用不是让你安全，而是让你知道自己正在接受哪些风险。

"容器不是安全边界"这句话该怎么理解

这句话在网上流传得很广，也经常被误读成"容器毫无安全性"。准确的说法应该拆成三句。第一句：容器确实是一层边界，它把进程能看到的东西和能用的资源都收窄了，这不是幻觉，是内核里实实在在的检查。第二句：这层边界的强度低于虚拟机，因为虚拟机靠硬件虚拟化把两套内核彻底分开，而容器里的所有进程和宿主机共享同一个内核——同一个内核意味着同一个漏洞对上面所有容器同时成立。第三句，也是最实用的一句：容器隔离的强度不是一个常数，而是一个由配置决定的变量。

Docker 的默认配置其实已经替你做了不少事：它把 root 的能力裁到十几项、给容器加载一份 seccomp 白名单、用 cgroups 划出资源上限、默认不允许访问宿主机的设备。这些默认值是 Docker 十年来一次次安全事件之后调出来的，它们不是装饰。危险之处在于，这些防护是可以被一条参数整体撤掉的：一个 --privileged 同时解除能力限制、设备限制和 seccomp 限制；一次 -v /var/run/docker.sock 的挂载，让容器绕过所有这些检查去指挥宿主机的守护进程。所以本章反复出现的句式会是同一个：这项措施在防什么，它的代价是什么，以及——如果你把它关掉了，你换来了什么。

回 望

第 01 章我们反复念过一句话：容器共享内核，虚拟机共享硬件。当时它是帮助你理解容器为什么轻、为什么启动只要几百毫秒的口诀。现在这句话露出了它的另一半面孔：共享内核既是容器高效的来源，也是它安全强度的上限。第 01 章还讲过隔离思想从 chroot 一路走到 namespace 加 cgroups 的历史，本章第一节的结论正好接在那条线的末端——隔离从来不是一次发明出来的开关，而是一层层加上的检查，每一层都可以被配置削弱。

比 喻

给自行车上锁这件事，没人会追求"绝对偷不走"。你追求的是一件更实际的事：让偷车的人觉得，隔壁那辆没锁的车更值得下手。锁的好坏、车停在哪、停多久，三个变量共同决定了你的车今晚的命运。安全配置也是这样一场成本博弈：你不可能让攻击者消失，但你可以让他为拿到你这台机器所付出的代价，超过他能得到的东西。想通这一层，你就不会再纠结"这个措施是不是万无一失"，而会开始问"它让攻击者多花了多少力气、又让我多花了多少力气"。

比喻之后回到技术本体：这里的"力气"有非常具体的形态。攻击者要多绕开一层 seccomp 过滤、多找一个能用的系统调用、多想一步怎么从非 root 变成 root、多花时间等一个内核漏洞的公开利用代码。每加一层，成本就上升一档，而你的成本也在上升——这就是第三节到第八节要反复算的那笔账。

方 法

威胁模型不是一个要学很久的学科，它是一个十五分钟就能做完的动作。找一个文本文件，写下这三行：这个服务在防谁（列出你真正担心的两类对手，不要写"黑客"这种无法行动的答案）；它最怕丢什么（写出具体的资产，比如"数据库里的 3000 条实验记录"而不是"数据"）；它现在暴露在哪里（端口、挂载、环境变量、密钥）。然后给每一条加固措施补一列：它对应上面哪一行威胁。写不出对应关系的那条措施，就先不要加——你加上的只是维护成本。最后再加一行，诚实地写下"我决定暂时接受哪几项风险，为什么"。这一行是整个威胁模型里最值钱的部分，因为它把"我不知道"变成"我选过了"。请你养成一个习惯：每接一个新项目、每上一次线，都重写一遍这张表。它不需要长，需要的是诚实。

安全的反面不是危险，是侥幸。侥幸的特征是：你说不出自己在防谁，也说不出自己在赌什么。

展开：威胁、脆弱性、风险，这三个词的分工

这三个词经常被混着用，混用会让你对扫描报告产生错误的判断。威胁是"谁可能伤害你"，它是一个主体，比如一个自动化扫描器。脆弱性是你身上被利用的那个点，比如一个版本过旧的组件、一条写错的权限配置。风险是前两者加上后果严重程度之后的乘积：被利用的概率越高、后果越重，风险越大。这条公式解释了两个常见的困惑。第一个困惑是"扫描出 40 个漏洞，我是不是完蛋了"——如果你这 40 个漏洞都在一个根本不联网、也不接受外部输入的内部工具镜像里，那它们的被利用概率极低，风险也就低。第二个困惑是"我扫出来 0 个漏洞，是不是安全了"——一个没有任何已知漏洞的镜像，如果它挂着 docker.sock 并以特权模式运行，它的风险依然高得离谱，因为它的脆弱性是配置层面的，扫描器扫不出来。所以本章后面出现的漏洞数量，请你始终把它读成"脆弱性的一个侧面"，而不是"风险的总分"。

还有一个问题我先留在这里，暂时不回答：你有没有想过，为什么 Docker 默认让容器以 root 用户运行？镜像里的默认用户是 root，这不是某个人一时疏忽，它是一个有历史原因、也有真实代价的选择。等你读完第三节，你会明白这个默认值是怎么来的，也会明白为什么今天的共识是"每一个生产镜像都应该显式声明自己的非 root 用户"。

思 考
  1. 你给室友演示课程设计的那台笔记本，和你们小组准备在机房跑三个月的服务端，需要的安全措施应该一样吗？请具体说出你会在哪台机器上省掉哪一项措施，以及你愿意承担什么后果。 提示：从"这台机器上有什么值得别人花力气的东西"这个角度切入。
  2. 如果你只有一天时间加固一个已经上线的容器，你会先做哪三件事？请给出排序的依据，而不是直接列参数。 提示：把措施分成"移除已经敞开的门""降低出事之后的后果""建立能持续的机制"三类，看看哪一类最划算。
  3. "我从不犯低级错误，所以我用不着这些配置"——这句话作为一条安全策略，它的漏洞在哪里？请举一个你自己真实犯过的操作失误。 提示：安全设计的对象是"人会犯错"这个事实，而不是"某个人"。

逃逸：门是从哪儿被打开的

先把术语说清楚。容器逃逸（Container Escape）指的是容器里的进程突破隔离，拿到了宿主机的权限、数据或资源。它听起来像电影桥段，实际发生的方式朴素得多：绝大多数逃逸不靠什么手法，靠的是一条配置。逃逸大致分两类——配置型的，和漏洞型的：配置型是你自己把门打开了（挂了不该挂的东西、给了不该给的能力），漏洞型是内核或容器运行时本身有缺陷。前者远多于后者，因为漏洞需要等、需要碰、需要技术，而配置失误只需要一个人手快，所以加固的重点应该放在前者。

第一条路：挂载 docker.sock

第 02 章讲 Docker 架构时画过那条链路：docker 命令行是客户端，把请求发给守护进程 dockerd，两者靠一个 Unix 套接字通信，Linux 上通常是 /var/run/docker.sock。当时留了一句警告，说这个套接字的权限等同于 root。现在兑现它。

把套接字挂进容器，就等于把宿主机的守护进程遥控器交给了容器里的一切进程。机理是：守护进程以 root 运行，有权创建容器、挂载宿主机的任意目录、读取任意镜像；容器里的进程只要能连上这个套接字，它发出的请求就会被当成合法的管理指令来执行——包括"帮我建一个把宿主机根目录挂进去的新容器"。这一步里没有任何漏洞被利用，全是正常功能。这也是它比内核漏洞可怕得多的原因：它不需要你运气不好，它只需要你配置过一次。

下面这个实验能让这件事具体起来。它只做一件事：在一个容器里列出宿主机的容器。我把话说明白——这是一次权限演示，不是攻击教程：只读、不写、不改，目的是让你亲眼看到隔离在这里已经不存在了。

实 验 一 · 套 接 字 之 门

目的：亲眼看见一个容器怎样跨过边界读到宿主机的信息。第一步，确认宿主机上有容器在跑，记下它们的名字。

docker ps --format "table {{.Names}}\t{{.Image}}"

这是宿主机上的一条普通命令，输出是当前正在运行的容器列表——记住你看到了几行。接下来那条命令里的 docker:cli 是一个只装了命令行客户端的小镜像，它本身什么服务都不跑。

docker run --rm -v /var/run/docker.sock:/var/run/docker.sock docker:cli docker ps

你会看到一份和上一条命令几乎一样的容器列表——但它是在一个容器内部执行的。容器里的 docker 客户端默认会去连 /var/run/docker.sock，而这个路径现在指向的是宿主机的守护进程。这就是全部要害：套接字没有"只读"这个概念，能读就能写。（在 Git Bash 里要把源路径写成两个斜杠 //var/run/docker.sock。）这一步做完，请把所有容器删掉或停掉，不要留着这个挂载。

docker run --rm -v /var/run/docker.sock:/var/run/docker.sock:ro docker:cli docker ps

有人会本能地想：加个 :ro 让它只读不就行了？它照样能列出容器。:ro 限制的是对这个文件的写入操作，而"通过一个已经打开的套接字发管理请求"发生在进程与守护进程之间，根本不是文件系统层面的写。挂载选项管的是文件和目录，管不了协议里说了什么。

现在请你解释这件事，并追问一个变体：为什么容器里这条命令看到的列表，和宿主机上看到的是同一份？因为它们是同一个守护进程给出的同一份答案。变体是：如果容器里那个进程不只是想看列表，而是想让守护进程做点别的，会发生什么？我不演示那一步，但你可以想通它：既然请求来自受信任的管理接口，守护进程不会区分它是"人敲的"还是"容器发的"。

那正确的做法是什么？如果容器只是需要知道一些运行时信息（比如"我这一批有几个副本"），这些东西往往已经在环境变量或标签里，读它就行。如果确实需要程序化地读取容器状态，正确的形态是把一个只暴露少量只读接口的代理放在守护进程前面；或者干脆把采集程序放在宿主机上，而不是塞进被监控的容器里。第 12 章讲集群时会看到同一套思路的放大版：不是把权限给出去，而是把权限切成刚好够用的形状再给。

回 望

第 02 章介绍守护进程时说过它监听一个 Unix 套接字，而这个套接字的权限等同于 root。当时那只是架构介绍里的一句注解，你大概扫过去就忘了；现在它变成了本章第一条结论：不要让任何不该拥有 root 的东西碰到这个套接字。再接上第 03 章的一个细节——镜像的层可以复用，你从别处抄来的那段 compose 片段里那个挂载，正是以这种方式在项目之间悄悄传播的。

第二条路：特权模式，和为了一个报错撤掉全部防线

--privileged 这个参数值得你用最谨慎的态度对待。它做的不是"多给一点权限"，而是：把内核全部能力一次性交给容器、解除设备访问限制（容器能看到并使用宿主机的各类设备节点）、关闭默认加载的 seccomp 白名单与 AppArmor 约束、允许改动一部分内核参数。一个以特权模式运行的容器，隔离基本只剩下一层目录视图。

人们加这个参数的原因通常特别无辜：某个程序启动时报权限错误，搜到一篇文章说加 --privileged 就好了，加上去果然好了。这时你实际做了一个交易——用整个宿主机的安全，换掉一个还没搞清楚的报错。专业做法是把报错读明白：它要的是哪一种能力？改文件属主（CAP_CHOWN）、绑定 1024 以下端口（CAP_NET_BIND_SERVICE）、跟踪别的进程做性能分析（CAP_SYS_PTRACE）、配置网卡与路由（CAP_NET_ADMIN）？绝大多数报错都能落到一项可单独授予的能力上，代价比 --privileged 小几个数量级。第四节把对照表给你。

第三条到第五条路：敏感目录、内核漏洞，以及它们的组合

挂载宿主机的敏感目录是第三条路。第 06 章讲绑定挂载时说过它把真实路径直接放进容器、两边实时同步——那是它的方便之处。另一面是：把 / 挂进去就等于把整台宿主机交出去；把 /etc 挂进去，容器可能读到系统账户与服务配置；把 /var/run 挂进去，你很可能顺带把 docker.sock 也带进去了。判断一条挂载安不安全，有个很土但有效的问题：如果容器里跑的是恶意程序，它从这个目录能得到什么？答案是"它能改我的系统"，这条挂载就不该存在，或者至少要加只读。

第四条路是内核漏洞。既然容器共享宿主机内核，内核里的一个缺陷就是所有容器的共同风险面。公开历史上有几个绕不过去的名字，你不需要记住细节，但值得知道它们的存在与类别：Dirty COW（CVE-2016-5195，写时复制实现里的一处竞态）、runc 的那次逃逸（CVE-2019-5736，容器内的进程可以覆盖宿主机的运行时程序）、Dirty Pipe（CVE-2022-0847，管道缓冲区的一个标志位未初始化）。它们的共同点是：都属于"内核或运行时的实现细节出了错"，而且都被迅速修复了。我这里只讲机理类别，不讲利用方法——理解机理能帮你判断自己的风险，学会利用方法对你没有任何好处。

防御思路有三条。最直接的一条是及时更新引擎与内核——对 Docker Desktop 用户有个提醒：你的容器内核其实是 WSL2 的内核，它跟着 Windows 更新走，也可以手动更新，而服务器上的内核要你自己主动管。第二条是在"拿到代码执行"和"拿到特权"之间多塞几道门：非 root、削减能力、seccomp 过滤。第三条是用户命名空间，它能让容器里的 root 在宿主机上贬值成普通用户——第三节细讲。

最后是组合。单独看，以 root 运行不致命，内核有漏洞也不致命；两者放在一起就是最坏的一类：容器内已经有 root，内核缺陷只需要把这一点权限换成宿主机的执行权。反过来，非 root 运行、丢弃多余能力、只读挂载根文件系统之后，同一个漏洞能给攻击者的东西就少得多——他得先在容器里提权，而这一步恰恰被能力限制挡住了。安全领域总在说"层"：单层强度不重要，重要的是让攻击者需要连续通过的条件数变多。

这条命令会为每个运行中的容器打印一行：容器名、是否特权模式、挂载了宿主机的哪些真实路径。PowerShell 里的 $(...) 会把 docker ps -q 的结果展开成容器 ID 列表传给 inspect，所以一条命令就能检查全部容器。要找两种东西：privileged=true，以及 mounts 里出现 /var/run 或你认不出的宿主机目录。某项为空说明那个容器没有挂载宿主机路径，这是好事。

从 root 到非 root：权限的真相

现在回答第一节留下的那个问题：为什么 Docker 默认让容器里的一切以 root 运行？原因分两半。一半是历史：容器刚出现时被当作"轻量虚拟机"，人们把完整系统塞进镜像，启动脚本要装包、要改目录属主、要绑低端口，这些以 root 做最省事。另一半是兼容性：如果默认非 root，历史上大量镜像会在启动时直接失败，而"装完就能跑"正是 Docker 当年赢下市场的关键。所以这个默认值是用便利换安全的交易，在十年前是划算的。

但默认值不等于免责。请你先做本章最便宜的一个实验，用两条命令看清"默认是谁"以及"身份是可以换的"。

docker run --rm alpine id

alpine 是一个体积极小的 Linux 基础镜像，它的 id 命令会打印当前进程的身份。你会看到 uid=0(root) gid=0(root)，后面还跟着一串组。这条命令的意义是：你什么都没指定，容器里的进程就已经是 root 了。注意这里是"你什么都没指定"，而不是"你必须这么做"。

docker run --rm --user 1000:1000 alpine id

--user 后面是"用户 ID 冒号 组 ID"。这次你会看到类似 uid=1000 gid=1000 的输出，而且没有用户名——因为 1000 这个编号在 alpine 的 /etc/passwd 里根本不存在。这一行透露了两件事：第一，身份的切换只是一个数字的事；第二，容器并不要求这个数字在镜像里有对应的账户记录，它只要求内核认这个数字。如果你的应用需要用户名（比如某些程序会去读 passwd），那就得在镜像里真的建一个用户，这是下面 Dockerfile 例子里要做的事。

"容器里的 root 和宿主机的 root 不一样"这句话，对在哪里又危险在哪里？对的部分：容器里的进程虽然 uid 是 0，但它能做的事被内核逐项筛过一遍——Docker 默认只留下十几项能力，还挂了一份 seccomp 白名单，很多危险操作直接被拒。危险的部分有四条。

第一条，留下那十几项能力里仍然有硬货。DAC_OVERRIDE 让文件权限位对你不构成阻碍——路径能看到，读权限检查就被绕过；CHOWN 与 FOWNER 让你改属主；SETUID 与 SETGID 让你切换身份；NET_RAW 让你构造任意网络包；MKNOD 让你创建设备节点。这些能力单独看不致命，合起来足以让"容器里的 root"在没有用户命名空间的情况下，对挂载进来的宿主机目录拥有完全的控制权。

第二条，在没有启用用户命名空间时，容器里的 uid 0 和宿主机的 uid 0 是同一个数字，而内核对权限的判断基于数字，不基于"你在哪个容器里"。所以一旦容器里的进程通过任何途径拿到宿主机的执行机会（比如利用一个内核缺陷），它已经是一个宿主机的 root，不需要再提权。

第三条，你对挂载进来的宿主机文件是 root。这就是为什么"把 .env 挂进容器让它读配置"这种做法比它看起来危险：容器里的 root 有 DAC_OVERRIDE，它能读这个文件；而如果同一份挂载是可写的，它也能改。第 06 章讲卷的时候我们关注的是数据能不能活过容器，这里补上另一半：挂载不仅传递数据，也传递权限。

第四条，root 能做更多系统调用，攻击面更大：同一个内核漏洞，从 root 出发的利用路径通常比从普通用户出发更短、更稳定。攻击者圈子里有句话叫"root 是最舒服的起点"，它的工程含义是——不要把他送到那个起点。

把非 root 写进 Dockerfile：Node 与 Python 两种真实写法

非 root 有两层做法。外层是运行时的 --user，它立刻生效、不用重建镜像，适合临时验证与排障；内层是 Dockerfile 里的 USER 指令，它写进镜像、跟着交付物走，才是真正该做的。原因是第 05 章那句老话：镜像才是你的交付物，命令行参数依赖别人的记忆，镜像里的声明依赖机制。

# Node 版本：直接用镜像里已经存在的 node 用户
FROM node:20-alpine
WORKDIR /app
COPY package.json package-lock.json ./
RUN npm ci --omit=dev
COPY --chown=node:node . .
USER node
CMD ["node", "server.js"]

node:20-alpine 里已经有一个 uid 1000 的 node 用户，不需要自己建。两个细节：COPY --chown=node:node 让拷进去的文件从一开始就属于 node，而不是先以 root 拷进去再 chown，这既少一层，也避免 root 的痕迹留在应用文件上。USER node 写在最后——第 05 章讲过的顺序规则在这里直接生效，把 USER 写在 RUN npm ci 之前，那次安装会以非 root 执行，很可能因为写不进全局目录而失败。

# Python 版本：Debian 系镜像里没有现成的非 root 用户，自己建一个
FROM python:3.12-slim
RUN groupadd --gid 10001 app \
    && useradd --uid 10001 --gid app --create-home --shell /usr/sbin/nologin app
WORKDIR /app
COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt
COPY --chown=app:app . .
USER app
CMD ["python", "app.py"]

这里建的是一个固定的数字身份：uid 10001、gid 10001，登录 shell 设成 nologin——这个用户不是用来登录的，只是用来"拥有一个身份"。固定数字不是洁癖，它和下一节的 uid 不匹配问题直接相关。如果你用 Alpine 系镜像（比如 python:3.12-alpine），对应命令是 addgroup -g 10001 app 与 adduser -D -u 10001 -G app app，思路一样。构建完成后务必验证一次，别相信记忆：docker inspect --format "{{.Config.User}}" 你的镜像名 看它是不是 app 或 10001，再用 docker run --rm --entrypoint id 你的镜像名 看真实身份。

uid 不匹配：一个不报错、但会让你半夜爬起来的问题

现在讲一个非常具体、常见、又容易被误解的现象。你有一个目录用绑定挂载进了容器，容器里的进程以 uid 1000 运行并创建了一个文件。这个文件在宿主机上的属主是谁？答案是 uid 1000 对应的那个用户——而 uid 1000 在不同机器上往往是不同的人：在你的 WSL 发行版里通常是你，在服务器上可能是另一个同学，在容器里可能是一个叫 node 的账户。数字相同、人不同，这是问题的全部来源。它有两种表现：一是你写的文件在宿主机上"属于别人"，别人改不了也删不掉；二是容器里的 uid 在宿主机上是个没有写权限的陌生人，于是应用在挂载目录里创建缓存时直接报权限错误。

在 Docker Desktop 的 Windows 场景里，这个现象会被抽象掉一层：绑定挂载的 Windows 目录在容器里看起来是一组所有权被统一处理过的文件，你不太容易观察到"文件被某个数字拥有"。所以这个实验最好放到 WSL2 里做——那也是容器真正运行的地方。做法很简单：把目录挂进容器，让容器以 1000 的身份创建文件，然后在 WSL 里用带数字的列表命令看属主。

docker run --rm -v ${PWD}:/data -w /data alpine sh -c "id && touch made-by-container && ls -ln made-by-container"

PowerShell 里的 ${PWD} 会展开成当前目录的完整路径。这条命令把当前目录挂到容器里的 /data、把工作目录设成 /data，然后以默认的 root 身份建一个文件，并用 -n 参数（显示数字而不是名字）打印属主。你会看到属主是 0 0，也就是 root root——这正是"文件被 root 拥有"的现场。变体实验：在前面加上 --user 1000:1000 再跑一次，属主会变成 1000 1000；接着在 WSL 里用 ls -ln 看同一个文件，数字一样，但它对应的"人"取决于你那台机器上 1000 是谁。

解决它有三种层次。第一种最省事：运行时用 --user $(id -u):$(id -g) 把宿主机当前用户的身份带进容器，让两边数字一致，开发机上最快见效。第二种，构建时把 uid 与 gid 做成构建参数，让镜像适配不同机器；代价是同一个镜像在不同机器上构建出的 uid 不同，破坏了"同一份镜像到处一样"的性质，所以它更适合开发环境。第三种最正规：让应用根本不需要往挂载目录写文件——数据写进命名卷，或者把要写的目录在构建时就设成应用用户拥有。绝大多数"权限不对"的根因，都是把该由存储层负责的事交给了文件系统权限。

再往下两层：用户命名空间与 rootless 模式

上面几条危险里，有一条的前提是"容器里的 uid 0 和宿主机的 uid 0 是同一个数字"。用户命名空间（User Namespace）正是冲着这个前提去的：它在容器内的用户编号与宿主机的用户编号之间插进一张映射表，容器里的 0 号可以映射到宿主机上一个高位编号，比如 100000。这样一来，攻击者即使在容器里成功提权到 root，他在宿主机上的真实身份仍然是一个几乎没有任何权限的普通用户。这层映射的好处是它不需要应用做任何改造——不改代码、不改镜像，它改变的是同一个数字在两边的含义。

rootless 模式走得更远：它让整个守护进程本身以普通用户身份运行，而不是以 root 运行。收益算得清：守护进程不再是特权进程，它被攻破的后果从"整台机器"降到"那个用户的家目录"，容器里的提权在宿主机上同样贬值。代价也算得清：绑定 1024 以下的端口需要额外配置，网络栈往往要走用户态转发因而行为与性能都有差异，卷的权限更绕，依赖特权的功能直接不可用。Docker Desktop 上这件事的形态有点特别——你的引擎本来就跑在一台专用的 Linux 虚拟机里，那台虚拟机替你承担了"隔离危险进程"的角色，所以 rootless 在这里的边际收益不像在裸机服务器上那么大。但思路值得你记住：当一层边界无法继续加固时，就在它外面再加一层承担风险的壳，这是安全设计里反复出现的招式。

回 望

第 05 章讲 Dockerfile 时提过三件事，现在它们被同一根线串起来了。第一，ARG 和 ENV 都可能把不该留的东西留在镜像里——第六节会专门兑现这个警告。第二，当时我们说"生产镜像应该显式声明非 root 用户"，但只给了半句话，没讲为什么以及怎么写，这一节补上了。第三，基础镜像的选择影响攻击面，当时是从体积和兼容性角度说的，第五节的镜像供应链会从漏洞数量这个角度接着说。同一份 Dockerfile，在不同的章节里被读出不同的风险，这本身就是"深度学习"该有的样子。

前 瞻

第 10 章讲 CI 时，你会把这一节的 --user 和第六节的密钥做法一起搬进流水线：构建阶段用密钥挂载读一次私有仓库的凭据，运行阶段用环境变量从密钥管理系统取值注入，镜像里干干净净。到那时你会发现，一个在本地靠"记得加参数"维持的安全习惯，在流水线里必须变成一条写进配置的规则——因为流水线上没有人记得任何事。第 11 章还会遇到一个新情况：AI 镜像往往以 root 运行、依赖庞大、镜像几个 GB，加固的难度和收益都会被放大。

思 考
  1. "容器里是 root，但和宿主机的 root 不一样"——请把这句话拆成"对的一半"和"危险的一半"，各举一个具体场景。 提示：一边是内核替你做过的筛选，另一边是数字相同这件事的后果。
  2. 你的应用需要往挂载进来的宿主机目录写日志。你会选哪一种解决方案：运行时 --user、构建期参数化 uid、还是改成写命名卷？请说明你为了这个选择放弃了什么。 提示：三种方案分别把成本放在了运行时、构建时和架构上。

把权限削到刚好够用：Capabilities 与内核级防护

上一节说容器里的 root 被内核筛过一遍，筛子就是 Linux 能力（Linux Capabilities）——内核把 root 那种"什么都能做"的超级权限拆成几十项具体特权，每一项管一小类操作。这个设计的意义在于：它让"管理员"这个身份从一个整体变成了一个可以逐项挑选的集合。它的存在也解释了一个初学阶段最容易误解的现象：同一个镜像，在你的笔记本上跑得好好的，在别人的机器上换个运行时可能就报权限错误——因为两边授予的能力集合不一样。

先看清楚你手里默认有什么。每个进程都能在自己的状态文件里读到当前生效的能力位图。

docker run --rm alpine grep Cap /proc/self/status

你会看到四行以 Cap 开头的输出：CapInh（可继承的）、CapPrm（允许的）、CapEff（当前生效的）、CapBnd（边界，也就是"你将来最多能拿到哪些"）。你最该看的是 CapEff，它是一串十六进制数字，默认情况下会是一个类似 00000000a80425fb 的非零值——这一串位就对应着 Docker 默认留给你的那十几项能力，包括 CHOWN、DAC_OVERRIDE、FOWNER、SETUID、SETGID、NET_RAW、SYS_CHROOT、KILL 等。位数与取值会随 Docker 版本和内核变化，所以你只需要记住一件事：默认不是零。

docker run --rm --cap-drop=ALL alpine grep CapEff /proc/self/status

加上 --cap-drop=ALL 之后，CapEff 会变成一长串 0。注意这里发生的事情：进程依然是 uid 0，身份没变，但它手里已经没有任何特权了。这就是"能力"这个概念最漂亮的地方——它把"你是谁"和"你能做什么"分开了。请记住这个区别，因为它正是"容器里的 root 不等于宿主机的 root"这句话的技术根据。

实 验 二 · 削 到 只 剩 所 需

目的：亲眼看一次"能力被拿掉之后，连 root 都会失败"。第一步，把能力全部丢掉，然后让 root 去改一个文件的属主——改属主需要 CHOWN 这项能力。

docker run --rm --cap-drop=ALL alpine chown nobody /etc/hostname

你会看到 chown: /etc/hostname: Operation not permitted。这不是文件权限的问题——是身份为 root 的进程缺少执行这类操作所需的那一项能力。第二步做一个变体：只把 CHOWN 加回来。

docker run --rm --cap-drop=ALL --cap-add=CHOWN alpine chown nobody /etc/hostname

这条命令什么都不输出，并且退出码是 0——同一件事，用一项精确授予的能力就完成了，而不是把全部特权交出去。请你解释一下这两条命令的差别，然后再想一个变体：如果你要跑 ping 这类需要构造原始网络包的诊断工具，缺的又是哪一项能力？答案是 NET_RAW，下面这条命令能验证它。

docker run --rm python:3.12-alpine python -c "import socket; socket.socket(socket.AF_INET, socket.SOCK_RAW, socket.IPPROTO_ICMP); print('raw socket ok')"
docker run --rm --cap-drop=ALL python:3.12-alpine python -c "import socket; socket.socket(socket.AF_INET, socket.SOCK_RAW, socket.IPPROTO_ICMP); print('raw socket ok')"

第一行会打印 raw socket ok：Docker 的默认能力集合里包含 NET_RAW，所以创建原始套接字是允许的——这就是容器里能跑 ping 的原因。第二行会抛出一个 PermissionError: [Errno 1] Operation not permitted，因为能力被丢光了，内核在创建套接字这一步就拒绝了。现在你手上有一个可以反复使用的判断方法：遇到"容器里某个工具报权限错误"，先问它需要哪一项能力，再用 --cap-add 精确补上，而不是加 --privileged。

能力它能干什么谁真的需要它不给它时会看到什么
CHOWN修改文件属主与属组启动脚本需要把数据目录交给应用用户启动时报 Operation not permitted
NET_BIND_SERVICE绑定 1024 以下的端口直接监听 80 或 443 的服务bind: permission denied

这张表里 SYS_ADMIN 那一行值得单独说一句：它在安全圈里常被形容为"半个 root"，因为它能挂载文件系统、能改的东西也特别多。你在网上搜到的很多"加上 SYS_ADMIN 就能跑"的解决方案，本质上是把一个业务容器变成了一个可以做系统管理操作的地方。如果某个程序坚持要它，正确的疑问应该是：这个程序为什么需要操作系统级的能力？它是不是本来该跑在宿主机上，或者该换一个实现？

能力只是第一层。往下一层是 seccomp（Secure Computing Mode，安全计算模式），它管的是更细的东西：进程允许调用哪些系统调用。系统调用是用户态程序向内核提请求的唯一正规入口——第 01 章讲过，容器里的程序和宿主机的普通程序走的是同一扇门。Docker 默认给容器加载一份白名单，把一批危险的、或对容器来说毫无意义的系统调用挡在门外，被挡掉的有四十多个名字，其中很多是早年间的冷门接口。它的价值在于：即使攻击者已经能在你的容器里跑任意代码，他要做的动作仍然可能一头撞在这张名单上。

再往下一层是强制访问控制，也就是 AppArmor 和 SELinux 这类框架。它和能力的区别用一句话就能说清：能力回答"你能不能做这类操作"，强制访问控制回答"你能不能碰这个对象"。哪怕你是 root、哪怕你有这项能力，只要策略里没写"允许访问这个路径"，你照样被拒。Docker 会为容器加载一份默认策略，名字叫 docker-default，它做的事比能力限制更细，但它的可用性与宿主机发行版强相关：Ubuntu 系默认启用 AppArmor，RHEL 系默认启用 SELinux，而 Docker Desktop 的 Linux 虚拟机是裁剪过的，你能看到什么取决于它的内核配置。别猜，直接问系统：

docker info --format "{{.SecurityOptions}}"

这条命令会打印当前守护进程启用了哪些安全机制。典型输出里你会看到 name=seccomp,profile=builtin 与 name=cgroupns，说明 seccomp 白名单正在生效；如果你的宿主机是 Ubuntu，这个列表里通常还会多出一个 name=apparmor。如果某个机制没有出现在这里，那它对你就等于不存在——这也是一个有用的自查动作：你以为存在的防护层，未必真的加载了。

第三层是只读根文件系统。这个措施的效果特别直观：容器启动时那一整套文件是只读的，任何试图写系统目录的操作都会立刻失败。它防的是什么？防的是"攻击者拿到执行权之后往容器里写东西"——写一个后门脚本、改一个配置文件、放一个挖矿程序。它同时也是防自己：一个只读的根文件系统会逼你把所有需要写的地方显式声明出来，这恰好是第 06 章讲的那条原则——容器无状态，数据外置。

docker run --rm --read-only alpine touch /newfile
docker run --rm --read-only --tmpfs /tmp alpine sh -c "touch /tmp/newfile && echo wrote-ok"

第一行会报 touch: /newfile: Read-only file system，退出码是 1。第二行会打印 wrote-ok：--tmpfs /tmp 在只读的根文件系统之上挂了一小块内存盘，所以 /tmp 是可写的，而其他目录依然只读。这两条命令合起来就是只读根文件系统的完整用法：先把根锁上，再为应用真正需要写的少数几个目录开小口。要注意的是，挂载进来的数据卷不受 --read-only 影响，它们该可写还是可写——这一点既是方便，也是提醒：只读根文件系统保护的是镜像那一侧，保护不了你自己挂进去的东西。

防护层它替你拦住了什么它拦不住什么启用它的代价
非 root 用户让"容器里提权"重新变成一件需要努力的事配置型的门（挂载、特权）要处理文件属主与端口权限
Capabilities 裁剪大量系统级操作，包括挂载与改属主不需要特权的普通攻击面个别工具要单独补能力
seccomp 白名单一批危险或无关的系统调用白名单之内调用里的逻辑漏洞极少，但排障时要先想到它
AppArmor / SELinux按对象与路径的越权访问策略没覆盖到的资源与发行版绑定，出错时很难一眼看出
只读根文件系统往容器里写后门、改配置、落地文件往卷与 tmpfs 里写东西应用需要在启动时报错并暴露写入点

把这张表竖着读一遍，你会看到纵深防御的思维方式：没有哪一层能独立解决问题，每一层都只负责提高攻击者需要的条件数。反过来，任何一层被整体关掉，你的防线就退回到上一层的水平。这就是为什么"为了排查问题先关掉 seccomp"和"为了跑起来先加 --privileged"是同一类错误的两种面孔——它们都在用"撤掉一层"的方式换取一时的顺利。

易 错 点

看到 Permission denied 就去搜参数，搜到的答案往往是最宽的那一个。这是最容易养成、也最难改掉的坏习惯。请给自己定一条规矩：任何一次为了"让它跑起来"而放宽权限的操作，都必须同时写下两样东西——这一项权限在防什么，以及你打算什么时候收回来。写不出来就别放宽。自查的方法是记下当时的报错原文和最终加的参数，一周后回头看：如果那个参数是 --privileged、--cap-add=SYS_ADMIN 或者 seccomp=unconfined，而你说不清具体原因，那就是该重做的时候了。

展开：Docker 为什么默认不把所有能力都丢掉

这是一个很值得琢磨的设计选择。理论上最安全的样子是"零能力加非 root"，但那样一来，大量现成镜像会在启动时立刻失败：启动脚本要 chown 数据目录、要写 /var/log、要绑 80 端口、要读 /etc/shadow 来做一些初始化工作。Docker 面对的是一个十多年前的现实——镜像世界的存量巨大，任何让"装完就不能跑"的改变都会赶走用户。所以它选择了"默认留下十几项、危险的那几十项丢掉"这条中间路线，属于兼容性优先的保守选择，也符合前面说的那笔交易。对你的启发是：默认值代表的是"绝大多数场景能被接受的最小集合"，而不是"你的场景所需的最小集合"。这两个集合之间的差，就是你能进一步削减的空间。测量方法很简单：把能力全部丢掉，跑一遍你的应用，看它在哪一步报错，然后只补那一项。你大概会发现自己加上两三行就够用了。

镜像供应链：你信任的到底是谁写的代码

现在把视线从"运行中的容器"移到"你拉下来的镜像"。Dockerfile 第一行写着 FROM，这是全篇最像"信任声明"的一行：你把自己整个应用的底座交给了那个镜像的作者，包括他填进去的每个软件包、每条配置、以及他依赖的那些东西。第 03 章讲基础镜像时是从兼容性和体积看它，现在换个角度：你继承的不只是操作系统和运行时，还有它全部的已知漏洞和全部的作者意图。

先说漏洞数量这个可测量的侧面。镜像的漏洞主要来自它装进来的软件包：包越多、越老、越冷门，命中已知漏洞的概率越高。所以基础镜像的选择直接决定了你的起点。下面这张表给出的是量级，不是精确数字——镜像每天在变，但量级关系相当稳定。

基础镜像压缩后体积量级软件包数量量级典型的漏洞数量级它的取舍
alpine3—4 MB十几个个位数，常常是 0 到几个极小、攻击面小；musl libc 可能带来兼容问题
python:3.12-slim约 45—50 MB一百个上下几十个量级兼容性最好的一档，体积与漏洞都可接受

这张表的读法比数字本身重要。第一，漏洞数量与镜像大小、包数量强相关，所以"选一个精简的基础镜像"是收益最高、成本最低的一件事。第二，漏洞数量不等于风险：一个不联网、不接受外部输入的构建阶段镜像，那几百个漏洞的被利用概率很低；而一个直接对公网提供服务的镜像，哪怕只有三个漏洞也值得逐个看清楚。第三，AI 场景是例外中的例外——第 11 章会讲，CUDA 镜像动辄几个 GB、上千个包，你没法靠"换个更小的基础镜像"解决，只能靠别的机制。

用 docker scout 扫描，以及扫不了的时候怎么办

镜像漏洞扫描（CVE 是公开漏洞的统一编号体系）做的是把镜像里的软件包版本与漏洞数据库比对，列出风险项。Docker Desktop 自带的工具叫 Scout，命令是 docker scout，你先用两个子命令就够：quickview 给概览，cves 给逐条明细。

docker scout version
docker scout quickview alpine:3.20

第一条只是确认你的 Docker Desktop 里装了这个插件——它会打印一个版本号，比如本文写作环境里的 v1.24.0。第二条给出概览：这个镜像基于什么、有多少个包、各严重级别各有多少漏洞。如果第二条报错说需要登录，先执行 docker login 再试；如果报"命令不存在"，说明 Desktop 版本偏旧，请直接跳到本节后面的替代路径，不要在这里卡住。

docker scout cves alpine:3.20

这条会逐条列出漏洞。第一次看这份输出，请只关注三列。第一列是严重级别（severity），从 Critical、High、Medium 到 Low，它表达的是"这个漏洞一旦被利用，后果有多严重"，不是"你有多危险"。第二列是漏洞编号（以 CVE 开头的那串字符），它是你和外界沟通这件事的唯一通用语言——查资料、找官方公告都靠它。第三列最重要，是"修好版本"那一列，它告诉你升级到哪个版本就能解决。一个没有修好版本的漏洞，对你来说暂时只是一个需要接受或绕过的事实；一个有修好版本的漏洞，才是一条可以立刻执行的动作。请把这份输出读成一张待办清单，而不是一张成绩单。

必须提前交代一个现实：docker scout 并不是所有环境都能用。它依赖较新的 Desktop 版本、需要插件存在、部分功能要登录，校园网或公司网络下还可能因为访问不到相关服务而超时。这不是你的错，也不该让你产生挫败感。下面是三条替代路径。

第一条，去 Docker Hub 的镜像页面看：官方镜像页带有漏洞概况，不需要你本地有任何工具。第二条，用"体积与包数量"做间接证据——这不是精确扫描，但它足以支撑同样的决策，因为漏洞数量与包数量强相关。

docker image ls alpine python:3.12 ubuntu:24.04
docker run --rm alpine:3.20 sh -c "apk info | wc -l"
docker run --rm python:3.12 sh -c "dpkg -l | wc -l"

第一行对比三个镜像的大小，量级差一眼可见。第二行数出 alpine 装了多少个包，通常十几到二十几个。第三行数出完整版 python 镜像里的包数，一千行上下（dpkg -l 含几行表头，自己减掉）；换成 python:3.12-slim 再跑，数量会掉到一百上下。这三条命令不依赖任何扫描服务，随时可跑。

第三条，如果你在用 WSL2 或一台 Linux 机器，可以用社区里成熟的开源扫描器，比如 Trivy 或 Grype。这里不给安装命令，因为它们版本更新很快，照着官方说明做更靠谱。原则只有一条：扫描器换来换去没关系，你要看的始终是同样三列——严重级别、漏洞编号、有没有修好的版本。

前 瞻

把扫描这件事从"我偶尔想起来跑一次"变成"每次构建都自动跑、不达标就不许合并"，是第 10 章要做的事：在 CI 里加一道扫描门禁，让安全从个人习惯变成流水线规则。第 11 章你会看到这道门禁在 AI 场景下变得更难执行——CUDA 镜像的漏洞数量会让任何"零漏洞"的门槛失去意义，那时候你要学会区分"必须处理"和"我们决定接受，并记录在案"。第 12 章再往上走一层：集群里除了镜像本身的漏洞，还有谁能部署什么、谁能读到哪些密钥的问题，那是 RBAC 和最小权限的地盘。

SBOM、来源证明与 digest 固定

扫描回答"现在有哪些已知问题"，但供应链安全还有两个更基本的问题没有回答：这个镜像里到底有哪些东西？它是谁、用哪份源码构建出来的？回答这两个问题的是两类元数据。

SBOM（Software Bill of Materials，软件物料清单）是镜像里全部软件组件与版本的清单，可以把它想成一张配料表。它的价值在危机时刻才显现：某个包被爆出严重漏洞的那天，你不必逐个镜像重扫，查一遍 SBOM 就能在几分钟内回答"我受不受影响"。来源证明（provenance）记录的是"这个镜像谁用什么命令构建、源码来自哪个提交"。这两样东西不需要额外服务，BuildKit 已经支持：

docker buildx build --sbom=true --provenance=true -t myapp:0.1 .
docker scout sbom alpine:3.20

第一条在构建时额外生成 SBOM 与来源证明，这类证明会跟着镜像一起被推送，可以用 docker buildx imagetools inspect 你的镜像名 在输出里看到对应段落；找不到它们，说明这个镜像没有附带证明——这本身就是有用的信号：你没法回答"它里面有什么、谁构建的"。第二条直接查看已有镜像的清单，让你先看看真实 SBOM 长什么样。这些机制要真正发挥作用需要把镜像推到仓库，本地构建结果里的信息并不完整，现在看不懂也不要紧。

第三个工具是 digest。第 03 章讲标签时埋过一个伏笔：标签是一个可变的指针，同一个 1.27 今天和明天可能指向完全不同的内容。digest 不一样，它是内容算出来的哈希，内容变一位它就变一位，冒充不了。固定的做法分两步：先查出 digest，再写进 FROM。

docker inspect --format "{{index .RepoDigests 0}}" alpine:3.20
docker buildx imagetools inspect alpine:3.20

第一条需要先 docker pull alpine:3.20，它会打印形如 alpine@sha256:一长串十六进制的摘要，这就是这个镜像内容的身份。第二条不下载镜像也能查到 digest 与多平台信息，适合网络受限或只想确认时使用。拿到 digest 之后，Dockerfile 里就可以写成 FROM alpine:3.20@sha256:那一长串——标签留着给人看，digest 用来锁住内容。代价必须说清楚：从此以后你拿不到"上游修好了"这个福利，基础镜像更新了你的构建不会跟着变，需要有人主动更新那串哈希。这是一个真实的交易，它的配套方案是第 10 章讲的定期重建——只做前一半，你会得到一个稳定但持续变旧的地基。

digest 能证明"内容没被换过"，但证明不了"它出自你以为的那个人"。回答后一个问题需要签名：给镜像附一份用作者密钥签出的声明，验证时用公钥核对。签名工具更新很快，动手时以官方说明为准，但判断标准不变——只有能回答"是谁构建的"的机制才谈得上来源可信，digest 单独只解决了完整性问题。

那个反直觉的问题：一个镜像放半年，漏洞会变多吗

请你先自己给一个答案，再往下读：把一个镜像原封不动地放上半年，不重建、不更新、不做任何操作，它的漏洞数量会变多、变少，还是不变？直觉会说是"不变"——毕竟什么都没动。正确答案通常是"变多"。

原因不在于镜像变了，而在于参照系变了。漏洞数据库是一个每天都在被充实的活体：安全研究者持续披露新问题，厂商持续给旧版本软件补上新的 CVE 编号。你镜像里那个半年没动过的 openssl 版本，在半年后的数据库里会匹配到更多条目——不是它变坏了，是人们对它的了解变多了。第二个原因是扫描工具本身在更新：规则更细、能识别的组件更多，同一份内容会扫出更多结果。第三个原因是"不动就不会变"这个假设可能不成立：如果你的 FROM 用的是可变标签而不是 digest，一次重新构建就会把地基换成半年后的新版本，它可能修好了一些漏洞，也可能带进来一批新依赖。你以为自己在原地不动，实际上构建结果一直在漂移。

这个反直觉的结论改变了安全在时间轴上的形态。一次扫描通过不等于永久通过；一份镜像的漏洞数量不是一个属性，而是"镜像加时间加漏洞数据库版本"三者的函数。所以你必须建立周期动作：定期用同一份 Dockerfile 与源码重建、重新扫描、重新决定要不要更新依赖。一条实用的起点是——基础镜像跟着上游的安全更新走，业务镜像每月重建一次，每次结果与上一次对比，这样你看见的是"这一个月里世界变了多少"，而不是一个吓人的总数。

思 考
  1. 一个镜像放半年不动，漏洞数量为什么会变多？请把这个结论讲给一个不做技术的朋友听，看他能不能听懂"参照系变了"这件事。 提示：可以借用体检报告的比喻——你的身体没变，但医学界对这项指标的判断标准变了。
  2. 如果供应链上游被投毒——你依赖的基础镜像里被塞进了恶意代码——你手上哪些手段能发现它，哪些手段完全发现不了？ 提示：把"漏洞扫描""SBOM""digest 固定""来源证明"四样东西逐个过一遍，看它们各自能回答什么、不能回答什么。
  3. 固定 digest 和定期重建是相互矛盾的两个动作，为什么必须一起做？如果你只能做一件，你会选哪一件，为什么？ 提示：一个解决"内容漂移"，另一个解决"内容过时"，它们的失效方向正好相反。

密钥治理：别把钥匙插在锁上

这一节要兑现第 05 章埋的那个警告。当时我们说 ARG 和 ENV 都可能把不该留的东西留在镜像里，现在来做一个可以自己验证的演示。先提一个问题，你猜猜答案：为什么一条你明明已经删掉的文件，用 docker history 还能看出痕迹？

先做准备。PowerShell 里 @' 到 '@ 之间是一个单引号 here-string（原样字符串），它会把内容原样写入文件、不做变量替换，正好适合写 Dockerfile。下面这段会在当前目录生成一份故意写坏的 Dockerfile，请不要把它用在任何真实项目里。

@'
FROM alpine:3.20
ENV API_TOKEN=demo-token-not-a-real-secret
RUN echo "token is $API_TOKEN" > /note.txt
'@ | Set-Content -Encoding ascii Dockerfile

这段脚本会在当前目录生成一个 Dockerfile：它把一个假令牌写进了 ENV，又在 RUN 里把令牌写进 /note.txt。如果执行时报错说找不到 here-string，请检查两个细节：@' 必须单独占一行且后面立刻换行，而结尾的 '@ 必须顶格写在行首。如果你的编辑器或 Shell 把行尾写成了 CRLF 也不用担心，现代构建引擎能正确处理；万一你遇到奇怪的解析错误，把文件另存成 LF 行尾再试一次。这个令牌是我编的，不是真的，请你自己也不要往里面填真的。

docker build -t leak-demo:v1 .
docker image history --no-trunc leak-demo:v1

第二条命令会打印这个镜像的每一层是怎么产生的。加 --no-trunc 是为了让它不要截断命令文本。请在输出里找那一行 ENV——你会看到完整的 ENV API_TOKEN=demo-token-not-a-real-secret 明明白白地躺在那儿。构建历史（也就是 docker history 读的那份记录）是镜像配置的一部分，它不是日志，不会被清理，删不掉。同一个秘密还可以从第二个出口被读到，下面两条命令分别从配置和从层里取证。

docker inspect --format "{{json .Config.Env}}" leak-demo:v1
docker run --rm leak-demo:v1 cat /note.txt

第一条把镜像的运行时环境变量打成 JSON，你会看到刚才那个令牌完整地出现在里面——这意味着任何能拉到这个镜像的人，一条命令就能拿到它。第二条更让人不安：它把 RUN 那一层里写下的文件内容原样打印出来，也就是 token is demo-token-not-a-real-secret。这个演示说明了一件必须刻进骨头里的事：镜像里的东西是可以被"阅读"的，而不是只能被"运行"的。只要它能被你拉下来，它里面的每一层、每一个文件、每一条元数据都能被翻出来。写到镜像里的秘密，等于公开的秘密。

现在回答开头那个问题：为什么删掉的文件还能被看出来？因为第 03 章讲过的那件事——镜像由只读层叠成，每一条指令产生一层；"删除"这个动作在联合文件系统里并不是把数据抹掉，而是加一个白障标记，让上层视图看不见下层那个文件。数据还在下面的层里，老老实实地待着。同理，你在一个 RUN 里先写密钥再删掉它，这两个动作会落在同一层或者相邻层，删除只影响最终视图，影响不了层的内容。这也解释了为什么"我在 Dockerfile 里用完就把密钥删了"这种自我安慰是无效的。

场景错误做法它错在哪里正确做法
构建时需要访问私有源ENV TOKEN=xxx 或 ARG TOKEN 之后 RUN 使用值留在配置与构建历史里，docker history 与 inspect 都能读到BuildKit 的 --mount=type=secret 把密钥挂进那一次 RUN，不进任何层
构建时下载私有依赖RUN git clone https://用户名:密码@...整条命令连同凭据被记录在该层的构建历史里同上，用 secret 挂载注入凭据，或用 SSH 转发
运行时的数据库密码写进 ENV，或写进镜像里的配置文件镜像本身携带秘密，谁拿到镜像谁拿到密码运行时注入：环境变量由密钥管理系统下发，或挂载只读文件
本地开发的配置把 .env 提交进 GitGit 历史几乎是永久且可被克隆的，删掉提交也还在.env 加进 .gitignore，仓库里只留 .env.example
临时传一个值docker run -e PASSWORD=xxx值会留在容器的配置里，docker inspect 一眼可见，还可能进 Shell 历史用只读文件挂载或编排系统的 secrets；至少改成从文件读取
生产环境的敏感配置把密钥和代码一起放在同一个仓库、同一份镜像里权限无法分离，轮换代价极高交给外部的密钥管理系统，容器只持有"读取它的凭据"

把正确的做法落到具体命令上。构建期的密钥注入在 BuildKit 里叫 secret 挂载，它的原理是：密钥在构建过程中被挂到一块临时内存里，只对当次 RUN 可见，用完即消失，既不进层也不进配置。下面这份 Dockerfile 和它对应的构建命令就是一个完整例子。

# syntax=docker/dockerfile:1
FROM alpine:3.20
RUN --mount=type=secret,id=api_token \
    echo "read a token of length $(wc -c < /run/secrets/api_token)"

这份 Dockerfile 里没有任何一行包含密钥的值。--mount=type=secret 让构建引擎在一次 RUN 期间把密钥文件挂到 /run/secrets/api_token 上，脚本可以从那里读它，但这条命令的记录里只有路径，没有内容。第一行的 # syntax 指令用来指定 Dockerfile 前端版本，因为 secret 挂载属于较新的语法。还有一个纪律要提醒：别把读到的值 echo 出来，构建日志本身也是一种泄漏渠道。

Set-Content -Encoding ascii token.txt "demo-token-from-a-file"
docker build --secret id=api_token,src=token.txt -t app:secret .
docker image history --no-trunc app:secret

第一条准备一个本地密钥文件——构建时它一直在你的仓库之外，不会被打包进构建上下文。第二条把文件作为 secret 传给构建。第三条你可以自己检查：输出的历史里只有那条引用 /run/secrets/api_token 路径的命令，没有任何令牌的值。请顺手做一件收尾的事：把 token.txt 加进 .gitignore，或者在实验结束后删掉它；很多人做实验时很谨慎，实验之后就把密钥文件留在仓库里了。

运行期的密钥有三种常见形态，按推荐程度排。第一种，从密钥管理系统取：应用启动时读环境变量，而这个环境变量由部署系统从外部密钥服务注入，容器自己不知道密钥的内容从哪里来。第二种，Compose 的 secrets：在文件顶层声明 secrets，在服务里引用，Compose 会把它挂到容器的 /run/secrets/ 下。要说明的是，在非集群模式下它本质是一个绑定挂载的只读文件，所以你在 docker inspect 的挂载列表里能看到它——那不算泄漏，因为它指向的是一份受控的外部文件，但你要知道它不是加密魔法。第三种，只读数据卷或者 tmpfs 挂载。第 06 章讲过 tmpfs，密钥这类东西放在内存盘里尤其合适。

还有两个你迟早会见到的名字。云厂商提供的密钥管理服务（Key Management Service，KMS）以及自建的 Vault 这类工具，负责的是"谁在什么时候能取到哪个密钥"，并记录每一次读取——它们把密钥从一个静态的值变成了一个有访问记录的对象。编排系统的 Secret 对象（第 12 章会讲 Kubernetes 的 Secret）解决的则是"怎么把密钥交给某一个容器而不是所有容器"。它们的思路和本章反复出现的那句话一致：不要把秘密放在交付物里，而是让交付物在需要的时候去受控的地方取。

回 望

第 06 章我们讲过数据卷与绑定挂载，当时的目标是让数据活过容器；这一节把同一个机制用在了另一个方向上——把密钥挡在镜像之外。第 03 章讲联合文件系统时提到的"白障"，当时只是解释"为什么删了文件镜像不变小"，现在它是"为什么删掉密钥也没用"的答案。同一套机制，在不同的章节里解释了不同的现象，这是第 03 章那句"层是 Docker 世界里最美的抽象"的真正含义：美不美另说，它足够基础，所以到处都在。

方 法

判断一个项目有没有把密钥管好，不需要读它的全部代码，做三个动作就够。第一个动作，搜镜像：docker image history --no-trunc 你的镜像名，在输出里找 ENV、找含密码或令牌字样的长字符串、找带用户名密码的 URL。第二个动作，搜配置：docker inspect 你的容器名，把 Config.Env 和 Mounts 两段看一遍，问自己每一个值是不是都必须在这里。第三个动作，搜仓库：在项目根目录全局搜索常见密钥关键词，再看一眼 .gitignore 里有没有 .env 与各类凭据文件。三个动作加起来五分钟，能把绝大多数低级泄漏找出来。更值得记住的是它们背后的同一个问题：这个秘密现在存在于哪些地方，需要它的人有几个？任何你答不上来的存在位置，都是一个潜在的事故现场。顺带说一句，把密钥外置还有一个比"防止泄漏"更容易说服同事的好处——轮换。密钥写在镜像里，轮换就意味着重新构建、重新发布、重新验证；密钥外置，轮换只是一次配置更新。这个理由在团队里比"这样更安全"有效得多，第八节会展开这一点。

展开：为什么"用 --build-arg 传密钥"有时看起来没事

你在一些教程里会看到用 --build-arg 传密钥，然后有人反驳说"ARG 会留在构建历史里"。这两种说法都有人验证过，原因在于构建引擎的版本与写法差异：旧构建器会把展开后的命令记进历史，而较新的 BuildKit 对某些情况做了处理，使得你打开 docker history 时可能看不出来。这种"有时看得见有时看不见"的状态最危险——它会让人误以为自己是安全的。判断标准不要建立在"我在我的机器上看了一眼没看见"上面，而应该建立在机制上：只要这个值在某一步被写进了文件系统或配置，它就在镜像里；只要它在构建命令里出现过，它就可能出现在某份记录、某个缓存、某段日志里。所以专业做法很简单：不赌，用 secret 挂载。这也是一个通用方法——当某个做法"似乎能用但说不清为什么安全"时，换一个你能说清机制的做法，而不是省那一步。

把这张表变成一条命令和一些配置，就是下面这些内容。它们可以直接抄，但请你在抄的时候对着上面的表说出每一行在防什么——说不出来的那行，先别加。

docker run -d --name web-hardened \
  --user 10001:10001 \
  --cap-drop=ALL \
  --cap-add=NET_BIND_SERVICE \
  --security-opt no-new-privileges:true \
  --read-only --tmpfs /tmp:rw,noexec,nosuid,size=64m \
  --pids-limit=200 --memory=512m --cpus=1 \
  -p 8080:8080 \
  nginx:1.27-alpine

逐项读一遍：--user 指定非 root 身份；--cap-drop=ALL 清空能力再只补回绑定低端口所需的那一项；no-new-privileges 阻止进程通过 setuid 之类的方式获得更多权限；--read-only 加 --tmpfs 把根文件系统锁上、只给 /tmp 留一块内存盘，顺便用 noexec 禁止在 /tmp 里执行程序、用 nosuid 忽略 setuid 位、用 size 限制它最多占 64 MB；--pids-limit 挡住 fork 炸弹；内存与 CPU 上限防止它拖垮整机。这条命令很可能跑不起来——因为真实的 nginx 官方镜像需要往若干目录写文件。让它跑起来的过程，恰好就是这节课最重要的练习：看懂每一个报错指向哪个目录，再决定那个目录该用 tmpfs 还是该用卷。

services:
  api:
    image: myapp:0.1
    user: "10001:10001"
    read_only: true
    tmpfs:
      - /tmp:noexec,nosuid,size=64m
    cap_drop:
      - ALL
    cap_add:
      - NET_BIND_SERVICE
    security_opt:
      - no-new-privileges:true
    pids_limit: 200
    mem_limit: 512m
    init: true
    secrets:
      - db_password

secrets:
  db_password:
    file: ./db_password.txt

这是同一份策略的声明式写法，也就是第 08 章那套思路的直接延续：你在命令行里敲的每一个参数，都能在 Compose 里找到对应的字段名。有两点值得单独指出。init: true 让 Compose 替你注入一个微型 init 进程当作 1 号进程，解决第 04 章讲过的信号转发与僵尸进程问题——安全清单里带上它，是因为"能优雅停机"本身就是可靠性的一部分。secrets 那两行则是第六节的落地形态：应用从 /run/secrets/db_password 读密码，密钥文件不进镜像、不进 Git。这份片段建议你存成一个模板，以后每个新项目都从它开始，而不是从空白文件开始。

如果只有一天时间，我会按什么顺序做？我的思路是把措施分成三层，从外向内推。第一层是"拆掉已经敞开的门"：把 docker.sock 的挂载去掉、把特权模式换成语义明确的能力、把不该挂的宿主机目录去掉。这一层的特点是改动最小、收益最大，而且做完之后没有任何可逆的麻烦。第二层是"降低出事之后的后果"：非 root、能力削减、只读根文件系统、资源上限。这一层会带来真实的适配工作，但每一项都是可以逐项验证、逐项上线的。第三层是"建立能持续的机制"：固定 digest、定期重建与扫描、密钥外置。这一层不解决今天的问题，它解决的是"半年后你的镜像变成什么样"。三层里最容易被跳过的是第三层，因为它今天不做也没事——这恰恰是它最危险的地方。

易 错 点

加固最常见的失败方式不是"加不上"，而是加上去之后应用起不来，于是有人在深夜把那一行删掉，附上一句"这个先不弄了"。从此这个项目就再也没人碰安全配置。避免这个结局的办法有两个。第一，加固要一项一改、改完验证，不要一次加十行然后面对一屏报错——那样你无法判断哪一行导致了失败，最后只能全部回退。第二，遇到 --read-only 引发的报错时，不要把它当成"只读方案不可行"的证据，而要当成"这份应用没有声明清楚它要写哪里"的证据。它每一次报错都在给你一份清单，告诉你这个应用的真实需求是什么。这份清单本身就有价值，哪怕你最后因为排期原因暂时把只读关掉，你也知道了这个应用到底在写些什么。

前 瞻

这份清单在本地靠你的自觉执行，到了第 10 章就要变成流水线里的硬性规则：镜像构建出来后自动扫描、发现高级别漏洞就拦下、构建时不开特权、密钥从 CI 的密钥存储里注入。原因很朴素——流水线上没有"记得"这件事，只有"配置了"和"没配置"两种状态。第 12 章会把这套思路抬升到集群层面：那时候你要管的不再是一个容器能不能挂载某个目录，而是"谁能部署、谁能读到哪个命名空间的密钥"，也就是最小权限原则在权限系统里的放大版。现在先埋一个伏笔：本章清单里的每一项，在 Kubernetes 里都有对应的字段，只是名字更绕。

安全与工程效率的张力

上一节那条加固命令大概率跑不起来，这不是我故意的，这是安全的真实面貌：每一项措施都在向你的工作流收税。收得最多的是两项，而它们恰好也是最有价值的两种思维训练。

第一笔税是没有 shell 可进。你习惯的排障方式是 docker exec -it 容器名 sh，但一个精简过的镜像（distroless 甚至只有你的二进制文件）里根本没有可用的 shell，你进去只会得到一个"executable file not found"。这正是第 05 章讲过的那个取舍：镜像越小、攻击面越小，你能用的工具越少。解法不是把 bash 装回生产镜像，而是接受一个事实：运行镜像和排障镜像可以不是同一个东西。做法有三种。第一种，在你的 Dockerfile 里保留一个专门的调试阶段：同一份基础镜像、同一份源码，但额外装上 curl、ping、htop 这类工具，构建出 myapp:0.1-debug 这个标签，只在需要时使用。第二种，起一个排障容器共享目标容器的命名空间，让它能看到同一个网络与同一批进程，这样你能用带工具的容器去观察一个没有工具的容器。第三种，用 Docker Desktop 提供的 docker debug 功能，它正是为这个场景设计的，能在不修改镜像的情况下给你一个带工具的调试环境；它需要较新的 Desktop 版本并可能要求登录账号，请先用一条 docker debug --help 确认你的版本里有没有这个命令，没有就走前两条路。

docker run --rm -it --pid=container:web-hardened --net=container:web-hardened alpine sh

这条命令起了一个临时容器，它和目标容器共享进程命名空间与网络命名空间：你在里面执行 ps 能看到的进程列表，和 web-hardened 里的是同一份；你能用它的网络去访问目标容器监听的端口。它比"进目标容器"的好处在于——目标镜像可以保持最小，你也不用改它。用完 --rm 自动清理，什么痕迹都不留。这里的 alpine 本身就是那个"带工具的容器"，你甚至可以换成自己公司统一的诊断镜像。请注意它同样是一条需要被管控的通道，不要在共享命名空间时顺手加上 --privileged。

第二笔税是只读文件系统带来的报错。应用在启动时嚷嚷着要写日志目录、要写缓存、要创建 pid 文件、要在自己的安装目录旁边生成配置文件——每一个报错都在挑战你想关掉 --read-only 的耐心。这时候请记住一条判断准则：需要写的目录是有限的、可以枚举的，而"以后可能还要写别的地方"这种担心是无限的。逐个枚举前一种、拒绝后一种，加固方案就一定能落地。具体动作是：看错误里的路径，把路径按用途分类（临时文件、缓存、日志、运行状态），临时文件与缓存给 tmpfs，日志与需要留存的状态给卷，其余的一律不准写。做完之后你会发现，一个说得清自己要写哪里的应用，本身就更接近第 06 章那条"容器无状态"的理想。

比 喻

最小权限听起来无懈可击，但它的极端形式是"什么权限都不给"，那样的系统连启动都做不到。它更像鞋带而不是保险柜：太松会绊倒你，太紧走不了路，合适的标准不是"越紧越好"，而是"能走路，但不至于掉"。判断边界的方法很具体——问一句"这个权限对应的是它完成本职工作必需的哪一步"，能答上来的就留，答不上来的就削掉。这跟写代码时判断一个函数该不该有某个参数的思路完全一样。

回到技术本体：这条边界在工程上有一个可操作的落点，叫"最小可行权限"。它的做法是先把权限剥到应用跑不动的临界点，然后只加回让它跑起来所必需的那几项，并把每一项写下理由。这个动作你已经在第四节做过一次了——chown 需要 CHOWN，ping 需要 NET_RAW。同样的方法论适用于用户、能力、挂载目录、网络端口、以及你在集群里分配给一个服务账号的权限。

方 法

安全措施最容易变成"相信它生效了"的仪式，破解方法是给每一项措施配一条验证命令。你加了 --cap-drop=ALL，就用 grep 去看 CapEff 是不是全 0；你设了非 root，就用 docker inspect 看 Config.User；你设了内存上限，就用 docker stats 看它是否真的被限制住；你挂了只读，就试着写一个文件看它是否被拒。第 04 章那套"用证据说话"的排障纪律，原封不动地适用于安全配置——它们的共同点是：你以为的配置和真实的配置，经常不是一回事。规则很简单：一条没法验证的安全措施，等于一条没有的安全措施。更进一步的习惯是，把这些验证命令攒成一个小脚本放进仓库，让它在部署之后自动跑一遍。到第 10 章你会看到，它天然就是流水线里的一道检查。

最后说一件比技术更难的事：怎么在团队里推动安全。有一个常见的失败姿势，是拿恐惧说服人——"你不加固，迟早会被黑"。这种话在第一次有效，第二次就变成了背景噪音，因为它不提供行动依据，只提供焦虑。更有效的方式是把对话换到成本这一侧，说三件具体的事。第一件，把风险换算成工作量：一次凭据泄漏意味着所有相关密钥的轮换、所有环境的重配、以及一次说不清的信任损失，而外置密钥让轮换变成改一个值。第二件，让安全的路径变成最省事的路径：给出一个 Dockerfile 模板、一段 compose 片段、一个新建项目的脚手架，把正确做法做成默认值。人不会走最安全的路，人会走最省事的路，所以你要做的是让这两条路重合。第三件，不要在评审里质问"为什么不用非 root"，而是把检查做进自动化门禁，让它成为构造的一部分——机器的一致性，永远比人的自觉更可靠。这三件事的共同点是：它们都不要求同事变得更在乎安全，只要求你把安全做得更顺手。

安全不是一堆参数，而是一串你答得出"为什么"的决定。答不出来的那条参数，迟早会被删掉。

检 查 题
  1. 预测下面两条命令的输出，并解释第二条为什么没有用户名。 
    docker run --rm alpine id
docker run --rm --user 1000:1000 alpine id
    参考答案

    第一条会打印 uid=0(root) gid=0(root) 以及一串附加组，说明镜像默认以 root 运行。第二条会打印类似 uid=1000 gid=1000，没有用户名，因为 1000 这个编号在 alpine 的 /etc/passwd 里没有对应条目。内核只认数字，用户名只是给人和程序看的名字。评分要点：要说出"镜像默认 root 不是必需的，只是默认值"，以及"用户名来自 passwd 文件，不是内核概念"。

  2. 有人说"容器里是 root，所以容器一点都不安全"。这句话哪里说对了，哪里说得不精确？请分三句改写它。
    参考答案

    对的部分：容器里的 uid 0 与宿主机的 uid 0 在没有用户命名空间时是同一个数字，而且默认留下的能力里包含 DAC_OVERRIDE、CHOWN、SETUID 等硬货，所以"以 root 运行"确实是风险的放大器。不精确的部分：它以偏概全地忽略了内核替你做的筛选（能力裁剪、seccomp 白名单、强制访问控制），也忽略了风险主要来自配置而不是默认值。三句改写可以是：容器确实是一层边界，但强度低于虚拟机；容器里的 root 与宿主机的 root 共享同一个数字，这是必须认真对待的事实；这层边界的实际强度由配置决定，而不是由"是不是 root"单独决定。评分要点：区分"默认防护存在"与"默认防护足够"。

  3. 下面这条命令为什么能列出宿主机的容器列表？加 :ro 为什么拦不住它？ 
    docker run --rm -v /var/run/docker.sock:/var/run/docker.sock docker:cli docker ps
    参考答案

    因为 /var/run/docker.sock 是宿主机的守护进程的通信端点，把它挂进容器就等于把这个管理接口交给了容器内的进程；docker:cli 里的客户端默认连的就是这个路径下的套接字，于是请求直接变成了对宿主机守护进程的管理指令。:ro 拦不住它，是因为只读挂载限制的是文件系统层面的写入操作，而"通过一个已连接的套接字发送请求"发生在进程间的协议通信里，不经过文件写入路径。评分要点：必须说出"挂载选项作用的层次与协议请求作用的层次不同"。

  4. 预测这两条命令的结果，并说明它们和 ping 之间的关系。 
    docker run --rm python:3.12-alpine python -c "import socket; socket.socket(socket.AF_INET, socket.SOCK_RAW, socket.IPPROTO_ICMP); print('ok')"
docker run --rm --cap-drop=ALL python:3.12-alpine python -c "import socket; socket.socket(socket.AF_INET, socket.SOCK_RAW, socket.IPPROTO_ICMP); print('ok')"
    参考答案

    第一条打印 ok，因为 Docker 的默认能力集合包含 NET_RAW。第二条抛出 PermissionError，错误号是 EPERM，因为创建原始套接字需要 NET_RAW，而能力被全部丢弃了。ping 之所以需要 NET_RAW，是因为它要自己构造 ICMP 包，而不是用普通的传输层套接字。这也解释了为什么有些精简镜像里 ping 不能工作：可能是缺工具，也可能是能力被削了，要先分清是哪一种。评分要点：说出"内核在创建套接字时就做了检查"，并能区分"缺工具"与"缺能力"。

  5. 给一个容器加 --read-only 之后，应用启动报"只读文件系统"。请写出你的排查顺序，并说明你会怎么处理 /tmp、缓存目录、日志目录这三类路径。
    参考答案

    顺序是：先读报错里的完整路径，不要急着关掉 --read-only；把路径按用途归类；然后逐类给方案。/tmp 与各类临时目录给 tmpfs，必要时加上 noexec、nosuid 与容量上限；缓存目录视情况给 tmpfs（缓存丢了没关系）或给一个卷（需要保住）；日志目录要重新想——容器里最正确的做法是让应用往标准输出打印，由外部系统收集，而不是写文件。如果某个目录是应用运行时必需的状态（比如 sqlite 数据库文件），那就该给它一个命名卷，或者把它移到独立的存储服务里。评分要点：必须体现"逐个枚举真实写入点"的思路，而不是"关掉只读"。

  6. 同事说："容器里 curl 一下 docker.sock 就能看到所有容器，太方便了，我也给我的服务挂上。"请用成本语言向他解释风险，并给出两个替代方案。
    参考答案

    风险的核心不是"能看到"，而是那个套接字同时也能"让它做"。它连接的是以 root 运行的管理接口，任何能连上它的进程都可以让守护进程创建容器、挂载宿主机目录。用成本语言说：为了省掉一次写脚本查状态的麻烦，你把整台宿主机的管理权交给了一个跑着业务代码的进程；一旦这个服务存在一个能被利用的漏洞，攻击者不需要找内核漏洞，直接指挥守护进程就够了。替代方案：一是读取运行时已经提供的元数据（环境变量、容器标签、Compose 注入的信息），很多"需要 API"的场景其实不需要；二是把状态采集放到宿主机侧执行，或者通过一个只暴露少量只读接口的代理转发请求。评分要点：要说清"读"与"写"在同一个接口上是不可分割的，并给出具体替代。

  7. 同一个镜像，digest 没变，三个月前扫描是 0 个漏洞，今天扫出 5 个。请解释原因，并说明这对"通过一次扫描就算安全"这个想法意味着什么。
    参考答案

    原因有三层：漏洞数据库在持续更新，新的 CVE 会被披露并回溯匹配到旧版本的软件包；扫描工具本身在升级，能识别的组件与规则更细；如果这三个月里有人用可变标签重新构建过，那么镜像内容其实已经不是同一份了——但即便内容真的没变，前两条也足以让结果变多。这意味着安全性不是一个可以一次性验收的状态，而是一项需要周期性重复的工作。可操作的推论是：定期重建并重新扫描、与上一次结果对比，而不是"扫过一次就归档"。评分要点：要说出"参照系变了"这个核心，并提到定期重建的纪律。

  8. 下面这段 Dockerfile 有什么问题？请指出问题出在哪一层，并给出两种修复方式。 
    FROM alpine:3.20
ARG DB_PASSWORD
ENV DB_PASSWORD=$DB_PASSWORD
RUN echo "$DB_PASSWORD" > /app/config.ini
RUN rm /app/config.ini
    参考答案

    问题有三处，而且互相叠加。第一，ARG 的值会进入构建相关的记录，构建历史里可能看得到。第二，ENV 会把值永久写进镜像的运行时配置，docker inspect 一条命令就能读到。第三，最后那条 rm 是无效的自我安慰：删除在联合文件系统里表现为加一个白障标记，数据仍然留在下面的层里，任何拿到镜像的人都可以从层里把它翻出来。修复方式：构建期改用 BuildKit 的 --mount=type=secret 把密码挂进那一次 RUN 使用，用完即消失，不进任何层；运行期改用外部注入（环境变量由密钥管理系统下发，或挂载只读的密钥文件），并顺手检查 .gitignore 与构建上下文，别让密码文件被打包进去。评分要点：必须指出"删除不等于抹掉"，并给出构建期与运行期两条不同的修法。

  9. 一个刚接手的项目里，作者为了排查一个权限报错加了 --privileged，并在注释里写了"临时"。你会怎么处理？请给出一个可执行的流程，而不是一句"去掉它"。
    参考答案

    第一步，先弄清它为什么被加上：在容器里复现那个报错，读原始错误信息，判断需要的是哪一种能力或哪一个设备。第二步，用最小替代方案验证：把 --privileged 换成具体的 --cap-add 或 --device，启动并跑通功能。第三步，做一次差异核对：对比替换前后 /proc/self/status 里的 CapEff，确认丢掉的能力里没有业务真正需要的。第四步，把这次替换写进提交信息或注释，说明"为什么是这一项能力"，让下一个人不必重新推导。第五步，把这条自查做成机制——例如在部署前的检查里打印所有容器的特权状态。评分要点：要体现"先理解再收紧"，并且强调把结论记录下来，避免下一次又被加回去。

  10. 假设一个容器被证明存在可远程触发的代码执行漏洞。请你分别估算"以 root 运行"和"以非 root 运行加 --cap-drop=ALL"两种配置下，攻击者从"能跑代码"到"控制宿主机"需要多走哪些路。
    参考答案

    以 root 运行时，攻击者已经在容器里有 uid 0 与十几项能力，他可以读写挂载进来的宿主机目录、用 DAC_OVERRIDE 绕过文件权限、必要时用能力完成进一步操作；如果存在一个能提权的内核缺陷，他还省掉了"先提权"这一步。以非 root 加能力清空运行时，他只能在自己的 uid 下活动，写不了系统目录与只有 root 能碰的文件，做不了需要能力的操作，想提权还得先找到一个本地提权漏洞，而即便提权成功，在启用了用户命名空间的环境里那个 root 在宿主机上也只是个普通用户。结论：非 root 不是"挡住了攻击"，而是把攻击链从一步变成了好几步，每一步都可能失败或留下痕迹。评分要点：要体现"提高条件数"而不是"绝对防护"的思路。

  11. 如果你只有一天时间给一个已经上线的容器加固，你会做哪三件事？请给出排序依据。
    参考答案

    合理答案不止一种，评分看排序依据而不是具体选项。一个可以参考的排序是：先去掉已经敞开的门（挂载的 docker.sock、特权模式、多余的宿主机敏感目录挂载），因为这几项是配置型逃逸的直接通道，改动小、收益大、不影响性能；再降低出事之后的后果（改用非 root 用户、清空能力后按需添加、给内存与进程数设上限），这些需要适配但不难验证；最后建立能持续的机制（固定 digest、建立定期重建与扫描的动作），它今天看不出效果，但决定了半年后的状态。评分要点：必须给出排序理由，并且说明每一项对应威胁模型里的哪一行；只列参数不给理由不给分。

  12. 一个安全措施让你失去了进容器排查的能力，你依然可以把它留着。请设计一套"平时收紧、出事时受控放开"的做法，并说明你怎么保证放开之后一定收回来。
    参考答案

    做法分两半。平时：生产镜像保持最小（不带 shell、只读根文件系统、非 root、能力清空），排障走独立通道——同一份源码构建一个带工具的调试标签，或者起一个与目标容器共享进程与网络命名空间的临时排障容器，用完即删。出事时：确实需要临时放宽某个参数（例如某次需要抓包要加 NET_RAW），把这次放宽当成一次有记录的变更——写下原因、写下期限、写下验证方式，并且优先在预发或复制的环境里做。保证收回的办法不是靠记性，而是靠机制：把"当前所有容器的特权状态与能力集合"做成一条定期执行的检查，任何超出基线的容器都会自己冒出来。评分要点：要说出"把放宽变成一次有记录的变更"和"用检查兜底"这两点。

  13. 动手任务：为你自己上一章做好的那个 Compose 项目写一份威胁模型，并据此改写加固配置。
    参考答案

    评分要点分四部分。第一，威胁模型要写成可读的三行以上：防谁（具体到"校园网里的自动化扫描"这种可行动的描述）、最怕丢什么（具体资产）、当前暴露面（端口、挂载、环境变量、密钥来源）。第二，必须包含一行"我决定暂时接受哪些风险以及为什么"，缺这一行说明只是抄清单。第三，加固配置要能对应到威胁模型：每一条措施说得清它在防上面的哪一行，说不清的删掉。第四，要有验证动作：用 docker inspect 检查 Config.User，用 grep CapEff 检查能力，用 docker history 检查有没有残留密钥。只改配置、不做威胁模型、不做验证的答案只能拿一半分。

自问自答：把知识压进长期记忆

自 问 自 答
  1. 合上页面，用自己的话讲：威胁模型是哪三个问题？为什么第三个问题最难？提示：难在它逼你承认安全有价格。
  2. 为什么说容器是一层边界，但强度由配置决定？请说出至少两个"整体撤掉一层防护"的参数。提示：一个撤掉能力与设备限制，一个撤掉套接字的距离感。
  3. "容器里的 root 和宿主机的 root 不一样"——你能一边画图一边给同学讲清这句话的两面吗？提示：一面是内核的筛选，一面是数字相同。
  4. 为什么 Docker 默认让容器以 root 运行？这个默认值今天还划算吗？提示：从历史与兼容性两端想，再想今天的镜像生态变了什么。
  5. seccomp、AppArmor、Capabilities 三个词，你能否各用一句话说清它们分别管什么？提示：一个管"能调哪些内核接口"，一个管"能碰哪些对象"，一个管"能做哪类操作"。
  6. 为什么往镜像里写密钥、再把文件删掉，等于没删？提示：联合文件系统的删除是一个标记，不是一个动作。
  7. 一个镜像放半年，为什么会变危险？这个结论改变了你对"上线"这件事的理解吗？提示：把安全从一次性验收改成周期性动作。
  8. 固定 digest 和定期重建，为什么必须成对出现？提示：一个防漂移，一个防过时，方向相反。
  9. 如果只能用一条命令来检查一台机器上的容器安全状况，你会用哪条？为什么是它？提示：想想哪条命令能一次暴露特权状态与宿主机路径挂载。
  10. 把"最小权限的边界在哪里"讲给你自己听，你会用哪个例子？提示：鞋带的松紧，或者"能完成本职工作的最小集合"。

本章总结

  • 安全从威胁模型开始：先回答"防谁、防什么、愿意付多少代价"，再决定加什么措施；说不清对应哪一行威胁的措施，加的只是维护成本。
  • 容器确实是一层边界，但强度低于虚拟机，而且强度由配置决定——一个 --privileged 或一次 docker.sock 挂载就能把默认防护整体撤掉。
  • 逃逸分配置型与漏洞型两类，现实里前者远多于后者，因为它不需要运气，只需要一次手快。
  • docker.sock 的挂载是最容易被低估的一条路：套接字没有只读概念，而它背后的守护进程以 root 运行；:ro 拦不住通过协议发出的请求。
  • --privileged 不是"多给一点权限"，它同时解除能力限制、设备限制与 seccomp 约束；绝大多数权限报错只需要一项具体能力。
  • 镜像默认以 root 运行是历史与兼容性的选择，不是必然；Dockerfile 里的 USER 加 COPY --chown 是非 root 的标准写法，运行时可以用 --user 临时验证。
  • 容器里的 root 与宿主机的 root 共享同一个数字，而默认能力集合里仍有 DAC_OVERRIDE、CHOWN、SETUID 这类硬货，所以对挂载进来的宿主机目录拥有完全控制权。
  • uid 不匹配是一个不报错的老问题：文件属主由数字决定，数字相同而人不同就是事故；解决办法从运行时指定身份，到参数化构建，到让应用根本不往挂载目录写东西。
  • Capabilities、seccomp、AppArmor 或 SELinux、只读根文件系统各自只拦一类东西，必须叠起来才叫纵深防御；每一层都要能用一条命令验证它真的生效了。
  • 漏洞数量与镜像的包数量和体积强相关——所以换一个精简的基础镜像常常是性价比最高的一步；同时它又是"镜像加时间加漏洞数据库"三者的函数，放半年不动的镜像漏洞也可能变多，定期重建与重新扫描因此是纪律而不是选项。
  • 写到镜像里的密钥等于公开的密钥——构建历史与层都能被读出来，"用完就删"在联合文件系统里无效；构建期用 secret 挂载，运行期用外部注入。
  • 这一章最重要的一个判断：安全措施的取舍标准不是"能不能万无一失"，而是"它在防什么、代价是多少、我能不能验证它生效"。

这一章教给你的东西，本质上不是一组参数，而是一种看系统的姿势：你不再把容器当成一个"应该安全"的黑箱，而是把它看成一份可以被逐项检查、逐项削减、逐项验证的权限清单。这份清单会随着你的项目一起长大——今天你只关心一个容器能不能写到某个目录，半年后你要关心一个流水线能不能拿到某个仓库的写权限，几年后你要关心一个服务账号在集群里能看到哪些密钥。边界会变，问题的形状不会变，那三个问题也不会变。第 10 章我们要把这些手工做熟的动作搬进流水线：让机器替你构建、扫描、检查、发布，让"记得加固"这件事彻底不需要人记得。

拓 展 阅 读

  • 开发安全最佳实践官方文档 https://docs.docker.com/develop/security-best-practices/ 这一页把本章的清单转成了"构建时该怎么做"的视角，正好补上我讲得比较快的部分：镜像越小越好的理由、多阶段构建与安全的关系、不要装多余工具、如何声明非 root 用户。带着一个问题读：我手上那个项目的 Dockerfile，按它的标准逐条对照，能打几分。读完请回去改一处你觉得最不体面的地方，改完再构建一次。
  • 镜像漏洞扫描（Scout）官方文档 https://docs.docker.com/scout/ 本章只用了 quickview 与 cves 两条子命令。这一页会告诉你其余能力：策略评估、把扫描接进 CI、把结果推回镜像仓库、以及与 SBOM 相关的查看方式。带着两个问题读：第一，severity 的分级依据是什么，为什么它和"我该先修哪个"并不完全一致；第二，如果我想让"高危漏洞为 0"成为一条合并门禁，该在哪个环节配它。第二个问题会是第 10 章的直接铺垫。
  • Docker 官方镜像（DHI）官方文档 https://docs.docker.com/dhi/ 如果你所在的环境对供应链有更严格的合规要求，官方维护的加固镜像体系值得了解：它们在基础镜像选择、漏洞基线、来源证明上都做了额外约束。读它的时候带着一个判断题：它解决的哪些问题，其实用本章讲的基础做法也能解决大部分；哪些是它独有的价值，值得你为它改变现有的构建流程。这一页也是你将来跟老师或实习面试官聊供应链安全时的一个具体抓手。
  • 构建最佳实践官方文档 https://docs.docker.com/build/building/best-practices/ 本章第六节讲的 secret 挂载、第五节讲的 SBOM 与来源证明，都属于构建阶段的能力，这一页是它们的完整入口。它同时把"构建缓存"与"安全"这两件看起来无关的事连了起来——缓存意味着旧内容会被复用，而旧内容里可能就包含你以为已经清掉的东西。带着一个问题读：我的构建过程里，有哪些东西是"用过一次就不该留下"的，它们分别该用哪种机制处理。
  • 开放容器倡议（OCI）规范组织 https://opencontainers.org/ 本章的很多机制之所以在 Docker、containerd、Kubernetes 之间通用，是因为它们背后的规范与实现是分开的。这个站点是理解"哪些是标准、哪些是某个产品的实现"的起点。带着一个问题读：镜像格式、运行时、以及签名与证明相关的规范，各自定义了什么，为什么这种"接口与实现分离"的设计对你的职业发展也有意义。不需要读技术细节，先把这个生态的地图看明白。
值 得 品 读 的 书
  • 《SRE：Google 运维解密》 编译自 Google SRE 团队的经验总结 这本书补的是"工程纪律"这一课。它讲的不是某条安全参数，而是如何把可靠性、变更管理、应急预案变成团队可执行的流程——而本章最重要的一条结论（安全是周期性动作，不是一次性验收）在它那里有完整的方法论支撑：变更要可回滚、监控要能回答"现在正常吗"、每一项规定都要能解释它防的是什么。建议在你做完本章第一个实验之后读，重点看与变更管理和应急响应相关的几章。带着一个问题读：如果我的项目也要写一份"出错时怎么办"的预案，它会长什么样。

  • 《深入理解计算机系统》（CS:APP） Randal E. Bryant、David R. O'Hallaron 著 这本书补的是"最底层的地基"，而且是为长期准备的。本章里那些名词——系统调用、进程与文件描述符、虚拟内存与写时复制、权限位——在它那里都有从硬件到软件的完整讲法。不要指望现在读完，建议先读与"系统级输入输出"和"虚拟内存"相关的部分：前者让你真正理解"往标准输出打印"这件事在操作系统里意味着什么，后者让你理解为什么容器能共享内存页、以及为什么写时复制会出现安全漏洞。带着一个问题读：一个系统调用从用户态走到内核态，中间经过了哪些检查；想通它，本章所有防护层的位置你都会记得很牢。
