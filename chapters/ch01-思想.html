思想的诞生：从"在我机器上能跑"说起

一切工程工具的诞生，都是某个痛苦的历史回声。

本 章 学 习 目 标
  • 能说清"在我机器上能跑"这句话背后到底藏着哪几层技术原因，而不是含糊地归因于"环境不一样"。
  • 理解程序对环境的依赖是分层的，能辨认出一个项目里哪些依赖是显式声明的，哪些是隐性的。
  • 能解释为什么 A 项目要 Python 3.8 加上旧版 numpy、B 项目要 Python 3.12 加上新版 numpy 时，"各让一步"在技术上不成立。
  • 能沿着一条有因果关系的时间线讲出隔离思想的演进：从分时系统、chroot、Jails、namespace 与 cgroups，一直到容器与 Docker。
  • 理解 Docker 在 2013 年成功的真正原因不是它发明了隔离，而是它解决了分发。
  • 能准确说出容器与虚拟机的本质差别是"共享内核"而不是"共享硬件"，并据此推断出各自的能力边界。
  • 理解隔离不是开与关的开关，而是一段可以配置、也必须被配置的强度阶梯。
学 完 之 后 ， 你 应 该 能 够
  • 能诊断一个"在我机器上能跑"的故障，并按依赖层次逐层排查出原因。
  • 能判断一个新项目应该用容器、用虚拟机，还是两者都要。
  • 能解释"同一个镜像跑两个容器却互不干扰"这一现象，并指出它和"镜像只有一个"为什么并不矛盾。
  • 能设计一个最小实验来验证某个技术断言，而不是只相信别人的结论。
  • 能向一位完全不懂技术的同学，用三分钟讲清容器是什么、以及它不是虚拟机。
  • 能识别"有了容器就不用管环境了"这类错误印象，并说出它错在哪个环节。

导学那一章我们把容器说成"被操作系统特殊照顾的一个进程"，还留下两句话没有兑现：一句是"它共享宿主机的内核"，一句是"Docker 并不是容器的发明者"。你可能点点头就翻过去了——那两句话听起来像口号。这一章我们要把它们拆开、装上零件、重新拼回去，直到它们不再是口号，而是你能拿来推理的工具。整章围绕一个问题展开：为什么一个开发者在 2013 年之后，突然不需要再向同事解释自己的电脑了？要回答它，我们得先回到那句被说过几百万次、每次都带着一点委屈的话——"在我机器上明明能跑"。

一句话，四种痛苦

先看一个场景，它平凡到你几乎一定见过。你们的课程设计是三个人一组，做一个用 Python 写的小系统，其中一个人负责数据部分。周三下午三点，负责数据的同学在群里发了一句话："在我机器上能跑。"这句话通常代表三件事同时成立：他本地的程序确实跑通了，他不知道为什么换个人就跑不通，他隐隐觉得这不是他的错。

作为被这句话折磨过的人，你大概会先怀疑代码。但你打开他的代码一看，逻辑没问题；你甚至把他整个文件夹拷过来，一个文件都没漏。然后你开始经历经典的三连击：程序报的第一条错误是一个你没见过的模块名；你装上这个模块之后，第二条错误变成一个版本号不兼容的 API 报错；你把版本降下来，第三条错误变成一句"找不到共享库"。第四步是崩溃，第五步是打开搜索引擎，第六步是三个小时过去，你开始相信编程这件事不适合人类。

我想请你先把"代码有 bug"这个直觉放到一边。因为在这类故障里，报错的从来不是你的代码，而是你的世界和别人的世界之间的差异。这句话是本章的第一块基石。代码只是世界里的一个居民，它出门要穿衣服、要坐车、要说同一种语言。你把居民搬过去了，却没搬他的世界。

这类痛苦并不是一种，而是一族。它们看起来都长着"跑不通"的脸，但解剖开来是四个不同的器官。后面的每一章我们都会回到这四个问题上来，所以现在值得花力气把它们分开命名。

这四个问题有一个共同点：它们的代价都不在写代码的时候付出，而在把代码交给别人的时候付出。这是软件工程里最贵的一类代价，因为它总在最不合适的时刻出现——答辩前一晚、演示前十分钟、上线前半小时。

回 望

第 00 章导学里，我们说容器是"一种进程的包装与约束方式"，还提到了环境漂移这个词。当时它只是一个名词。现在我们给它一个具体的形状：如果你的开发机是一台被手工修改了两年、装了七个全局工具、改过两个配置文件的机器，那么你的机器已经和全世界的任何一台机器都不一样了。程序在这样的机器上跑通，是一件概率性事件，而不是一个必然结果。

请注意我上面用的词：概率性事件。这是个很重的说法。它意味着"在我机器上能跑"这句话在逻辑上其实等价于"我这里恰好凑齐了一组没人记录过的条件"。程序能跑不是因为它的环境是对的，而是因为它的环境碰巧是对的。这个区别决定了你在遇到问题时是去修复世界，还是去祈祷。

易 错 点

初学者遇到"跑不通"时的第一反应是怀疑代码，于是花几个小时重构、加日志、改逻辑，最后发现一行代码都不需要改。还有一个同样常见的反方向错误：因为现在有了容器，就把一切失败都归因于"环境问题"而不去看代码。分辨方法其实很朴素：问自己这个失败与"换一台机器"有关吗？把同样的代码在一个干净的环境里跑一遍，如果结果不同，那是环境差异；如果结果相同，那就是代码或需求本身的问题。这个两分钟的对照实验能挡掉你后面大量的无效调试。

先做一次最小的接触：hello-world

在你继续被这些概念名词压着之前，我们先碰一下真东西。打开 PowerShell，敲下面这一行。它不需要你做任何准备，只要 Docker Desktop 正在运行。

docker run hello-world

你会看到一段分行的输出。第一行是"Unable to find image 'hello-world:latest' locally"，意思是本地没有这个镜像，于是它去仓库找；接着是几行 "Pulling from library/hello-world"，说明正在从镜像仓库下载；然后是 "Digest: sha256:…" 和 "Status: Downloaded newer image for hello-world:latest"；之后有一句 "Hello from Docker!"，并附上一段说明它做了哪几步的文字。最后这个容器退出了，你在终端里回到提示符——但容器并没有留在那里运行。

这段输出里藏着的环节清单，长到有点荒谬：查找本地镜像、向远程镜像仓库发起请求、下载若干层、把层解包成镜像、根据镜像创建容器、给容器准备一个隔离的文件系统视图、把主进程启动起来、把主进程的输出接到你的终端上、主进程退出后把容器停下来。你一条命令，触发了后面七章要讲的全部主要机制。这就是为什么这一章要从"你只会敲一条命令"的阶段就开始讲思想：命令太短，短到它会骗你，让你以为底下什么都没有。

前 瞻

这九个环节分别由谁执行？你的 docker 命令其实只是客户端，真正干活的是后台的守护进程，它再把一部分工作交给 containerd 与 runc。第 02 章会把这条调用链一层层剖开，并且告诉你为什么"连不上 Docker"这类故障要先去确认守护进程是不是活着。现在你只需要记住：你敲的命令和真正执行的动作之间，隔着好几个部件。

思 考
  1. 如果你是一名 2008 年的工程师，要说服老板把生产环境切到"把应用装进盒子里"的方案，你会怎么讲这件事的价值？如果他反问"我们已经在用虚拟机了，为什么还要这个"，你能给出哪三个理由，又会在哪一点上承认他其实是对的？提示：可以从"交付物是什么""机器之间能不能互相理解""你付出了多少隔离强度来换这些好处"三个角度分别写一段话。
  2. "在我机器上能跑"这句话，在你学完容器之后，真的会彻底消失吗？请构造一个具体场景，说明它仍然可能出现，并说明这种残留的失败和今天这种失败在性质上有什么不同。提示：想一想那些永远留在这台机器上的东西——显卡驱动、时钟、网络、远处的那台数据库。
  3. 把这四个问题排个序：环境不一致、依赖冲突、交付物模糊、迁移与扩缩。对一个三个人一周的课程设计来说，哪个最致命？对一个要跑三年的线上系统来说，排序会不会反过来？提示：考虑"出错的频率"和"出错后的修复成本"是两个不同的维度。

程序到底依赖什么

要理解"环境"这个词，我们必须先回答一个更具体的问题：一个程序跑起来，究竟需要什么？这里的答案不是"需要电脑"，而是六层可以逐层检查的具体依赖，而它们的可怕之处在于可见性完全不同。

六层依赖，六种被忘记的方式

第一层是运行时本身。Python 代码需要 Python 解释器，而解释器有版本。这句话你早就知道，但你未必意识到这个版本差异有多大：Python 3.8 与 Python 3.12 之间，标准库的行为发生了变化，语法糖被加入，而某些第三方库干脆只支持 3.9 以上。它不是"同一个东西的新版本"，而是"两个脾气不太一样的东西共用一个名字"。

第二层是第三方库及其版本。这是最常被抱怨的一层，因为它有明确的名字，所以它会出现在报错信息里，也因此最容易被误认为是全部原因。这里有一个关键的机制必须讲清楚：很多 Python 库不是纯 Python，而是把 C 或 C++ 写好的代码编译成二进制再包给你的。这种库叫做扩展模块，它编译出来的是针对某个具体 Python 版本、某个具体操作系统、某种具体 CPU 架构的机器码。所以同一个 numpy 版本，在 Python 3.8 的 Windows 上和在 Python 3.12 的 Linux 上，装进去的其实是两个不同的二进制文件。这就解释了一个让初学者极为困惑的现象：你的报错信息看起来是"版本不兼容"，但换个 Python 版本，同样的版本号就忽然兼容了。

docker run python:3.12-slim python -c "import sys; print(sys.version); print(sys.executable)"

你会看到两行输出：一行是 Python 3.12 的完整版本字符串，一行是解释器在容器里的路径，看起来像 /usr/local/bin/python。注意这个路径属于容器的文件系统，它在你的 C 盘上并不存在。这条命令真正的含义是：我没有在你的电脑上安装任何东西，却得到了一次确定的 Python 3.12 执行。

第三层是系统库与动态链接。这一层是初学者最容易彻底错过的，因为它没有出现在 requirements.txt 里。你的程序在启动时，操作系统要先去做一件事：把程序依赖的那些共享库（Linux 上后缀通常是 .so，Windows 上是 .dll）找出来并装进内存。在 Linux 上，这个"找"的过程由动态链接器负责，它按固定顺序去若干目录里检索，并读环境变量 LD_LIBRARY_PATH 的指示。如果你把它要找的东西挪走了，你得到的错误可能是"error while loading shared libraries: libssl.so.3: cannot open shared object file"——注意这个错误里没有 Python，也没有你的代码，它发生在你的代码第一行执行之前。

展开：glibc 与 musl 之争，为什么它会在你最开心的时候咬你一口

几乎每一个 Linux 发行版都会带一套 C 标准库实现，它提供最底层的那些函数：怎么开文件、怎么分配内存、怎么把字符串里的数字读出来。绝大多数发行版（Ubuntu、Debian、CentOS）用的是 GNU 的 glibc；而 Alpine 这个以极小著称的发行版用的是 musl。二者在绝大多数情况下行为一致，但在一些边缘处不同：DNS 解析的细节、区域设置、某些函数的实现方式。

它咬你的典型姿势是这样：你在本地用 Debian 基础镜像做得好好的，为了让镜像从 800 MB 变成 90 MB，你换成了 Alpine，然后某个用 C 扩展写的库开始报错，或者某个二进制文件报出 "not found"——而这个文件明明就在那里。原因是这个二进制在编译时链接的是 glibc，Alpine 里没有它。你的排查会极其痛苦，因为"文件不存在"这个提示是假的，真正缺的是一个你没有意识到自己依赖过的东西。

这个例子值得你记住的不是"别用 Alpine"，而是：你真正的依赖清单，比你能写出来的那份长得多。凡是没被别人替你整理成一份清单的依赖，都是隐性依赖。

第四层是环境变量与配置文件。这里有一个很微妙的事实：环境变量不在代码里，不在版本控制里，不在文档里，它只存在于"某次有人 export 过它"这个事实里。你的程序可能依赖一个 DATABASE_URL，而队友的机器上它指向 localhost，你的指向一个早就关掉的测试库。这类问题最讨厌的地方在于它经常不报错，而是悄悄换了一个行为：连到了错的库、用了错的时区、走了错的代理。

第五层是文件路径与权限。这一层在跨操作系统的协作里杀伤力极大，因为三个平台的规则不一样。Windows 的路径分隔符是反斜杠，Linux 是斜杠；Windows 的文件名不区分大小写，Linux 区分，所以 import DataUtils 在你机器上能跑，在 Linux 服务器上会说不存在 DataUtils 这个模块；Windows 的文本文件默认换行是回车加换行两个字节，Linux 只有一个字节，于是你的 shell 脚本拉到 Linux 上会报一句莫名其妙的 "\r: command not found"；Linux 每个文件还有可执行位，一个脚本文件在 Windows 上做出来、复制到 Linux，可能因为没有执行权限而拒绝运行。

第六层是外部服务。数据库、缓存、消息队列、对象存储——这些不是"环境"，它们是"别人"。你的代码依赖一个正在监听的数据库，而这个数据库的版本、字符集、时区设置、扩展插件，全都是环境的一部分。这一层是无法被完全装进盒子的，我们在本章后面会专门谈它带来的边界。

易 错 点

初学者最常见的诊断错误是"只查看得见的那一层"。看到 ModuleNotFoundError 就一直折腾 pip，看到版本冲突就一直降级，却从不检查系统库、环境变量和路径规则。一个实用的自查习惯是：当你连续两次修改依赖版本都没解决问题时，就说明问题不在依赖版本这一层，赶紧换一层查。另一个自查动作是把故障分成两类："启动前就失败"通常指向系统库、动态链接、权限、路径；"启动后行为不对"通常指向环境变量、配置、外部服务。这个二分法能省下你大量时间。

比 喻

很多人把项目想成一份菜谱：写好步骤，谁都能照着做出来。但真实的项目更像一株植物——菜谱只写了"每天浇水"，却没有写这株植物需要什么样的土、什么样的酸碱度、多少小时的日照、以及它已经在这个花盆里长了两年这件事。你把植物搬到别人家，浇水的方法完全一样，它还是死了。而容器做的事，是把土一起装进花盆。回到技术本体：镜像里装的不只是你的代码，还有运行时、系统库、目录结构、默认环境变量这一整套"土"，它让"照做"这件事第一次有了确定的起点。

方 法

当你遇到一个说不清原因的"环境问题"时，不要从"我该装什么"开始想，而从"我要证明哪一个差异"开始想。具体的动作是：把两台机器上同一层次的信息各打印一份，逐行对比，直到找出第一处不同。层次顺序就是上一张表的顺序——先看运行时版本，再看库版本，再看系统库（Linux 上 ldd 打印出的动态库清单非常有用），再看环境变量（env 或 PowerShell 的 Get-ChildItem Env:），最后看路径与权限。这个方法的威力在于它把玄学变成了差分。排障的本质是找差异，不是找答案。这个习惯会跟着你走进后面每一章。

为什么"各让一步"做不到

现在来正面回答那个让很多人困惑的问题：两个项目依赖冲突时，为什么不能让它们各退一步、商量出一个共同版本？

先看清楚一个被普遍误解的细节。冲突不是发生在"一台机器装不下两个 Python"上，而是发生在"一个名字只能同时指向一个东西"上。在传统的 Linux 或 Windows 环境里，当你执行 python 这个命令，系统必须决定它指向哪一个解释器；当你 import numpy，解释器必须决定它加载哪一个 numpy。这些名字是全局的、单数的。所以哪怕你的硬盘有 2 TB 空间、装得下十个 Python，那条命令依然只能指向一个。这不是空间问题，是名字的唯一性问题。

那能不能靠虚拟环境（比如 Python 的 venv）解决？能解决一半，也正好把问题暴露得更清楚。venv 的作用是让每个项目拥有一份独立的 site-packages，也就是让 import numpy 在 A 项目里加载 1.x、在 B 项目里加载 2.x。但 venv 只管 Python 库，它不管你的 Python 解释器本身是哪个版本，不管你的系统库里装的是哪个 OpenSSL，不管你的 CUDA 是哪一个版本，也不管那个要连的数据库是 5.7 还是 8.0。所以你用 venv 走到一半，会发现剩下的半个问题依然在那里等着你。虚拟环境是一种局部的隔离，容器是一种更彻底的隔离。这个对比很有用，我们在第 09 章讲安全时还会回到"隔离的边界划在哪里"这个问题。

再往深处看一层，为什么库的作者不干脆做到"新旧都能用"？这里有一个残酷的工程现实：兼容不是免费的。假设某个库的 1.x 里有一个函数叫 array，它接收一个列表；2.x 的作者发现这个设计有缺陷，改成了接收一个生成器，并且要求显式指定数据类型。如果他为了兼容，让 array 同时猜两种输入，那么代码会变得难以维护，出错时也分不清是谁的问题。于是他选择了一次破坏性变更，并在文档里写上一行迁移说明。这个决定在单项目视角下是合理的，在多项目视角下就是灾难——而两个视角都是对的，这正是依赖冲突没法被"技术手段彻底消灭"的原因。

展开：一个真实的版本冲突长什么样

设想你要把一个旧项目交给老师检查。它需要 numpy 1.x，因为里面用到了几个在 2.x 里被改掉的接口；同时你要装一个新的可视化库，而这个库的最新版本明确要求 numpy 2.x。你在同一台机器上装： pip install "numpy<2" 之后，旧项目好了，新库报错； 你改成 pip install "numpy>=2"，新库好了，旧项目在运行到第 40 行时抛出属性错误。 你尝试找一个既能满足旧接口又有新库支持的中间版本，翻遍发布记录，发现那个版本根本不存在——新库的第一个版本发布时，旧接口已经被移除了。

请注意这个故事的结局：无解。不是因为你不够聪明，而是因为约束本身互相矛盾。当约束互相矛盾时，工程上的出路不是调和约束，而是改变约束所在的边界。容器的解法正是后者：不再让两个项目共享一个 numpy，而是让它们各自拥有一个世界。这句话是整个 Docker 思想的核心，值得你在此处停下来想一分钟。

思 考
  1. 假设一个库的作者声称"我们的 2.0 版本完全向后兼容"，你作为使用者应该怎么验证这句话？如果验证成本很高，你更愿意相信它，还是更愿意用隔离来避开这个问题？这个选择反映了你什么样的工程价值观？提示：把"相信"和"隔离"各自的成本列出来对比，一个是长期的不确定性，一个是短期的结构复杂度。
  2. 你的项目依赖一个云上的数据库服务。容器装得下代码、装得下系统库，但装不下那台数据库。那么"环境一致"这个目标，在什么意义上算是达成了一半？剩下那一半该由什么来保证？提示：想想"配置"和"代码"是不是应该被同等对待。

在容器之前：人们怎么隔离

到这里，我们已经把要解决的问题解剖清楚了。接下来换一个视角：不要问"容器是怎么做的"，而问"人类是怎么一步步走到这里的"。这一节是一条时间线，但我希望你读它的方式和读历史课本不同——每一次技术进步都不是"又加了一个功能"，而是"上一次的做法被证明有一个具体的漏洞"。

先留一个问题给你，它的答案在这一节末尾：改变根目录这个技术 1979 年就有了，它能给一个进程一个假的文件系统；那么为什么直到 2013 年，"把应用装进盒子里"才成为一个普通人日常使用的工具？是技术终于成熟了，还是别的什么终于齐了？先带着这个疑问往下读，我们中途不回答它。

从分时系统到 chroot

隔离这件事比计算机本身年轻不了多少。1960 年代的分时系统让多个用户同时使用一台机器，随之立刻出现了一个需求：用户 A 不应该能看见、更不能破坏用户 B 的文件和进程。这不是安全问题，而是可用性问题——只要有一个人的程序把内存写坏，全机的人都得重启。所以从第一天起，"隔离"就是一个工程必需，不是后来才被想出来的附加功能。今天我们讲的容器隔离，做的是同一件事，只是把"用户"换成了"应用"。

1979 年，Unix 里出现了一个系统调用：chroot，字面意思是改变根目录。它做的事情简单得让人意外——把某个进程眼中的根目录 / 换成文件系统里的另一个目录。这个进程之后打开 /etc/passwd，读到的其实是 /some/jail/etc/passwd。它看不见外面了，因为它连"外面"这个概念都没有了。

chroot 的用处一直很实在：给 FTP 服务做一个只能看到某个目录的牢笼，给编译环境准备一套干净的依赖。它也是我们整条故事线的祖先，因为它第一次实现了那个关键的错觉：让一个进程以为它看到的世界就是全部的世界。容器给你的全部错觉，本质上是同一个错觉的加强版。

但 chroot 的隔离弱得像个笑话。第一，它只隔离文件系统，不隔离进程：在 chroot 里面执行 ps，你依然能看到机器上所有其他进程。第二，它不隔离网络：里面的程序照样能连出去。第三，它不隔离用户：如果你在 chroot 里面是 root，那你依然是这个机器上的 root。第四，也最要命的一点是，一个进程如果已经是以 root 身份跑起来的，逃出 chroot 的技巧多到像一扇装了纱窗的门——它可以先打开一个目录的文件描述符，chroot 之后再从那个描述符往上爬；可以在牢笼里造一个设备节点然后挂载真文件系统；可以进入还没被隔离的 /proc 干各种事。它不是"很难逃"，而是"原则上困不住有权限的人"。

于是接下来的二十年，人们一直在往同一个方向上加东西：既然只隔离"文件视图"不够，那就把别的维度也隔离掉。

命名空间与 cgroups：把错觉外包给内核

2002 年，Linux 内核开始引入命名空间（Namespace）机制。你可以把它想成内核的一次重构：过去内核里有很多"全局唯一"的东西——进程号的编号空间、网络设备与端口、主机名、挂载表、进程间通信的标识符、用户与组的编号。命名空间做的事情是把这些全局资源改造成"每个命名空间一份"，于是一个进程在它自己的命名空间里看到的是一个完整的世界，而内核心知肚明这世界只是许多世界中的一个。

请特别注意这个设计的优雅之处：它没有发明"容器"这个新东西，它只是给已经存在的东西加了"视野限制"。内核里还是那一个进程表、那一个网络栈，只是当一个进程去查询时，内核按它所属的命名空间返回过滤后的结果。隔离是在查询的时候被实现出来的，而不是在存储的时候。这一句如果你记住了，后面讲容器网络和容器安全时会轻松很多。

命名空间管的是"你能看见什么"（也叫视野隔离）。它不回答另一个同样重要的问题：你能用多少？一个进程即使被关在小世界里，也可以把机器的内存吃光、把 CPU 占满，让其他所有容器一起饿死。这部分工作由另一套机制承担：cgroups，控制组，2006 年前后在 Google 内部被发明出来（当时叫 process containers，后来改名），2008 年进入 Linux 内核主线。它给一组进程设上限并统计实际用量，Docker 后来命令行里的 --memory 和 --cpus，翻译成内核语言就是往 cgroups 里写几个数字。

两句话记住这对搭档：命名空间回答"你能看见什么"，cgroups 回答"你最多能用多少"。它们合起来，才构成了一个容器所需要的全部内核能力。

docker run --rm --memory=64m --cpus=0.5 alpine cat /sys/fs/cgroup/memory.max

你会看到这个容器被允许使用的内存上限被打印出来，数值大致是 67108864（也就是 64 MiB）。也就是说，你在命令行里写的 64m，最终变成了容器内一个文本文件里的一个数字。资源限制在你的电脑上不是一句约定，而是内核确实在按这个数字执行。不同内核版本下这个文件名可能是 memory.max 或 memory.limit_in_bytes，如果报"文件不存在"，把路径换成 /sys/fs/cgroup/memory/memory.limit_in_bytes 再试一次。

2008 到 2013：为什么是那一年

2008 年，一个叫 LXC 的项目把命名空间和 cgroups 打包起来，第一次给了普通人一个可以用的"容器"命令。它能做到今天容器的大部分事情：起一个隔离环境、在里面跑一个发行版、限制它的资源。你在 2008 年就能用它跑一个 Ubuntu 容器。那么问题来了：既然 2008 年就有了容器，为什么是 2013 年，一个叫 Docker 的项目让这件事忽然传遍了全世界？

答案不在隔离里，而在分发里。这是本章最重要的一段，我要把它讲得慢一点。

用一个最朴素的场景来感受差别。2008 年，你用 LXC 做了一个跑着你项目的小盒子。现在你要把它交给同学，让他也能跑起来。你怎么办？你没有一个标准格式能把"这个盒子"整体导出成一个文件；即使能导出，它也是几个 GB，没有地方托管，没有版本管理，没法像 git 那样对比两个版本之间的差异。于是现实做法退回到老路：写一份文档，列出"先装 Ubuntu，然后 apt 装这些包，然后配这个文件"，让同学自己重建一遍。你隔离了运行环境，却没有办法把运行环境当作一个可以传递的物件。容器当时是个好工具，但它不是个好交付物。

Docker 的革命性在于它同时给了三样东西。第一样是一个真正可分发、可分层、按内容寻址的镜像格式：镜像被拆成若干层，每一层有自己的哈希，可以从远处只下载你缺的那几层，也可以在本地被许多镜像共享。第二样是一个把"怎么造出这个镜像"写成文本的工具，也就是 Dockerfile，它让环境从"某台机器上的既成事实"变成了"一段可以提交、可以评审、可以改变的说明"。第三样是一个公共的镜像仓库 Docker Hub，让下载一个环境变得像下载一个软件包一样简单。

把这三样合起来看，你会发现它们解决的是同一个问题的三个面：环境本身，第一次成了一个可以被命名、被版本化、被传递、被复现的对象。在此之前，环境是形容词，是"我这台机器上大概是这样"；在此之后，环境是名词，是一个有摘要、有名字、有标签的东西。这才是 2013 年的真正分界线。

回 望

导学里你听过一句话：容器只是一种进程的包装方式。现在我们往回看这句话，会发现它少说了一半。作为内核能力，容器确实是进程的包装；可作为一种被几百万开发者使用的东西，容器的威力来自包装之外——来自那个可以被命名、被传递、被复现的镜像。技术有了名字才能被讨论，被讨论了才能形成生态。第 00 章那句话描述的是它的身体，这一节补上的是它的语言。

前 瞻

你可能会想到一个反对意见：如果分层与复用是这么关键的东西，那么它总有代价吧？会。第 03 章会讲清这些代价的样子：层让"删除文件"变得反直觉，让构建顺序影响构建速度，也让镜像的膨胀变得难以察觉。第 05 章还会告诉你，Dockerfile 里指令的先后顺序会直接影响每一次构建要花多久。任何一个优点，只要你往深处走一步，都能看到它配着的那份账单。

思 考
  1. 很多人把 2013 年那场演示看作一个传奇时刻。如果我们要用工程语言而不是传奇语言来描述它，那句话应该怎么说？请写出一句不含"伟大""颠覆""革命"这类词的描述，并说明你为什么选择这些词。
  2. 请为这个论断找一个反例：有没有可能一项技术早就足够好，却永远没有流行起来，因为缺少某个非技术的条件？如果你能举出一个例子，它和容器的故事有什么共同点？提示：想一想那些因为"没有统一的格式"或"没有地方共享"而没能传开的技术。
方 法

读技术史时，有一个提问方式比记住年份有用得多：问"上一个做法到底失败在哪里"。chroot 失败在只隔离了文件视图，Jails 的失败在于跨不出 BSD 世界，LXC 失败在没法把环境当作交付物，每一条都能推出下一个技术的设计目标。用这种方式读历史，你得到的不再是一串时间点，而是一张因果链。我建议你在读任何技术演进史的时候都做这个小练习：把每一个新技术写成"它修好了前一个的哪个洞"。做上五次，你会发现技术史忽然变得可以推理了。

回 望

导学里我们说过一句话：Docker 并不是容器的发明者。现在你有了完整的证据链：命名空间、cgroups、组合它们的 LXC，全都早于 Docker，而且它们都还在用、都还在被维护。Docker 的贡献是包装与分发。这个区分不是为了贬低 Docker，恰恰相反——它让你看清一件更难的事：把一个已有的能力变成所有人都愿意用的东西，其难度不亚于发明那个能力本身。这也是本书后面反复出现的主题之一，我们在讲镜像格式与 OCI 标准时会再遇到它。

思 考
  1. 如果 2013 年那场演示发生在 2008 年，它会不会同样成功？请分别从技术条件、网络条件（当时的带宽与云服务普及度）、开发者文化三个角度判断，并说出你认为最关键的一个变量。
  2. chroot 的隔离很弱，但它至今仍然被大量使用。找出至少两个它至今仍是正确选择的场景，并解释为什么在这些场景里"更强的隔离"反而不是更好的选择。提示：考虑"我需要保护谁"和"我付出了什么代价"这两个问题。
  3. 假设你是一名 2008 年的工程师，手里有 LXC，也听说了 Docker 的设想。你会认为 Docker 只是一个"更方便的 LXC 包装"吗？如果会，你会漏掉什么？

实验：亲眼看见"共享内核"

前面讲了很多断言，现在该让它们接受检验了。这一节是一场实验，我希望你亲手做完，因为容器技术里有些事实必须亲眼看见，否则它们永远只是别人告诉你的句子。

实验一：容器里的内核是谁的

实验目的：验证"容器共享宿主机的内核"。命令分两步。第一步在容器里查内核版本，第二步在你的机器上查内核版本。

docker run --rm alpine uname -r

你会看到一个内核版本号，形如 6.6.87.2-microsoft-standard-WSL2，也可能是一串 5.15 或 6.6 开头的数字。它的具体内容取决于你的 Docker Desktop 与 WSL2 版本，不必和别人对答案。

wsl uname -r

你会看到一行内核版本号。把它和上一条命令的输出逐字符对比。如果你用的是 Docker Desktop 的 WSL2 后端（默认后端），这两个数字应该完全一样，包括后面那串 -microsoft-standard-WSL2 后缀。这不是巧合：那个 Alpine 容器里的 uname 命令，问的正是这台 WSL2 内核。容器没有自己的内核，它借用你的。

wsl ls /mnt/c/Users

你会看到你的 Windows 用户目录列表。这条命令确认了 WSL 里确实能看到 Windows 的 C 盘，也就是说我们上一条对比的内核，就是喂给容器的那一个内核。用 macOS 或纯 Linux 的同学把这条跳过即可，前两条实验的结论不受影响。

现在做第二步对比，它会给你一点小小的世界观冲击：

docker run --rm alpine cat /etc/os-release

你会看到 NAME="Alpine Linux"、ID=alpine、VERSION_ID 之类的字段，还有一行把版本号（例如 3.20）写进 PRETTY_NAME。

docker run --rm ubuntu cat /etc/os-release

你会看到 NAME="Ubuntu"、ID=ubuntu、VERSION_ID="24.04"（或你拉到的那个版本）。同一台电脑，同一个内核，两个完全不同的发行版。

这两个结果放在一起，就是本章最有冲击力的那对矛盾：它们的内核相同，发行版不同。用一句话把这件事说清：镜像是用户空间（userland），内核是内核空间。容器搬走的是用户空间——那些可执行文件、库、配置、目录结构；内核不属于镜像的一部分，它由宿主机提供。你在 Alpine 容器里执行 cat，用的是 Alpine 提供的那个小小二进制文件；这个进程发起 read 与 write 系统调用，被对接到 WSL2 的那个内核上去执行。

想让它更刺眼一点，看这个：

docker run --rm alpine ls /lib

你会看到 ld-musl-x86_64.so.1 和 libc.musl-x86_64.so.1 之类的名字。musl 就是 Alpine 的 C 标准库。Ubuntu 镜像里对应的位置放的是 glibc 的库文件。两套标准库，一个内核，互不干扰地各自工作。这也解释了第 2 节里提到的那个坑：为 glibc 编译的程序拿到 Alpine 里运行，会找不到它要的库。

实验二：同一个镜像，两个容器，互不干扰

实验目的：看清"容器之间的隔离"到底隔离了什么，并顺便发现一个看起来自相矛盾的现象。

开第一个 PowerShell 窗口，敲：

docker run -it --name a ubuntu bash

你会进入一个以 root@一长串十六进制字符开头的提示符，那是容器的主机名。现在在里面造一个文件：

echo hello-from-a > /tmp/proof.txt
cat /tmp/proof.txt

第二行会打印 hello-from-a，说明文件确实存在。请不要关这个窗口，它是容器 a 的主进程。macOS 或 Linux 用户在第 02 节换用 docker run -it --name a --rm ubuntu bash 时，复制粘贴这些容器内的命令即可。

现在开第二个 PowerShell 窗口，敲：

docker run -it --name b ubuntu bash

你会进入另一个容器，主机名不同。现在查那个文件：

cat /tmp/proof.txt

你会看到 "No such file or directory"，而不是 hello-from-a。同一个 ubuntu 镜像，同一台电脑，同一秒钟在跑，文件却不存在。

请你停下来，在心里把这件事解释一遍，再往下看。我要的不是"因为它们是不同容器"这种套话，而是机理：容器 a 启动时，Docker 在镜像的只读层之上给它加了一层可以写的层；容器 b 启动时，又加了属于它自己的另一层。你在 a 里写的文件落在 a 的可写层里，b 的可写层是另一个地方，两者从来不会见面。它们共享的是下面那些只读的层，分开的是各自顶上那一层可写的层。

现在讲那个自相矛盾的现象，它是我希望你在这章里真正想通的一点。你在宿主机上执行：

docker images ubuntu

你会看到只有一行：一个 ubuntu 仓库、一个标签、一个镜像 ID、一个体积。不是两份，也不是两份加起来。可是刚刚明明有两个 ubuntu 容器在跑，各自有自己的文件系统。同一个镜像怎么会有两份不一样的内容？

这就是"镜像"与"容器"的分界线，也是初学者最容易混淆的地方：镜像是一份只读的模板，容器是模板加上一份私有的可写层。一个是名词性的存在，一个是运行中的状态。你在 a 里改的东西没有改到镜像，所以 b 看不见；镜像本身没有被改，所以 docker images 里还是一行。更妙的是，如果这时候你在 a 里把某个系统文件删掉，Ubuntu 镜像的体积也不会变小——因为你删的只是可写层上的一个标记，下面那一层里的原文件完好无损，还在被 b 和所有其他基于它的容器使用。

前 瞻

上面这段解释里有几个词我用得比较随意：层、可写层、标记。它们每一个都值得单独讲清。第 03 章会把镜像彻底拆开：层到底是什么、为什么它按内容算哈希、写时复制是怎么做到"先共享、要改才复制"的、以及删除文件为什么不会让镜像变小。第 06 章会回答一个更实际的问题：既然容器里的文件会随着容器一起消失，你的数据该放在哪里？现在你只要建立那个基本图像：模板是共享的，状态是私有的。

方 法

这个实验体现了一种学习方法：当你要理解一个隔离机制时，不要只读它的定义，去设计一个"如果它成立，我就应该看到某现象"的实验。这次的推理链是这样的：如果两个容器各自有独立文件系统，那么在 a 里写的文件在 b 里应该看不见；如果它们共享同一个镜像，那么镜像列表中应该只有一份。两个推论都被验证了，你对机制的理解就不再是背下来的，而是推导出来的。以后你遇到不熟悉的机制，都可以问自己："如果它是这样工作的，我会观察到什么不一样的现象？"

思 考
  1. 如果容器之间真的完全隔离，为什么两个容器可以同时读取同一个镜像的同一份文件？这种"共享的隔离"到底是省下了什么，又埋下了什么风险？提示：省下的东西是磁盘和时间；风险要从"如果底层被改动"这个方向去想。
  2. 在这个实验里，容器停止之后，a 里那个 /tmp/proof.txt 去了哪里？如果你用 docker start a 再把它启动起来，文件还在吗？请先猜，再动手验证，然后解释你的猜测错在哪。提示：可写层的生命周期和容器的生命周期是什么关系。

实验三：一个 5 MB 的"系统"

实验目的：感受"没有内核的操作系统"能小到什么程度。

docker pull alpine

你会看到若干行下载进度，最后一行是 "Status: Downloaded newer image for alpine:latest"，或者提示你镜像已是最新。

docker images alpine

看 SIZE 那一列。多数情况下它显示在 7 MB 到 9 MB 之间，取决于版本与压缩方式。作为对照，ubuntu 镜像通常在 75 MB 到 80 MB，而一个最小化的 Windows 或 Linux 虚拟机镜像动辄几个 GB。请你把这两个数字记在心里，因为它们是本章后面那张对比表的底气。

为什么它能这么小？因为它里面真的只有用户空间的那一小撮东西：一个 busybox 风格的 shell 与工具集、musl、apk 包管理器、一点配置。没有内核，没有桌面，没有 systemd，没有你从来不用的打印机驱动。你过去以为"一个操作系统"必须有几十万个文件，其实那是发行版的习惯，不是系统的必然。这句话值得你多想一会儿，因为它动摇了你关于"系统"这个词的直觉——而这一章后面还要再动它一次。

易 错 点

看了这个实验之后，一种很常见的错误推论是"小就是好，以后全部用 alpine"。请先别下这个结论。小确实带来更小的攻击面、更快的下载、更少的内存占用，代价是缺少常用工具（Alpine 里的 shell 是简洁版的，很多调试命令要么不存在要么行为不同）、musl 与 glibc 的兼容差异、以及某些语言生态的二进制包不提供 musl 版本。第 05 章会专门讲基础镜像的取舍。现在的作业是记住那个态度：体积是一个需要权衡的指标，不是一个需要最大化优化的美德。

容器不是小虚拟机

现在我们对容器已经有了一些亲眼见过的事实。接下来要建立一个对比框架，因为几乎每一个初学者都会带着虚拟机的直觉来理解容器，而这个直觉会让你在至少五个地方判断错误。我们要做的不是把虚拟机贬低一番，而是把两者的分界线画得非常清楚，清楚到你以后能一眼看出某个场景该用哪个。

先把两个词的定义补上，因为你在这本书里会反复用到它们。虚拟化（Virtualization）是把一份物理资源抽象成多份"看起来各自独立"的逻辑资源这件事的总称。虚拟机（Virtual Machine，VM）是虚拟化在硬件层面的实现：用软件模拟出完整的虚拟 CPU、虚拟内存、虚拟磁盘、虚拟网卡，然后往里面装一整套操作系统。负责创建和调度这些虚拟机的软件层叫 Hypervisor，也就是虚拟机监视器。容器（Container）则不模拟硬件，它让宿主机内核上的一个进程以为自己是这台机器上唯一的居民。

把这句话说得再锋利一点：虚拟机共享硬件，容器共享内核。这一行字的差别，决定了后面所有其他差别。

对比维度容器虚拟机差别从何而来
启动速度几百毫秒级（常见 0.3—1 秒）通常数十秒级，取决于系统初始化容器只是启动一个进程，虚拟机要启动一整套系统
磁盘占用镜像常为几十 MB 级，小的可到 5—10 MB动辄数 GB，因为里面有一份完整系统容器不复制内核与全套工具
内存开销接近普通进程，页可以共享每台都有独立的系统与内存占用有没有第二份内核与系统服务
部署密度一台机器上几十到上百个很常见一台机器上十几个已属不少每个实例的固定开销差了一个数量级
隔离强度中等到强，取决于配置强，由硬件虚拟化支撑共享内核意味着共享了攻击面
能不能换内核不能，只能用宿主机的内核能，每台自带内核内核是共享资源还是私有资源
能不能跑不同操作系统不能，在 Linux 上只能跑 Linux 容器能，Linux 上可以跑 Windows 虚拟机同一个原因
典型使用场景交付应用与开发环境、微服务、批量任务需要不同内核、强隔离、完整系统、异构系统并存由上面的能力差异推导出来

这张表最好用的读法不是从上往下看，而是从"差别从何而来"那一列往左看。你可以把每一行都当成一个推论去验证：容器不复制内核，所以启动快、体积小、密度高；也因为不复制内核，所以不能换内核、不能跑别的操作系统、隔离强度受限于内核。所有差别都能追到同一个源头，这就是一个理论该有的样子。如果哪一天你听到一个关于容器的说法，无法从这个源头推导出来，那你应该对它保持怀疑。

还有一件事需要澄清，因为很多科普文章把它讲错了：在 Windows 和 macOS 上使用 Docker Desktop，实际上仍然运行着一台虚拟机。因为 Windows 内核和 macOS 的 XNU 内核都不能直接执行 Linux 容器所需要的那些内核接口（命名空间、cgroups 这些是 Linux 内核的东西）。所以 Docker Desktop 在你的机器上偷偷起了一个轻量 Linux 环境——默认是 WSL2——把 Docker 引擎放在里面跑。你的容器共享的是那个 WSL2 内核，不是 Windows 内核。

这件事有个立竿见影的实用推论：你在 Windows 上看到的"容器里的内核版本"永远不会是 Windows 的版本号，而会带上一串类似 microsoft-standard-WSL2 的后缀。这不是 bug，这是分层。也正因为如此，Windows 上的 Docker 会比原生 Linux 上多一层开销，这就是"共享内核"这个原理在你自己电脑上的直接体现。

docker version

你会看到两块信息：Client 部分是你敲的 docker 命令行客户端，Server 部分是真正干活的引擎。在 Docker Desktop + WSL2 的默认配置下，Server 的 Os/Arch 会显示为 linux/amd64（或 linux/arm64），Operating System 会提到 Docker Desktop。请特别留意这一行：你在 Windows 上，但引擎报告自己是 Linux。这就是我们上面说的那件事的直接证据。

docker context ls

你会看到一列表格，其中至少有一个 default 和一个 desktop-linux，当前生效的那个前面有一个星号。这一行说明一件很重要的事：你的 docker 命令并不是"本机程序"，它是一个客户端，通过某份连接配置去找到某个引擎。切换到另一个上下文，同一条命令就会作用到完全不同的机器上。

易 错 点

第二个高频误解是：既然容器比虚拟机省资源，那"把整个服务器换成容器"总是更划算。请谨慎。容器省下的是"每台实例重复一份内核与系统"的开销，它不省 CPU 与内存本身。如果你的应用本来就是 CPU 密集的，容器不会让计算变快。而且你很快就会遇到那些"装不进盒子里"的东西：需要特定内核模块的任务、需要 GUI 与桌面环境的软件、需要跟内核版本强绑定的驱动。容器减少的是重复，不是需求。这句话可以帮你避免很多不切实际的期待。

前 瞻

表里"能不能跑不同操作系统"这一行，在 Windows 上有一个例外：Docker Desktop 支持切换到 Windows 容器模式，让你运行 Windows 容器。但那要求宿主机就是 Windows 内核，也就是说你依然无法在同一台机器上同时原生地运行 Linux 容器和 Windows 容器。原理是完全一致的：容器的内核必须来自宿主机。第 04 章讲命令与生命周期时，我们会看到这个限制在日常操作里长什么样。

思 考
  1. 请找出至少一个容器明显不擅长的场景，并说明虚拟机在那个场景里为什么仍然更合适。不要满足于"跑 Windows 软件"这一个答案，想一个与你专业方向相关的场景。提示：想想那些必须碰内核、必须长年运行、必须与他人强隔离的东西。
  2. 如果容器共享内核，而 Docker Desktop 在 Windows 上又提供了一台虚拟机，那么这台虚拟机到底在替谁承担成本？把成本账单列出来（内存、磁盘、启动时间、网络路径），然后判断这笔账值不值。
  3. "系统"这个词到底由什么定义？一个共享别人内核、没有自己内核的东西，凭什么让人觉得它是一台独立的系统？如果"系统"只是一套让你产生连续感的接口与文件布局，那么这份连续感是被谁维护出来的？

内核共享的代价，与三个必须被纠正的第一印象

我们已经说了很多容器的好话，也该认真谈谈它的代价了。一位负责任的作者不会只告诉你工具能做什么，还会告诉你它会在哪里失效。这一节的三个后果，全部来自同一件事：容器共享内核；而在理解这三条代价之后，我们才有力气去纠正三个几乎人人都会有的错误印象。

三个不是"缺点"而是"结构性后果"的事

第一个后果：容器不能装一个不一样的内核。如果你的程序需要某个内核模块，需要特定版本的文件系统特性，或者需要一套和宿主机不同的内核参数，容器给不了你。你不是"配得不对"，你是碰到了原理边界。遇到这种情况的出路通常是三条：换成虚拟机、换一台内核版本合适的宿主机、或者改掉那个对内核的依赖。注意最后一条往往是最便宜的，但它需要你真的理解自己为什么需要那个模块。

第二个后果：内核漏洞可能成为逃逸通道。这是个让人不太舒服但必须直说的事实。容器里的程序在运行时，是在向同一个宿主机内核发起系统调用；每一次系统调用都是一个请求，而内核必须判断"这个请求该不该被批准"。判断逻辑写在几十万行内核代码里，而其中任何一处漏洞，都可能让一个本该被拦住的操作通过。这就是容器逃逸漏洞的根源。它的现实含义是：容器的隔离强度不由口号决定，而由三样东西决定——你的内核有没有及时打补丁、你的容器配置是否收敛了权限、你的进程是不是以不必要的身份在跑。

第三个后果：宿主机的内核版本决定了你能跑的容器。这一点很多人从来没想过。镜像里的用户空间是很老的系统也没关系，比如一个十年前做的 CentOS 镜像，只要它需要的系统调用今天的 Linux 内核还提供，它就能跑。反过来，一个用新特性做的镜像，拿到一台内核过老的机器上就跑不起来，而且报错往往很隐晦——可能表现为某个功能失效，而不是启动失败。这条后果解释了为什么运维团队在升级内核时格外谨慎：它不是一个独立的决定，它会一次性影响机器上所有容器的能力边界。

展开：隔离强度是一个阶梯，不是开关

初学者常把"隔离"想成有或没有。真实情况更像一颗洋葱，每一层单独都不够，合起来才形成可接受的安全边界。以下是从外到内的几个层次，按通常的强度递增排列：

1）命名空间：让进程看不见别的进程、别的网络、别的挂载。它只限制视野，不限制权限。

2）cgroups：限制资源的用量，防止一个容器拖垮其他容器。它是可用性保护，不是安全边界。

3）Linux 能力（Capabilities）：把 root 的权力拆成几十项细小权限，容器默认丢弃了一大批危险项。这意味着容器里的 root 不是宿主机的完整 root。

4）seccomp：过滤进程可以调用哪些系统调用，把用不到的调用直接挡住。这一层针对的正是"内核漏洞被利用"这个攻击面。

5）AppArmor 或 SELinux 这类强制访问控制：即使进程是 root，访问文件、网络、设备也要通过策略检查。

6）用户命名空间：让容器内的 root 映射成宿主机上的一个普通用户，即使容器内提权成功，落到宿主机上也只是个无权用户。

7）rootless 模式：整个 Docker 引擎都不以 root 运行。

8）虚拟机或硬件级隔离：直接换一层更硬的地基，代价是回到较重的方案。

你要建立的感觉是：说"我们用了容器"并不能回答"我们的隔离有多强"。强不强取决于上面这几层被配置到了哪一步。第 09 章会把每一层讲透并给出检查方法。现在你只需要知道这个阶梯存在，并且知道"默认配置"通常只是中间位置，不是最强的那一档。

回到那个一开始有点吓人的问题：把两家互相不信任的公司的程序跑在同一台机器上，安全吗？现在你可以给出一个比"安全"或"不安全"更有用的答案了：这取决于隔离配置、内核维护水平、以及你能承受的损失上限这三件事的组合。如果两家公司都能接受一定程度的相互风险、内核补丁跟得上、容器不以特权模式运行、并且都不用 root 身份，那么这在工程上是可做的；如果其中任何一条不成立，那么正确做法是把它们放在不同的物理机或至少不同的虚拟机上，用一层更硬的地基把风险切开。工程判断的美感就在这里：它不给你一个永远正确的答案，它给你一组可以逐项检查的条件。

方 法

面对"这个技术安全吗"这类问题时，一个可靠的思考套路是把它改写成三个具体问题：我要防的是谁？他能做什么？我出事之后损失多大？这三个问题分别对应威胁模型、攻击面、影响范围。绝大多数关于技术安全性的争论，其实是因为大家在回答不同的问题——有人在防隔壁桌的同学，有人在防有资源有耐心的攻击者，有人只是担心自己误操作。把这三个问题先摆到桌面上，讨论会立刻变得清晰。这个套路不只适用于容器，它适用于你以后遇到的每一个安全决策。

回 望

第 00 章导学提到过，"容器共享宿主机的内核"这句话既解释了它为什么轻，也预告了它的边界。现在我们把这层意思补全了：共享内核不是一句中性的技术描述，它同时是一份明确的能力清单和一份明确的代价清单。你得同时收下这两张清单，才算真的理解了这句话。

前 瞻

这一节提到的能力、seccomp、强制访问控制、用户命名空间，在第 09 章会变成一组可以实际操作的命令与检查清单：怎么让容器以非 root 运行、怎么只加必需的那一项能力、怎么扫描镜像里的已知漏洞、怎么用软件物料清单在爆出漏洞时快速判断自己是否受影响。现在你要做的是记住这个阶梯的形状，别急着记住每一层的名字。

三条代价讲完，我们可以回头处理三个几乎人人都会有的错误印象了。把它们放在代价之后讲是有原因的：这三个印象之所以危险，是因为它们不会让你报错，只会让你在关键时刻做出错误的判断——而它们的错处，恰好都藏在上面那三条结构性后果里。错误的印象比错误的命令更危险，因为命令错了有报错提示你，印象错了没人提示你。

第一印象：容器是轻量级虚拟机

错。它根本不是虚拟机，甚至不是"虚拟化"这个词在通常意义上的用法。虚拟机是硬件层面的虚拟化：它模拟出虚拟 CPU、内存、磁盘，然后在里面装一个完整的操作系统。容器不是模拟硬件，它是让宿主机内核把某个进程的视野和权限改小，让它以为自己是唯一的居民。虚拟机模拟的是一台机器，容器约束的是一个进程。这个区分有非常实际的后果：虚拟机的隔离强度不依赖宿主机内核对调用者的检查是否严密，容器依赖。

为什么这个印象如此顽固？因为它符合一种很自然的类比习惯：看到"里面有一个看起来像系统的东西"，就认定它是一台小机器。而它之所以"看起来像系统"，是因为镜像里装了足够的用户空间——一个 shell、一批命令、一套目录布局。这份相似是观感上的相似，不是原理上的相同。你以后判断一个技术类比是否可靠，可以问自己一句："它们的相似是在表面上，还是在机制上？"

第二印象：Docker 就是容器

错，而且这个错误会在两个方向上害你。一个方向是技术上的：当你遇到问题时，你会以为是 Docker 出了问题，而实际上可能是 containerd 在拉镜像、runc 在创建进程、或者是内核拒绝了某个操作。另一个方向更隐蔽：当你需要学习新东西时，你会以为"Docker 不会就完了"，从而拒绝了解那些正在取代 Docker 部分职责的工具。事实上，"容器"这个词今天指的是一个由多方共同维护的接口与规范生态，Docker 是其中最流行的工具链之一。

要理解这件事，看看 2015 年之后发生了什么。业界成立了开放容器倡议（Open Containers Initiative，OCI），把镜像格式与运行时接口写成公开规范。Docker 公司把负责创建容器的核心组件 containerd 捐给了一个中立基金会。Kubernetes 在编排之争中胜出，成为事实标准，而它并不依赖 Docker 这个具体工具——它可以调用任何符合规范的运行时。"容器"从一家公司的产品，变成了整个行业的接口。这个过程本身就是本章主题的一次重演：先是有一个具体的东西被做出来，然后是它被抽象成接口，最后是这个接口让所有人都能参与进来。

这件事的实用含义是：你学的东西有层次。表层是 Docker 的命令，中层是镜像格式与运行时规范这些跨工具的概念，底层是 Linux 的隔离机制。表层的知识会随工具更替而过时，中层和底层不会。本手册的安排也照这个思路：先把命令用熟，再把概念打深，最后带你看规范的入口。

第三印象：有了容器就不用管环境了

错，而且我认为这是三个里最危险的一个，因为它会让你省掉本该做的功课。容器没有让环境消失，它让环境显式地写下来了。过去环境是一个"事实"，藏在某台机器的当前状态里，没人知道全貌；现在环境是一份文本，静静地躺在仓库里，谁都可以读，谁都可以评审，谁都可以改。

这个转变是巨大的，但它不是免费的。写下来意味着你必须真的写全：如果你忘了声明某个系统依赖，它今天不会报错——因为它恰好在基础镜像里存在；等到某天基础镜像升级，那个依赖被移除了，你的构建会在半年后突然失败。类似地，如果你的容器还是要去连一个外部的数据库，那么那个数据库的版本与配置依然是环境的一部分，容器帮不到你；如果你把密钥写进了镜像，那么环境里就多了一个永远不会消失的漏洞。

所以我希望你用这句话替换掉那个错误印象：容器把环境的复杂度从"运行时的不确定性"转移成了"构建时的显式声明"，代价是你必须对那份声明负责。问题没有消失，它被搬到了一个更容易被发现、也更容易被管理的地方。这个搬家动作是本章所有内容里最有价值的一件事，也是"基础设施即代码"这个思想的日常版本。

docker run --rm -e APP_ENV=demo alpine sh -c "echo env is $APP_ENV"

你会看到 env is demo。请注意这里发生了什么：你没有修改镜像，只是通过 -e 在启动时注入了一个环境变量，这正是"配置与镜像分离"的最小示范——同一份镜像可以在不同环境里表现出不同行为，而镜像本身保持不动。还有一个细节值得你亲自验证：在这一行里，把 $APP_ENV 展开掉的是你这台机器上的 shell，不是容器；docker 收到的已经是被替换成 demo 的字符串。如果你把同一行命令写进 .sh 脚本、放到 Linux 上跑，就必须给 $APP_ENV 加上反斜杠，否则展开会发生在错误的一侧。命令在哪里被解析，往往比命令写了什么更重要。

展开：为什么说"环境被写下来"是一件有历史分量的小事

在计算机发展史里，有一类进步看起来毫不激动人心，却改变了整个行业的工作方式：把隐含的知识变成显式的、可被机器读取的文本。

当年的构建过程常常是某位资深工程师记在脑子里的一串手工步骤，或者是 Makefile 里一堆依赖本机路径的命令。后来有了持续集成，构建被写进了配置文件；再后来有了配置管理工具，服务器状态被写成了代码；再到容器，运行环境本身也被写成了文本。每一次转变都伴随同样的抱怨："这样写太麻烦了，我手动两步就好了。"而每一次转变的收益都要等一两年才显形：当有人离职、当机器损坏、当需要复制第五套环境时，那些写在文本里的知识救了所有人。

有一个更早的对照值得你去看：十二要素应用的方法论把"依赖必须显式声明"和"配置存在环境里"写成了原则。它发布于容器流行之前，却几乎是为容器时代量身写的。第 10 章我们会逐条对照它自查项目。现在你可以带着一个问题去读它：这份清单里哪几条，恰好是你上一个项目偷偷违反了的？

环境从来没有消失过，它只是从"没人记得的样子"变成了"写在文件里的句子"。

方 法

这一节纠正的三个印象，其实都是同一类错误的三个样本：把"看起来像"当成了"机制上就是"。这种错误在技术学习里出现的频率高得惊人，而且它不会报错，所以很难自己发现。有一个很便宜的破解办法：每当你打算说"这个东西就是那个东西的某种形式"时，立刻追问一句"那么它们在哪个具体行为上会不一样"，然后为那个行为设计一个能跑的验证。上一节那个 uname 对比实验就是这句话的一个实例。如果设计不出任何能区分两者的观察，说明你的类比可能只是修辞，先把它放在一边。

自己动手：让环境差异现形

这一节的最后，我给你一个可以立刻做的实验，它的目的不是学习某个命令，而是让你亲手制造一次"环境不一致"，然后观察它的形状。

实验目的：让同一个程序在两个不同的环境里表现出不同行为，并解释原因。第一步，在最新版 Python 里跑一段代码：

docker run --rm python:3.12-slim python -c "import sys; print(sys.version_info.major, sys.version_info.minor)"

你会看到 3 12。这是环境一。

docker run --rm python:3.8-slim python -c "import sys; print(sys.version_info.major, sys.version_info.minor)"

你会看到 3 8。这是环境二。同一个镜像名 python，两个不同的世界。注意你完成这件事没有修改自己电脑上的任何 Python 安装——这正是容器在开发机上的第一大用途：把不同版本的工具链并存而不互相污染。

现在变体来了，这才是真正要你想的地方：请你自己设计一个实验，让同一个版本的 Python 在两个容器里对同一份输入给出不同的输出。可行的方向有：设置不同的时区（用 -e TZ=UTC 与 -e TZ=Asia/Shanghai，然后打印当前时间）；设置不同的区域设置；用一个环境变量切换程序的行为；或者挂载一份不同的配置文件进去。做完之后请回答两个问题：第一，程序本身变了没有？第二，如果这份差异没有被写进任何文档，一年后的你会不会记得？

前 瞻

第 06 章会告诉你一个和这个实验直接相关的事实：容器里的文件在容器被删除时会一起消失，所以你刻意准备的那些"环境差异"如果要留下来，就必须放到容器之外。这引出了全书最重要的一条设计原则——容器无状态，数据外置。现在先记住这个悬念：你刚造出来的那个世界，是一只随时可以扔掉的信封。

    参考答案

    思路：把"能跑"这个事实从一个属性改写成一种依赖关系。参考表述：程序能跑，不只因为你写对了代码，还因为你电脑上恰好装着它需要的一整套东西——解释器版本、库、系统组件、配置。这套东西从没被写下来，别人的电脑上也不会有。所以程序在你这跑得通，是一组没被记录的条件恰好凑齐了，不是代码自身完备。

  2. 下面这条命令会输出什么？为什么输出里不会出现你 Windows 的版本号？请解释这条命令走的路径。 
    docker run --rm alpine uname -r
    参考答案

    思路：输出的是宿主机的 Linux 内核版本（在 Docker Desktop 默认配置下通常带 -microsoft-standard-WSL2 后缀）。原因：uname 这个程序由 Alpine 镜像提供，运行在宿主机内核之上，它通过系统调用向内核询问版本，内核返回的是自己的版本。Windows 的版本号不会出现，因为容器从来不用 Windows 内核；在 Windows 上跑 Linux 容器时，Docker Desktop 先起了一台轻量 Linux 环境，容器共享的是那台环境的内核。

  3. 你执行 docker run -it --name a ubuntu bash，在里面创建了 /tmp/note.txt，然后在另一个窗口执行 docker run -it --name b ubuntu bash，在 b 里 cat /tmp/note.txt 会得到什么？如果此时执行 docker images ubuntu，会看到几个镜像？说明这两件事为什么可以同时成立。
    参考答案

    思路：b 里会得到"没有这个文件"。docker images 只有一行。理由是镜像与容器的分工：镜像是共享的只读模板，容器是模板加一层私有的可写层。a 写文件时写在它自己的可写层，b 的可写层是另一处，两者不重叠；而两个容器底下的只读层是同一份，所以镜像列表里只有一份。回答时要明确区分"只读的共享部分"和"可写的私有部分"。

  4. 解释为什么 A 项目要 Python 3.8 加旧版 numpy、B 项目要 Python 3.12 加新版 numpy 时，问题不能靠"硬盘还有空间，装两套就行"来解决。评分要点：必须指出"名字的唯一性"这一层，而不是停在空间层面。
    参考答案

    思路：冲突的核心不是空间，而是名字解析。当系统执行 python 或 import numpy 时，必须唯一地确定用哪一个；全局环境里这个名字只能指向一个对象。装两套解释器解决不了"python 指向谁"，装两套库也解决不了"numpy 指向谁"。虚拟环境能解决一部分（让每个项目有自己的库目录），但管不到解释器版本、系统库、外部服务。真正彻底的解法是改变边界：让每个项目运行在自己的世界里，这就是容器。

  5. 一个程序在启动的第一行代码执行之前就失败了，报错里出现了 "cannot open shared object file"。你判断问题出在哪一层？下一步你会执行什么命令来获取更多信息？
    参考答案

    思路：这是系统库与动态链接层的问题：程序启动时，动态链接器要先找到它依赖的共享库，找不到就退出，此时你的代码还没有机会运行。下一步在 Linux 环境下用 ldd 打印出这个可执行文件依赖的完整动态库清单，把其中的库逐个与目标环境里存在的库对比，找出第一个缺失项。在容器场景里，常见成因是基础镜像换了（例如从 glibc 系发行版换到 Alpine 的 musl），或者构建产物是在另一个发行版上编译的。

  6. 你的同学在他的 Windows 电脑上写了一个 shell 脚本，放进 Linux 容器里运行时报 "\r: command not found"。请解释这个报错的成因，并说出两种修复方式。
    参考答案

    思路：Windows 上的文本文件用回车加换行两个字节表示换行，Linux 只用换行一个字节。多出来的回车字符被 shell 当成了命令名的一部分，于是找到了一个叫 "\r" 的假命令。修复方式一是把文件的换行格式改成 LF（编辑器里通常有换行格式选项），方式二是在容器里执行一次转换命令把回车去掉（例如 dos2unix，或 sed 把 \r 删除）。更根本的做法是在项目里规定换行格式并写进配置文件，让所有人的编辑器遵守同一规则。

  7. 判断正误并说明理由："因为容器没有自己的内核，所以容器一定比虚拟机不安全。"
    参考答案

    思路：前半句对，后半句是不能直接推出的结论。"共享内核"确实意味着容器多了一条共享的攻击面，隔离强度依赖内核补丁与配置，这是静态事实。但安全性是配置的结果：加上能力收敛、seccomp 过滤、强制访问控制、用户命名空间、只读文件系统、非 root 运行这些措施之后，容器可以在许多真实场景里达到足够的安全水平；反过来，一台配置糟糕、补丁三个月没打的虚拟机也不安全。评分要点：要区分"结构性风险"与"实际安全水平"，不能简单地把它们等同。

  8. 你想让一个旧的 CentOS 7 应用跑起来，但你的宿主机内核比较新。请判断：这个容器能不能跑？为什么一个十年前的镜像能在今天的机器上运行，而一个依赖新内核特性的镜像在旧机器上会失败？评分要点：必须用到"内核由宿主机提供"这一条。
    参考答案

    思路：通常能跑，因为镜像里装的是用户空间，它需要的是内核提供的系统调用接口；Linux 内核在系统调用层面长期保持向后兼容，所以老程序在新内核上一般仍可运行。反过来，用新特性（新的系统调用、新的文件系统能力、新的 cgroup 接口）做出来的镜像拿到旧内核上就缺少支撑，表现为功能失效或启动失败。结论：容器的能力上限由宿主机的内核决定，不由镜像决定。

  9. 如果你是 2015 年前后的技术决策者，Docker 公司在推广把镜像格式与运行时接口交给中立标准组织。你会认为这是"慷慨"还是"策略"？请给出你的判断以及一个能支持这个判断的历史事实。
    参考答案

    思路：两者并不互斥，但可以有偏好立场。支持"策略"的事实：把接口标准化能让自己成为生态的中心节点，同时避免整个市场因为格式分裂而无法成长，而标准化之后各家在工具链与商业产品上的竞争反而更激烈。支持"慷慨"的事实：标准化确实降低了所有参与者的迁移成本，也让用户不必被单一厂商绑定。评分要点：答案要有立场、要有证据、要承认另一面的合理性，这是开放题的评分方式。

  10. 动手任务：在一台机器上同时启动三个不同版本的 Python 容器，分别在每个容器里打印版本号，并说明这个做法相比"在自己电脑上装三个 Python"有什么优势与什么代价。
    参考答案

    思路：可以用 docker run --rm python:3.8-slim python -V、python:3.11-slim、python:3.12-slim 三条命令完成。优势：三个版本完全并存且互不影响，不需要改系统的默认 python，不需要动环境变量与 PATH，删掉镜像就等于彻底卸载，而且这套命令可以直接写进文档给同学复现。代价：每个版本都要下载一份镜像（占用磁盘），容器与你本机的文件系统默认是分离的，想做交互式开发需要额外配置挂载或进入容器，另外你多了一层需要理解的东西。

  11. 请预测下面这条命令的输出，并解释你预测的依据。 
    docker run --rm --memory=64m alpine cat /sys/fs/cgroup/memory.max
    参考答案

    思路：会打印出 67108864，也就是 64 MiB。依据是 cgroups 把内存上限表示为一个以字节为单位的数字，写在 cgroup 目录下的文件里；命令行里的 64m 只是人写的方便记号，最终会被翻译成这个数字写进内核。如果报文件不存在，说明内核或挂载布局不同，可以改看 memory/memory.limit_in_bytes。这道题真正考的是"资源限制不是约定，而是内核里的事实"这个认识。

  12. 故障诊断：队友说"容器里没有网络，curl 一个网址就超时"，但你确定容器是运行着的。请列出三个你会依次检查的方向，并说明每一个方向检查的依据。
    参考答案

    思路：第一，检查容器是否有网络接口与 IP（docker exec 进去看 ip 或直接用 docker inspect 看网络配置），依据是"没有接口就谈不上连通"。第二，检查 DNS 解析是否正常，依据是"curl 超时"与"无法解析域名"是两种不同的故障，先在容器里解析一个域名再决定方向。第三，检查是不是镜像本身就没有装 curl 或证书，依据是 Alpine 这类极小镜像默认不带这些工具，你看到的报错可能来自工具缺失而不是网络不通。若这三步都正常，再往宿主机与 Docker 网络配置层查，这是第 07 章的内容。

  13. 方案取舍：你们要把一个仅有三人的课程设计交给老师检查。方案 A 是写一份详细的安装文档，方案 B 是提供一个镜像。请分别说出两个方案在"老师第一次能跑起来"这件事上的失败概率来源，并给出你的选择与理由。
    参考答案

    思路：方案 A 的失败来源是文档与现实的偏差——漏写步骤、软件源变动、老师机器上的既有环境不同、隐含前置条件未写。方案 B 的失败来源更集中：老师要有 Docker 环境、镜像要能拿到（本地文件或仓库）、容器里缺的东西（比如数据、密钥、外部服务）依然要额外说明。在真实条件下，方案 B 把不可控因素从"十几个手工步骤"压缩成"一件事能跑起来"，因此更可靠；但如果老师完全没有 Docker 环境，方案 A 反而更稳。评分要点：要看得出"失败点数量"与"单点失败成本"是两个维度。

本章总结

  • "在我机器上能跑"不是一句抱怨，而是一个技术判断：程序能跑意味着它所依赖的一整套条件恰好凑齐了，而这套条件从来没有被记录过。
  • 程序的环境依赖分成六层：运行时、第三方库、系统库与动态链接、环境变量与配置、路径与权限、外部服务。越往下越不容易被写进文档，也越容易成为"幽灵问题"。这一章最重要的一个判断是：环境问题不是被解决掉的，而是被显式写下来的；容器把不确定性从运行时搬到了构建时。
  • 依赖冲突无法通过"各让一步"解决，因为冲突的根源是名字的唯一性，而不是空间的稀缺。当约束互相矛盾时，出路是改变约束所在的边界。
  • 隔离思想的历史是一部补漏洞的历史：1960 年代的分时系统需要隔离用户，1979 年的 chroot 隔离了文件视图，FreeBSD Jails 与 Solaris Zones 加上了进程与网络，2002 年起的命名空间逐个维度实现视野隔离，2008 年进入内核的 cgroups 负责资源上限，LXC 把这些拼成"容器"这个概念。
  • 命名空间回答"你能看见什么"，cgroups 回答"你最多能用多少"。这两句话是理解容器全部行为的两把钥匙。
  • Docker 真正解决的是分发问题：分层且按内容寻址的镜像格式、把环境写成文本的 Dockerfile、让下载环境变简单得像装软件包的公共镜像仓库。技术早就成熟了，缺的是让环境成为一个可命名、可传递、可复现的物件。
  • 容器共享宿主机的内核，这一条同时解释了它的优点与边界：启动快、体积小、密度高，但换不了内核、跑不了别的操作系统、隔离强度取决于内核与配置。
  • 虚拟机共享硬件，容器共享内核。所有其他差别都能从这一句推导出来，包括"在 Windows 上跑 Linux 容器其实仍需要一层虚拟机"这件反直觉的事。
  • 隔离的强度是一段阶梯：命名空间、资源限制、能力收敛、系统调用过滤、强制访问控制、用户命名空间、无根模式、虚拟机。说"我们用了容器"没有回答"我们隔离得多强"。
  • 镜像与容器的分工是理解一切容器现象的基础：镜像是共享的只读模板，容器是模板加一层私有的可写层。这解释了为什么两个容器的文件互不可见，而镜像列表里依然只有一份。
  • 小不等于好。Alpine 的几 MB 换来了更小的攻击面，也带来了工具缺失与库兼容差异，这属于需要权衡的取舍，不是需要崇拜的美德。
  • 这一章证明了"共享内核"这四个字不是口号：它可以从一个 uname 命令、一份 cgroup 文件、一次 docker images 的输出里被看见、被验证、被推导。

如果只从这一章带走一样东西，我希望是那个习惯：听到一个关于技术的断言时，先问"如果它成立，我应该看到什么"。这一章里所有的结论，都是从一次可以亲手做的观察里长出来的，而不是从别人的结论里抄来的。宇宙很大，而你要学的从来不是某一条命令，是在陌生的深海里自己找出路的能力。下一章我们不再谈历史，而是把 Docker 这台机器拆开——你会看到那条 docker run 命令在几百毫秒里，究竟经过了哪些部件的手，以及为什么第一步永远是确认那个后台的守护进程还活着。
