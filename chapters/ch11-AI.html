AI 时代的容器：当计算开始学习

把环境的痛苦交给容器，把心力留给模型与思想。

第 10 章你把镜像送上了流水线：代码一推，机器自动构建、自动打标签、自动部署。现在把注意力转到一个更热闹、也更混乱的地方。你读这本书，多半是因为你想做人工智能——想训一个自己的模型，想复现某篇论文的结果。而你很快会撞上一堵墙，这堵墙不是数学，也不是代码，而是环境。同一份代码，在别人机器上跑出 92% 的准确率，在你这里连 import 都过不去；昨天还能跑的脚本，今天更新了一个包，报错信息长得像天书；你花三天配好一台机器，第四天要换一张卡，一切从零开始。本章要把你在前十章攒下的工具一次性对准这个最难的战场。看完你大概会有一种迟来的释然：Docker 不是为部署 Web 服务发明的，它更像是为 AI 开发者准备的救生衣。

回 望

第 01 章我们讲过"在我机器上能跑"这句程序员的老笑话，第 05 章给了你消灭它的武器——Dockerfile，第 06 章教你把重要的东西从容器里搬到容器外。前面几章的例子基本是 Web 服务、数据库、命令行工具，它们对环境的要求相对温和：一个运行时，几个库，一些配置。这一章你会看到，当"环境"的复杂度被推高一个数量级，前面那些抽象到底还站不站得住。

为什么偏偏是 AI，把环境问题逼到了极端

先讲一件你多半已经经历或即将经历的事。你找到一篇论文的开源代码，作者写了怎么跑：装依赖、下载数据、执行训练脚本。你照着做，第一步就卡住了——包管理器在解析十几个包的版本关系，最后给你一段红字，大意是"找不到能同时满足这些要求的组合"。你搜了半小时，改了两个版本号，依赖装上了，跑起来又报了一个关于显卡的错误。再改，代码终于开始训练，但准确率比论文低了六个百分点，而你完全不知道问题出在哪一环。这是这个领域的结构性问题，暴露在了一个人身上。

Python 生态的版本纠缠

Web 项目的依赖通常是一主线加几个工具：一个框架、一个数据库驱动、一个序列化库，冲突规模有限，锁版本就能解决。深度学习不一样。你装一个框架，背后拖着一条极长的链条：数值计算库、图像与科学计算库、编译期扩展，以及最麻烦的那位——GPU 计算库。这些包的版本之间不是可以自由组合的关系，而是一张被官方矩阵钉死的方格表：框架的某个小版本只接受某几个范围内的数值计算库；数值计算库的某个大版本会一次性删掉一批旧接口，让下游全部报错；而 GPU 计算库的版本又必须和框架的编译选项对齐。你从网上抄来的依赖清单，抄到的是别人昨天那台机器的快照，不是一份规格说明。更隐蔽的一层是：包管理器默认解的是"我装得上吗"，不是"我装出来的行为和作者一致吗"。

易 错 点

初学者最常犯的错，是在一个环境里靠命令一个个把包装出来，装到能跑为止，然后把它当成"我的环境"长期使用。它在当下可用，在认知上却不可知——你没有任何一份文件能说明它里面有什么。真正的危险不是它坏掉，而是它坏了以后你修不回原来的样子。自查方法：导出一次完整依赖清单，和你手写的那份对比；差出十几行，你现在的环境就已经不是你以为的那个环境了。

复现一篇论文，为什么常常失败

复现（Reproducibility，用同样的输入与步骤得到同样的结果）在计算机科学里是基本礼貌，在机器学习里却是一道难关。失败的原因有四类，你要学会区分，因为它们对应的解法完全不同。环境不可复现：依赖版本、CUDA 版本、系统库不一致，代码跑不起来，或者跑起来但数值行为有差异——这一类容器能解决绝大部分。数据不可复现：数据集被更新过、划分方式没写清、预处理里藏着一行随机增广——这一类需要数据版本管理，容器只能帮你把"用了哪一份"记清楚。随机性不可复现：随机种子、显卡上某些算子的非确定性实现、多线程调度顺序——这一类必须在代码层面显式固定。记录不可复现：作者根本没写超参数、没写轮数、没写学习率调度——这一类是纪律问题，工具只能降低你犯错的概率。

把这张清单记住，它奠定本章的一个核心判断：容器解决的是"环境"这一格，它是复现链条上最基础、最容易做、收益最大的一格，但它不是全部。这里先放下一个问题，你别急着答：容器的承诺是"同样的镜像在任何地方跑出同样的行为"，那为什么同一个镜像在两张不同的显卡上训练，损失曲线还是可能不一样？我们后面会回到它。

换卡重配，以及算错的代价

Web 服务的迁移相对温和：换一台服务器，拉代码、装运行时、配反向代理，半天能搞定，因为它的依赖面窄，且大多不依赖特定硬件。AI 的迁移要粗暴得多。它依赖的东西里有一样是硬件本身，而硬件带着厂商、型号、驱动版本、计算能力这些无法用软件包描述的属性。你在宿舍笔记本上跑通的脚本搬到实验室那张卡上，"在我机器上能跑"就精确地变成了"在我这张卡上能跑"。这正是容器在 AI 领域能给出最优解的地方：它把"与代码有关"的部分冻结进镜像，成为可版本控制、可复制、可推送的交付物；把"与硬件有关"的部分留在一个明确、单一、数量最少的接口上，也就是宿主机的显卡驱动。你不必再对齐十几件事，只需要对齐这一件。

比 喻

传统开发的环境像一间你亲手布置的房间：桌子摆哪、灯放哪，你住久了很熟，但朋友来借住一晚，会发现找不到开关。容器化等于把这间房连同家具装进标准集装箱，谁都能吊走、放下、原样打开。而 AI 的环境像一间必须接上特定电压的车间：集装箱可以标准化，插座却必须按当地电网来。本章真正的技术难点全在"集装箱"与"插座"之间那个接头上——也就是显卡驱动与 CUDA 的关系。

还有一个差别值得单独说。Web 服务出问题的形式是"服务挂了""接口变慢了"，你立刻知道，也能立刻回滚。机器学习实验出问题要安静得多：训练正常跑完，日志正常打印，损失曲线漂亮地下降，然后你得到一个比别人差的结果。你不会收到任何报警。所以请记住一个判断：在 AI 里，"能跑"和"可信"是两件不同的事，而容器能保证的是前者。愿意为后者付出多少纪律，是这个领域里区分业余与专业的那条线。

CUDA 的四层版本关系：本章真正的技术核心

如果本章只允许你记住一件事，就记这一节。前面讲的所有痛苦，超过一半都从这个接口上长出来。CUDA（Compute Unified Device Architecture，统一计算设备架构）是显卡厂商提供的让你用显卡做通用并行计算的平台。它不是一个软件包，而是一整套跨越"硬件—驱动—运行时—应用"的栈。在这套栈里，版本号出现在四个不同的地方，而它们之间的兼容关系有明确的方向性。你以后遇到的"CUDA 不可用""版本不匹配""找不到设备"，几乎都能用这张表定位。

层次它是什么装在哪里谁决定它的版本容器能固定它吗
第一层：显卡驱动让操作系统认识并使用显卡的内核态软件，同时提供访问显卡的底层接口宿主机（Windows 上经 WSL2 可见）你安装的驱动版本，它决定这台机器最高能支持到哪个 CUDA 版本不能。它必须匹配硬件与内核，跑在容器之外
第二层：CUDA 驱动接口驱动暴露给上层的那组接口，CUDA 程序通过它和显卡说话随第一层驱动一起提供，不单独安装由驱动版本决定不能，它是驱动的组成部分
第三层：CUDA 运行时你真正调用的那些库与工具，例如并行计算库、深度神经网络加速库镜像里（例如 nvidia/cuda 系列基础镜像）你选的镜像标签能，而且这是容器最擅长的事
第四层：框架编译绑定深度学习框架在打包时选择链接了哪个版本的运行时与加速库镜像里，随框架一起你安装的框架发行版能，但必须与第三层对齐

看最后一列。第一、二层属于宿主机，容器动不了；第三、四层属于镜像，容器能锁死。这就是容器在 AI 场景里的全部价值主张：它把四层里最烦、最常变、最难对齐的两层固定下来，只给你留下一层需要操心。

向后兼容是有方向的

四层之间的规则可以压缩成一句话：新驱动能带动旧运行时，旧驱动带不动新运行时。方向是单向的。为什么？想象驱动和运行时之间有一份接口清单：运行时声明"我需要第 1 到第 20 项能力"，而驱动说"我这里有第 1 到第 25 项"，前者要的后者都有，于是能用；反过来，运行时需要第 25 项而驱动只提供到第 20 项，它开局就找不到要的东西，直接报错。厂商为了让新驱动能跑老程序，会在驱动里长期保留老接口；却没办法让一个已经发布的旧驱动凭空长出从未实现过的新接口。

展开：显卡工具里那个版本号到底在说什么

nvidia-smi 输出的表格右上角会有一行形如"CUDA Version: 某版本号"的字段。它的准确含义是：这份驱动在向后兼容的意义上最高支持到哪个 CUDA 版本。它不代表你系统里装了这个版本的 CUDA 工具包——很可能你系统里一份都没装，程序用的是镜像内那一份。最实用的读法是把它当成一道门槛：那个数字就是你选镜像标签时不要越过的上限。具体版本号会随时间变化，请以显卡厂商官方镜像的标签页与深度学习框架官网的版本矩阵为准，不要背任何数字。

一条可以直接照做的排查顺序

把规则变成动作，就是一条固定的排查顺序，请把它抄在实验记录本第一页。顺序很重要，因为它保证你每次都先检查最外层的原因，而不是一头扎进最里层改代码。第一步，看宿主机。在宿主机（Windows 上是 WSL2 里）执行 nvidia-smi，确认它能正常输出，记下它给出的 CUDA 版本上限。这一步就失败，后面全都不用做，问题在驱动层，与容器无关。第二步，看镜像标签。用第一步得到的上限约束镜像选择：镜像里的运行时版本不能超过它。优先选带完整版本号的标签，不要用会漂移的宽泛标签。第三步，看框架。去框架官网的安装页面查版本矩阵，确认你打算装的框架发行版对应的正是第二步选定的运行时版本。这一步最容易被跳过，也最容易导致"能 import 但一跑就崩"。第四步，在容器里验证。进容器后再跑一次显卡工具，然后跑框架自己的可用性检查。两层都通过，这条链路才算完整。

方 法

处理"多层版本耦合"这类问题，有一个能迁移到任何技术栈的方法：先画出层次，再标出每一层的所有权，最后确定检查顺序。层次让你知道有几种可能；所有权告诉你这一层该由谁更新（是你的代码、是镜像、还是机房里的驱动）；检查顺序让你每次从最外层开始，避免在里层做无用功。它的对立面是"看到报错就去搜索报错文本"，那样你最快得到的，是一个碰巧让别人也生效过的改动，而不是一个你能解释的原因。

现在回到刚才那个悬着的问题。容器固定的是第三、四层，也就是"软件怎么调用显卡"；它固定不了第一层的硬件本身——不同的显卡型号、不同的显存大小、不同代的计算能力，会让底层算子的实现与数值精度产生细微差异。容器把"环境"这个变量压到了最小，但没有把它压到零。明白这一点，你就不会在追求复现时走火入魔，也不会因为一次不一致就怀疑整套方法。

GPU 容器实战：让显卡接进木箱，以及没有显卡时的另一条路

把显卡交给容器，需要有人做一件事：把宿主机的设备节点、驱动库以及那几个命令行工具挂进容器。做这件事的组件在 Linux 上叫 NVIDIA Container Toolkit（NVIDIA 容器工具包），它把自己注册成容器运行时的一个钩子，在容器启动时把显卡相关的文件塞进去。Windows 上的 Docker Desktop 通过 WSL2 提供了对应能力，你通常不需要手工安装它，但要保证 WSL2 里的驱动可用：先在 Windows 侧装好支持 WSL 的显卡驱动，再在 WSL2 里执行一次 nvidia-smi。它能打印出显卡型号与驱动版本，才说明宿主机这一侧通了。

docker run --rm --gpus all nvidia/cuda:12.4.0-base-ubuntu22.04 nvidia-smi

你会看到一张与宿主机上几乎一致的显卡信息表，包括驱动版本、CUDA 版本上限、显存总量、温度与功耗。这个镜像标签里的版本号会随时间变化，写在这里只是让你看到一个真实可读的例子；实际使用时请去官方镜像的标签页挑一个与你的驱动上限匹配的版本，一切以官方版本矩阵为准。

与它相对的是旧式写法：早期用 --runtime=nvidia 把整台机器的显卡能力一次性交出去。现在推荐用 --gpus，因为粒度更细，可以直接写成 --gpus '"device=0,1"' 只给容器两张指定的卡，更符合"按需授权"的原则。

易 错 点

一个高频误解是：只要镜像里装了 CUDA，容器就能用显卡。不是的。镜像里有 CUDA 运行时，只说明这个容器"会开车"；能不能真开上车，取决于你有没有把车交给它——也就是有没有 --gpus 参数、以及宿主机这一侧有没有可用驱动。现象上很好辨认：宿主机一切正常，容器里跑显卡工具却报"找不到命令"或"驱动通信失败"。第二个高频误解是把 --gpus all 当成性能参数，它其实是权限参数，与速度无关。

没有 NVIDIA 显卡的读者，请从这里开始

如果你用的是集成显卡、别的品牌的显卡，或者只是一台普通笔记本，请把上面那段当成背景知识读完，然后跟着下面这条路径做完本章所有实验。你不需要任何显卡就能学会这一章的全部工程方法，因为本章真正教的是"如何组织一个可复现的计算环境"，而显卡只是这个环境里的一个可选部件。你少的只是执行速度，不少任何概念。先建立一个基线环境：下面这条命令把当前目录挂进容器、把工作目录切到那里，然后给你一个可以随意折腾的 Python 环境。

docker run -it --rm -v "${PWD}:/work" -w /work python:3.12-slim bash

你会得到一个容器内的 bash 提示符。${PWD} 在 PowerShell 与 bash 里都会展开为当前目录，所以这条命令在两个终端里都能用；如果你更喜欢 Windows 原生风格，把它换成 ${PWD.Path} 效果一样。注意 -it 与 bash 的组合：这是"我要进去敲命令"的标准姿势。退出后容器被 --rm 自动清理，宿主机上只留下你写进 /work 的文件。

python -c "import platform, os; print(platform.platform()); print(platform.machine()); print('CPU cores:', os.cpu_count())"

你会看到容器内的操作系统标识与 CPU 核心数。这里有个值得停留的细节：容器报告的 CPU 数量可能与你笔记本的真实核心数不同，因为容器看到的是它被允许使用的资源视图，而不是整机的物理规格。顺便说明：在真正的显卡实验里，这个位置本该打印出显卡型号与可用显存；如果你没有卡，你刚刚用同一套流程验证了镜像、挂载、交互这三件事，它们才是本章的主干。

想做一点真实的数值计算，可以在容器里装纯 CPU 版本的数值库与框架。官方为 CPU 场景提供了专门的安装渠道：在框架官网的安装页面选择 CPU 平台，它就会给出对应的命令。具体命令与版本号随迭代变化，请以框架官网的版本矩阵为准；核心是那条命令里对计算平台的指定，它决定了你装到的是不是 CPU 版本。

pip install --no-cache-dir numpy
python -c "import numpy as np; a = np.arange(6).reshape(2, 3); print(a); print(a.sum())"

你会看到一个小矩阵和它的元素和。这个例子朴素得有点可笑，但它证明了完整链路：镜像里有 Python、容器里有网络能装包、装上的包能正常导入并计算。本章后面每一个实验都可以在这个基础上完成——把模型换成小一点的、能在 CPU 上几十秒跑完的版本，你的学习效果和有卡的同学完全一样。

前 瞻

第 12 章会把这个场景放大到集群规模：当你有八台机器、三十二张卡，而一堆训练任务在抢这些卡时，"哪张卡给谁用"就不再是命令行参数能解决的问题了。编排系统会引入资源请求与调度队列。--gpus 这个参数的粒度是"容器级"的，它回答不了"排队与公平"。当你开始觉得需要排队时，你已经到了该学编排的时候。

往下走之前，再留一个问题给你想：一张卡上同时跑两个容器，它们说自己在"共享"这张卡。这个"共享"意味着什么？是各自分到一半显存、一半算力，还是别的什么？我们稍后揭晓，你也可以先用 docker stats 自己观察一下。

交互式环境：把 Jupyter 装进木箱

训练环境和 Web 服务有一个根本区别：它大部分时间不是"服务"，而是"工作台"。你需要在里面试探、画图、改一行再跑一次、看看中间结果长什么样。所以 AI 场景里最常见的容器形态不是后台守护的服务，而是一个给你交互的界面。Jupyter（Jupyter Notebook，把代码、运行结果、图表与说明文字混排在一个浏览器页面里的交互式计算环境）就是这类工作台里最常用的一个。

docker run -it --rm -p 8888:8888 -v "${PWD}:/home/jovyan/work" jupyter/scipy-notebook

你会看到一段以 http://127.0.0.1:8888/ 开头的地址，末尾带一串很长的令牌参数。把它整段复制到浏览器里，你就得到一个完整的数据科学环境。三个细节值得注意：-p 8888:8888 把容器端口发布到宿主机，这是第 07 章讲的；-v "${PWD}:/home/jovyan/work" 把当前目录挂进那个镜像约定的工作目录，这是第 06 章讲的；这个镜像属于官方维护的系列之一，标签与可用变体会随时间调整，请以官方镜像的标签页为准。

回 望

第 06 章我们反复讲一条原则：容器可以被当成随时会消失的东西，数据不可以。当时讨论的是数据库文件、配置文件。这一节是那条原则最容易被忘记的一次应用，因为它太不像"数据"了：你的笔记本文件名义上是代码，实际上同时装着代码、运行结果、图表和你的思考过程，它是你几个小时工作的全部痕迹。不挂载的 Jupyter 容器，是一个会忘记你所有工作的容器。这不是 bug，这是容器本来的设计。

现在做一个你一定会记住的实验。在浏览器里新建一个笔记本，运行下面两行。

import pathlib
pathlib.Path("hello_from_container.txt").write_text("这是一行写在容器里的字\n", encoding="utf-8")
print("已写入:", pathlib.Path("hello_from_container.txt").resolve())

你会看到打印出的路径，形如 /home/jovyan/work/hello_from_container.txt，第一段是容器内的目录。然后离开浏览器，在宿主机的文件管理器或终端里打开你启动容器时所在的那个目录，找到这个文件，打开它，你会看到同一行字。这一步是本节的全部意义：绑定挂载把"容器里的一个目录"和"你笔记本上的一个目录"变成了同一个东西的两扇门，第 06 章的文字此刻变成了你亲手验证过的现象。追问的变体：删掉挂载参数重新启动一个 Jupyter 容器，再写一个文件，然后关掉它、换一个新容器去找——它不在了。镜像让环境可复现，卷让工作可延续，两件事必须同时做到，你的实验才是可持续的。

易 错 点

Jupyter 容器有一个安全坑，性质比"忘记挂载"更严重。带令牌的地址是一把钥匙，而端口发布会把服务暴露到宿主机所有网络接口上。如果你的笔记本连着实验室或宿舍的局域网，同网段的人只要拿到那个地址，就能在你的容器里执行任意代码——而你容器里的文件，挂载在你自己磁盘上。两个防护动作：不要把这种地址贴进群里或公开笔记；只想本机访问时，把端口发布写成只绑本机地址的形式。还要清楚一点：Jupyter 默认带终端功能，它天生不是面向公网的服务，不要把它当部署方案。

想把环境真正固化下来，只有一条路：把你用过的每一个包写进 Dockerfile 或依赖清单，而不是靠手工安装慢慢累积。下面这个实验让你亲身体会"累积"与"声明"的差别。实验目的：观察一个手工装过包的环境在容器销毁后留下了什么。预期现象：什么也没留下。你要解释的是为什么——不要只回答"因为容器删了"，请回答"被删掉的到底是什么，为什么它不该被保留"。

docker run --rm python:3.12-slim pip install --no-cache-dir requests
docker run --rm python:3.12-slim python -c "import requests"

第一条命令会下载并安装一个网络请求库，安装过程看起来完全成功，容器退出后自己消失。第二条命令会给你一个模块找不到的错误。这个报错就是本节最重要的一课：那次安装发生在容器的可写层里，属于"这次运行的状态"，不属于"这个镜像的定义"。你要建立的条件反射是：环境应该是被声明出来的，不是被累积出来的。追问的变体：如果你确实需要这个包，正确做法是什么？想让它留下就写进 Dockerfile——永远不要在一个长期运行的容器里手工装包，然后指望它明天还在。

训练环境的工程化：让一次实验成为可交付的事

到这里我们开始做正事：把你那靠记忆维护的训练环境改造成一套有结构、可传承的东西。你其实在管理四种性质完全不同的东西，它们的正确归属各不相同。下面这张表请读三遍，本节剩下的内容都是它的展开。

你的东西性质归属为什么
训练代码、依赖清单、Dockerfile文本，可版本控制，变更频繁进镜像，并用 Git 管理它是你唯一的事实来源，必须能被评审与回滚
数据集体积大，变更少，可能带使用条款绑定挂载或只读卷几十 GB 的东西不该进镜像层；进去一次就永久占空间且难撤
checkpoint 与输出训练过程中不断产生，丢了会心疼挂载到宿主机目录或数据卷容器随时可能被杀，几小时算力换来的权重不能放在可写层里
日志与实验记录体积小但价值高，需要在容器死后仍可读挂载出来，或写成事件流由外部收集第 10 章讲过：应用只管往标准输出打印，由外部负责留存

先回答一个你可能会反问的问题：数据进镜像到底有什么不好？第一是层的物理性质。第 03 章讲过，镜像层是只读的、按内容哈希标识的。一份 40 GB 的数据集复制进去就是一层 40 GB 的内容，它会被完整地算哈希、完整地推送到仓库、完整地下载给每一个需要这个镜像的人。第二是合规。很多数据集有使用条款，不许再分发；把它打进镜像再推给别人，性质上就从"我按条款使用"变成了"我在传播它"。第三是构建上下文。第 05 章讲过，构建命令结尾那个点会把你指定的目录整包发给构建引擎；数据如果躺在项目目录下，即使 Dockerfile 里没写复制它，构建的第一秒你也要为它付出代价。那"如果数据只有 20 MB 呢"？答案会变：这个量级的传输与存储代价几乎可以忽略，换来的是"一条命令就有完整环境"的便利，在教学和小规模实验里是划算的。所以真正的判据不是一条教条，而是一笔账：当数据的体积或合规要求超过它带来的便利时，它就该被移出镜像。

docker run -it --rm --name train-exp001 -v "${PWD}:/workspace" -v "${PWD}/data:/data:ro" -v "${PWD}/runs:/runs" -w /workspace python:3.12-slim bash

你会得到一个工作目录在 /workspace 的容器，其中 /data 只读、/runs 可写。三个设计点：数据用 :ro 声明只读，这是对自己的一道保险，训练脚本写错路径时最多报错，不会把原始数据改坏；输出单独用一个目录挂出来，让"清除输出、重跑实验"变成一条命令，而不用去容器里翻找；--name 起了名字，让你在另一个终端里能用 docker exec 进去看情况。

易 错 点

训练容器最惨痛的失败不是报错，而是"跑了六个小时，权重没了"。造成它的写法通常是：训练脚本把 checkpoint 存到容器内的当前目录，你没挂载任何输出目录，而容器因为内存超限被杀、终端被关掉或机器休眠而退出。容器一被删除，可写层跟着消失，六个小时的算力没有任何痕迹。自查方法：启动训练前先问一句"这次训练里最贵的东西现在被写在哪个路径下？这个路径在宿主机上对应哪个目录？"如果你答不出第二个问题，就先不要按回车。

cat > requirements.txt <<'EOF'
# 请把每个包的版本写死，具体版本以各项目官方版本矩阵为准
numpy
EOF
cat > Dockerfile <<'EOF'
# 有显卡时：把基础镜像换成与宿主驱动匹配的 CUDA 运行时镜像
FROM python:3.12-slim
WORKDIR /workspace
COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt
COPY . .
CMD ["python", "train.py"]
EOF
docker build -t my-exp:0.1 .

你会看到构建逐层进行，最后给出镜像名与标签。三个决策点：第一行 FROM 是本章最需要动脑的一行，有显卡的读者应换成带 CUDA 运行时的基础镜像并让版本与宿主驱动对齐；依赖清单放在源码之前复制，是为了让"改一行训练代码"不触发依赖重装，这是第 05 章那条缓存规则的原样应用；安装时带上 --no-cache-dir，因为下载缓存对运行毫无用处。

回 望

第 09 章讨论镜像扫描与最小权限时，例子是一个 nginx 容器。AI 镜像把这个问题放大了一个数量级：一个带完整 CUDA 工具链与深度学习框架的镜像，体积动辄几个 GB，里面装着几百个包、编译器、示例数据与测试脚本，其中相当一部分在运行推理时根本用不到。体积大不等于更危险，但它意味着需要被扫描的东西更多、需要打补丁的面更宽。下面要讲的镜像瘦身，因此在 AI 场景里既是空间问题，也是安全问题。

显存、算力与"共享"的真相

先补上前面的问题：一张卡上跑两个容器，它们真的共享算力吗？默认情况下，两个容器都能看见整张卡，谁先用谁先拿；显存被占满的那一刻，第三个申请显存的进程就被拒绝——这不是排队，而是先到先得加随时可能失败。计算能力则被显卡的调度器在两个进程之间交替分配，所以你会看到"两个都变慢了"。默认的共享是"抢占式共用"，不是"公平切分"。它没有配额，没有隔离，也没有保障。想让资源变得可预期，你需要显式分配：用设备号把容器钉在指定的卡上，或者用工具层面的约束限制它能看到多少算力。

关于镜像体积，给你一份现实的账：一个带完整 CUDA 运行时和深度学习框架的镜像，几个 GB 是常态；带编译工具链的那一类还要更大。缓解手段按收益排序：第一，选对基础镜像变体，不需要编译扩展就不要选带完整工具链的版本；第二，多阶段构建，只把产物带进最终镜像；第三，共享基础层，层复用会替你省下重复下载；第四，清理缓存，在同一条指令里下载、安装、删源。

做法省下的量级代价什么时候值得做
从工具链版本换成运行版本一个数量级容器内无法再编译扩展、缺少部分调试工具依赖都是预编译包时，几乎总是值得
多阶段构建几百 MB 到数 GBDockerfile 复杂度上升，构建步骤要重组需要从源码编译依赖，或需要构建产物
共享同一基础镜像每个镜像数 GB 的重复下载基础镜像升级时所有下游要一起重建同时维护训练与推理两个镜像时
清理包管理器缓存几十 MB 到几百 MB几乎为零，只是要求把命令合并永远值得，属于基本卫生
把权重从镜像移到挂载几百 MB 到几十 GB部署多一步文件准备，要保证两边一致权重更新频繁或体积很大时
思 考
  1. 把模型权重放进镜像，和把权重挂载进容器，各自让你失去了什么？如果这个模型每周更新一次，而线上有一百个实例，你的选择会变吗？
  2. 如果你一年后要重跑今天这个实验，你需要保存哪些东西才能保证成功？请具体到文件名或命令，并说明每一项如果丢了会发生什么。

实验身份：三个东西让一次实验可以被指认

下面这个观点是本章最值钱的工程结论，请慢读。在一次实验里你会看到很多数字：准确率、损失、学习率、批次大小、训练轮数。这些数字里只有少数能回答"这次实验到底是什么"。你需要的不是更多数字，而是一份身份——一组能唯一指认这次实验的组合，它必须满足两个条件：别人（或者一年后的你）能凭它精确重建环境；它能区分"只是重跑了一次"和"改动了一处"。满足这两个条件的是三件东西：镜像 digest、代码提交哈希与超参数。digest 的必要性来自第 03 章：标签是可以被覆盖的可变指针，而 digest 由镜像内容算出，没法被冒充；提交哈希回答"这个镜像是用哪次提交构建的"，它把代码逻辑也钉住；超参数既不在镜像里也不在代码里，只存在于你启动训练时敲下的那些参数中，漏掉它，前两件就白做了。

三者合起来构成一次实验的身份：镜像 digest + 提交哈希 + 超参数 = 可复现的实验身份。缺任何一件，你都会陷入一种熟悉的困境：结果出现了偏差，你知道有问题，却不知道该回退哪一部分。配套动作是不要在容器里手工敲训练命令，让参数从环境变量进入，并把它连同身份信息写进日志的第一行。

docker run --rm --gpus all -v "${PWD}/data:/data:ro" -v "${PWD}/runs:/runs" -e EPOCHS=10 -e LR=0.001 my-exp:0.1 python train.py

你会看到训练脚本按指定轮数与学习率运行，输出目录里出现日志与 checkpoint。这里没有用 -it，因为训练任务不需要交互；用 -e 传参数而不是改代码，是为了让同一份镜像承载不同配置的实验。也请注意 --gpus all 这一句在无显卡的机器上会直接失败，把它去掉，你的 CPU 版本一样能跑完整个流程。

展开：为什么"重跑一次"也需要记录身份

很多人以为实验记录是为了对比不同配置，它更重要的用途是对比"同一个配置的两次运行"。深度学习训练里有相当多的非确定性来源：参数初始化、数据打乱顺序、底层算子的实现细节。你今天跑出 91.2%，明天跑出 90.6%，差的那 0.6 个百分点是改动带来的，还是随机波动？没有身份记录，你无法回答，于是你会开始根据噪声做决策——调了一个超参数，结果变好了，其实只是这次随机种子比较走运。这是机器学习实践里最昂贵的自我欺骗之一。

前 瞻

第 12 章之后你会发现，今天你手写在记录本上的这三件东西，会被工具接过去：实验追踪系统替你保存参数与指标，模型注册表替你保存"哪个权重对应哪次实验"。它们不是新概念，只是同一条纪律被自动化了。现在先把这条纪律建立在你自己的实验记录里，比先装任何工具都重要。

从训练到服务：把模型变成可被调用的东西

训练完之后，你手里有一个权重文件，它本身不会做任何事。要让它产生价值，你得把它包成一个可以被别人调用的东西，通常是一个 HTTP 接口：你发一段输入过去，它返回一个结果。这件事叫模型部署（Model Serving，把训练好的模型包装成可被外部调用的服务）。这一节的核心观点是：训练环境和推理环境要的东西不一样，因此它们应该是两个镜像，而不是一个。

对比项训练镜像推理镜像
目标能训出好模型，允许慢、允许折腾又快又稳地响应请求，越简单越好
要不要编译工具链经常要，因为可能要编译扩展不要，依赖都是预编译的
要不要数据集要，而且是几十 GB 级不要，只要权重
要不要画图与追踪库要不要，纯属攻击面与体积负担
体积容忍度与启动时间几 GB 可以接受，启动分钟级无所谓越小越快越好，会直接影响扩容速度
关键指标吞吐：每秒处理多少样本延迟与并发：一次请求多久返回

看这张表，推理镜像的需求几乎是训练镜像的一个子集，这正是多阶段构建的用武之地：一个阶段负责准备依赖，最终阶段只带上运行时和加载权重所需的库。第 05 章讲多阶段构建当时是为了省体积，在这里它同时解决另一个问题——把训练期才需要的东西彻底挡在服务之外。下面这份骨架是一个能跑起来的推理服务，只有两个接口：一个健康检查，一个预测；我刻意把它写得很短，因为这一节的目的是让你看到工程决策。

mkdir -p serving
cat > serving/app.py <<'EOF'
# 最小推理服务骨架：重点是结构，不是这个模型有多聪明
from fastapi import FastAPI
from pydantic import BaseModel

app = FastAPI()

class Item(BaseModel):
    x: float

# 真实项目里：在这里加载模型权重，并且只加载一次
# 权重路径应来自环境变量或挂载点，不要写死在代码里
MODEL = {"slope": 2.0, "intercept": 1.0}

@app.get("/health")
def health():
    return {"status": "ok"}

@app.post("/predict")
def predict(item: Item):
    return {"y": MODEL["slope"] * item.x + MODEL["intercept"]}
EOF
cat > serving/requirements.txt <<'EOF'
fastapi
uvicorn
EOF

你在 serving 目录下得到两个文件。三个决策点：模型加载放在模块级别而不是请求处理里，因为每次请求都重读权重会让延迟从毫秒级涨到秒级，这是新手最常见的性能错误；权重路径应来自环境变量，这样同一个镜像能用在不同环境而不用重新构建；健康检查接口不是装饰，第 10 章讲过编排系统要靠它判断实例是否可用。真实的依赖版本请以各项目官方版本矩阵为准写死，不要留空。

cat > serving/Dockerfile <<'EOF'
FROM python:3.12-slim
WORKDIR /app
COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt
COPY app.py .
RUN useradd -m appuser
USER appuser
EXPOSE 8000
# 监听 0.0.0.0，否则容器外访问不到
CMD ["uvicorn", "app:app", "--host", "0.0.0.0", "--port", "8000"]
EOF
docker build -t my-serving:0.1 ./serving

你会看到构建完成。这几行里藏着三个你以后一定会踩的坑。第一是启动命令里的 --host 0.0.0.0：只监听本机回环地址时，容器内部自己测是通的，从宿主机访问却是拒绝连接——第 07 章讲端口映射时提过这个区别。第二是 USER appuser：第 09 章讲过非 root 运行，在推理服务里尤其值得做，因为它是长期在线、直接面对请求的组件。第三是复制顺序：依赖先拷、代码后拷，让"改一行服务逻辑"不必重装依赖。

docker run -d --name serving -p 8000:8000 my-serving:0.1
curl.exe -s http://127.0.0.1:8000/health
curl.exe -s -X POST http://127.0.0.1:8000/predict -H "Content-Type: application/json" -d "{\"x\": 3}"

第一条命令会打印一长串容器 ID，说明服务已在后台运行；第二条应返回一个含状态字段的 JSON；第三条应返回计算后的结果。为什么写 curl.exe？因为在 PowerShell 里 curl 是另一个命令的别名，参数解释方式和你预期的不一样，明确写成 curl.exe 可以避开这个混乱；在 Git Bash 或 WSL 里直接写 curl 即可。如果第二条返回连接被拒绝，按固定顺序检查：容器是否真的在跑、日志里有没有报错、端口有没有发布、服务有没有监听 0.0.0.0。

推理服务真正的难点在哪里

让一个接口返回结果是最简单的部分。真正让它变难的是下面几件事，它们都和容器化直接相关。批处理与延迟的取舍：显卡擅长一次算一批数据，但用户希望一次请求立刻拿到结果；把请求攒成一批能显著提高吞吐，代价是每个请求多等一会儿，一个离线批量打分任务和一个交互式对话服务的答案完全相反。显存管理与并发：一张卡通常只能装下一份模型，所以同一个容器内的多个工作进程会争抢显存；常见做法是让一个进程独占模型、请求排队进入，而进程数往往写在启动命令里。冷启动时间：镜像越大、权重越多，从启动到能响应第一次请求的时间就越长，这在需要快速扩容时会变成硬约束。

最后是版本切换与回滚，它同时也是"权重放镜像还是挂载"这个问题真正的分水岭。如果权重在镜像里，切换模型就是切换镜像标签，回滚就是切回上一个标签，干净利落，与第 10 章讲的不可变基础设施完全一致；如果权重是挂载的，你可以在不改镜像的情况下换权重，代价是"哪个镜像配哪份权重"变成了一份需要维护的对应关系。两种做法都对，但你必须明确选一种并写下来。最糟的情况是两种混用——同一个镜像在不同机器上挂到了不同的权重，于是没有人说得清线上跑的是哪个模型。

展开：量化与蒸馏，你至少该知道它们在解决什么

量化大致是"用更少的比特表示模型的参数与计算"，目的是让模型更小、跑得更快、显存占用更低。蒸馏大致是"用一个大模型指导一个小模型训练"，目的是让小的那个在保持大部分效果的同时变得轻。两者共同的目标都是把模型压到能经济地跑起来的大小。对容器化的影响在于：压缩后的模型可能需要不同的运行时支持，于是"镜像里到底装了什么"对能否跑通变得至关重要——训练时你可以用通用实现，部署时你必须精确控制。

MLOps 全景与前沿的边界

现在把镜头拉到最远。你已经会构建可复现的训练环境，也知道怎么把模型变成服务。剩下的问题是：当这些东西不是做一次，而是要每周、每天、由多个人重复地做时，怎么组织？这个问题的答案叫 MLOps（Machine Learning Operations，机器学习运维）。我想先给你一句能省下很多时间的话：MLOps 不是一套新发明的方法论，它是把第 10 章的流水线思想，从"代码"延伸到了"数据"与"模型"。

MLOps 环节它解决什么它在第 10 章的对应物
数据版本让"这次训练用了哪一份数据"有唯一答案，而不是靠目录名和记忆代码的版本控制
实验追踪把每次运行的参数、指标、环境身份自动记下来，取代手抄在纸上的数字构建日志与流水线记录
模型注册给训练产物一个正式身份与阶段标签，明确"哪个权重可以被部署"镜像仓库与标签策略
自动部署把通过验证的模型推上服务，不靠人手工操作持续部署流水线
监控与漂移发现"输入数据的分布在变，模型在悄悄失效"这类不会报错的故障可观测性三支柱
回滚出事时能迅速回到上一个已知可用的模型不可变交付物与版本回退

看最后两行，它们最容易被自学的人跳过，也最有价值。传统软件里，一个函数写错了，测试会失败，或者用户立刻反馈。机器学习系统最危险的失效方式是静默失效：接口返回 200，格式完全正确，延迟也正常，只是答案慢慢变得不对了——因为现实世界的数据分布和你训练时不一样了。这件事有个名字叫数据漂移，它没有任何告警能自动发现，除非你主动监控输入分布与预测分布。这也回到本章开头那个判断：在 AI 里，"能跑"和"可信"是两件事。容器能保证前者，而且保证得非常出色，但它对后者几乎无能为力。容器让你的系统可靠地运行，监视让你的系统运行得可靠。

方 法

面对 MLOps 这种环节很多的体系，最有效的入门方法不是从工具开始，而是从"如果出错了，我怎么知道、怎么回到上一个好状态"开始。逐条问自己：数据换了，我怎么知道？模型变差了，我怎么知道？新版本上线后出问题，我多久能退回去？退回去要动几个地方？一个体系的价值不在于它有多少组件，而在于它坏掉的时候给你多少余地。

最后我给你一张地图的边界，而不是预测未来。有三件事已经明确存在，你能亲眼观察，但我不给它们配时间表。第一，推理的容器化已经是默认做法，原因和前面讲的一样：它让"上线的是哪个版本"变得没有歧义；驱动它的不是技术时髦，而是运维的现实需求。第二，显卡资源的共享与切分仍在演进，一条路是把一张卡切分给多个隔离的使用者，另一条路是让多个任务按时间轮转共用一张卡，两者各自要解决不同的问题，具体机制与命名以各家官方文档为准。第三，模型的打包与分发格式正在向"带上运行时的标准化产物"演进，它的动机你可以完全理解，因为那就是本书第 01 章那个问题在模型层面的重演——交付物应该是自包含的，而不是一份需要读者自行拼装的清单。

思 考
  1. 一个在云端笔记本环境里跑通的训练脚本，迁移到你自己的容器里常常失败。容器能解决其中哪些部分？哪些部分它永远解决不了？请把问题分成"环境""网络""数据""硬件"四类来回答。 提示：云端环境替你做好了很多你没看见的事，试着列出你"没有被要求做"的那些事。
  2. 如果 CUDA 的版本关系如此复杂，为什么显卡厂商不把它做成"永远兼容"？把这个问题当成一次软件设计练习来回答。 提示：想清楚"向上兼容"需要谁付出什么代价，以及谁有能力单方面决定这件事。
  3. 为什么 AI 领域的"环境"问题，比传统 Web 开发更严重？如果你的答案是"因为依赖更多"，请再往下问一层：依赖更多为什么就导致问题更严重，而不只是更麻烦？ 提示：比较一下"装错了会怎样"——Web 服务装错通常是报错，AI 环境装错可能是静默地算错。
  4. 一张卡上跑两个容器，第二个总是因为显存不足起不来。你会怎么验证自己的猜测，而不是直接去重启第一个任务？ 提示：想一想"占用"这个数字是怎么算出来的，以及显存是不是可以随便切片的一整块。

在传统软件里，环境是一个你希望它消失的麻烦；在机器学习里，环境是实验结果的一部分。你无法把一个变量排除在结论之外——你只能把它记下来。

前 瞻

第 12 章会把这一章的场景推到集群规模。今天的 --gpus all 表达的是"这个容器可以用显卡"；到了集群里，你要表达的是"这个任务需要多少张卡、需要什么样的卡、如果暂时没有我愿不愿意等"。你会第一次遇到"资源和调度"这类非功能性问题——它们和代码写得对不对无关，却决定了系统能不能被多人一起用。第 12 章给你的正是那套思维。

自测：检验你是否真的学懂了

检 查 题
  1. 宿主机上显卡工具显示驱动支持到的 CUDA 版本是某个数字，而容器里用的是比它低的运行时。这能跑吗？反过来呢？
    参考答案

    能跑：新驱动可以带旧运行时，它报出的是上限。反过来不行——运行时要求高于驱动的上限时，开局就找不到所需接口。

  2. 容器启动成功，但容器内执行显卡工具报找不到命令。最可能的原因是哪一类？给出两种性质不同的可能。
    参考答案

    一是镜像里根本没有显卡工具链，比如纯 Python 镜像；二是镜像里有组件却没把显卡交给容器，但那种情况通常报驱动通信失败。

  3. 你在 Jupyter 容器里写完一个笔记本，关掉容器后重新启动，代码没了。发生了什么？下次要加哪个参数？
    参考答案

    文件在可写层里，容器一删它就没了。下次用挂载参数把宿主机目录挂到镜像约定的工作目录。

  4. 你执行了 docker run --rm python:3.12-slim pip install requests，成功之后，下一条 docker run --rm python:3.12-slim python -c "import requests" 会输出什么？为什么？
    参考答案

    报模块找不到。安装只进了那次容器的可写层，第二条命令从干净镜像重新开始——环境是声明出来的，不是累积出来的。

  5. 有人在 Dockerfile 里写了一行把 40 GB 的数据目录复制进镜像。请说出至少三个后果，并给出替代方案。
    参考答案

    镜像多出一层 40 GB 的内容，推送与拉取都要传这么多；构建上下文也要先发送它；数据若有再分发限制还违反了条款。用挂载代替。

  6. 一张卡上跑两个容器，第二个报显存不足，而第一个的显存占用看起来还有很多空余。请给出至少两种解释。
    参考答案

    显存碎片让剩余空间不连续，无法满足一次较大分配；你看到的"空余"是瞬时值，而训练峰值可能远高于它。

  7. 请为一次实验写一份"实验身份"记录：你用某个镜像训练了一个图像分类模型，学习率是某个值，跑了若干轮。每一项缺了会发生什么？
    参考答案

    要写镜像 digest（不是标签）、代码提交哈希、全部超参数。缺 digest 复现不出环境，缺提交哈希不知道代码版本，缺超参数不知道当时让它做了什么。

  8. 为什么推理镜像通常要比训练镜像小得多？请从"它需不需要"和"它被怎么用"两个角度回答。
    参考答案

    推理不需要工具链、数据集与追踪库，只要运行时和加载权重的依赖；它还要能快速扩容、长期在线，所以小意味着冷启动快、攻击面小。

  9. 你在一台没有显卡的笔记本上完成了本章全部实验。你实际验证了哪些能力，又刻意跳过了哪一项，为什么？
    参考答案

    验证了构建、挂载、一次性环境、Jupyter、推理服务与实验身份；跳过了显卡直通与其版本排查，因为宿主机没有可暴露的设备。没学与没验证是两回事。

  10. 为什么数据集不适合写进镜像，而模型权重却经常写进镜像？这两者的差别在哪里？
    参考答案

    数据集大而稳定，进镜像的传输存储代价高、还可能触碰合规；权重是"这次发布的产品本身"，进镜像让上线版本没有歧义。这是权衡，不是规则。

  11. 动手任务：写出一条命令，把当前目录挂载进一个 Python 容器，在里面装一个包并退出，然后再起一个新容器确认包不在。每条命令验证了什么？
    参考答案

    第一条用交互加自动清理的方式起容器并挂载当前目录，在里面执行安装；第二条用同样的基础镜像起新容器执行导入，得到模块找不到的错误。前者验证"安装是这次运行的状态"，后者验证"新容器从镜像定义出发，不带任何历史"。

本章总结

  • 深度学习把"环境不一致"推到了极端：依赖链条长、版本被官方矩阵钉死、硬件还带进一层无法用软件包描述的属性。
  • 复现失败有四类原因：环境、数据、随机性、记录。容器能彻底解决第一类，帮助记录第二类，对后两类无能为力。
  • CUDA 的四层是宿主机驱动、驱动接口、镜像内运行时、框架编译绑定。前两层属于宿主机，后两层属于镜像。
  • 版本兼容是单向的：新驱动能带动旧运行时，旧驱动带不动新运行时。排查顺序是先看驱动上限，再选镜像标签，最后核对框架版本。
  • 容器的价值主张只有一句话：它固定四层里最烦的两层，只留一层给你操心，但不能把变量压到零。
  • 没有显卡完全不妨碍学会这一章。用 CPU 镜像做完所有实验，你少的只有执行速度，不少任何概念与方法。
  • 交互式环境必须挂载目录，否则容器一删，几个小时的探索痕迹全部消失。
  • 环境应该是被声明出来的，不是被累积出来的。靠手工装包才存在的环境，不可解释也不可重建。
  • 代码进镜像，数据与输出挂载出来，日志交给外部留存。这四种东西的归属不能混。
  • 镜像 digest + 代码提交哈希 + 超参数 = 可复现的实验身份。这是本章最重要的一个判断：三者缺一，你就无法指认自己做过什么。
  • 训练镜像与推理镜像的需求不同，应该是两个镜像；推理镜像要小、要快、要少，多阶段构建同时解决体积与边界。
  • MLOps 是把第 10 章的流水线思想延伸到数据与模型；容器保证系统可靠地运行，监控保证系统运行得可靠。

写到这里，你手上已经有了把一次 AI 实验从头做到尾的全部工具：声明一个环境、挂载进数据、保存住权重、记录下身份、把模型变成服务。这些工具朴素得几乎不像"AI 技术"，它们不涉及任何模型结构、任何损失函数、任何训练技巧。但正是这些朴素的纪律，决定了一个人的实验能不能被自己重跑，决定了三个月的努力是一份资产还是一次性的手气。下一章，我们要把这一整套东西从一台机器搬到一群机器上——那里没有单机命令能直接解决的排队与调度问题，而你已经具备理解它们的全部前置知识。

  • 多阶段构建官方文档 https://docs.docker.com/build/building/multi-stage/ 带着"训练阶段与推理阶段"这个场景重读，重点看它如何通过命名阶段与选择性复制控制最终镜像里有什么。
  • Docker Hub官方镜像 https://hub.docker.com/ 本章提到的显卡基础镜像与数据科学笔记本镜像都在这里有官方仓库。带着问题去读：那些后缀不同的变体各自意味着什么？一切以官方版本矩阵与标签页说明为准。
  • 容器资源约束官方文档 https://docs.docker.com/engine/containers/resource_constraints/ 讲清了 Docker 能约束哪些资源、用什么参数。带着一个问题读：为什么显卡的资源约束在容器参数层面比处理器和内存粗糙得多？
  • Compose 示例合集官方仓库 https://github.com/docker/awesome-compose 想把本章的推理服务再推一步，加上反向代理与数据库时，这里有可直接对照的完整示例。挑最接近的一个逐行问它解决什么问题。
  • WSL 官方文档（中文）官方文档 https://learn.microsoft.com/zh-cn/windows/wsl/ Windows 上的显卡直通要经过 WSL2 这一层。带着问题读：容器里的进程跑在哪个内核上、设备是怎么被暴露出来的？
值 得 品 读 的 书
  • 《Docker 实战》 Jeff Nickoloff 著 对层、卷、网络、资源限制的讲解比大多数教程扎实，正好补上本章为聚焦 AI 场景而略过的细节。做完实验后带着一个具体问题读：我该怎么给一个长跑的训练容器配资源与重启策略？
  • 《深入浅出 Docker》 Nigel Poulton 著 如果你读本章时觉得镜像层复用、容器与虚拟机的边界还有点飘，这本书能把整体图像重新钉牢。适合当复习读物，只读你卡住的那几章即可。
